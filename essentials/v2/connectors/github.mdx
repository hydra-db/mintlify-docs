The GitHub connector syncs issues and pull requests from selected repositories. Code, commits and diffs are not synced. Each issue and each pull request is one document that carries its body and its whole discussion: conversation comments and, for a pull request, review comments and review summaries.

Issues and pull requests link to the issues they reference or close, to their parent issue, and to the Linear issues, Slack messages and Notion pages they link to.

A private repository's items are limited to its collaborators and teams only when Enforce ACL is on and HydraDB can read its collaborators. Deleted issues and pull requests stay in HydraDB.

## Permissions

Turn on **Enforce ACL** for this connector to make search follow GitHub permissions. With Enforce ACL off, HydraDB does not enforce them. Only a workspace owner or writer signed in to HydraDB can turn it on. API-key requests must omit `enforce_acl`, including `false`. See [Enforce ACL](/essentials/v2/connectors#enforce-acl).

- **Who can read an item:** Access follows the repository, not the single issue. A public or internal repository can be read by everyone who can query the collection unless you set an access rule. A private repository can be read by its collaborators and by the organization teams that have access to it.
- **How a person is identified:** The email address on a collaborator's public GitHub profile. Teams are added as groups.
- **When permissions cannot be read:** If a collaborator hides their profile email, the collaborator list is incomplete, there are too many people to express, or GitHub refuses a request, the connector reports a permission warning. On HydraDB Cloud, with Enforce ACL on, such an item follows the access rule you set on its resource. With no rule, it is hidden from search. Self-hosted deployments can be configured differently. Permission warnings appear in [Get Connector Status](/api-reference/v2/endpoint/get-connector-status).
- One collaborator with a hidden public email stops HydraDB from capturing a private repository's audience. Set an access rule on such a repository.
- Internal repositories are open to everyone who can query the collection. Check that this matches who should see them.

You can also [set your own rule on a resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).

## Before you connect

### Credentials

GitHub uses a personal access token. The setup steps below use a classic token, which needs `repo`, or `public_repo` for public repositories only. A fine-grained token works if GitHub grants it read access to the repositories you want and to their issues.

<ResponseField name="access_token" type="secret string" required>
A GitHub personal access token with read access to repositories and issues.
</ResponseField>

**Scopes for a classic token**

- `public_repo`: public repositories only. Use this or `repo`.
- `repo`: private and public repositories. Reading a private repository's collaborators for permissions also needs it.
- `read:org`: reads which organization teams can access a repository, for permissions. If GitHub refuses it, the connector reports a permission warning.

A successful token check does not guarantee access to every repository. Confirm that the repositories you need are listed when you select them.

### Set it up

<Steps>
  <Step title="Create a token">
    In GitHub, create a personal access token with `repo`, or `public_repo` for public repositories only. Add `read:org` if you want organization team access captured.
  </Step>
  <Step title="Create the connector">
    Paste the token as `access_token`.
  </Step>
  <Step title="Select repositories">
    HydraDB lists every repository the token's user owns, collaborates on, or can see as an organization member. Select the repositories to sync.
  </Step>
</Steps>

One connector reads the repositories one token's user can see.

To connect more than one GitHub account, give each connector its own `provider_account_scope`, such as `github-account-a` and `github-account-b`. These are labels you choose, not GitHub's own account ids, and HydraDB does not check them. Two connectors that share a scope and write to the same collection can overwrite each other's items. See [several accounts from one provider](/essentials/v2/connectors#6-connect-several-accounts-from-one-provider).

<Accordion title="Connect through the API">

Use provider `github` with [Create Connector](/api-reference/v2/endpoint/create-connector). Then call [Discover Connector Resources](/api-reference/v2/endpoint/discover-connector-resources) to list the resources the connector can sync, and [Configure Connector](/api-reference/v2/endpoint/configure-connector) to choose what to sync.

</Accordion>

## Keeping in sync

- **First sync:** Reaches back 30 days by default, set by `lookback_days`. The window is measured from the repository's most recent activity, not from today, so a quiet repository still brings in its last stretch of work.
- **New and changed items:** Each sync asks GitHub for items updated since the last sync. A changed item is sent again with its whole discussion.
- **Edits:** Editing an issue or pull request, or adding a comment, moves its updated time, so the whole item is sent again.
- **Deletions:** Deleted issues and pull requests are not removed. An item that disappears from GitHub can stay searchable in HydraDB.
- GitHub rate limits apply per token. A large first sync can use its hourly quota.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` on the connector to change it.

## What gets synced

### Issues and pull requests

- **One document:** One issue or one pull request, with its whole discussion inside it. A search result is the issue or pull request, not an individual comment.
- **Title:** The issue or pull request title.
- **Text:** The issue or pull request body and its discussion are searchable together. Comments and reviews include their author and time. Review comments also include the file, line and reply context. Empty comments are skipped. Labels are written as a `Labels` line, the creation time as a `Created` line, and a sub-issue's parent as a `Parent` line. The title is searchable too.
- **Date:** When the issue or pull request was last updated.
- **Link back:** The issue or pull request page on GitHub.
- **Files:** Images and files in bodies and comments are not downloaded.

**Example searches**

- Which pull request fixed issue `acme/api#412`?
- Which issues in `acme/api` are labelled bug and mention the login timeout?
- Which Linear issue does this pull request close?

## How it fits into the graph

- Issues and pull requests use the Ticket class.

[Graph classes](/essentials/v2/connector-providers#graph-classes) explains each class.

**Connections GitHub creates**

- A sub-issue to its parent issue.
- An issue or pull request to each issue or pull request it references in its body or discussion.
- A pull request to each issue its body closes with a closing keyword.
- An issue or pull request to a Linear issue it links to, or names after a closing word.
- An issue or pull request to a Slack message or Notion page it links to.
- In the other direction, Linear issues link to the GitHub pull requests attached to them.
- References inside code blocks, inline code and HTML comments are ignored.

**People and groups**

- The author of each comment, as a commenter.
- Each `@username` mentioned in the body.
- The opener and assignees are not attached to the item as people in the graph.

**Found in the text**

The body and discussion text of each issue and pull request. HydraDB identifies people, organizations, projects and other named things in this text. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Not synced

- Code, commits and diffs.
- Releases, wikis, projects and GitHub Discussions.
- Images and files attached in bodies and comments.
- Repositories the token's user cannot see.
