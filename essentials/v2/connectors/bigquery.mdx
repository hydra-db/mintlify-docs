Sync rows from the BigQuery tables you select in one Google Cloud project. Each row is one document. Every non-empty column of the row becomes searchable text, including sensitive columns.

BigQuery access controls are not imported, so every synced row is visible to everyone who can query the collection unless you set an access rule. Rows deleted in BigQuery stay in HydraDB. You choose, table by table, how new and changed rows are found: a timestamp column, BigQuery's change history, or a full read of the table on every sync.

<Note>
BigQuery is in beta.
</Note>

## Permissions

<Warning>
BigQuery permissions are not imported, so **Enforce ACL** is unavailable for this connector. Every synced item is visible to everyone who can query the collection, unless you [set an access rule on the resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).
</Warning>

- BigQuery dataset, table, row-level and column-level access controls are not reproduced.

API-key requests must omit `enforce_acl`, including `false`. See [ACL on synced content](/essentials/v2/connectors#5-acl-native-rbac-awareness).

## Before you connect

<Warning>
Set a primary key for every table you select. HydraDB updates a row's document by its key. If a table has no real unique key, different rows can be treated as the same document and replace each other.
</Warning>

### Credentials

Use a service-account JSON key, a service-account email and private key, or a pre-issued OAuth client id, client secret and refresh token. Paste one complete credential set. HydraDB does not offer an interactive sign-in flow. The JSON key is the recommended option.

**What the service account needs**

- `BigQuery Data Viewer`: role on the project.
- `BigQuery Job User`: role on the project.
- `https://www.googleapis.com/auth/bigquery`: scope, in the OAuth option. Google rejects query jobs under the read-only BigQuery scope.

### Set it up

<Steps>
  <Step title="Create a service account">
    In Google Cloud, create a service account. Give it the BigQuery Data Viewer and BigQuery Job User roles on the project, and download its JSON key.
  </Step>
  <Step title="Create the connector">
    Paste the key as `credentials_json`. Add `project_id` only if the key file does not name a project. To narrow which tables HydraDB lists, set `datasets`.
  </Step>
  <Step title="Select tables">
    HydraDB lists the tables in the project, narrowed by `datasets` when you set it. Select the tables to sync. Each selected table becomes its own set of documents, one per row.
  </Step>
  <Step title="Choose how each table finds changes">
    If the table has a timestamp column that changes on every insert and update, such as `updated_at`, make it the table's `replication_key`. This column is the table's sync cursor. If rows are only ever inserted, set `change_history` to `appends`. If rows are also updated and there is no such column, set `change_history` to `changes`. A table with none of these is read in full on every sync, which is expensive on large tables.
  </Step>
  <Step title="Turn on change history for tables set to changes">
    Run `ALTER TABLE dataset.table SET OPTIONS(enable_change_history=true)` once in BigQuery for that table. It changes no data.
  </Step>
  <Step title="Set each table's primary key">
    Add `primary_keys` with the column or columns that identify one row, unless the table already has a primary key defined in BigQuery.
  </Step>
  <Step title="Send the settings when you configure">
    Through the API or SDK, send the per-table settings as `table_configs` on the same Configure Connector request that selects the tables. The dashboard collects them on the table-selection screen.
  </Step>
</Steps>

One `table_configs` entry per table, for each way of finding changes. A table's own `change_history` overrides its cursor setting. Otherwise, a usable table or connector-wide cursor takes priority over the connector-wide `change_history` fallback.

<CodeGroup>
```json Timestamp cursor
{
  "table": "sales.orders",
  "replication_key": "updated_at",
  "primary_keys": [
    "order_id"
  ]
}
```
```json Inserts only
{
  "table": "web.page_views",
  "change_history": "appends",
  "primary_keys": [
    "event_id"
  ]
}
```
```json Inserts and updates
{
  "table": "crm.accounts",
  "change_history": "changes",
  "primary_keys": [
    "account_id"
  ]
}
```
```json Changes only, skip existing rows
{
  "table": "crm.accounts",
  "change_history": "changes",
  "snapshot": "none",
  "primary_keys": [
    "account_id"
  ]
}
```
```json Full read
{
  "table": "ref.countries",
  "primary_keys": [
    "code"
  ]
}
```
</CodeGroup>

One connector reads one Google Cloud project.

## Keeping in sync

- **First sync:** A table with a cursor column reads back the window set by `lookback_days`, 30 days by default. A change-history table starts capturing changes at its first sync, not when you create the connector, and then loads its existing rows in slices of 1,000 per sync. Set `snapshot` to `none` to skip existing rows, or to a number to load at most that many rows, in no particular order. With `none`, changes between creating the connector and its first sync are not recovered. While existing rows are loading, deleting rows in BigQuery can cause other rows to be missed.
- **New and changed items:** A cursor table picks up rows whose cursor value moved past the last sync. A `changes` table reads BigQuery's change history, about 11 minutes behind the current time. An `appends` table sees new rows only. A table with neither is read in full on every sync, and rows whose content did not change are skipped.
- **Edits:** An edited row updates the same document, as long as its key is unique. In `appends` mode, edits to existing rows are never seen.
- **Deletions:** Deleted rows are not removed. A row deleted in BigQuery stays searchable in HydraDB.
- BigQuery keeps change history for its time-travel window, 2 to 7 days. If a change-history table is not synced within that window, for example while the connector is paused, the table is skipped with an error on each sync until it is loaded again from the start.
- A dataset name containing `__` can display incorrectly as a table label. Which table a row belongs to is not affected.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` on the connector to change it.

## What gets synced

### Table rows

- **One document:** One row of a selected table, as long as the table's key is unique. Rows that share a key replace one another.
- **Title:** The first non-empty column named `name`, `title`, `subject`, `summary` or `email`. Otherwise, the first non-empty, non-numeric scalar column in alphabetical column order is used. If there is none, the first numeric column is used. A row with none of these is titled with its table and row key.
- **Text:** The title on the first line. Then every non-empty column in alphabetical order, as `Column Name: value`: underscores become spaces and words are capitalised. Lists of scalar values are joined with commas. Nested records and lists of records are written as compact JSON. In change-history mode, each row also has `_change_type` and `_change_timestamp` columns, and both appear in the text.
- **Date:** The first recognised time column with an RFC3339 timestamp or epoch-seconds value sets the result date. The columns are checked in this order: `updated_at`, `modified_at`, `last_modified`, `updated`, `created_at`, `created`, `timestamp`, `event_time` and `inserted_at`. BigQuery DATETIME values have no time zone and do not set it. A row with none has no date.
- **Link back:** None.
- **Files:** None. Column values are kept as text only.

<ResponseField name="Row columns" type="Searchable text">
Every non-empty column is searchable as text. Columns are not individual query filters. A table name in a text query does not reliably select that table. Use `additional_metadata.container_name` or `additional_metadata.container_id`.
</ResponseField>

<ResponseField name="updated_at" type="Result date">
The value of the first recognised time column, used as the result date. A sync cursor with another name does not set it. This attribute is not searchable, but a source column of the same name is part of the row text like any other column.
</ResponseField>

<ResponseField name="additional_metadata.container_name" type="Query filter">

</ResponseField>

<ResponseField name="additional_metadata.container_id" type="Query filter">
The table as `dataset__table`, with two underscores. Another way to limit a query to one table. Not searchable.
</ResponseField>

<ResponseField name="additional_metadata.container_type" type="Query filter">
Always `table`. Not searchable.
</ResponseField>

<ResponseField name="connector_id" type="Query filter">
Limits a query to this connector's rows. Not searchable.
</ResponseField>

<ResponseField name="provider" type="Query filter">
Always `bigquery`. Limits a query to BigQuery rows. Not searchable.
</ResponseField>

## How it fits into the graph

- Table rows use the Record class.

[Graph classes](/essentials/v2/connector-providers#graph-classes) explains each class.

**Connections BigQuery creates**

The connector creates no explicit links between rows or to other tools. A column containing another row's key does not create a link. Each row is grouped under its table.

**People and groups**

The connector does not explicitly attach rows to people. A column such as `email` or `user_id` is part of the row text only. It does not make the row a person in the graph.

**Found in the text**

The row text. Anything found there comes from reading the text, not from joining table keys. HydraDB identifies people, organizations, projects and other named things in this text. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Not synced

- Tables you did not select.
- Rows deleted in BigQuery: they stay in HydraDB.
- Updates to existing rows in tables set to `appends`.
- BigQuery dataset, table, row-level and column-level access controls.
- Table and column descriptions and other schema details. Only row values are kept.
