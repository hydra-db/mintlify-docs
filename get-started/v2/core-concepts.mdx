Every integration works with three things. The [Glossary](/essentials/v2/glossary) defines every term the docs use.

| Term | What it means | Guide |
| --- | --- | --- |
| **Database** | An isolated store for your context, such as `acme_corp`. A query never searches another database. Inside it, **collections** such as `company_docs` or `user_123` group related context. | [Databases and Collections](/essentials/v2/multi-tenant) |
| **Context** | Everything you store: **knowledge** and **memories**. One stored unit is a **source**, with an `id` you use to check its status, update it, or delete it. | [Knowledge](/essentials/v2/knowledge), [App Sources](/essentials/v2/app-sources), [Memories](/essentials/v2/memories) |
| **Query** | The operation that reads context. It returns ranked **chunks** (passages of your sources) and the **context graph**: relationships HydraDB extracted from your context. | [Query](/essentials/v2/query), [Context Graphs](/essentials/v2/context-graphs) |

## Choose knowledge or memory

Use **knowledge** for what your AI reasons over: documents such as a policy PDF, and **app sources**, which are records your code or a connector already parsed, such as a Zendesk ticket or a Slack message. Use **memories** for what should carry between conversations: preferences, decisions, and inferred behavior traits.

For memories, `infer: false` (the default) stores what you send. With `infer: true`, HydraDB extracts facts and preferences from text or dialogue and checks them against what it already holds in that collection, which improves accuracy. Your application chooses what to save; HydraDB does not record interactions you have not sent it.

## Choose where context goes

Create a database before you ingest context. Collections are created when you first write to them, so there is no separate collection-creation call. If you omit `collection`, HydraDB writes to and reads from the default collection only. Send the same collection name when you query or check indexing status.

For most products, one collection is the right answer. To build a company brain, connect every connector and ingest all your context into one collection, so one query searches all of it. To keep some results away from some users, stay in that one collection and use [metadata filters](/essentials/v2/metadata), such as a team field, and [access control](/essentials/v2/access-control), either the source app's permissions or your own rules. HydraDB enforces both inside a single query.

Separate collections are for context that should never meet in one query, such as one user's memories.

## Query

[`POST /query`](/api-reference/v2/endpoint/query) is how agents read from HydraDB. It searches knowledge, memories, or both, chosen with `type`: `"knowledge"`, `"memory"`, or `"all"`.

A query is a multi-stage pipeline in a single call: metadata filtering, semantic and keyword retrieval, and [context graph](/essentials/v2/context-graphs) traversal. It returns ranked chunks with their source details and the graph around them; your application puts them into the model's prompt. See [Query](/essentials/v2/query) for the request and every parameter.

A query without `acl` ignores document permissions. If your application has signed-in users, send each user's identity as `acl`, taken from their session on your backend, never from the client.

## Filter with metadata

Metadata filters are the `WHERE` clause of a query: only context whose fields match is considered, for example policies whose `status` is `approved`. Declare the fields you filter on in the database's metadata schema. Use `additional_metadata` for free-form fields such as a document's author or URL. See [Metadata](/essentials/v2/metadata) for both.
