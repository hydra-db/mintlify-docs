Context is everything you give HydraDB so your AI can find it later. It comes in two types, and most applications use both:

| | Knowledge | Memories |
|---|---|---|
| What it is | What your organization has written down | What your agent has learned about a user |
| Examples | Product docs, policy PDFs, runbooks, Slack threads, tickets, emails | Preferences, decisions, things already tried, past conversations |
| Usually shared by | Everyone who may read it | One user |
| Ingest with | `type=knowledge` | `type=memory` |
| What you send | Files, or records from an app (**app sources**) | Text or a conversation |
| Changes when | The document changes | The user says or does something new |

The two types work the same way. Both go to [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context), both are saved in a [collection](/essentials/v2/databases-and-collections), both are indexed in the background, and both come back from [`POST /query`](/api-reference/v2/endpoint/query). Each item you ingest is a **source**; HydraDB splits it into searchable passages called **chunks** and builds a context graph from it.

They are stored separately, so a query chooses what to read: `type: "knowledge"`, `type: "memory"`, or `type: "all"` for both in one ranked list. A support agent, for example, answers from the help center (knowledge) and from the fact that this customer already tried restarting (a memory).

## 1. Ingest knowledge

There are three ways to ingest knowledge:

- **Files:** upload PDF, DOCX, Markdown, CSV, or TXT files, and HydraDB reads them for you.
- **App sources:** send records your application already holds from an app, such as a Slack message or a Jira ticket.
- **[Connectors](/essentials/v2/connectors):** connect an app such as Slack, Google Drive, Notion, or GitHub once, and HydraDB keeps it in sync.

### Upload files

The request is **multipart/form-data** with these fields:

| Form field | What to send |
|---|---|
| `type` | `knowledge` |
| `database` | An existing [database](/api-reference/v2/endpoint/create-database) |
| `collection` | Optional. Leave it out to use the database's default collection. A query that names another collection does not read the default one. |
| `documents` | One or more files |
| `document_metadata` | One item per file, in the same order, as a JSON string. Optional, but this is where a file's `id` and `metadata` go. |
| `upsert` | Leave it out. It defaults to `true`, so a file sent again with the same `id` replaces the saved one. |

<Accordion title="Upload files: Python, TypeScript, or cURL">

Set up your [SDK client](/api-reference/v2/sdks#client-setup) before running the Python or TypeScript example.

<CodeGroup>
```python Python SDK
import json

with open("/path/to/policy.pdf", "rb") as f1, open("/path/to/runbook.pdf", "rb") as f2:
    result = client.context.ingest(
        type="knowledge",
        database="acme_corp",
        documents=[
            ("policy.pdf", f1, "application/pdf"),
            ("runbook.pdf", f2, "application/pdf"),
        ],
        document_metadata=json.dumps([
            {"id": "policy_v2", "metadata": {"document_type": "policy", "status": "approved"}},
            {"id": "runbook_deploy", "metadata": {"document_type": "runbook"}},
        ]),
    )
```
```typescript TypeScript SDK
const result = await client.context.ingest({
  type: "knowledge",
  database: "acme_corp",
  documents: [
    { path: "/path/to/policy.pdf", filename: "policy.pdf", contentType: "application/pdf" },
    { path: "/path/to/runbook.pdf", filename: "runbook.pdf", contentType: "application/pdf" },
  ],
  documentMetadata: JSON.stringify([
    { id: "policy_v2", metadata: { document_type: "policy", status: "approved" } },
    { id: "runbook_deploy", metadata: { document_type: "runbook" } },
  ]),
});
```
```bash cURL
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=knowledge" \
  -F "database=acme_corp" \
  -F "documents=@/path/to/policy.pdf" \
  -F "documents=@/path/to/runbook.pdf" \
  -F 'document_metadata=[
    { "id": "policy_v2", "metadata": { "document_type": "policy", "status": "approved" } },
    { "id": "runbook_deploy", "metadata": { "document_type": "runbook" } }
  ]'
```
</CodeGroup>

The response lists each file in `data.results` with its `id` and a `status` of `queued`. The payload is wrapped in the standard envelope, so read it from `response.data`:

```json
{
  "success": true,
  "data": {
    "success": true,
    "message": "Knowledge uploaded successfully",
    "results": [
      { "id": "policy_v2", "filename": "policy.pdf", "status": "queued", "error": null },
      { "id": "runbook_deploy", "filename": "runbook.pdf", "status": "queued", "error": null }
    ],
    "success_count": 2,
    "failed_count": 0
  },
  "error": null,
  "meta": {
    "request_id": "9d13aef4-02f4-4e73-8c62-4c2601d04f9d",
    "latency_ms": 12.3
  }
}
```

</Accordion>

Each `document_metadata` item takes these properties:

| Property | What it is |
|---|---|
| `id` | Your stable ID for the file, and the upsert key. Send the same `id` later to replace the file, or use it to check status and delete. Leave it out to have one generated; the response returns it either way. |
| `metadata` | Values you filter on at query time, such as `document_type`. Declare the keys in the database's [metadata schema](/essentials/v2/metadata). Up to 16 KiB as compact JSON. |
| `additional_metadata` | Free-form values for display and bookkeeping. Filterable only when nested under `additional_metadata` in `metadata_filters`. Up to 1 KiB as compact JSON. |
| `relations` | Other sources this file belongs with, as `{ "ids": [...] }`. See [Link documents that belong together](#6-link-sources-that-belong-together). |

The key list is closed. Any other key, including `title`, `type`, `url`, and `timestamp`, returns `400`. [Ingest Context](/api-reference/v2/endpoint/ingest-context#supported-file-formats) lists the supported file formats.

### Send app sources

When your application already holds the text and fields of a Slack message, a Jira ticket, a Notion page, or a CRM record, send it as an **app source** instead of a file. HydraDB keeps the app's structure: the author, the thread, the ticket's status, and the links between records.

The request goes to the same endpoint, with `app_knowledge` in place of `documents`. One request can carry both. `kind` says what the record is (`email`, `message`, `ticket`, `knowledge_base`, `comment`, `meeting`, or `custom`), and `fields` carries its content. An app source can also carry an `acl`, the list of principals allowed to retrieve it. [Ingest Context](/api-reference/v2/endpoint/ingest-context) lists the fields of every kind.

## 2. Save memories

HydraDB does not capture memories on its own: your application saves one when a user states a preference, makes a decision, finishes a task, or corrects the agent. Give each user their own collection, such as `user_john_123`, and send it on every ingest, status check, and query. Your backend picks it from the signed-in session; the name itself does not authenticate anyone.

The request is the same as for knowledge, with `type=memory` and a `memories` list in place of files:

| Form field | What to send |
|---|---|
| `type` | `memory` |
| `database` | An existing [database](/api-reference/v2/endpoint/create-database) |
| `collection` | The user's own collection, such as `user_john_123`. |
| `memories` | One item or a list of items, as a JSON string |
| `upsert` | Leave it out. It defaults to `true`, so sending an item again with the same `id` replaces the saved memory. |

<Accordion title="Save a memory: Python, TypeScript, or cURL">

Set up your [SDK client](/api-reference/v2/sdks#client-setup) before running the Python or TypeScript example.

<CodeGroup>

```python Python SDK

        {
            "text": "Prefers short, direct answers with no preamble.",
            "infer": True,
            "user_name": "John",
        }

```

### Let HydraDB infer the memory

`infer` controls whether HydraDB extracts the memory from what you send or stores it as written.

| | `infer: true` | `infer: false` (the default) |
|---|---|---|
| What HydraDB does | Extracts the useful preference, trait, or fact from messy or indirect evidence. | Stores and indexes exactly what you send. There is no extraction step, so it is faster and deterministic. |
| Use it for | Dialogue where the preference is implicit, behavior logs and event streams, and feedback like "the last summary was too long." | Facts you already captured, such as `"User's plan tier is Pro"`, pre-structured notes, and text you want to retrieve exactly as written. |

`custom_instructions` takes effect only when `infer: true`. Use it to guide extraction, for example: `"Focus on UI and notification preferences only"`.

<Accordion title="Infer a preference from a behavior log: Python, TypeScript, or cURL">

If you sent the same input with `infer: false`, HydraDB would index the event log verbatim. That is useful only when you want to retrieve the log itself.

</Accordion>

### Send text or a conversation

Each memory item takes either `text` or `user_assistant_pairs`, **not both** (sending both returns `400`).

- **`text`:** prose of any kind, such as observations, captured facts, meeting notes, or semi-structured records. Set `is_markdown: true` when the content uses Markdown (headings, lists, code blocks) so HydraDB keeps that structure during chunking and embedding.
- **`user_assistant_pairs`:** dialogue, especially when the preference is implied rather than stated. Each pair is `{ "user": "...", "assistant": "..." }`.

<Accordion title="Input shapes: text, Markdown, and user-assistant pairs">

Markdown notes, stored as written:

```json
{
  "text": "# Meeting Notes\n\n## Key Points\n- Budget approved",
  "is_markdown": true,
  "infer": false
}
```

A plain statement, with the preference extracted:

```json
{
  "text": "Prefers detailed technical explanations and works in PST.",
  "infer": true
}
```

A conversation, with the preference extracted:

```json
{
  "user_assistant_pairs": [
    { "user": "Remember I like dark mode", "assistant": "Noted." }
  ],
  "infer": true
}
```

</Accordion>

## 3. Wait for indexing

Knowledge and memories are indexed the same way, in the background: HydraDB parses each source, splits it into chunks, infers the memory if you asked it to, finds the people, teams, and topics it mentions and how they relate, and builds the search indexes. The ingest request returns `202 Accepted` with each source's `id`.

Poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) with those ids and the same `collection` every few seconds. A source's `indexing_status` moves forward through `queued`, `processing`, `graph_creation`, and `completed`, or lands in `errored` on failure:

- At `graph_creation` the source is already searchable.
- Wait for `completed` only when you need full graph traversal. Most documents complete in 1 to 5 minutes.

[Ingestion Status](/api-reference/v2/endpoint/source-status) has the full status table. To skip polling, register a [webhook](/api-reference/v2/endpoint/webhooks-overview).

<Accordion title="Poll until indexed: Python, TypeScript, or cURL">
<CodeGroup>
```python Python SDK
import time

ids = ["policy_v2", "runbook_deploy"]
terminal = {"completed", "errored"}

while True:
    status = client.context.status(
        database="acme_corp",
        collection="default",
        ids=ids,
    )
    if all(s.indexing_status in terminal for s in status.data.statuses):
        break
    time.sleep(5)
```
```typescript TypeScript SDK
const ids = ["policy_v2", "runbook_deploy"];
const terminal = new Set(["completed", "errored"]);

let status;
while (true) {
  status = await client.context.status({
    database: "acme_corp",
    collection: "default",
    ids: ids,
  });

  const allDone = (status.data?.statuses ?? []).every((s) => terminal.has(s.indexingStatus ?? ""));
  if (allDone) break;

  await new Promise((r) => setTimeout(r, 5_000));
}
```
```bash cURL
while true; do
  response=$(curl -s -G 'https://api.hydradb.com/context/status' \
    -H "Authorization: Bearer $HYDRADB_API_KEY" \
    -H "API-Version: 2" \
    --data-urlencode "database=acme_corp" \
    --data-urlencode "collection=default" \
    --data-urlencode "ids=policy_v2" \
    --data-urlencode "ids=runbook_deploy")

  statuses=$(echo "$response" | jq -r '.data.statuses[].indexing_status')
  if echo "$statuses" | grep -qv '^\(completed\|errored\)$'; then
    sleep 5
    continue
  fi
  echo "$response" | jq
  break
done
```
</CodeGroup>

Each status in the `data` payload looks like this:

```json
{
  "statuses": [
    {
      "id": "policy_v2",
      "indexing_status": "completed",
      "success": true
    }
  ]
}
```

</Accordion>

## 4. Query knowledge and memories together

[`POST /query`](/api-reference/v2/endpoint/query) reaches each type through the `type` parameter:

- `type: "knowledge"` (the default) searches files and app sources.
- `type: "memory"` searches memories.
- `type: "all"` searches both and returns one merged, ranked list.

Both types are read from the collections you name. Shared knowledge usually lives in one collection and each user's memories in their own, so list both in `collections`. If some sources carry an `acl`, also send the caller's identity as `acl`. [Query](/essentials/v2/query) covers the other parameters and how to pass the result to a model.

<Accordion title="Search shared documents and a user's memories together: Python, TypeScript, or cURL">

<CodeGroup>
```python Python SDK
result = client.query(
    database="acme_corp",
    collections=["company_docs", "user_john_123"],
    query="How do I reset my password?",
    type="all",
    mode="thinking",
    max_results=8,
)
```
```typescript TypeScript SDK
const result = await client.query({
  database: "acme_corp",
  collections: ["company_docs", "user_john_123"],
  query: "How do I reset my password?",
  type: "all",
  mode: "thinking",
  maxResults: 8,
});
```
```bash cURL
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "collections": ["company_docs", "user_john_123"],
    "query": "How do I reset my password?",
    "type": "all",
    "mode": "thinking",
    "max_results": 8
  }'
```
</CodeGroup>

Knowledge and memories come back together in `data.chunks`, ranked as one list. To let the user's memories outrank the shared documents, send weights instead of a list:

```json
{
  "collections": {
    "user_john_123": 2,
    "company_docs": 1
  }
}
```

</Accordion>

## 5. Update or delete context

To change a source or a memory, send it again with the same `id`. `upsert` defaults to `true`, so the saved one is replaced; include everything you want to keep. Wait for the previous ingestion to reach `completed` or `errored` before sending the next update for the same `id`.

To remove one, call [`DELETE /context`](/api-reference/v2/endpoint/delete-source) with its `id` and the same `collection`.

## 6. Link sources that belong together

Forceful relations are links you declare between knowledge sources when you ingest them. When a query matches a source that has forceful relations, HydraDB returns the linked sources in the `additional_context` field of the response, alongside the primary chunks.

This is separate from the context graph HydraDB builds on its own. Use forceful relations for documents that belong together when the text does not say so: a contract and its addendum, or a runbook and its troubleshooting guide. They link whole **sources**. To declare the entity and relation graph within one document, replacing extraction for it, use [Bring Your Own Graph](/essentials/v2/bring-your-own-graph#using-byog-without-cypher).

On a file, set `relations.ids` on its `document_metadata` item. On an app source, set `relations.ids` the same way, and name the relationship in `app_relations` so the link also carries a predicate. `relations.ids` is what makes the linked text come back with query results; a named relationship alone connects the sources without requesting their text.

```bash cURL
      "relations": { "ids": ["auth-troubleshooting"] },
      "app_relations": [
        { "predicate": "linked_to", "target": { "source_id": "auth-troubleshooting" } }
      ]
    }
  ]'
```
</CodeGroup>

</Accordion>

`query_forceful_relations` defaults to `true`; set it to `false` to skip the linked sources.

<Note>
**Knowledge sources, `thinking` mode only:** Forceful relations stay within one store, so pointing a knowledge source at a memory ID silently returns nothing. Linked context is fetched only when `mode: "thinking"` is set on the query, or when `mode: "auto"` routes to thinking. In `fast` mode, `query_forceful_relations` is ignored even if set to `true`.
</Note>

## Field reference

<AccordionGroup>
<Accordion title="Ingest request fields">

| Field | Default | Description |
|---|---|---|
| <Field name="type" type="knowledge or memory" required /> | None | Selects the type of context. |
| <Field name="database" type="string" required /> | None | Target database. |
| <Field name="collection" type="string" /> | default collection | The collection to save into. If omitted, context goes to the database's default collection, which a query naming another `collection` does not read. |
| <Field name="documents" type="file[]" /> | None | Knowledge only. Files for HydraDB to parse. |
| <Field name="document_metadata" type="string (JSON array)" /> | None | Knowledge only. One item per file in `documents`, in the same order. |
| <Field name="app_knowledge" type="string (JSON array)" /> | None | Knowledge only. App sources. |
| <Field name="memories" type="string (JSON array)" /> | None | Memories only. Memory items. |
| <Field name="upsert" type="boolean" /> | `true` | Replace existing context with the same `id`. |

</Accordion>
<Accordion title="App source fields by kind">

Set `kind` on the app source and repeat it as `fields.kind`. Every other key in `fields` is optional.

| Kind | Use it for | Keys in `fields` |
|---|---|---|
| `email` | An email | `subject`, `body`, `from`, `to`, `cc`, `bcc`, `thread_id`, `reply_to_id`, `forwarded_from_id`, `created_at`, `url` |
| `message` | A chat message | `body`, `author`, `thread_id`, `parent_id`, `mentions`, `created_at`, `edited_at`, `url` |
| `ticket` | A ticket or issue | `title`, `description`, `status`, `priority`, `assignee`, `reporter`, `parent_id`, `linked_issue_ids`, `created_at`, `updated_at`, `url` |
| `knowledge_base` | A wiki page or article | `title`, `body`, `parent_id`, `created_by`, `updated_by`, `created_at`, `updated_at`, `url` |
| `comment` | A comment on another record | `body`, `author`, `parent_id`, `thread_id`, `created_at`, `updated_at`, `url`, `properties` |
| `meeting` | A meeting or call | `title`, `body`, `host`, `host_email`, `participants`, `started_at`, `updated_at`, `labels`, `url` |
| `custom` | Any other record, such as a CRM deal or a database row | `body`, `parent_id`, `thread_id`, `data` |

</Accordion>
<Accordion title="Memory item fields">

| Field | Description |
|---|---|
| <Field name="id" type="string" /> | Optional stable ID. Acts as the upsert key. |
| <Field name="title" type="string" /> | Short label for display in `/context/list` and query results. |
| <Field name="text" type="string" recommended /> | Raw text or Markdown content. Required unless `user_assistant_pairs` is provided. |
| <Field name="user_assistant_pairs" type="array" recommended /> | Conversation pairs in the shape `{ "user": "...", "assistant": "..." }`. Required unless `text` is provided. |
| <Field name="is_markdown" type="boolean" /> | Treat `text` as Markdown for chunking and indexing. |
| <Field name="infer" type="boolean" /> | When `true`, HydraDB extracts the underlying preference, trait, or fact. When `false` (the default), it stores the input as written. |
| <Field name="custom_instructions" type="string" /> | Guides extraction when `infer: true`. Ignored when `infer: false`. |
| <Field name="user_name" type="string" /> | User name used during inference. |
| <Field name="metadata" type="object" /> | Metadata schema fields for filtering. Send this as an object inside each `memories[]` item, for example `"metadata": { "department": "support" }`. Up to 16 KiB as compact JSON. |
| <Field name="additional_metadata" type="object" /> | Free-form per-memory fields for display or bookkeeping. Send this as an object. Up to 1 KiB as compact JSON. |

`memories` is a JSON string. Inside each item, `metadata` and `additional_metadata` are plain objects; do not stringify them again.

```json
{
  "id": "pref_dark_mode",
  "text": "User prefers dark mode and concise answers.",
  "infer": true,
  "metadata": { "department": "support", "workspace": "docs" },
  "additional_metadata": { "source": "onboarding" }
}
```

</Accordion>
</AccordionGroup>

## Common mistakes

| Mistake | What goes wrong | Fix |
|---|---|---|
| Storing shared documents as memories | They do not surface when querying `type: "knowledge"` | Ingest them with `type=knowledge`. |
| Querying with the wrong `type` | Nothing returned: the other type was searched | Use the matching `type`, or `"all"`. |
| Omitting `collection` for per-user memories | The memory lands in the default collection and may surface in the wrong scope | Use the user's ID as `collection` to keep each user separate. |
| Querying before indexing finishes | Results are empty | Wait for `indexing_status` to reach `graph_creation` or `completed`. |
| Sending `document_metadata`, `app_knowledge`, or `memories` as a JSON object | `multipart/form-data` validation fails | Send each as a JSON string. |
| Sending pre-extracted facts with `infer: true` | HydraDB may re-derive the memory and change the original phrasing | Use `infer: false` for already-structured facts. |
| Extracting preferences yourself instead of sending the raw logs | You duplicate work HydraDB can do for you | Send the raw signal with `infer: true`. |
| Pointing a forceful relation from knowledge to a memory | Nothing is returned: relations stay within one type | Link knowledge to knowledge. |
