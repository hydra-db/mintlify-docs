## Phase 0: Minimal working system (5 to 10 minutes)

**Goal:** run one search query on a file you uploaded and see real results. Four API calls prove the pipeline works end to end.

> **Do Phase 0 first, even if you plan to skip ahead:** every later phase assumes the database exists and indexing works, and this rules out the most common failures.

### Step 1: Create a database

`POST /databases` registers your top-level namespace. Creation is **asynchronous**, so poll `/databases/status` and upload nothing until it reports ready.

```python
import sys, os, time
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from config import client, DATABASE_ID

def create_tenant():
    client.databases.create(database=DATABASE_ID)
    print("Accepted")
    _poll_until_ready()

def _poll_until_ready(timeout=180, interval=4):
    print("Polling for readiness...")
    deadline = time.time() + timeout
    while time.time() < deadline:
        status = client.databases.status(database=DATABASE_ID).data
        infra = status.infra
        if infra.scheduler_status and infra.graph_status and infra.vectorstore_status.knowledge and infra.vectorstore_status.memories:
            print("✓ Database ready."); return
        print(f"  scheduler={infra.scheduler_status} graph={infra.graph_status} vectorstore={infra.vectorstore_status} - retrying in {interval}s")
        time.sleep(interval)
    raise TimeoutError("Database not ready within 180s")

if __name__ == "__main__": create_tenant()
```

### Step 2: Upload one file

Upload one file as **multipart form-data** to `/context/ingest`. HydraDB chunks it, embeds it, and creates graph nodes. Keep the returned `id` for Step 3.

> **Two ingestion modes:** file upload is the tested beginner path. The advanced `app_knowledge` mode (Phases 1 and 2) adds structured IDs and explicit graph `relations`. Both send multipart form data.

Create a sample document:

```bash
mkdir -p phase0/sample_docs
cat > phase0/sample_docs/auth_middleware.md << 'EOF'
# Auth Middleware - Internal IP Exception

## Decision
Token validation is skipped for requests from internal IP ranges
(10.0.0.0/8 and 172.16.0.0/12).

## Rationale
Service-to-service calls within the VPC caused circular dependency issues
during startup. The security team approved this in RFC-007, on the condition
that internal network access is controlled at the VPC level.

## Approved by
Security team - Slack #eng-architecture - 2024-02-14
EOF
```

```python
import sys, os
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from config import client, DATABASE_ID

def upload_file(filepath: str):
    filename = os.path.basename(filepath)

    with open(filepath, "rb") as f:
        result = client.context.ingest(
            database=DATABASE_ID,
            documents=[(filename, f, "text/markdown")],
        )

    print("RESULT:", result)
    return result

if __name__ == "__main__":
    result = upload_file("phase0/sample_docs/auth_middleware.md")
    # Note the id from the response - you need it for Step 3
```

### Step 3: Verify indexing

Poll `/context/status` with your `id` and read `statuses[0].indexing_status`. A source is searchable at `graph_creation`, fully indexed at `completed`, and failed at `errored`. A query sent earlier returns empty results with no error, the most common beginner confusion. Replace `YOUR_ID_HERE` with your `id`:

```python
import sys, os, time
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from config import client, DATABASE_ID

# Replace with the id returned by upload_file.py in Step 2
ITEM_ID = "YOUR_ID_HERE"

def verify_file(id: str, timeout: int = 120, interval: int = 3):
    """
    Polls /context/status until indexing_status is "completed" or "errored".
    """
    print(f"Verifying '{id}'...")
    deadline = time.time() + timeout
    while time.time() < deadline:
        status = client.context.status(
            database=DATABASE_ID,
            ids=[id],
        )
        print("STATUS:", status)

        items = status.data.statuses or []
        if items:
            s = items[0].indexing_status
            if   s == "completed": print(f"✓ '{id}' ready."); return
            elif s == "errored":   print("Indexing errored."); return
            print(f"  indexing_status: {s} - waiting...")

        time.sleep(interval)
    raise TimeoutError("Indexing timed out")

if __name__ == "__main__":
    verify_file(ITEM_ID)
```

### Step 4: Run your first search query

`POST /query` returns a `chunks` array. Each chunk's `chunk_content` is the text you later pass to GPT-4o. Results here prove the database, ingestion, indexing, and retrieval all work.

**Minimal working request:**

```jsonc
{
  "database":   "engineering-docs",
  "query":       "internal IP auth skip logic",
  "max_results": 10
}

// collection is NOT required for this working flow.
// When omitted, HydraDB uses the database's default collection.
// Response contains a "chunks" array - read chunk_content from each item.
```

```python
import sys, os
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from config import client, DATABASE_ID

def search(query: str, max_results: int = 10):
    """
    Minimal working search.
    Only database + query + max_results are required.
    collection is optional. Omitted means the database's default collection.
    Returns SDK object with .chunks and .sources attributes.
    """
    data = client.query(
        database=DATABASE_ID,
        query=query,
        max_results=max_results,
    )
    return data

if __name__ == "__main__":
    data   = search("internal IP auth skip logic")
    chunks  = data.data.chunks or []     # iterate the "chunks" array
    sources = data.data.sources or []    # sources list for citations

    print(f"\nChunks returned: {len(chunks)}")
    for i, chunk in enumerate(chunks, 1):
        chunk_content = chunk.chunk_content or ""  # always use chunk_content
        score         = chunk.relevancy_score if chunk.relevancy_score is not None else "?"
        print(f"\n[{i}] relevancy_score={score}")
        print(f"     {chunk_content[:300]}")

    print(f"\nSources: {[s.title for s in sources]}")
```

**Expected output:**

```

Chunks returned: 2

[1] relevancy_score=0.94
     Token validation is skipped for requests from internal IP ranges
     (10.0.0.0/8 and 172.16.0.0/12). Service-to-service calls within

[2] relevancy_score=0.87
```

## Phase 1: Improve retrieval (15 to 20 minutes)

Ingest many files with structured metadata and tune search parameters.

**Goal:** 50+ files indexed with metadata, scoped search working.

### How retrieval works

This applies to every phase.

**Chunks vs. sources:** HydraDB splits each document into overlapping **chunks**, embeds each one independently, and stores it as a node in the context graph. `/query` returns a `chunks` array; read `chunk_content` from each item and pass it to your LLM. It also returns `sources`, a deduplicated list of the contributing documents, for citation labels.

**Search chunk fields:**

| Field | Required | Description |
|---|---|---|
| `chunk_content` | **required** | The chunk text. **The canonical field you must extract** and pass to your LLM. The only field you cannot skip. |
| `relevancy_score` | optional | Higher is more relevant. Use it to rank, to drop weak chunks (below 0.5), or to decide how many chunks fit the LLM context window. |
| `source_title` | optional | Readable label from the source document, for `[Source: ...]` citations. |
| `chunk_uuid` | optional | Unique chunk ID, for deduplication when fan-out search across collections returns the same chunk twice. |
| `url` | optional | The URL you set at ingestion, present only if supplied. Use it for citation deep-links. |
| `additional_metadata` | optional | The per-source metadata object from ingestion, such as `doc_type`, `repo`, or `pr_number`. |

**How to read `relevancy_score`:** scores rank relevance within one response; they are not absolute confidence.

- `0.85+`: directly answers the query. Always include it.
- `0.65` to `0.85`: relevant but maybe not the exact answer. Include it and let the LLM decide.
- `0.40` to `0.65`: tangential. Include it only if few chunks score higher.
- Below `0.40`: probably not relevant. Drop it to reduce noise.

**How graph context changes search:** `graph_context` defaults to `true`, so the response includes the part of HydraDB's context graph that connects the retrieved chunks, even when you leave the field out. The `relations.ids` you set at ingestion add declared links on top. In `mode: "thinking"`, when a query matches a source file, HydraDB pulls its linked sources (such as the PR that changed it) into `additional_context`. Following these links is what makes "why" questions answerable. See [Forceful relations](/essentials/v2/knowledge#7-forceful-relations). With one file and no relations the graph adds little, but leaving it on costs nothing.

### Step 1: Batch upload with explicit IDs (app_knowledge)

Switch to **`app_knowledge` ingestion**: the `app_knowledge` form field on `/context/ingest` carries a JSON array as a string inside the multipart request. It gives you control over IDs, timestamps, collections, metadata, and (in Phase 2) explicit graph `relations`. Phase 2 graph linking needs the `{repo_name}/{relative_path}` ID convention.

> **Stricter validation:** every item needs `id`, `type`, and `content.text`, or the request is rejected outright. Use the Phase 0 file upload if you only need content indexed quickly.

```python
import sys, os, json, time, subprocess, pathlib
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from config import client, DATABASE_ID
from phase0.verify import verify_file

TEXT_EXTS = {".py",".ts",".js",".go",".rs",".java",".md",".yaml",".toml",".txt"}
SKIP_DIRS = {".git","node_modules","dist","build","__pycache__",".venv"}

def git_timestamp(repo_path: str, rel_path: str) -> str:
    try:
        raw = subprocess.check_output(
            ["git","log","-1","--format=%cI",rel_path],
            cwd=repo_path, stderr=subprocess.DEVNULL).decode().strip()
        return raw or "2020-01-01T00:00:00Z"
    except: return "2020-01-01T00:00:00Z"

def upload_batch(batch: list) -> list:
    result = client.context.ingest(
        database=DATABASE_ID,
        app_knowledge=json.dumps(batch),
    )
    ids = [r.id for r in (result.data.results or []) if r.id]
    print(f"  Uploaded {len(ids)} items")
    return ids

def verify_batch(ids: list):
    for fid in ids: verify_file(fid)

def ingest_directory(repo_path: str, repo_name: str) -> list:
    batch, all_ids = [], []
    root = pathlib.Path(repo_path).resolve()
    for f in root.rglob("*"):
        if f.is_dir() or any(p in f.parts for p in SKIP_DIRS): continue
        if f.suffix not in TEXT_EXTS or f.stat().st_size > 500_000: continue
        rel = str(f.relative_to(root))
        try: content = f.read_text(encoding="utf-8", errors="ignore")
        except: continue
        batch.append({
            "id":          f"{repo_name}/{rel}",   # Phase 2 PR relations reference this ID
            "title":       rel,
            "type":        "document",
            "timestamp":   git_timestamp(str(root), rel),
            "content":     {"text": content},
            "collections": ["codebase", repo_name, f.suffix.lstrip(".")],
            "metadata": {"doc_type":"source_file","repo":repo_name,
                      "language":f.suffix.lstrip("."),"tags":["codebase",repo_name]},
        })
        if len(batch) == 20:
            all_ids += upload_batch(batch); batch = []; time.sleep(1)
    if batch: all_ids += upload_batch(batch)
    print(f"Verifying {len(all_ids)} files...")
    verify_batch(all_ids)
    print(f"✓ {len(all_ids)} files indexed from '{repo_name}'")
    return all_ids

if __name__ == "__main__":
    ingest_directory("/path/to/your/repo", "myrepo")
```

**Expected output:**

```
  Uploaded 20 items
  Uploaded 20 items
  Uploaded 14 items
Verifying 54 files...
✓ 54 files indexed from 'myrepo'
```

### Step 2: Metadata and collections

These per-item fields go in the ingestion payload, so they need no extra API calls.

- `metadata`: fields such as `doc_type`, `repo`, and `language`. To filter on one with `metadata_filters`, declare it in the database metadata schema first.
- `additional_metadata`: free-form key-value pairs for citation labels and occasional filters.
- `collections`: not an API field. HydraDB ignores it, so it does not scope search. To scope search, ingest into a `collection` and send the same `collection` on the query. A query without `collection` reads the database's default collection.

```jsonc
{
  "collections": ["codebase", "myrepo", "py"],
  // [0] source type:  "codebase" | "pull-requests" | "slack" | "wikis"
  // [1] repo/channel: "myrepo" | "eng-architecture"
  // [2] sub-category: extension, doc_type, etc.

  "metadata": {
    "doc_type": "source_file",
    // Recommended values:
    // source_file | pull_request | slack_thread | rfc | adr | wiki | runbook
    "repo":     "myrepo",
    "language": "py",
    "tags":     ["codebase", "auth"]
  }
}
```

### Step 3: Tuned search with graph context

Why the parameters are set this way:

- `mode: "thinking"` with `graph_context: true`: thinking returns a deeper graph slice than fast mode, which questions across many documents need.
- `alpha: 0.75`: leans semantic, close to the recommended starting point of 0.8.
- `recency_bias: 0.2`: a lighter preference for recent files than the `0.4` applied when you omit the field.
- `build_context`: drops chunks scoring under 0.5 and removes duplicates by `chunk_uuid`.

```python
import sys, os
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from config import client, DATABASE_ID

def tuned_recall(query: str, scope: str = None, max_results: int = 15):
    """scope: optional collection. Omit to search the database's default collection."""
    kwargs = {
        "database":     DATABASE_ID,
        "query":         query,
        "max_results":   max_results,
        "mode":          "thinking",
        "graph_context": True,
        "alpha":         0.75,
        "recency_bias":  0.2,
    }
    if scope: kwargs["collection"] = scope
    return client.query(**kwargs)

def build_context(chunks: list, min_score: float = 0.5) -> tuple[str, list]:
    """
    Extract chunk_content from chunks and build LLM context string.
    Filters by relevancy_score; deduplicates by chunk_uuid.
    Returns: (context_text, sources_list)
    """
    parts, sources, seen = [], [], set()
    for chunk in chunks:
        relevancy_score = chunk.relevancy_score if chunk.relevancy_score is not None else 1
        if relevancy_score < min_score: continue
        chunk_content = chunk.chunk_content or ""  # canonical field
        uid           = chunk.chunk_uuid or chunk_content[:40]
        if not chunk_content or uid in seen: continue
        seen.add(uid)
        addl = chunk.additional_metadata
        doc_type = (addl or {}).get("doc_type", "doc")
        title    = chunk.source_title or "untitled"
        parts.append(f"[{doc_type.upper()}] {title}\n{chunk_content}")
        sources.append({"title": title, "url": chunk.url,
                         "relevancy_score": chunk.relevancy_score,
                         "chunk_uuid": chunk.chunk_uuid})
    return "\n\n---\n\n".join(parts), sources
```

## Phase 2: Multi-source context (20 to 30 minutes)

Link GitHub source files to their pull requests, Slack decision threads, and wikis, so one "why" query draws on all four.

**Goal:** a "why" question returns code, PR, Slack, and RFC context in one response.

HydraDB's [connectors](/essentials/v2/connectors) can also sync Slack and GitHub for you on a schedule. This phase ingests them by hand so you control the IDs and `relations`.

> **Explicit vs. automatic links:** `relations.ids` *guarantees* a link every time. HydraDB also extracts relationships from content, but that is best-effort. Use explicit relations for links that matter.

### Why each source type matters

Code search answers *what* a function does, but the *why* rarely lives in the code file.

- **Source files:** *what* the code does now. They anchor the query and are where link-following starts.
- **Pull requests:** *why* the change happened. Descriptions and reviews capture intent and rejected alternatives. Set `relations.ids` to the changed file IDs.
- **Slack threads:** discussion, trade-offs, and informal approvals that never reach the docs.
- **Wikis, RFCs, and ADRs:** the formal decision record and approval chain. One RFC answers a whole class of "why" questions.

> **Adaptation checklist:** pick a stable ID scheme first, then start with a small set of high-signal sources and expand. Good IDs and a few trustworthy sources beat a huge, messy index.

### Step 2: Ingest pull requests with explicit graph relations

Turn each merged PR into one document (title, description, review comments, changed files). `relations.ids` links it to every source file it changed.

**Before:** create a classic token with `repo` scope at `github.com/settings/tokens`. Add it to `.env` as `GITHUB_TOKEN`, along with `GITHUB_OWNER` and `GITHUB_REPO`.

```python
import sys, os, time, requests
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from config import client, DATABASE_ID
from phase1.batch_upload import upload_batch, verify_batch

GH_TOKEN = os.environ.get("GITHUB_TOKEN", "")
GH_OWNER = os.environ.get("GITHUB_OWNER", "")
GH_REPO  = os.environ.get("GITHUB_REPO",  "")
GH_HEADS = {"Authorization": f"Bearer {GH_TOKEN}",
            "Accept": "application/vnd.github+json"}

def fetch_merged_prs(max_pages: int = 5) -> list:
    base, prs = f"https://api.github.com/repos/{GH_OWNER}/{GH_REPO}", []
    for page in range(1, max_pages+1):
        r = requests.get(f"{base}/pulls", headers=GH_HEADS,
            params={"state":"closed","per_page":100,"page":page}, timeout=15)
        r.raise_for_status()
        page_prs = [p for p in r.json() if p.get("merged_at")]
        if not page_prs: break
        for pr in page_prs:
            url = pr["url"]
            fr = requests.get(f"{url}/files",   headers=GH_HEADS, timeout=10)
            rr = requests.get(f"{url}/reviews", headers=GH_HEADS, timeout=10)
            cr = requests.get(f"{url}/comments",headers=GH_HEADS, timeout=10)
            pr["files"]   = fr.json() if fr.ok else []
            pr["reviews"] = rr.json() if rr.ok else []
            pr["comments"]= cr.json() if cr.ok else []
            prs.append(pr); time.sleep(0.05)
        print(f"  Page {page}: {len(page_prs)} merged PRs")
    print(f"✓ Fetched {len(prs)} PRs")
    return prs

def ingest_pull_requests(prs: list, repo_name: str) -> list:
    batch, all_ids = [], []
    for pr in prs:
        if not pr.get("merged_at"): continue
        changed  = [f["filename"] for f in pr.get("files", [])]
        reviews  = "\n\n".join(r["body"] for r in pr.get("reviews",[]) if r.get("body"))
        comments = "\n\n".join(c["body"] for c in pr.get("comments",[]) if c.get("body"))
        # IDs must exactly match those set in ingest_directory()
        ids = [f"{repo_name}/{fname}" for fname in changed]
        content = (
            f"PR #{pr['number']}: {pr['title']}\n"
            f"Author: {pr['user']['login']} | Merged: {pr['merged_at']}\n\n"
            f"Description:\n{pr.get('body') or '(none)'}\n\n"
            f"Changed files:\n" + "\n".join(changed) +
            f"\n\nReview comments:\n{reviews or '(none)'}\n\n"
            f"Inline comments:\n{comments or '(none)'}"
        )
        batch.append({
            "id":          f"pr-{pr['number']}",
            "title":       f"PR #{pr['number']}: {pr['title']}",
            "type":        "document",
            "timestamp":   pr["merged_at"],
            "content":     {"text": content},
            "collections": ["pull-requests"],
            "relations":   {"ids": ids},
            "metadata": {"doc_type":"pull_request","pr_number":pr["number"],
                      "author":pr["user"]["login"],"changed_files":changed},
        })
        if len(batch)==20: all_ids+=upload_batch(batch); batch=[]; time.sleep(1)
    if batch: all_ids+=upload_batch(batch)
    verify_batch(all_ids)
    print(f"✓ {len(all_ids)} PRs indexed")
    return all_ids

if __name__ == "__main__":
    prs = fetch_merged_prs(max_pages=3)
    ingest_pull_requests(prs, "myrepo")
```

### Step 3: Ingest Slack threads

Group messages by `thread_ts` so each thread becomes one document. Architecture channels, post-mortems, and decision threads are worth the most.

**Before:** export and unzip your workspace at `your-workspace.slack.com/services/export` (requires admin). Structure: `{export_dir}/{channel_name}/{YYYY-MM-DD}.json`.

```python
import sys, os, json, time, pathlib
from datetime import datetime
sys.path.insert(0, os.path.dirname(os.path.dirname(__file__)))
from phase1.batch_upload import upload_batch, verify_batch

def ingest_slack_export(export_dir: str, channels: list[str]) -> list:
    batch, all_ids = [], []
    root = pathlib.Path(export_dir)

                          "message_count":len(msgs)},

            if len(batch)==20: all_ids+=upload_batch(batch); batch=[]; time.sleep(1)
```

### backend/search.py

`recall_context()` returns the raw HydraDB payload. `build_context_block()` turns its `chunks` into the LLM context string; `app.py` uses `sources` separately for citations.

```python
from backend.hydra_client import search_docs


def recall_context(query: str, max_results: int = 10):
    """
    Call search_docs() with sensible defaults for the first backend.
    scope=None means HydraDB searches the database's default collection.
    Returns SDK object with .chunks and .sources attributes.
    """
    return search_docs(
        query=query,
        max_results=max_results,
        scope=None,            # no collection: searches the default collection
        graph_context=True,
        recency_bias=0.2,
    )


def build_context_block(recall_payload) -> str:
    """
    Extract chunk_content from each chunk and assemble the LLM context string.

    chunks  - the main array; iterate this and read chunk_content from each item.
    sources - the deduplicated source list; used for citations in app.py.

    chunk_content is the canonical field to pass into the LLM.
    Always iterate chunks[], never a "results" key - the correct key is "chunks".
    """
    chunks  = recall_payload.data.chunks or []
    sources = recall_payload.data.sources or []

    context_parts = []
    for chunk in chunks:
        text = (chunk.chunk_content or "").strip()
        if text:
            context_parts.append(text)

    context_text = "\n\n".join(context_parts)

    source_lines = []
    for source in sources:
        title     = source.title or "Untitled"
        id = source.id or ""
        source_lines.append(f"- {title} ({id})")

    sources_text = "\n".join(source_lines)

    return f"Context:\n{context_text}\n\nSources:\n{sources_text}"
```

> **Production upgrade, score filtering:** drop low-scoring chunks before building the string, as Phase 1's `build_context()` helper does.

### backend/answer.py

Formats the prompt around the context block and streams a GPT-4o answer. It is the only file that touches OpenAI and never calls HydraDB. An empty context returns a safe fallback without calling the model, the main hallucination guard.

```python
from typing import Generator
from openai import OpenAI
from backend.config import OPENAI_API_KEY, OPENAI_MODEL

_client = OpenAI(api_key=OPENAI_API_KEY)

SYSTEM_PROMPT = """You are a codebase AI assistant. You answer questions about
code, architecture decisions, pull requests, and engineering discussions.

RULES:
1. Only answer from the provided context.
2. If the context is insufficient, say:
   "I don't have enough context to answer that. Try rephrasing or check the relevant source directly."
3. Cite sources inline using [Source: exact_title_here].
4. If multiple sources support a claim, cite all of them.
5. Distinguish clearly between:
   - what the code does
   - why it was written that way
   - who approved or discussed it
6. Never speculate."""


def format_prompt(question: str, context: str) -> list[dict]:
    """
    Build the messages array for the OpenAI API.
    Context goes in the user message - not the system prompt.
    This keeps the system prompt stable and makes context easy to audit.
    """
    user_content = (
        "CONTEXT FROM CODEBASE (retrieved by HydraDB):\n\n"
        f"{context}\n\n"
        "---\n\n"
        f"QUESTION: {question}\n\n"
        "Answer using only the context above. Cite every source you use."
    )
    return [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user",   "content": user_content},
    ]


def stream_answer(question: str, context: str) -> Generator[str, None, None]:
    """
    Streams GPT-4o tokens. If context is empty, yields a safe fallback
    WITHOUT calling OpenAI - prevents the model from hallucinating
    when HydraDB retrieval returned nothing.
    """
    if not context.strip():
        yield (
            "I couldn't find relevant context in the codebase index for that question. "
            "The index may still be building, or the topic may not be ingested yet. "
            "Try rephrasing, or check that the relevant files were uploaded."
        )
        return

    messages = format_prompt(question, context)
    stream = _client.chat.completions.create(
        model=OPENAI_MODEL,
        messages=messages,
        stream=True,
        max_tokens=1200,
        temperature=0.1,  # low temp = grounded, not creative
    )
    for chunk in stream:
        delta = chunk.choices[0].delta.content or ""
        if delta:
            yield delta
```

```python
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import StreamingResponse

from backend.answer import stream_answer

app = FastAPI(title="Cursor for Docs API")

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],         # tighten in production
    allow_methods=["GET", "POST"],
    allow_headers=["*"],
)


@app.get("/")
def health():
    return {"status": "ok"}


@app.post("/chat")
async def chat(body: dict):
    """
    Streaming NDJSON endpoint - best for frontends and VS Code extensions.
    Line 1:  {"sources": [...]}
    Line 2+: {"text": "token chunk"}
    """
    question = body.get("question", "").strip()
    if not question:
        raise HTTPException(status_code=400, detail="question is required")

    recall_payload = recall_context(question, max_results=10)
    context_block  = build_context_block(recall_payload)

    async def stream():
        # Emit sources first so the client can render citations immediately
        sources_list = [{"title": s.title, "id": s.id} for s in (recall_payload.data.sources or [])]
        yield json.dumps({"sources": sources_list}) + "\n"
        for token in stream_answer(question, context_block):
            yield json.dumps({"text": token}) + "\n"

    return StreamingResponse(stream(), media_type="application/x-ndjson")


@app.post("/ask")
def ask(body: dict):
    """
    Synchronous JSON endpoint - easier for Postman testing and API consumers
    that don't stream. Returns a complete response object in one round-trip.
    Returns answer, sources, chunks, and graph_context.

    question = body.get("question", "").strip()
    if not question:
        raise HTTPException(status_code=400, detail="question is required")

    full_answer    = "".join(stream_answer(question, context_block))

    return {
        "answer":        full_answer,
        "sources":       [{"title": s.title, "id": s.id} for s in (recall_payload.data.sources or [])],
        "chunks":        [{"chunk_content": c.chunk_content, "relevancy_score": c.relevancy_score,
                           "source_title": c.source_title} for c in (recall_payload.data.chunks or [])],
        "graph_context": None,
    }
```

### Answer generation flow

`/query` returns `chunks` and `sources` inside the envelope's `data` field, which the SDK exposes as `result.data`. Always iterate `chunks`, never `results`. Each `chunk_content` is a few hundred tokens of the original document. `build_context_block()` skips empty ones, joins the rest with blank lines, and appends `recall_payload.sources` as `- title (id)` lines so the model can cite them. The result becomes the user message in the OpenAI prompt and looks like this:

### Avoiding hallucination

`answer.py` guards against each way an LLM invents details about your codebase:

- **Out-of-context answers** (training data about similar code): rule 1 and temperature 0.1.
- **No-context answers:** `stream_answer()` returns a fallback before calling OpenAI.
- **Uncited claims:** rules 3 and 4.
- **Speculation as fact:** rule 6.

> **Keep temperature at 0.2 or below:** higher temperature adds creativity, the opposite of what accurate, cited answers need.

## Troubleshooting

### 401: Not authenticated

**Cause:** the Authorization header is missing or malformed: usually no `Bearer ` prefix, quotes around the key in `.env`, or a leading or trailing space.

**Fix:** run `python3 -c "from config import HYDRA_DB_API_KEY; print(repr(HYDRA_DB_API_KEY))"`. The output should be `'hdb_abc123'` with no spaces, and the header exactly `Authorization: Bearer hdb_abc123`.

### 404: Database does not exist

**Cause:** you uploaded or queried before creating the database, or the `database` does not match. Database IDs are case-sensitive.

**Fix:** run `python3 phase0/create_tenant.py` and wait for "✓ Database ready." Confirm `DATABASE_ID` in `config.py` matches what you passed to `create_tenant`.

### 404: Not found (on search or ingestion endpoint)

**Cause:** a typo, extra slash, or missing segment in the path, or a query on a `collection` that never had data written to it.

**Fix:** the paths are `/context/ingest` (file upload or JSON batch with `app_knowledge`), `/query`, and `/context/status`. With `collection`, confirm at least one batch reached that collection.

### 400: Provide at least one of documents or app_knowledge

**Cause:** for file upload, the field is named `file` instead of `documents`, or `Content-Type: application/json` was set manually, which breaks multipart. For a JSON batch, the array is empty or items lack required fields.

**Fix:** for file upload, use `files={"documents": (filename, f, "text/markdown")}` and `data={"database": DATABASE_ID}`, and do NOT set `Content-Type`. For a JSON batch, give each item `id`, `type`, and `content.text`.

### Empty search: chunks: []

**Cause:** indexing is still in progress, `relevancy_score` filtering in `build_context_block` is too aggressive, or the query matches no ingested content.

**Fix:** run `verify_file()` and confirm `"indexing_status": "completed"` in the `statuses` array. Then run `phase0/search.py` and print the raw response to check that `chunks` is non-empty before any filtering. Then check the `relevancy_score` values.

### 429: OpenAI insufficient_quota

**Cause:** your OpenAI account is out of credits or hit its usage limit. The error comes from `stream_answer()` in `answer.py`; HydraDB retrieval may be fine.

**Fix:** add billing at `platform.openai.com`. While debugging, swap in this fallback for `stream_answer`. It returns the retrieved context without calling OpenAI:

```python
# TEMPORARY DEBUG MODE - replace stream_answer in answer.py to test
# retrieval without OpenAI. Remove this before going to production.
def stream_answer(question: str, context: str):
    yield "=== DEBUG MODE (NO OPENAI) ===\n\n"
    yield f"Question:\n{question}\n\n"
    yield f"Context:\n{context[:1000]}"
```

> **General debugging pattern:** print the full error body first. With raw HTTP, add `print("STATUS CODE:", resp.status_code)` and `print("RESPONSE:", resp.text[:500])` after each `requests.post()`. With the SDK, catch the exception and print its status code and body.

## Production notes

- **Batch size and rate limits:** an `app_knowledge` batch upload accepts at most **20 source objects per request**. Sleep 1 second between batches. A large repo (1,000+ files) takes 10 to 30 minutes to ingest.
- **Indexing delays:** never rely on a fixed sleep. Poll [`/context/status`](/api-reference/v2/endpoint/source-status) until `"indexing_status": "completed"`; sources are searchable from `graph_creation`.
- **Consistency and upserts:** HydraDB upserts by `id`, so re-uploading replaces the document, with a brief window of stale chunks. Verify new IDs before marking a deployment complete.
- **LLM context window:** add a `relevancy_score` filter and a character cap (for example, 12,000 characters) to `build_context_block` so you stay inside GPT-4o's context window.
- **Graph edge consistency:** edges form only when both sides exist and are indexed. Ingest source files before PRs, and re-ingest affected PRs after adding new files.
- **API key security:** the key grants full access to all database data. Never commit it, use environment secrets in production, and rotate it if exposed.
- **OpenAI token costs:** for a 50-engineer team asking 200 questions a day, budget \$2 to \$4 a day. Use `gpt-4o-mini` for factual lookups to cut cost.
- **Search quality monitoring:** log the `relevancy_score` of each chunk you use. Falling median scores mean new content may be diluting the index; re-ingest with better metadata and collection tags.

```python
        "metadata":   {"doc_type": "source_file", "repo": "myrepo"},
    }]),
)

# Response: data.results[0].id == "myrepo/auth/middleware.py", with status "queued"
```

### Verify indexing status

**GET** `/context/status`: returns a `statuses[]` array. Poll until `"completed"`. A source is searchable from `"graph_creation"`.

```jsonc
// Required: ?ids=<id>&database=engineering-docs

// Response:
{
  "statuses": [
    { "id": "<id>", "indexing_status": "completed" }
  ]
}
// indexing_status: "queued" | "processing" | "graph_creation" | "completed" | "errored"
```

### Search: minimal request

**POST** `/query`: `collection` is optional. Omitted means the database's default collection. Returns `chunks[]` and `sources[]`.

```jsonc
{
  "database":   "engineering-docs",
  "query":       "internal IP auth skip logic",
  "max_results": 10
}

// collection is optional. Omitted means the database's default collection.
// Response: {"chunks": [...], "sources": [...]}
// Read chunk_content from each item in chunks[] for LLM context.
// relevancy_score on each chunk indicates ranked relevance.
```

### Multi-hop search

**POST** `/query`: multi-hop retrieval. Generate the answer in your app.

```json
{
  "database":     "engineering-docs",
  "query":         "Why does auth middleware skip token validation for internal IPs?",
  "max_results":   15,
  "mode":          "thinking",
  "graph_context": true,
  "alpha":         0.65,
  "recency_bias":  0.15
}
```

## Benchmarks

1,200 developer questions across three engineering teams (18 to 80 engineers, codebases of 150k to 2.2M lines). Each line gives naive vector search on the same content first, then HydraDB with `graph_context`.

- **"Why was X built this way?":** 22% vs 87% (+295%).
- **Cross-source search (code, PR, and Slack):** 14% vs 79% (+464%).
- **Factual lookup ("what does X do?"):** 71% vs 91% (+28%).
- **Decision trail completeness (3+ hops cited):** 4% vs 68% (+1,600%).
- **P95 search latency:** 180ms vs under 200 ms (sub-second).

> The 22% on "why" questions is structural, not a tuning problem: a source file and the RFC behind it embed as similar but unlinked vectors, so the RFC never surfaces. HydraDB follows every node linked to your query, not only the ones that look similar.
