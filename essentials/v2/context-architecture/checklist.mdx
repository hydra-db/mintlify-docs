Use this checklist before calling a HydraDB-backed system production-ready. Items assume v2 surfaces: [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context), [`POST /query`](/api-reference/v2/endpoint/query), [databases/collections](/essentials/v2/multi-tenant), [metadata](/essentials/v2/metadata), [graphs](/essentials/v2/context-graphs).

<Tip>
  Print or copy into your launch doc. Every unchecked item is a known class of incident or silent quality loss.
</Tip>

---

## Security

- [ ] API keys stored in a secret manager — never in client apps or git
- [ ] All HydraDB calls use `Authorization: Bearer` and `API-Version: 2`
- [ ] Customer/org isolation uses separate `database` values (not metadata-only)
- [ ] Environment isolation uses separate databases (`prod` vs `staging`)
- [ ] Session → `database` / `collection` mapping is server-side only
- [ ] Prompts never include raw API keys or cross-tenant identifiers from logs
- [ ] Erasure / retention path can [`DELETE /context`](/api-reference/v2/endpoint/delete-source) by id
- [ ] Highly sensitive content is not written to shared Knowledge collections

---

## Observability

- [ ] Ingest responses log returned source `id`s
- [ ] Status polling or [webhooks](/essentials/v2/webhooks) track `queued → completed` / `errored`
- [ ] `errored` statuses alert with `error_code` + message
- [ ] Query latency (p50/p95) measured per feature path
- [ ] Empty-result rate tracked (often scope/filter bugs)
- [ ] Correlate user request ids with HydraDB `database` + `collection` in your logs
- [ ] Dashboard for knowledge vs memory ingest volume
- [ ] Alert on sudden duplicate-id upsert spikes or delete bursts

---

## Performance

- [ ] Hot paths choose `mode: "fast"` vs `"thinking"` deliberately
- [ ] `graph_context: false` when graph unused
- [ ] `max_results` capped to the real context window budget
- [ ] `query_by: "text"` used for literal token lookups when appropriate
- [ ] Avoid unbounded `collections` fanout on latency-sensitive routes
- [ ] Async ingest never blocks the user-facing request thread beyond enqueue
- [ ] Bulk sync jobs are rate-aware and retry with backoff on transient errors

---

## Retrieval Quality

- [ ] Golden questions with expected source ids exist per major feature
- [ ] `type` (`knowledge` / `memory` / `all`) matches the product intent
- [ ] Personalized features verified with `type: "all"` or dual query merge
- [ ] Citations shown from returned `sources` (see [API Results](/essentials/v2/api-results))
- [ ] App-source features set `query_apps: true` when thread/ID behavior matters
- [ ] `additional_context` request hint used only when the raw query is ambiguous
- [ ] Regressions caught when upsert refresh changes rankings

---

## Metadata

- [ ] `database_metadata_schema` declared before bulk ingest of filter fields
- [ ] Hot filters use schema `metadata` with `enable_match: true` where intended
- [ ] Ad-hoc fields live in `additional_metadata`, not fake schema keys
- [ ] Every safety-critical query sends `metadata_filters`
- [ ] Team knows filters are exact equality (no silent OR/fuzzy)
- [ ] Label-only edits use [PATCH source metadata](/api-reference/v2/endpoint/update-source-metadata)
- [ ] Content edits use upsert re-ingest with the same `id`
- [ ] Additive schema changes planned via [metadata schema update](/api-reference/v2/endpoint/update-metadata-schema)

---

## Namespaces (databases & collections)

- [ ] Written collection map documented (user / workspace / team)
- [ ] Ingest and query use the **same** collection values
- [ ] Shared Knowledge scope is intentional (default vs team collection)
- [ ] No customer shares a database with another customer
- [ ] Staging data never points production agents at staging databases by mistake
- [ ] Collection naming is stable and non-PII where possible (hashed ids OK)

---

## Inference

- [ ] Raw conversational signal uses `infer: true` when preferences should be extracted
- [ ] Already-structured facts use `infer: false`
- [ ] `custom_instructions` reviewed for high-stakes extraction
- [ ] Inference never used as a substitute for Knowledge document ingest
- [ ] Inferred memories land in the correct user `collection`

---

## Memory

- [ ] Durable preferences have stable memory `id`s and upsert
- [ ] Ephemeral/session memories set `expiry_time`
- [ ] Write-back after agent turns is scoped and rate-limited
- [ ] Memory-only features query `type: "memory"`
- [ ] Contradictory prefs have an overwrite strategy (same id)
- [ ] Memory deletion path tested for user reset / logout cleanup where required

---

## Knowledge

- [ ] Stable source `id`s derived from upstream keys / `external_id`
- [ ] Upsert refresh path exists for wiki/ticket/doc changes
- [ ] Connector or app-source sync covers the systems of record
- [ ] Binary vs app-source ingest path chosen correctly ([Knowledge](/essentials/v2/knowledge))
- [ ] Forceful `relations` only for known product links
- [ ] Deleted upstream docs trigger HydraDB deletes

---

## RBAC

- [ ] Your app enforces who may read/write which `database` / `collection`
- [ ] HydraDB credentials are not end-user-scoped unless intentionally designed
- [ ] Department/ACL attributes encoded in metadata **and** enforced with filters
- [ ] Admin tools cannot query arbitrary customer databases without authz
- [ ] Support tooling audit logs include tenant identifiers

<Warning>
  HydraDB isolation primitives are necessary but not sufficient. **RBAC lives in your application** around tenant resolution and feature authorization.
</Warning>

---

## Lifecycle

- [ ] Creation → status → query gate implemented
- [ ] Version or latest-wins policy documented
- [ ] Archive convention (`status=archived`) + default filters
- [ ] Retention job hard-deletes when required
- [ ] Learning loop does not unbounded-grow Memories
- [ ] Replay/eval stores source ids for past answers
- [ ] See [Context Lifecycle](/essentials/v2/context-architecture/lifecycle)

---

## Evaluation

- [ ] Offline eval set per critical intent
- [ ] Online feedback loop can down-rank or delete bad sources
- [ ] Separate evals for Knowledge-only vs personalized (`all`) paths
- [ ] Graph-on vs graph-off compared where latency matters
- [ ] Empty-result troubleshooting runbook exists

---

## Deployment

- [ ] Database provisioning automated on tenant signup
- [ ] Traffic waits until [vectorstore + graph status](/api-reference/v2/endpoint/tenant-status) ready
- [ ] Feature flags can disable write-back or graph independently
- [ ] Runbooks for ingest backlog and query SLO burn
- [ ] SDKs pinned; breaking API-Version changes reviewed
- [ ] Load test includes ingest + query together, not query alone
- [ ] Rollback plan: pin corpus version via metadata filter or freeze upsert jobs
