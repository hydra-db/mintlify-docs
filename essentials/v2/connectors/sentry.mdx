Sync issues and error events from the Sentry projects you select, plus project, team and member records. Each issue, event, project, team and member is one document. Teams and members cover the whole organization, even when you select only a few projects.

Sentry access controls are not imported, so every synced item is visible to everyone who can query the collection unless you set an access rule. An event is not linked to the issue it belongs to. Issue comments, stack traces and breadcrumbs are not synced.

<Note>
Sentry is in beta.
</Note>

## Permissions

<Warning>
Sentry permissions are not imported, so **Enforce ACL** is unavailable for this connector. Every synced item is visible to everyone who can query the collection, unless you [set an access rule on the resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).
</Warning>

- Sentry team-based project access is not reproduced.

API-key requests must omit `enforce_acl`, including `false`. See [ACL on synced content](/essentials/v2/connectors#5-acl-native-rbac-awareness).

## Before you connect

### Credentials

Sentry uses an internal integration token.

<ResponseField name="api_token" type="secret string" required>
The token of a Sentry internal integration, created under Organization settings, Developer settings.
</ResponseField>

**Connector settings**

<ResponseField name="organization" type="string">
The organization slug. If you leave it out, HydraDB uses the first organization the token returns, and warns if the token reaches more than one.
</ResponseField>

**Scopes to give the internal integration**

- `org:read`
- `project:read`
- `event:read`

### Set it up

<Steps>
  <Step title="Create an internal integration">
    In Sentry, open your organization's Developer settings and create an internal integration with `org:read`, `project:read` and `event:read`. Copy its token.
  </Step>
  <Step title="Create the connector">
    Paste the token as `api_token`. If the token reaches more than one organization, set `organization` to the one you want.
  </Step>
  <Step title="Select projects">
    HydraDB lists the projects the token can see, by slug. Listing stops after 20 pages. Select the projects to sync.
  </Step>
</Steps>

One connector reads one Sentry organization.

<Accordion title="Connect through the API">

Use provider `sentry` with [Create Connector](/api-reference/v2/endpoint/create-connector). Then call [Discover Connector Resources](/api-reference/v2/endpoint/discover-connector-resources) to list the resources the connector can sync, and [Configure Connector](/api-reference/v2/endpoint/configure-connector) to choose what to sync.

</Accordion>

## Keeping in sync

- **First sync:** Issues and events reach back the window set by `lookback_days`, 30 days by default. Issues are measured by when they were last seen, events by when they were created. Selected projects, teams and members are read in full, whatever their age.
- **New and changed items:** Each sync reads issues seen again since the last sync and events created since then. Selected projects, teams and members are read in full on every sync.
- **Edits:** An issue is read again when it recurs. A change of status or assignee without a new occurrence may not be picked up.
- **Deletions:** Resolving or ignoring an issue changes its status. It does not remove the document. An item deleted in Sentry stays searchable in HydraDB.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` on the connector to change it.

## What gets synced

### On every Sentry item

<ResponseField name="connector_id" type="Query filter">
Limits a query to this connector's items. Not searchable.
</ResponseField>

<ResponseField name="provider" type="Query filter">
Always `sentry`. Not searchable.
</ResponseField>

### Issues

- **One document:** One Sentry issue: a group of similar errors.
- **Title:** The issue title. An issue with no title is called `Sentry issue` with its id.
- **Text:** The title, then a `Culprit` line, the exception type and value, and `File`, `Function`, `Level` and `Project` lines. The status, the assignee and the issue's short id are searchable too.
- **Date:** When the issue was last seen, else when it was first seen.
- **Link back:** The issue page in Sentry.

<ResponseField name="Issue id" type="Searchable text">
The short id, such as `PROJECT-123`, else the numeric id. Keeps later syncs on the same document, and a search can match it.
</ResponseField>

<ResponseField name="status" type="Searchable text">
`resolved`, `unresolved` or `ignored`, so a query can match the issue's status.
</ResponseField>

<ResponseField name="assignee" type="Searchable text, Graph connection, Graph identity">
The assigned user's or team's name, else their email, written as an `Assignee` line. A team assignment also links the issue to that team's record through `related_to`, using the Sentry team ID. A user assignment does not link to an organization member record.
</ResponseField>

<ResponseField name="Project id" type="Graph connection">
The Sentry project ID links the issue to its project's record through `part_of`. Not searchable.
</ResponseField>

<ResponseField name="culprit" type="Searchable text">
The code location Sentry blames, written as the `Culprit` line.
</ResponseField>

<ResponseField name="level" type="Searchable text">
The severity, written as the `Level` line.
</ResponseField>

<ResponseField name="first_seen, last_seen" type="Result date">
When the issue first and last occurred. The last occurrence, else the first, is the result date. Not searchable.
</ResponseField>

<ResponseField name="additional_metadata.sentry_id" type="Query filter">
The numeric issue id. Picks out one issue. Not searchable.
</ResponseField>

<ResponseField name="additional_metadata.sentry_short_id" type="Query filter">
The short id, such as `PROJECT-123`. Picks out one issue. This key is not searchable, but the short id is part of the issue text.
</ResponseField>

<Accordion title="Stored only, not searchable (2)">

<ResponseField name="num_comments, user_count" type="Stored only">
How many comments the issue has and how many users it affected.
</ResponseField>

<ResponseField name="logger, platform" type="Stored only">
The logger and platform that produced the issue.
</ResponseField>

</Accordion>

### Error events

- **One document:** One error event.
- **Title:** The event title, else its message. An event with neither is called `Sentry event` with its id.
- **Text:** The title, then `Message`, `Culprit`, `Location`, `Platform` and `Project` lines. The event id is searchable too.
- **Date:** When the event was created.
- **Link back:** None.

<ResponseField name="Event id" type="Searchable text">
The Sentry event id. Keeps later syncs on the same document, and a search can match it.
</ResponseField>

<ResponseField name="message, culprit, location, platform" type="Searchable text">
The event message, the blamed code location, the location and the platform, each written as its own line.
</ResponseField>

<ResponseField name="project_id, parent_id" type="Searchable text, Graph connection">
The event's project, as `project:<id>`, written in the `Project` and `Parent` lines. Links the event to its project's record.
</ResponseField>

<ResponseField name="Event time" type="Result date">
When the event was created. Not searchable.
</ResponseField>

<Accordion title="Stored only, not searchable (1)">

<ResponseField name="group_id" type="Stored only">
The id of the issue the event belongs to. It does not link the event to the issue.
</ResponseField>

</Accordion>

### Projects and teams

- **One document:** One Sentry project or team.
- **Title:** The name, else the slug. A record with neither gets a generated title with its id.
- **Text:** The name and a `Slug` line. A project also has `Platform` and `Status` lines. The title is searchable too.
- **Date:** When the project or team was created.
- **Link back:** None.

<ResponseField name="Project id" type="Graph connection">
A project's id, as `project:<id>`. Issues and events of the project link to this record. Not searchable.
</ResponseField>

<ResponseField name="Owning team ids" type="Graph connection">
The Sentry team IDs link a project to each owning team's record through `part_of`. Not searchable.
</ResponseField>

<ResponseField name="Team id" type="Graph connection">
The Sentry team ID identifies the record that assigned issues and owned projects link to. Not searchable.
</ResponseField>

<ResponseField name="Creation time" type="Result date">
When the project or team was created. Not searchable.
</ResponseField>

<Accordion title="Stored only, not searchable (1)">

<ResponseField name="object_type" type="Stored only">
`project` or `team`.
</ResponseField>

</Accordion>

### Members

- **One document:** One organization member.
- **Title:** The member's name, else their email. A member with neither gets a generated title with their id.
- **Text:** The name, then `Email`, `Role` and `Invite status` lines, and any contact details Sentry reports, such as names, organization, emails, phone numbers, a profile link and the creation and update times. The title is searchable too.
- **Date:** When the membership was created.
- **Link back:** The member's profile link, when Sentry reports one.

<ResponseField name="email, emails" type="Searchable text, Graph identity">
The member's primary and other emails. Identify the member as a person in the graph.
</ResponseField>

<ResponseField name="display_name, provider_user_id" type="Searchable text, Graph identity">
The member's display name and Sentry user id. Name the member as a person in the graph.
</ResponseField>

<ResponseField name="first_name, last_name, job_title, organization_name, organization_id, lifecycle_stage" type="Searchable text">
Names, organization, role and invite status, when reported.
</ResponseField>

<ResponseField name="owner, owner_email" type="Searchable text, Graph identity">
The record owner and their email, when reported. The graph records the owner as a person.
</ResponseField>

<ResponseField name="phones" type="Searchable text">
Phone numbers, when reported. They do not identify the person in the graph.
</ResponseField>

<ResponseField name="url" type="Searchable text">
The profile link, when reported. Also the link back.
</ResponseField>

<ResponseField name="created_at" type="Searchable text, Result date">
When the membership was created.
</ResponseField>

<ResponseField name="updated_at" type="Searchable text">
The last reported update, else the creation time. The graph also records it as when the member was last updated.
</ResponseField>

**Example searches**

- Which unresolved Sentry issues mention a timeout in the payments project?
- Who is assigned to PAYMENTS-482?
- Which file and function raise the KeyError issue?

## How it fits into the graph

- Issues use the Ticket class.
- Error events use the Ticket class.
- Projects and teams use the Page class.
- Members use the Contact class.

[Graph classes](/essentials/v2/connector-providers#graph-classes) explains each class.

**Connections Sentry creates**

- An error event to its project's record.
- Issues link to their project through `part_of` and, when assigned to a team, to that team through `related_to`. Projects link to each owning team through `part_of`.
- These links use Sentry's project and team IDs, not display names, and are fully resolved only after the target is indexed in the same database and collection.
- Event-to-issue and user-assignee-to-member links are not provided. An event's numeric group ID does not identify the issue's short ID, and a user ID is distinct from an organization member ID.
- Stack traces are not read for links to code.
- No links to items in other tools.

**People and groups**

- The assignee of each issue.
- Each organization member, identified by email.

**Found in the text**

Issue and event titles, messages, culprits and exception text. HydraDB identifies people, organizations, projects and other named things in this text. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Not synced

- Projects you did not select.
- Issue comments and activity. Only the comment count is kept.
- Stack traces, breadcrumbs and tags beyond the issue summary.
- Releases, alerts, performance data and replays.
- Sentry team-based project access.
