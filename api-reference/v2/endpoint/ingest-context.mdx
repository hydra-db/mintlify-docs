Ingest context into a database. Ingestion is asynchronous: the response returns an ID for each item, and an item is searchable once indexing completes. A database holds one corpus, so you never choose where an item goes. Choose the payload by what you are storing:

| Payload | Send | Use for |
| --- | --- | --- |
| Context items | `context`, a list of items, as a JSON body or a multipart form field | Text you already have: notes, preferences, decisions, support answers, and past conversations. Each item is a `text` string or a `conversation`. See [Context item fields](#context-item-fields). |
| Files | `documents`, in a multipart form | Binary uploads that HydraDB should parse: PDFs, Office and iWork files, spreadsheets, images, and plain text. See [Supported file formats](#supported-file-formats). |

Send items and files in separate requests. A form that carries both `context` and `documents` returns `400`.

<Note>
Do not send `type`. A database created before unified databases became the default is a split database, which takes `type` and a different set of upload fields. See [Split databases](/essentials/v2/split-databases).
</Note>

## Request fields

| Name | Description |
| --- | --- |
| <Field name="database" type="string" required /> | Target database. |
| <Field name="collection" type="string" /> | Collection to write to. A new name creates the collection automatically. Omit it to use the default collection. List existing collections with [List Collections](/api-reference/v2/endpoint/list-collections). |
| <Field name="context" type="object[]" /> | The items to ingest, from 1 to 100. In a JSON body send the list itself. In a multipart form send it as a JSON string in a field named `context`. Required unless you upload files. See [Context item fields](#context-item-fields). |
| <Field name="enrich" type="boolean" /> | Default for every item's `enrich`. (default=`true`) |
| <Field name="upsert" type="boolean" /> | Default for every item's `upsert`. For files, replaces existing files with the same ID; set to `false` to error on conflict, and a file whose ID exists comes back `failed` with `error_code: "E9003"`. (default=`true`) |
| <Field name="graph_payload" type="object" /> | Map of item ID to your own entities and relations. Replaces LLM graph extraction for each keyed item. Keys are `context_id` values for items, or `document_metadata` ids for files. In a multipart form, send it as a JSON string. See [Bring your own graph](#examples). |
| <Field name="documents" type="file[]" /> | Files to parse, in a multipart form only. Cannot be combined with `context`. See [Supported file formats](#supported-file-formats). (default=`[]`) |
| <Field name="document_metadata" type="string (JSON array)" /> | One entry per file in `documents`, in the same order. The counts must match, or the request returns `400`. If omitted, files index with inferred defaults such as filename and title. See [File fields](#file-fields). |

- **JSON or multipart:** Send `context` as an `application/json` body, or as a JSON string in a `multipart/form-data` field. The SDKs use the form. Files need the form. A body that is neither returns `415`.
- **Limits:** At most 100 items per request, 1 MiB of text per item, and 8 MiB of text per request. Over a limit returns `400`; split the request.
- **Unknown keys are refused:** An unknown key in a JSON body, or inside a `context` item, returns `400`. The message names the key and lists the accepted fields, so a misspelling never disappears silently. An extra top-level field in a multipart form may be ignored.
- **`202 Accepted` means queued, not indexed:** A successful response only confirms your items were accepted, not that they are ready to query. Before querying, poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) with the returned IDs until each item reaches `graph_creation` (searchable), `completed`, or `errored`. Alternatively, register a webhook for `indexing.status_changed` events (see [Webhooks](/api-reference/v2/endpoint/webhooks-overview)).

## Context item fields

Each item in `context` carries exactly one of `text` or `conversation`. Every other field is optional.

| Field | Description |
| --- | --- |
| <Field name="text" type="string" recommended /> | Raw text or markdown. Required unless `conversation` is provided. |
| <Field name="conversation" type="object[]" recommended /> | Turns of a chat, `{ "role", "content" }`, the shape you already send to a chat model. `role` is `user`, `assistant`, or `system`. `system` turns steer enrichment and are never stored as facts. Required unless `text` is provided. |
| <Field name="context_id" type="string" /> | The item's ID and its upsert key. Use your application's ID to keep the same identifier in both systems. At most 100 bytes. Must not contain a comma (`,`), which is the ID separator on [Ingestion Status](/api-reference/v2/endpoint/source-status), and must not start with `att_` or `cmt_`. (default=generated) |
| <Field name="title" type="string" /> | Label returned as `title` by [List Context](/api-reference/v2/endpoint/list-context). At most 1,024 bytes. Give two items with the same text different titles. |
| <Field name="user_name" type="string" /> | The person speaking: the author of a `text` item, or the `user` side of a `conversation`. Feeds enrichment. (default=`"User"`) |
| <Field name="enrich" type="boolean" /> | Run additional enrichment on this item. Explicit `false` skips that enrichment; ingestion, indexing, and entity/graph extraction may still run. (default=the request's `enrich`, else `true`) |
| <Field name="upsert" type="boolean" /> | Replace an existing item with the same `context_id`. Lets one request replace some items and add others. (default=the request's `upsert`, else `true`) |
| <Field name="happened_at" type="string (YYYY-MM-DD)" /> | The date the content is about, for example the day a meeting took place. Any other format returns `400`. |
| <Field name="attributes" type="object" /> | Schema-backed fields for filtering and search, declared in the database's `database_metadata_schema`. Filter on them with `attributes` on [Query](/api-reference/v2/endpoint/query#request-body). At most 16 KiB. |
| <Field name="custom_attributes" type="object" /> | Free-form fields for display or bookkeeping. No schema declaration is required. At most 1 KiB. |
| <Field name="context_category" type="string" /> | A label you put on the item: `user_preference` or `business_knowledge`. The label is stored on the item, can be filtered on in [List Context](/api-reference/v2/endpoint/list-context#filters), and comes back on query chunks as `enrichment_kind`. It does not change how the item is processed. (default=`"auto"`, which stores no label) |
| <Field name="forceful_relations" type="object" /> | Other items this one belongs with: `{ "context_ids": ["..."], "properties": { ... } }`. `properties` is optional, holds flat string, number, or boolean values, and is stored on each link. A thinking-mode query follows these links and returns the linked items in `data.forceful_relations`. See [Link items that belong together](#examples). |
| <Field name="acl" type="string[]" /> | Who may retrieve this item: bare emails, `user_email:`, `group:`, or `domain:` principals, or `__public__`. Omit it to leave the item unrestricted. An empty list restricts it to nobody. A malformed principal returns `400`. |

See [Metadata Filters](/essentials/v2/metadata#overview---two-layers) for choosing between `attributes` and `custom_attributes`, and [metadata size limits](/essentials/v2/metadata#size-caps) for how HydraDB measures the caps.

## Supported file formats

<span id="size-limit"></span>

Each file in `documents` can be up to **50 MB**. A larger file returns `413` with a message naming the file, and no part of the request is processed. Split larger files before uploading.

<Accordion title="View supported and unsupported file formats">

HydraDB accepts these formats through `documents`:

| Type | Formats |
| --- | --- |
| Documents | `.pdf` `.doc` `.docx` `.docm` `.dot` `.dotx` `.odt` `.ott` `.rtf` |
| Spreadsheets | `.xls` `.xlsx` `.xlsm` `.xlsb` `.ods` `.ots` `.csv` `.tsv` |
| Presentations | `.ppt` `.pptx` `.pptm` `.odp` `.otp` |
| Apple iWork | `.pages` `.numbers` `.key` |
| Images | `.png` `.jpg` `.jpeg` `.tif` `.tiff` `.webp` `.gif` `.bmp` |
| Plain text | `.txt` `.md` `.markdown` `.json` |

What HydraDB extracts differs by type:

| Type | What gets indexed |
| --- | --- |
| Documents and presentations | The text, in reading order. Slide titles and body text both come through. |
| Spreadsheets | Cell values rendered as a table, one per sheet. Formulas are indexed as their computed result, not the formula itself. |
| Images and scans | Text read out of the picture with OCR. A photo of a page and a scan of a page both work. |
| Plain text | The file as-is. |

Files with no readable text fail with [`E2002`](/api-reference/v2/error-responses#ingestion-error-codes). Upload a version containing text.

### Unsupported formats

| Format | Upload this instead |
| --- | --- |
| `.heic` `.heif` `.avif` | Export the photo as JPEG or PDF |
| `.svg` `.ico` | Export as PNG or JPEG |
| `.html` `.htm` `.xml` | Save the page as PDF |
| `.eml` `.msg` | Save the message as PDF, or sync the mailbox with a [connector](/essentials/v2/connectors) |
| `.epub` `.wpd` | Convert to PDF or DOCX |
| `.zip` | Upload the files individually |

Use the file's real extension. When the filename has no extension, HydraDB uses the part's `Content-Type`. Renaming an unsupported file does not convert it: a renamed file may fail during indexing. Check [Ingestion Status](/api-reference/v2/endpoint/source-status) for that failure.

### When a file is not supported

An unsupported file is rejected in the upload response and does not block other files in the upload. The request returns `202` as usual. The rejected file comes back with `status: "failed"` and `error_code: "E1002"`, and every other file is queued normally:

```json
{
  "success": true,
  "data": {
    "success": false,
    "message": "Upload completed with some failures.",
    "results": [
      { "id": "6cc7bcd185b044cd", "filename": "report.pdf", "status": "queued", "error": null, "error_code": null },
      { "id": "f47411c736447126", "filename": "photo.heic", "status": "failed", "error": "This file format isn't supported. Please upload a PDF, Office document (Word, Excel, PowerPoint), image, CSV or text file.", "error_code": "E1002" },
      { "id": "d0c919bdec196a8d", "filename": "notes.txt", "status": "queued", "error": null, "error_code": null }
    ],
    "success_count": 2,
    "failed_count": 1
  },
  "error": null,
  "meta": { "request_id": "bcd03673-174d-4a73-83e6-73bfcdc16061", "api_version": "2.0.1" }
}
```

`data.success` is `true` only when every file was queued. Check `data.results` for individual failures.

Files rejected with `E1002` have no ingestion status record. Handle the format error from the upload response.

</Accordion>

## File fields

Each entry in `document_metadata` describes the file at the same position in `documents`.

| Field | Description |
| --- | --- |
| <Field name="id" type="string" /> | The file's ID and its upsert key. Same rules as `context_id`: no comma, at most 100 bytes. (default=generated) |
| <Field name="metadata" type="object" /> | Schema-backed fields, the file equivalent of an item's `attributes`. At most 16 KiB. (default=`{}`) |
| <Field name="additional_metadata" type="object" /> | Free-form fields, the file equivalent of an item's `custom_attributes`. At most 1 KiB. (default=`{}`) |
| <Field name="relations" type="object" /> | Other items this file belongs with. Shape: `{ "ids": ["...", "..."] }`. |
| <Field name="infer" type="boolean" /> | Run model enrichment on this file. (default=`false`) |
| <Field name="evidence_kind" type="string" /> | How this content came to be known: `assertion`, `record`, `said`, `done`, `third_party`, or `inferred`. Any other value returns `400`. |
| <Field name="evidence_subject" type="string" /> | A stable handle for who or what the content is about. |

Those seven, plus the deprecated aliases `source_id` and `file_id` (for `id`) and `document_metadata` (for `additional_metadata`), are the only keys accepted. Anything else (including `title`, `type`, `url` and `timestamp`) is rejected with a `400` naming the unsupported key, rather than being silently dropped.

A file's **title is derived, not settable**. It defaults to the uploaded filename and is returned as `title` on `/context/list`. It cannot be overridden at ingest, and [`PATCH /context/{id}/metadata`](/api-reference/v2/endpoint/update-source-metadata) only merges `additional_metadata` and `database_metadata`. Use `additional_metadata` for your own display fields.

  | <Field name="entities[].name" type="string" required /> | Entity name. Normalized (lowercased) server-side so it matches at query time. At most 256 chars. |
  | <Field name="entities[].type" type="string" /> | Entity type (e.g. `PERSON`, `POLICY`). Stored as supplied. |
  | <Field name="entities[].namespace" type="string" /> | Logical grouping for the entity. Stored as supplied. |
  | <Field name="entities[].identifier" type="string" /> | Optional external id (email, URL, etc.), display only. |
  | <Field name="relations" type="array" /> | Edges referencing entity-map keys. |
  | <Field name="relations[].source" type="string" required /> | Entity-map key of the source entity. |
  | <Field name="relations[].target" type="string" required /> | Entity-map key of the target entity. |
  | <Field name="relations[].predicate" type="string" required /> | Relationship label, any plain string. At most 256 chars. |
  | <Field name="relations[].context" type="string" /> | Optional sentence supporting the edge. At most 2,000 chars. |
  | <Field name="relations[].temporal_details" type="string" /> | Optional timing info (e.g. "since 2021", "in Q3"). |

  **Caps per graph:** at most 5,000 entities, 10,000 relations, and 500 relations per entity; over-cap returns `400`. Graphs survive re-ingest: a re-upload or connector re-sync re-applies the stored graph.
