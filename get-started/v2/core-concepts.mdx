Five ideas cover the product. Later pages are the details.

## Knowledge

Knowledge is shared context in a database: PDFs, DOCX, Markdown, CSVs, emails, Slack threads, Notion pages, and other app content.

HydraDB parses each source and links related pieces in a [context graph](/essentials/v2/context-graphs). Vector search finds what is similar to the question. The graph finds what is connected to it, such as material that shares a project or a person. A query uses both.

Query it with [`POST /query`](/api-reference/v2/endpoint/query) and `type: "knowledge"`.

Details: [Knowledge](/essentials/v2/knowledge).

## Memories

A memory is context about one user: a preference, a past conversation, or a fact HydraDB inferred from something they did.

Two people can ask "Project Acme changelog" and need different pages. One has been following backend design decisions. The other reads release notes. Memories are how you store that difference, so retrieval fits the person asking and not only the query. You do not set them once at onboarding. They build up with every interaction.

`infer` controls what gets stored:

- `infer: false` (the default): HydraDB stores exactly the text you send. Use it for facts you already captured.
- `infer: true`: you send raw signal, such as interaction events, UI actions, or dialogue. HydraDB extracts and stores the preference or fact inside it.

Query memories with `type: "memory"`. Use `type: "all"` when one answer should use shared documents and that user's memories. Both come back in one ranked list. `type: "all"` reads both stores from the same collection, so if the shared documents live in a different collection, list both in `collections`. See [How to Use API Results](/essentials/v2/api-results).

Details: [Memories](/essentials/v2/memories).

## How knowledge and memories differ

- Knowledge is shared across users. A memory belongs to one user. Both are stored in a `collection`, and a query reads only the collections it names (the default collection if it names none).
- You replace or delete a knowledge source when it changes. You add memories as the user interacts.
- Query knowledge with `type: "knowledge"` and memories with `type: "memory"`.
- Only memories take `infer`. Knowledge is parsed and chunked.

## Query

[`POST /query`](/api-reference/v2/endpoint/query) is how agents read. One call can filter on metadata, match by meaning and by keyword, and walk the [context graph](/essentials/v2/context-graphs).

- `type` chooses `knowledge`, `memory`, or `all`.
- `query_by` chooses `hybrid` (meaning plus keywords) or `text` (keywords only).
- `mode` chooses `fast` (one pass), `thinking` (expands the query and reranks), or `auto` (the default, which picks one per query).
- `graph_context` returns the graph relations behind the results. It is on by default. Sending `false` takes effect only in `fast` mode.

Details: [Query](/essentials/v2/query).

## Databases and collections

A **database** is an isolated workspace. One database cannot read another database's data. A customer organization is usually one database.

A **collection** is a partition inside a database: a user, a team, or a project.

- **B2B:** one database per customer. Collections are their teams or users.
- **B2C:** one database for your app. Each person is a collection.
- **Internal tools:** one database per company or environment. Collections are departments or projects.

In requests, send `database` and `collection`. Older clients send `tenant_id` and `sub_tenant_id`. Those names still work as deprecated aliases.

To restrict individual documents to certain people inside one database, use [Access Control](/essentials/v2/access-control).

Details: [Multi-tenant](/essentials/v2/multi-tenant).

## Metadata

Use metadata when a result must match a hard rule, such as "only Engineering docs" or "only approved policies". The filter runs before ranking.

Two fields:

- `metadata`: fields you declare in the database schema. Filter them with `metadata_filters`. Plan these before you ingest. You can add fields later, but you cannot rename, retype, or delete one once it exists.
- `additional_metadata`: free-form fields on a single document. Use them for extra context your agent can read, or for fields that are not part of the schema.

At ingest, both go on each item of `document_metadata` (one item per file) or on each memory item:

```json
{
  "metadata": { "compliance_framework": "SOC2", "region": "us" },
  "additional_metadata": {
    "owner": "sarah.chen@acme.com",
    "status": "approved"
  }
}
```

At query time:

```json
{
  "query": "latest pricing strategy",
  "metadata_filters": { "compliance_framework": "SOC2" }
}
```
