HydraDB requests can look nearly identical while producing meaningfully different behavior. Each decision card below changes one field, asks you to predict the result, and then shows the control and variant together.

<Info>
  These cards complement the canonical [Knowledge](/essentials/v2/knowledge), [Memories](/essentials/v2/memories), [Query](/essentials/v2/query), and [Ingest Context](/api-reference/v2/endpoint/ingest-context) documentation. Use those pages for the complete parameter reference.
</Info>

## Choose the store you query

Use `type` to choose whether the same query searches per-user Memories or shared Knowledge.

<Accordion title="Predict before you reveal: what changes when type changes?">
  `type: "memory"` searches context scoped to a user or collection. `type: "knowledge"` searches shared documents and app content. The query text and retrieval method can remain identical, but the result comes from a different store.

## Choose whether HydraDB infers a memory

Use `infer` to decide whether HydraDB should extract a useful memory from raw signal or store the input literally.

<Accordion title="Predict before you reveal: what changes when infer changes?">
  `infer: true` asks HydraDB to extract the underlying preference, trait, or fact. `infer: false` stores and indexes the text as written. Keep the raw input identical so the extraction step is the only behavioral variable.

### Requests

For a clean probe, use a fresh throwaway database for the pair. Inspect the control after it becomes queryable, then submit the variant with the same ID. Upsert is enabled by default, so the variant replaces the control while `infer` remains the only changed request field.

<Columns cols={2}>
  <Card title="Control: Extract meaning">

  **Changed field:** `infer: true`

  ```bash
  curl -X POST 'https://api.hydradb.com/context/ingest' \
    -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
    -H "API-Version: 2" \
    -F "type=memory" \
    -F "database=contrastive_docs_demo" \
    -F "collection=reader_001" \
    -F 'memories=[{
      "id": "preference_probe",
      "text": "The reader switched to dark mode, kept it for a month, briefly tried light mode, then returned to dark mode.",
      "infer": true
    }]'
  ```

  </Card>
  <Card title="Variant: Store literally">

  **Changed field:** `infer: false`

  ```bash
  curl -X POST 'https://api.hydradb.com/context/ingest' \
    -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
    -H "API-Version: 2" \
    -F "type=memory" \
    -F "database=contrastive_docs_demo" \
    -F "collection=reader_001" \
    -F 'memories=[{
      "id": "preference_probe",
      "text": "The reader switched to dark mode, kept it for a month, briefly tried light mode, then returned to dark mode.",
      "infer": false
    }]'
  ```

  </Card>

### Inspect each stored result

After the control becomes queryable, inspect it before submitting the variant. Then run the same request again after the variant becomes queryable. [`GET /context/inspect`](/api-reference/v2/endpoint/fetch-content) returns the `content` and `inferred_content` fields compared below.

```bash
curl -G 'https://api.hydradb.com/context/inspect' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "id=preference_probe" \
  --data-urlencode "database=contrastive_docs_demo" \
  --data-urlencode "collection=reader_001" \
  --data-urlencode "mode=content"
```

### Responses

<Info>
  Verified against HydraDB v2 on July 21, 2026. In all three matched runs, `infer: true` populated `inferred_content` and `infer: false` left it `null`. The normalized wording varied slightly; the extraction-versus-literal distinction did not.
</Info>

**First meaningful difference:** compare `inferred_content` after each item becomes queryable. The inferred item contains the extracted preference; the literal item preserves the raw event description and leaves `inferred_content` empty.

**Selection rule:** use `infer: true` for raw, noisy, or indirect signals. Use `infer: false` when your application already has the exact memory it wants to store.

```yaml Agent decision record

use_variant_when: the input is already the exact memory to retain
```

## Read the evidence safely

- Treat result ordering and absolute relevance scores as run-specific noise.
- Treat inferred wording as nondeterministic; compare whether meaning was extracted, not the exact sentence.
- Compare only the field or content difference named by the card.
- `type` selects which store is searched; isolation still depends on database, collection, and authorization.
- Wait until ingestion reaches a queryable status before comparing results.
