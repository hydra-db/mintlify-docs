## Overview - Two layers

| Layer | What it is | Use for |
| --- | --- | --- |
| `metadata` | Declared in the schema and typed, so filters on it are fast. | Fields you filter on often, like department or status. |
| `additional_metadata` | Free-form with no schema. Filters can be slower, since they may be checked after retrieval. | Display values, citations, and external IDs. |

## Schema fields

| Option | Rule |
| --- | --- |
| `name` | Must be unique (case-insensitive). |
| `data_type` | Defaults to `VARCHAR`. `ARRAY` isn't supported. |
| `max_length` | Defaults to 1024, up to 65535. |
| Dense/sparse flags | Make a `VARCHAR` field searchable through `query`, not through filters. |

A database allows up to 32 fields and 6 embedding flags. Values must match their declared type, and unknown keys are rejected.

## Lifecycle & how filters run

Create the database with a schema and wait until it's ready. Ingest your sources with metadata values, wait for them to reach `completed`, then query with `metadata_filters`.

When a query runs, HydraDB:

- Finds the sources that match the filter, retrieves only from those, then rechecks every chunk, including graph paths.
- Returns an empty result if nothing matches. It never falls back to a wider search.

## Operators

| Operator | Matches | Types |
| --- | --- | --- |
| `equals` | The exact whole value | Any |
| `contains` | One member of a multi-value field | `VARCHAR` only |
| `contains_any` | Any of the listed values (OR) | `VARCHAR` only |

| Behavior | Rule |
| --- | --- |
| Multiple keys | All must match (AND). |
| Null, range, fuzzy | Not supported. |
| OR across keys | Run separate queries and combine the results. |
| `additional_metadata` | Takes bare values or arrays only, not operators. |

## Multi-value fields

- Store the values as one comma-joined `VARCHAR` and filter for a member with `contains`.
- Set `max_length` large enough for the whole string up front, since it can't be raised later.

## Errors

- A wrong type, multiple operators in one object, or a null value returns `400`.
- A misspelled operator, or an operator inside `additional_metadata`, doesn't error but silently returns nothing.
- Bare filters without an operator still work but are deprecated.

## Size caps

Caps are measured in bytes of compact JSON, and keys count toward the total.

| Limit | Cap |
| --- | --- |
| `metadata` (stored) | 16 KiB |
| `additional_metadata` (stored) | 1 KiB |
| Values per filter list | 500 |
| Whole `metadata_filters` object | 64 KiB |

- Going over a cap fails the request with `400`.
- If you need more than 500 values, add a grouping field and filter on that instead. Long text belongs in the source body.

## Schema changes

- Schemas are add-only: you can't delete, retype, or rename a field.
- Fields added later can't be made searchable.
- Filtering on an undeclared key matches nothing, except for keys written by connectors.

## Edit in place (`PATCH /context/{id}/metadata`)

- Send `database_metadata` and/or `additional_metadata`. `collection` is required.
- Sent keys are merged into existing metadata, while `acl` replaces the stored list. Searchable fields sync immediately and can't be set to null.
- To remove a connector source's own ACL and use its connector resource permissions again, send `acl_inherit: true` without `acl`. This can widen access. See [Restore resource permissions](/essentials/v2/connectors#restore-resource-permissions).
- To replace the content as well, re-ingest with `upsert: true`.

## List (`/context/list`)

Browse sources without ranking, filtering by `metadata`, `additional_metadata`, or source fields.

## Best practice

- Declare `status` and `language` from the start.
- Use filters to isolate data within a collection, and separate collections only when data must never be searched together.
- Add filters one at a time and check counts as you go.
