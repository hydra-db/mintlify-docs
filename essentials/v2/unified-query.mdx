---
title: "Query on a unified database"
description: "How POST /query behaves without a corpus selector, and what the additive graph and forceful_relations fields contain."
---

On a unified database, `POST /query` needs no `type`: one call returns the documents you uploaded and the conversations you saved, ranked together. The endpoint, the request fields and the response envelope are the v2 ones; two fields are added to the response.

For the split-database `type` parameter, see [Query](/essentials/v2/query).

---

## 1. The minimum request

```json
POST /query
{
  "database": "acme",
  "collection": "team-1",
  "query": "what does the team prefer for billing?"
}
```

Everything else has a default: hybrid retrieval, ten results, graph context on, declared relations followed. Sending `type: "unified"` is equivalent to omitting it; `type: "all"` is accepted too.

---

## 2. What "no type" actually does

| Database | Behaviour |
| --- | --- |
| unified | both kinds of item share one physical store, so one retrieval pass covers everything |
| split | absent `type` still means `knowledge`; send `type: "all"` to search both corpora, merged |

To narrow a unified database to one kind of item, filter on `is_memory`, which HydraDB sets on every item: `true` for a conversation, `false` for plain text. You never send it at ingest.

```json
{
  "database": "acme",
  "query": "what does the team prefer?",
  "attributes": { "is_memory": true }
}
```

`is_memory` is only filterable on a unified database. On a split database the two kinds live in separate stores and the column is absent from rows written before this change, so filtering on it there is rejected; select the corpus with `type` instead.

## 3. The response

The body is the familiar `{ "success": true, "data": ... }` envelope. `data` keeps every existing field and adds `graph` and `forceful_relations`:

```json
{
  "success": true,
  "data": {
    "chunks": [
      {
        "chunk_uuid": "doc-001_chunk_0",
        "id": "doc-001",
        "chunk_content": "Acme runs billing on the Ledger service...",
        "source_title": "architecture.md",
        "relevancy_score": 1.09,
        "metadata": { "department": "eng" },
        "additional_metadata": { "author": "sam@acme.com" },
        "extra_context_ids": ["doc-001_chunk_1"]
      }
    ],
    "sources": [ { "id": "doc-001", "title": "architecture.md", "timestamp": "2026-08-16T10:00:00Z" } ],
    "graph": {
      "paths": [
        {
          "triplets": [
            { "source": { "name": "Ledger" }, "relation": { "canonical_predicate": "OWNED_BY" }, "target": { "name": "Payments team" } }
          ],
          "relevancy_score": 0.82,
          "combined_context": "Ledger is owned by the Payments team.",
          "chunk_ids": ["doc-001_chunk_0"]
        }
      ]
    },
    "forceful_relations": {
      "declared": [
        { "via": { "from": "doc-001", "to": "doc-007" }, "chunk": { "chunk_uuid": "doc-007_chunk_0", "id": "doc-007" } }
      ],
      "inferred": []
    },
    "graph_context": { "query_paths": [], "chunk_relations": [], "chunk_id_to_group_ids": {} },
    "additional_context": {}
  }
}
```

### Reading `graph.paths[]`

One list, ordered: paths that answered the query come first, then paths reached by expanding out from a retrieved chunk. Each path carries its own `chunk_ids`, naming the retrieved chunks it is evidence for, so the join you used to do between `paths[].group_id` and `chunk_id_to_group_ids` is already done. A path with an empty `chunk_ids` answered the query directly rather than being anchored to a chunk.

### Reading `forceful_relations`

`declared` holds relations you asserted at ingest, each with the `via` edge that produced it. `additional_context` returned the same chunks as a flat map keyed by chunk uuid, which showed you the related chunk but not what it was related *to*. `inferred` is reserved for relationships HydraDB derives itself; those currently come back in `graph.paths[]`, so the list is present and empty.

### The deprecated fields

`graph_context` and `additional_context` are still returned on every database so existing readers keep working. They are marked deprecated in the OpenAPI document and the SDKs; new code should read `graph.paths[]` and `forceful_relations`.

## 4. Filtering on attributes

`attributes` accepts a MongoDB-like operator query over the attributes you ingested:

```json
{
  "database": "acme",
  "query": "billing incidents",
  "attributes": {
    "department": "eng",
    "priority": { "$gte": 3 },
    "$or": [
      { "status": { "$in": ["open", "triaged"] } },
      { "escalated": true }
    ]
  }
}
```

Supported: `$eq $ne $gt $gte $lt $lte` for comparison, `$in $nin` for sets, `$exists` for presence, and `$and $or $not` for composition. A bare value is an implicit `$eq`. Values are matched against the type you declared for the field, so a filter that cannot be typed is rejected rather than silently ignored.

`attributes` compiles to a filter applied inside the vector search, which only works on values stored as columns: the database attributes you declare in your schema, plus `is_memory` on a unified database. Per-item `custom_attributes` are not columns, so the operator language rejects them with a `400` naming the limitation. Filter those with `metadata_filters`, which supports equality matching and reaches document metadata through a nested `additional_metadata` object. The two compose: `attributes` narrows on columns, `metadata_filters` narrows on everything else, and an item has to satisfy both.
