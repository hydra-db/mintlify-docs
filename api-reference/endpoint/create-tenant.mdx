## Creating Additional Sub-Tenants

**No Separate API Required**: HydraDB doesn't require a separate API call to create additional sub-tenants. Sub-tenants are created automatically when you first use a new `sub_tenant_id` that doesn't exist yet.

### How Sub-Tenant Creation Works

1. **Automatic Creation**: When you upload content with a `sub_tenant_id` that doesn't exist, HydraDB automatically creates that sub-tenant
2. **First Upload Triggers Creation**: The first API call with a new `sub_tenant_id` will create the sub-tenant and then process your content
3. **Immediate Availability**: Once created, the sub-tenant is immediately available for all subsequent operations

### Sub-Tenant ID Best Practices

**For B2C Applications (Individual Users):**

```javascript
// Use user IDs as sub-tenant IDs for personal workspaces
sub_tenant_id: "user_12345"
sub_tenant_id: "user_67890"
```

**For B2B Applications (Departments/Teams):**

```javascript
// Use descriptive department or team names
sub_tenant_id: "engineering"
sub_tenant_id: "sales"
sub_tenant_id: "hr"
sub_tenant_id: "marketing"
```

**For Project-Based Organizations:**

```javascript
// Use project identifiers
sub_tenant_id: "project_alpha"
sub_tenant_id: "client_acme_corp"
```

<Info>
  **Naming Convention**: Use consistent prefixes like `user_`, `dept_`, or `project_` to make the purpose of each sub-tenant clear. Avoid special characters and keep names descriptive but concise.
</Info>

<Warning>
  **Important**: Tenant metadata field names are **immutable** once set during tenant creation. Choose your field names carefully as they cannot be modified later. Document metadata remains fully flexible and can be set per document during upload.
</Warning>

## Reserved Keywords

The following keywords are **reserved** and cannot be used as `name` values in `tenant_metadata_schema`:

- `id`
- `source_title`
- `source_url`
- `source_type`
- `source_collection`
- `source_owner`
- `source_collaborator`
- `source_upload_time`
- `source_last_updated_time`
- `chunk_id`
- `chunk_uuid`
- `chunk_content`
- `document_metadata`
- `base_metadata`
- `layout`
- `description`

These keywords are used internally by HydraDB for document processing and search functionality. Using any of these reserved keywords as tenant metadata field names will result in an error during tenant creation.

## Metadata Schema Structure

Each schema object in the `tenant_metadata_schema` array should specify:

- **name**: The metadata field name (immutable once set)
- **data_type**: Milvus data type — use `VARCHAR` for text fields that need embeddings (default: `VARCHAR`)
- **max_length**: Maximum length for `VARCHAR` fields (default: `1024`)
- **enable_match**: Enable `TEXT_MATCH` filtering on this field (default: `false`)
- **enable_dense_embedding**: Generate dense embeddings for semantic similarity search (default: `false`)
- **enable_sparse_embedding**: Generate sparse embeddings (BM25) for keyword search (default: `false`)
- **nullable**: Whether the field can be null (default: `true`)

## Supported Data Types

The `data_type` field accepts the following Milvus data types:

| Type          | Description                | Use Cases                                          |
| ------------- | -------------------------- | -------------------------------------------------- |
| **VARCHAR**   | Variable-length text       | Categorical data, identifiers, labels, descriptions. Required for fields with embeddings enabled. |
| **BOOL**      | Boolean values             | Binary flags, status indicators                    |
| **INT32**     | 32-bit integer             | Counts, priorities, versions                       |
| **INT64**     | 64-bit integer             | Large numeric identifiers, timestamps              |
| **FLOAT**     | Single-precision float     | Scores, percentages                                |
| **DOUBLE**    | Double-precision float     | High-precision numeric values                      |
| **JSON**      | JSON object                | Structured nested data                             |
| **ARRAY**     | Array of values            | Multi-value attributes, tags, categories           |

<Note>
  Fields with `enable_dense_embedding` or `enable_sparse_embedding` set to `true` must use `VARCHAR` as the `data_type`.
</Note>

## Search Capabilities

Understanding the search capability flags is crucial for optimal metadata design:

**1. Semantic Search (`enable_dense_embedding`)**

- **Purpose**: Fields that can be used in **semantic search queries** and **QnA operations**
- **Behavior**: A dense vector embedding field is created for AI-powered similarity search
- **Use When**: You want users to find documents by asking natural language questions about these fields
- **Example**: `"Which documents are from the Engineering department?"`

```json
{
  "name": "department",
  "data_type": "VARCHAR",
  "max_length": 256,
  "enable_dense_embedding": true,
  "enable_sparse_embedding": true
}
```

**2. Exact Match Filtering (`enable_match`)**

- **Purpose**: Fields that can be used for **precise filtering** and **exact matching**
- **Behavior**: Content is indexed for fast exact-match filtering operations
- **Use When**: You want to narrow down results with precise criteria
- **Example**: `department = "Engineering" AND status = "active"`

```json
{
  "name": "data_classification",
  "data_type": "VARCHAR",
  "max_length": 256,
  "enable_match": true
}
```

**3. Keyword Search (`enable_sparse_embedding`)**

- **Purpose**: Fields that can be used for **BM25 keyword search**
- **Behavior**: A sparse vector field is created for traditional keyword matching
- **Use When**: You want both semantic and keyword-based search on the same field

```json
{
  "name": "compliance_framework",
  "data_type": "VARCHAR",
  "max_length": 256,
  "enable_dense_embedding": true,
  "enable_sparse_embedding": true,
  "enable_match": true
}
```

## Metadata Best Practices

**1. Naming Conventions**

- **Use snake_case**: `business_unit` instead of `businessUnit`
- **Be descriptive**: `data_classification_level` instead of `classification`
- **Use consistent prefixes**: `compliance_*`, `security_*`, `business_*`

**2. Search Capability Strategy**

- **`enable_dense_embedding`**: Enable on fields users will ask natural language questions about
- **`enable_sparse_embedding`**: Enable on fields where keyword matching is important
- **`enable_match`**: Enable on fields used for precise exact-match filtering
- **Combine all three**: For fields used in both semantic search and filtering
- **`enable_match` only**: For sensitive data or exact-match-only requirements

**3. Performance Considerations**

- **Limit total fields**: Keep metadata schema focused and purposeful
- **Increase `max_length`** for longer text content (e.g., `4096` for descriptions)
- **Consider query patterns**: Design for your most common use cases
- **Embedding fields add storage**: Each `enable_dense_embedding` field creates a vector index

### Query Examples

With the metadata schema defined above, users can perform sophisticated queries:

#### Semantic Search (`enable_dense_embedding` fields)

```

"Find all engineering documents about security compliance"
```

- Searches through `department` (dense embedding enabled)
- Searches through `compliance_framework` (dense embedding enabled)
- Searches through document content and titles

#### Precise Filtering (`enable_match` fields)

```

department = "Engineering" AND data_classification = "internal"
```

- Exact match on `department` (match enabled)
- Exact match on `data_classification` (match enabled)

#### Combined Queries

```

"Show me all SOC2 compliance documents from the Product business unit"
```

- Semantic search for "SOC2 compliance" (dense embedding fields)
- Precise filter: `business_unit = "Product"` (match enabled)

#### 2. Engineering Documentation

**Schema**: Product line, team, component
**Query**: "Show me all API documentation from the backend team"
**Filter**: `product_line = "API" AND team = "backend"`

#### 3. HR Document Management

**Schema**: Department, employee type, status
**Query**: "Find all active full-time employees in the Engineering department"
**Filter**: `department = "Engineering" AND employee_type = "full_time" AND status = "active"`

### Metadata Inheritance

All documents in your tenant automatically inherit the tenant metadata schema you define. This means:

1. **Consistency**: Every document will have the same tenant metadata structure
2. **Compliance**: Organizational policies are enforced across all documents
3. **Queryability**: You can always filter and search by tenant-level attributes
4. **Scalability**: New documents automatically follow your established schema

### Migration and Updates

<Warning>
  **Schema Immutability**: Once you create a tenant with a metadata schema, the field names cannot be changed. However, you can:

  - Add new fields to document metadata (fully flexible)
  - Update values for existing tenant metadata fields
  - Create new sub-tenants with different schemas if needed
</Warning>

> **Note:**
>
> - The `tenant_metadata_schema` field in the request body is optional but recommended for enterprise setups. It defines immutable tenant-level metadata fields that will apply to all documents in this tenant.
> - For more detailed information about metadata usage, filtering, and querying, see our [Metadata documentation](/essentials/metadata).

```json

  "tenant_id": "B1SlKQ2j2l1aWYLa"
```

### Functionality

- Accepts an optional `tenant_id` via query
- Generates a new `tenant_id` if none is provided
- Creates and persists the tenant
- Returns the final `tenant_id` and a confirmation message

> Note: If your use case is to directly upload and search embeddings (without document/text ingestion), use the dedicated embeddings-tenant endpoint instead: `/embeddings/create_tenant`. This sets `sub_tenant_id = tenant_id` and prepares the tenant for embeddings-first workloads.
