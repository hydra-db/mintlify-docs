## Section 0: Before You Write Any Code

> You have data. HydraDB has two stores: Knowledge and Memory.
> Every piece of data you own belongs in exactly one of them.
> Get this wrong and your queries return nothing.
> This section tells you which is which.

| Data you have | Store | Why | `type` at query |
|---|---|---|---|
| Slack messages (org-wide) | Knowledge | Shared across all users | `"knowledge"` |
| Notion pages / wikis | Knowledge | Shared reference docs | `"knowledge"` |
| PDF files, runbooks, policies | Knowledge | Shared, versioned content | `"knowledge"` |
| User's chat history with your AI | Memory + `infer: true` | Per-user, behavioral signal | `"memory"` |
| User's stated preference ("I like bullet points") | Memory + `infer: false` | Already structured fact | `"memory"` |
| CRM contact notes per user | Memory | User-scoped context | `"memory"` |
| You need both for one query | Both | Personalized + grounded | `"all"` |

<Note>
**The one question:** "Should every user in this database be able to retrieve this?"
Yes → Knowledge. No → Memory.
</Note>

## Section 1: Set Up Your Database

One database = one organization. One collection = one user.

```
Database: acme_corp
├── Knowledge store (shared across all users)
│   ├── Slack export
│   ├── Notion pages
│   └── Policy PDFs
└── Collections (per-user Memory)
    ├── collection: user_alice → her preferences, her chat history
    ├── collection: user_bob  → his preferences, his chat history
    └── collection: user_carol → ...
```

<Note>
In API requests, a database is set with the **`database`** field (formerly `tenant_id`) and a collection with the **`collection`** field (formerly `sub_tenant_id`). The old names still work as deprecated aliases.
</Note>

Create the database and wait until it's ready for ingestion:

<CodeGroup>
```python Python SDK
import os
import time
from hydra_db import HydraDB

client = HydraDB(token=os.environ["HYDRA_DB_API_KEY"])

try:
    client.databases.create(database="acme_corp")
except Exception as e:
    if "already exists" not in str(e).lower():
        raise

while True:
    infra = client.databases.status(database="acme_corp").data.infra
    if infra.ready_for_ingestion:
        break
    time.sleep(5)
```
```typescript TypeScript SDK

  const { data } = await client.databases.status({ database: "acme_corp" });
```

## Section 2: Ingest Your Knowledge (Shared Data)

### 2a: Files (PDFs, DOCX, Markdown)

Use Path A — binary file upload — when HydraDB should parse the document for you.

The `id` in `document_metadata` is your upsert key. When you update a policy PDF, re-ingest it with the same `id` and HydraDB replaces the old chunks without duplicating them.

<CodeGroup>
```python Python SDK
import json

with open("policy.pdf", "rb") as f:
    result = client.context.ingest(
        type="knowledge",
        database="acme_corp",
        documents=[("policy.pdf", f, "application/pdf")],
        document_metadata=json.dumps([
            {
                "id": "policy_refund_v3",
                "metadata": {"document_type": "policy", "status": "approved"},
                "additional_metadata": {"owner": "legal@acme.com"},
            }
        ]),
    )

ids = [r.id for r in result.data.results]
```

### 2b: App Sources (Slack, Notion, Gmail)

App sources use Path B — pass pre-extracted records via the `app_knowledge` parameter. You supply app-native fields and HydraDB preserves app structure at query time.

| App | `provider` | `kind` | Primary content field |
|---|---|---|---|
| Slack | `"slack"` | `"message"` | `fields.body` |
| Notion | `"notion"` | `"knowledge_base"` | `fields.body` |
| Gmail | `"gmail"` | `"email"` | `fields.body` |
| Jira | `"jira"` | `"ticket"` | `fields.description` |
| Generic / custom | your choice | `"custom"` | `fields.data` |

<Warning>
`kind` selects the app parser. Wrong `kind` = content parsed incorrectly.
Always match `kind` to what the record actually is.
</Warning>

Ingest Slack and Notion in the same call using `app_knowledge`:

### 2c: Wait for Indexing

Poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) until each item reaches a terminal state.

Status stages: `queued → processing → graph_creation → completed`

<Note>
Items at `graph_creation` are already queryable. Wait for `completed` only if you need full graph traversal.
</Note>

<CodeGroup>
```python Python SDK
import time

terminal = {"completed", "graph_creation", "errored"}

while True:
    statuses = client.context.status(
        database="acme_corp",
        ids=ids,
    ).data.statuses
    if all(s.indexing_status in terminal for s in statuses):
        break
    time.sleep(5)

failed = [s for s in statuses if s.indexing_status == "errored"]
if failed:
    raise RuntimeError(f"Indexing failed for: {[s.id for s in failed]}")
```
```typescript TypeScript SDK
const terminal = new Set(["completed", "graph_creation", "errored"]);

let statuses: { id: string; indexingStatus: string }[] = [];
while (true) {
  const { data } = await client.context.status({ database: "acme_corp", ids });
  statuses = data.statuses;
  if (statuses.every((s) => terminal.has(s.indexingStatus))) break;
  await new Promise((r) => setTimeout(r, 5_000));
}

const failed = statuses.filter((s) => s.indexingStatus === "errored");
if (failed.length) throw new Error(`Indexing failed for: ${failed.map((s) => s.id)}`);
```
```bash cURL
while true; do
  RESP=$(curl -sf -G 'https://api.hydradb.com/context/status' \
    -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
    -H "API-Version: 2" \
    --data-urlencode "database=acme_corp" \
    --data-urlencode "ids=slack_pricing_2026_0520" \
    --data-urlencode "ids=notion_onboarding_wiki") || {
    echo "ERROR: status request failed" >&2; exit 1
  }
  STATUSES=$(echo "$RESP" | jq -r '.data.statuses[].indexing_status')
  if ! echo "$STATUSES" | grep -qvE '^(completed|graph_creation|errored)$'; then break; fi
  sleep 5
done

if echo "$STATUSES" | grep -q 'errored'; then
  echo "ERROR: one or more sources failed indexing" >&2; exit 1
fi
```
</CodeGroup>

## Section 3: Ingest User Memories (Per-User Data)

### 3a: The `infer` Decision

`infer` is the most important flag on memory ingestion. It controls whether HydraDB extracts a preference from raw signal, or stores exactly what you send.

```
Do you have raw, unstructured signal?
(conversation logs, UI events, feedback)
        │
       YES → infer: true  → HydraDB extracts the preference
        │
        NO
        │
Do you already have a structured fact?
("User is on Pro plan", "prefers dark mode")
        │
       YES → infer: false → HydraDB stores exactly what you send
```

Same user, two paths:

<CodeGroup>
```python Python SDK
import json

# Path 1: raw chat log → infer: true
result1 = client.context.ingest(
    type="memory",
    database="acme_corp",
    collection="user_alice",
    memories=json.dumps([
        {
            "user_assistant_pairs": [
                {"user": "Can you make that shorter?", "assistant": "Sure, here's a shorter version..."},
                {"user": "Perfect, I like it that way.", "assistant": "Noted."},
            ],
            "infer": True,
            "custom_instructions": "Focus on communication style preferences.",
            "user_name": "Alice",
        }
    ]),
)
memory_ids = [r.id for r in result1.data.results]

# Path 2: pre-extracted fact → infer: false
result2 = client.context.ingest(
    type="memory",
    database="acme_corp",
    collection="user_alice",
    memories=json.dumps([
        {
            "id": "alice_plan_tier",
            "text": "User is on the Pro plan. Renewal date: 2027-01-15.",
            "infer": False,
        }
    ]),
)
memory_ids += [r.id for r in result2.data.results]

# Wait for memory indexing before querying
terminal = {"completed", "graph_creation", "errored"}
while True:
    statuses = client.context.status(
        database="acme_corp",
        ids=memory_ids,
    ).data.statuses
    if all(s.indexing_status in terminal for s in statuses):
        break
    time.sleep(5)

failed = [s for s in statuses if s.indexing_status == "errored"]
if failed:
    raise RuntimeError(f"Memory indexing failed for: {[s.id for s in failed]}")
```
```typescript TypeScript SDK

  memStatuses = data.statuses;

  await new Promise((r) => setTimeout(r, 5_000));

if (memFailed.length) throw new Error(`Memory indexing failed for: ${memFailed.map((s) => s.id)}`);
```

```bash cURL
    -H "API-Version: 2" \

    $(echo "$MEMORY_IDS" | xargs -I{} echo "--data-urlencode ids={}")) || {

done
if echo "$MEM_STATUSES" | grep -q 'errored'; then
  echo "ERROR: one or more memory sources failed indexing" >&2; exit 1
fi
```

<Warning>
Always use the user's ID as `collection`. If you skip it, memories land in the default collection and can surface for the wrong user. `collection` is the new name for `sub_tenant_id` — both work in the API, but `collection` is preferred in v2.
</Warning>

For a deeper reference on `infer`, see [Infer Guide](/essentials/v2/infer-guide).

## Section 4: Querying — One Endpoint, Three Modes

<Warning>
**Poll before querying — both stores.**

`type: "all"` merges Knowledge and Memory at query time. If either store hasn't reached at least `graph_creation`, those chunks will be missing from your results with no error returned.

Run the status loop from Section 2c for your Knowledge sources **and** your Memory sources before issuing any query. Querying immediately after `ingest` is the most common cause of empty results.
</Warning>

The four endpoints form one loop:

```
POST /context/ingest   ← write data in
GET  /context/status   ← wait for indexing
POST /query            ← read data out  ← THIS is where your agent lives
```

Pick the query mode based on what you need:

| You want… | Use `type:` | When |
|---|---|---|
| Only shared docs | `"knowledge"` | Lookup, RAG, search |
| Only this user's memory | `"memory"` | Personalization, preferences |
| Both merged in one call | `"all"` | Production agents (use this by default) |

### 4a: `type: "all"` — The Production Pattern

`type: "all"` + `collection` = personalized answers grounded in shared docs. HydraDB runs both stores in parallel and merges results into one ranked list.

<CodeGroup>
```python Python SDK
result = client.query(
    database="acme_corp",
    collection="user_alice",    # scopes memories to Alice
    query="What is our refund policy?",
    type="all",                 # hits Knowledge + Memory together
    query_by="hybrid",
    mode="thinking",
    max_results=10,
)
```

<Warning>
**Knowledge is database-wide. Memory is collection-scoped.**

When you ingest Knowledge (PDFs, Slack, Notion), do NOT pass a
`collection` — it makes that knowledge available to all users.

When you query with `type="all"` and `collection="user_alice"`,
HydraDB returns:
- Memory chunks scoped to `user_alice` ✓
- Knowledge chunks available to the whole database ✓

If your Knowledge chunks are not surfacing in `type="all"` results,
check that you ingested them WITHOUT a `collection` parameter.
Knowledge ingested into a specific collection is only visible
to queries scoped to that same collection.

To verify: run the same query with `type="knowledge"` and no
`collection`. If chunks appear there but not in `type="all"`,
this is the cause.
</Warning>

<Note>
Always pass `collection` when using `type: "all"` or `type: "memory"`.
Without it, the memory store queries the default collection, not your user's.
</Note>

### 4b: When to Query Separately

If you need to label Knowledge and Memory results differently in your prompt, run two queries in parallel:

<CodeGroup>
```python Python SDK
import asyncio
from hydra_db import AsyncHydraDB
from hydra_db.helpers import build_string

hydra = AsyncHydraDB(token=os.environ["HYDRA_DB_API_KEY"])

knowledge_result, memory_result = await asyncio.gather(
    hydra.query(
        database="acme_corp",
        query="refund policy",
        type="knowledge",
        query_by="hybrid",
        mode="thinking",
    ),
    hydra.query(
        database="acme_corp",
        collection="user_alice",
        query="communication style preferences",
        type="memory",
        query_by="hybrid",
    ),
)

prompt_context = (
    f"User preferences:\n{build_string(memory_result)}\n\n"
    f"Relevant company knowledge:\n{build_string(knowledge_result)}"
)
```

```bash cURL
curl -sf -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{"database":"acme_corp","query":"refund policy","type":"knowledge","query_by":"hybrid","mode":"thinking"}' \
  -o "$KNOWLEDGE_FILE" &

curl -sf -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{"database":"acme_corp","collection":"user_alice","query":"communication style preferences","type":"memory","query_by":"hybrid"}' \
  -o "$MEMORY_FILE" &

wait

KNOWLEDGE_CONTEXT=$(jq -r '[.data.chunks[].chunk_content] | join("\n---\n")' "$KNOWLEDGE_FILE")
MEMORY_CONTEXT=$(jq -r '[.data.chunks[].chunk_content] | join("\n---\n")' "$MEMORY_FILE")
rm -f "$KNOWLEDGE_FILE" "$MEMORY_FILE"
```

Use `build_string` / `buildString` from the SDK to convert the query response into a clean string for your LLM. It strips IDs and metadata noise, preserves chunk order, and includes graph context.

## Section 6: Common Mistakes

| Mistake | What goes wrong | Fix |
|---|---|---|
| Storing shared docs as Memories | They won't surface on `type: "knowledge"` queries | Use Knowledge ingestion for any content all users should see |
| Storing per-user data as Knowledge | Data bleeds across users | Use Memory with `collection` set to the user's ID |
| Missing `collection` for memory queries | Default collection is queried; wrong user's memories surface | Always pass `collection` matching ingestion `collection` |
| Querying before indexing completes | Empty results | Poll `/context/status` until `graph_creation` or `completed` |
| Using `infer: true` for structured facts | HydraDB re-derives the memory, phrasing may change | Use `infer: false` for facts you've already extracted |
| Using `infer: false` for raw conversation logs | Noise is stored verbatim, not as insight | Use `infer: true` for raw signal |
| Setting `custom_instructions` with `infer: false` | Instructions are silently ignored | Only `custom_instructions` + `infer: true` does anything |
| Using `query_forceful_relations` with `mode: "fast"` | Flag is rejected with HTTP 422 | Set `mode: "thinking"` or remove the flag |
| Pointing forceful relations across stores | Knowledge→Memory or Memory→Knowledge silently returns nothing | Relations work within the same store only |
| Not using `build_string` | Raw JSON is passed to LLM, wasting tokens | Use `build_string` / `buildString` from the SDK |
| Re-sorting chunks client-side | Overrides HydraDB's relevance ranking | Preserve server-returned order |
