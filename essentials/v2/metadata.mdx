---
title: "Scoping using metadata"
description: "How HydraDB uses metadata to scope query results with schema-backed fields, free-form additional metadata, source metadata edits, and exact metadata filters."
---

Metadata is structured data attached to [Knowledge](/essentials/v2/knowledge) and [Memories](/essentials/v2/memories). Use it for a hard constraint you know before retrieval runs, such as `department=legal`, `region=us`, `status=published`, or `author=alice`.

HydraDB has two metadata layers:

- **Database metadata (`metadata`):** fields declared in the database's `database_metadata_schema`. Filter on them with top-level keys in `metadata_filters`. This is the fast path. Older docs and the `tenant_metadata` alias call it tenant metadata.
- **Additional metadata (`additional_metadata`):** free-form fields on one source or memory, with no schema. Filter on them under `metadata_filters.additional_metadata`. This is the flexible, slower path.

```json
{
  "metadata_filters": {
    "department": "legal",
    "additional_metadata": {
      "author": "alice"
    }
  }
}
```

---

## 1. Choose the right metadata layer

- **Fields you scope on in most queries:** stable fields such as department, region, plan, customer, or status. Put them in `metadata` and declare them in the [database schema](/api-reference/v2/endpoint/create-tenant). Filter with `metadata_filters: { "department": "legal" }`.
- **Ad hoc or source-specific fields:** author, Slack timestamp, external ID, document version, or anything unique to one document. Put them in `additional_metadata`. Filter with `metadata_filters: { "additional_metadata": { "author": "alice" } }`. Best for display, citations, debugging, and occasional filters.
- **Hard scoping plus semantic search:** send `metadata_filters` with a natural-language `query`. Filters narrow the candidates. The query still drives ranking.
- **Semantic search over a metadata text field:** declare it in `metadata` with `enable_dense_embedding: true` (`VARCHAR` only). Put the concept in `query`, not in `metadata_filters`.
- **Keyword search over a metadata text field:** declare it in `metadata` with `enable_sparse_embedding: true` (`VARCHAR` only). Normal `/query` text (BM25) search then covers it.
- **Partition by user, workspace, or team:** send `collection` on every request. Metadata filters narrow results inside that partition. They do not replace it. See [Multi-Tenant](/essentials/v2/multi-tenant).

`database` was formerly `tenant_id` and `collection` was formerly `sub_tenant_id`. The old names still work as deprecated aliases. See [when to use `database` and `collection`](./multi-tenant#2-when-to-use-each).

## 2. How metadata filters run

HydraDB applies `metadata_filters` correctness-first:

1. **MongoDB source-id prefilter:** safe scalar database and additional metadata filters resolve to matching `source_id`s in MongoDB.
2. **Scoped retrieval:** vector and BM25 retrieval search only those source IDs.
3. **Post-filter correctness net:** hydrated chunks are checked again against the filter, so graph expansion and fallback or retry paths cannot leak excluded sources.

A valid filter that matches no sources returns an empty result. HydraDB never widens it into an unfiltered search.

### Filter semantics

- **Multiple keys:** AND. Every key must match, across both layers.
- **Operators:** each top-level `metadata` key takes `{"equals": value}`, `{"contains": value}`, or `{"contains_any": [values]}`. See [Filter operators](#filter-operators).
- **Lists:** **ANY, not ALL.** `tags: ["alpha", "beta"]` matches a source tagged `"alpha"` and a source tagged `"beta"`. Use `{"contains_any": [...]}` on a top-level `metadata` key, or a bare list in `additional_metadata`. More values widen the results, and there is no ALL operator within one key. Lists work on `VARCHAR` fields only. A list for a declared field of another type returns `400 VALIDATION_ERROR`.
- **Null values:** rejected with `400` (`metadata_filters values cannot be null`).
- **Range and fuzzy:** not supported. Put fuzzy concepts in `query`, use semantic metadata fields, or post-process client-side.
- **OR:** within one key, use `contains_any`. Across keys, run several queries and union the results client-side.
- **Graph context:** paths from excluded sources are removed.
- **Size:** at most **500** values per list and **64 KiB** for the whole object. See [Filter size limits](#filter-size-limits).

<Warning>
  `metadata_filters` are hard constraints, not semantic hints. `{ "mood": "happy" }` requires that exact stored value, not "joyful" or "cheerful". For semantic matching, use `enable_dense_embedding` and put the concept in `query`.
</Warning>

### Filter operators

Each top-level `metadata` key in `metadata_filters` takes an operator object.

| Operator | Value | Matches |
| --- | --- | --- |
| `equals` | a single value | sources whose **whole** field value is exactly that value |
| `contains` | a single value | sources whose field **holds** that value, at any position in a multi-value field |
| `contains_any` | an array | sources holding **any one** of the listed values (OR/IN) |

`contains` and `contains_any` need a `VARCHAR` field. `equals` works on any type.

```json
{
  "metadata_filters": {
    "department": { "equals": "legal" },
    "attendee_emails": { "contains": "b@company.com" },
    "tags": { "contains_any": ["alpha", "beta"] }
  }
}
```

Given four sources with these `emails` values:

- A: `a@company.com`
- B: `a@company.com,b@company.com`
- C: `c@company.com`
- D: `x@company.com,a@company.com,z@company.com`

The filters return:

- `{"equals": "a@company.com"}` returns A.
- `{"contains": "a@company.com"}` returns A, B, D.
- `{"contains_any": ["a@company.com", "c@company.com"]}` returns A, B, C, D.

Operators apply to top-level `metadata` keys only. Inside `additional_metadata`, use a bare scalar for an exact match or a bare array to match any listed value.

<Warning>
  How operator objects are parsed:

  - **Operator inside `additional_metadata`:** not rejected. It is read as an exact match against a stored object, so it matches nothing and returns `200` with an empty result.
  - **Wrong operand type, or several operators in one object:** rejected with `400 VALIDATION_ERROR`.
  - **Misspelled operator:** `{"contian": "x"}` reads as a stored-object filter and matches nothing.
  - **Reserved key names:** an object built only from `contains`, `contains_any` and `equals` is read as an operator. `{"contains": "x"}` is the `contains` operator, `{"contains": "a", "equals": "b"}` is rejected with `400`, and `{"contains": "a", "other": 1}` is still an exact-match object filter. This only matters for a `JSON`-typed field storing an object whose keys all come from those three words. Rename the nested key or the field.
</Warning>

<Note>
  Bare forms still work but are **deprecated**, because they infer the comparison from the JSON shape. A bare scalar acts as `equals`, a bare array as `contains_any`, and a bare single-element array as `contains`. So `{"emails": "a@x"}` and `{"emails": ["a@x"]}` differ by one character and return different results.
</Note>

### Storing multiple values in one field

A declared field holds one value. To store several, declare it as `VARCHAR` and join the values with commas:

```json
{
  "metadata": {
    "attendee_emails": "a@company.com,b@company.com"
  }
}
```

Then filter for one member with `contains`:

```json
{
  "metadata_filters": {
    "attendee_emails": { "contains": "b@company.com" }
  }
}
```

- `data_type: "array"` is **not** accepted on a declared field (`400`). An array **value** for a declared `VARCHAR` field is also rejected: `metadata field "attendee_emails" must be of type string, got array`. Join the values yourself.
- The comma is the separator, so a value that contains a comma will not match as expected. Use a field per value or another format.
- Size the field for the whole joined string. `max_length` defaults to `1024`, has a maximum of `65535`, and **cannot be raised after the field is created**.
- `equals` compares the entire joined string, so use `contains` on a multi-value field.

## 3. Plan your schema

- **Declare scoping fields before first ingest:** [`PATCH /databases/{database}/metadata-schema`](/api-reference/v2/endpoint/update-metadata-schema) can add fields later, but you cannot rename, retype, or change the flags of an existing field. Declare every field you will scope on.
- **Undeclared keys match nothing:** a top-level filter key is never ignored. It is matched against each source's stored `metadata`, and a database with a schema rejects undeclared keys on ingest and edit, so no source holds one. The exception is `connector_id` and `provider`, which [connectors](/essentials/v2/connectors#metadata-on-synced-objects) write on every synced object. To fix it, add the field with [`PATCH /databases/{database}/metadata-schema`](/api-reference/v2/endpoint/update-metadata-schema), then ingest or edit sources with a value.
- **Use `metadata` for hot paths, `additional_metadata` for cold ones:** database-level scopes are pre-applied in the vector store. An `additional_metadata` filter that cannot run before retrieval makes HydraDB over-fetch about 3x and match afterwards.
- **Keep keys stable:** renaming a key requires re-ingesting affected sources.
- **Edit in place:** [`PATCH /context/{id}/metadata`](/api-reference/v2/endpoint/update-source-metadata) merges new values into an indexed source. See [section 7](#7-update-metadata-without-re-ingesting).

## 4. Minimal working example

Declare the schema on the database, [attach values at ingest](#5-attach-metadata-at-ingest), then [**scope at query**](#6-query-with-metadata-filters).

### Step 1: Create metadata

#### Step 1a: Declare the schema at database creation

<CodeGroup>
```bash cURL
curl -X POST 'https://api.hydradb.com/databases' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "database_metadata_schema": [
      {
        "name": "department",
        "data_type": "VARCHAR"
      },
      {
        "name": "priority",
        "data_type": "INT64"
      },
      {
        "name": "summary_label",
        "data_type": "VARCHAR",
        "enable_dense_embedding": true,
        "enable_sparse_embedding": true
      }
    ]
  }'
```
```python Python SDK
client.databases.create(
    database="acme_corp",
    database_metadata_schema=[
        {"name": "department", "data_type": "VARCHAR"},
        {"name": "priority", "data_type": "INT64"},
        {
            "name": "summary_label",
            "data_type": "VARCHAR",
            "enable_dense_embedding": True,
            "enable_sparse_embedding": True,
        },
    ],
)
```
```typescript TypeScript SDK
await client.databases.create({
  database: "acme_corp",
  databaseMetadataSchema: [
    { name: "department", dataType: "VARCHAR" },
    { name: "priority", dataType: "INT64" },
    {
      name: "summary_label",
      dataType: "VARCHAR",
      enableDenseEmbedding: true,
      enableSparseEmbedding: true,
    },
  ],
});
```
</CodeGroup>

### Schema field options

| Field | Type / values | Purpose |
| --- | --- | --- |
| `name` | string | Starts with a letter or `_`. Letters, numbers, and underscores only. Not a reserved system name such as `source_id`, `chunk_id`, or `metadata`. |
| `data_type` | `VARCHAR`, `BOOL`, `INT8`, `INT16`, `INT32`, `INT64`, `FLOAT`, `DOUBLE`, `JSON` or friendly aliases `string`, `boolean`, `integer`, `float`, `object` | Defaults to `VARCHAR`. `ARRAY` is **not** supported and is rejected with `400`. See [Storing multiple values in one field](#storing-multiple-values-in-one-field). |
| `max_length` | integer | `VARCHAR` length. Default `1024`, maximum `65535`. Sizes one field, **not** the per-request budget ([Size limits](#size-limits)). |
| `enable_dense_embedding` | boolean | Dense semantic-search lane. `VARCHAR` fields only. |
| `enable_sparse_embedding` | boolean | Sparse (BM25) keyword-search lane. `VARCHAR` fields only. |
| `searchable` | boolean | Accepted for backward compatibility. Do not rely on it. Set `enable_dense_embedding` / `enable_sparse_embedding` directly. |

Limits and guardrails:

- Up to 32 custom database metadata fields.
- Up to **6 embedding-enabled** fields per database. `enable_dense_embedding` and `enable_sparse_embedding` each count as one, so a field with both counts as two. Exceeding the limit fails database creation with `400` before anything is provisioned.
- Field names are unique case-insensitively.
- In a database with a schema, runtime `metadata` values must match the declared type, and unknown keys are rejected on ingest and on edit.

### Size limits

Ingest and metadata edits check two caps:

| Layer | Send as | Cap |
| --- | --- | --- |
| Database (tenant) metadata | `metadata` at ingest, `database_metadata` on edit | **16 KiB** (16,384 bytes) |
| Document metadata | `additional_metadata` | **1 KiB** (1,024 bytes) |

Older spellings are accepted, but **not on every endpoint**:

| Alias | On `/context/ingest` | On `PATCH /context/{id}/metadata` |
| --- | --- | --- |
| `tenant_metadata` | accepted | accepted (`database_metadata` wins if both are sent) |
| `document_metadata` | accepted | **rejected with `400`**: send `additional_metadata` |

An accepted alias has the same cap as the canonical field.

Each cap covers the **whole map**, measured as compact JSON in UTF-8 bytes:

- **Keys and punctuation count:** quotes, colons, commas and braces.
- **Bytes, not characters:** accented Latin characters cost 2 bytes, most CJK characters 3, and emoji 4.
- **Budget in bytes from the start:** a 950-character summary with two small sibling keys serializes to 1,015 bytes, 65 of them structure. At 1,000 characters the request is rejected at 1,065 bytes.

```json Document metadata: 1,015 bytes, just inside the 1 KiB cap
{"title":"Q3 Board Deck","author":"ada@example.com","summary":"<950 characters>"}
```

Exceeding either cap fails the whole request with `400` before anything is ingested:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "INVALID_INPUT",
    "message": "additional_metadata is too large (1065 bytes when serialized; the maximum is 1024). Reduce the number or size of metadata fields."
  }
}
```

On [`PATCH /context/{id}/metadata`](/api-reference/v2/endpoint/update-source-metadata) the same message is prefixed with `invalid metadata edit:`.

<Tip>
  For more than 1 KiB of descriptive metadata, put the long text in the document body, where it is chunked and embedded. Keep `additional_metadata` for short values you filter on.
</Tip>

### Filter size limits

`metadata_filters` on [`/query`](/api-reference/v2/endpoint/query) has separate caps on what you send at query time:

- **Values in any one list:** **500**.
- **Whole `metadata_filters` object:** **64 KiB** (65,536 bytes).

The object is measured the same way, including the nested `additional_metadata` object, **after** operator objects are reduced to their values. So `{"contains": "x"}` counts as `["x"]`: the cap bounds the expression sent to the vector store, and spelling does not change it.

The list cap catches one runaway list. The object cap catches many legal lists adding up: twenty lists of 500 values pass the list cap but total roughly 127 KiB, so the object cap rejects them.

Over either limit returns `400` before the query runs:

```
metadata_filters.customer_id (got 743) must contain at most 500 values

metadata_filters is too large (130251 bytes when serialized; the maximum is 65536).
Reduce the number or size of filter values.
```

<Tip>
  Needing far more than 500 values usually means the constraint belongs in the data. Add a field that groups those values (a segment, tier, or cohort key) and filter on that.
</Tip>

### Add schema fields later

[`PATCH /databases/{database}/metadata-schema`](/api-reference/v2/endpoint/update-metadata-schema) adds fields after database creation. It cannot delete fields or change the type or flags of existing ones. To change a field, create a new database with the corrected schema.

<Warning>
  Adding fields updates the stored schema only. Existing Milvus collections are not yet altered or backfilled for new dense or sparse metadata lanes. If a new field must take part in semantic or BM25 metadata search over existing data, create a new database with that schema and re-ingest, or confirm the current migration path with support.
</Warning>

## 5. Attach metadata at ingest

For knowledge, send `metadata` and `additional_metadata` on each `document_metadata[]` or `app_knowledge[]` item.

<CodeGroup>
```bash cURL
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=knowledge" \
  -F "database=acme_corp" \
  -F 'app_knowledge=[
    {
      "database": "acme_corp",
      "collection": "default",
      "id": "auth-controls-001",
      "kind": "knowledge_base",
      "fields": {
        "title": "Authentication controls",
        "body": "Authentication controls are reviewed quarterly for SOC2."
      },
      "metadata": {
        "department": "security",
        "priority": 7,
        "summary_label": "quarterly access control review"
      },
      "additional_metadata": {
        "author": "alice",
        "doc_version": 3
      }
    }
  ]'
```
```python Python SDK
import json

client.context.ingest(
    type="knowledge",
    database="acme_corp",
    app_knowledge=json.dumps([
        {
            "database": "acme_corp",
            "collection": "default",
            "id": "auth-controls-001",
            "kind": "knowledge_base",
            "fields": {
                "title": "Authentication controls",
                "body": "Authentication controls are reviewed quarterly for SOC2.",
            },
            "metadata": {
                "department": "security",
                "priority": 7,
                "summary_label": "quarterly access control review",
            },
            "additional_metadata": {"author": "alice", "doc_version": 3},
        }
    ]),
)
```
```typescript TypeScript SDK
await client.context.ingest({
  type: "knowledge",
  database: "acme_corp",
  appKnowledge: JSON.stringify([
    {
      database: "acme_corp",
      collection: "default",
      id: "auth-controls-001",
      kind: "knowledge_base",
      fields: {
        title: "Authentication controls",
        body: "Authentication controls are reviewed quarterly for SOC2.",
      },
      metadata: {
        department: "security",
        priority: 7,
        summary_label: "quarterly access control review",
      },
      additional_metadata: { author: "alice", doc_version: 3 },
    },
  ]),
});
```
</CodeGroup>

<Warning>
  For `type=memory`, the `memories` multipart field is JSON-stringified, but each item's `metadata` and `additional_metadata` are plain objects, as on `document_metadata` and `app_knowledge` items. Do not stringify them a second time.
</Warning>

## 6. Query with metadata filters

Mix database-level (top-level) and document-level (nested) scopes in one `metadata_filters` object:

<CodeGroup>
```bash cURL
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "collection": "default",
    "query": "How do access control reviews work?",
    "type": "knowledge",
    "query_by": "hybrid",
    "metadata_filters": {
      "department": "security",
      "priority": 7,
      "additional_metadata": {
        "author": "alice"
      }
    }
  }'
```
```python Python SDK
result = client.query(
    database="acme_corp",
    collection="default",
    query="How do access control reviews work?",
    type="knowledge",
    query_by="hybrid",
    metadata_filters={
        "department": "security",
        "priority": 7,
        "additional_metadata": {"author": "alice"},
    },
)
```
```typescript TypeScript SDK
const result = await client.query({
  database: "acme_corp",
  collection: "default",
  query: "How do access control reviews work?",
  type: "knowledge",
  queryBy: "hybrid",
  metadataFilters: {
    department: "security",
    priority: 7,
    additional_metadata: { author: "alice" },
  },
});
```
</CodeGroup>

Use the legacy alias only for older clients:

```json
{
  "metadata_filters": {
    "document_metadata": { "author": "alice" }
  }
}
```

If both aliases are objects, `additional_metadata` wins on conflicts.

## 7. Update metadata without re-ingesting

Use [`PATCH /context/{id}/metadata`](/api-reference/v2/endpoint/update-source-metadata) to update an existing source's metadata in place.

```json
{
  "database": "acme_corp",
  "collection": "default",
  "database_metadata": {
    "department": "legal"
  },
  "additional_metadata": {
    "author": "grace"
  }
}
```

- The source must already exist, and `collection` is required.
- Send at least one of `database_metadata` (deprecated alias `tenant_metadata`), `additional_metadata`, or `acl`. `document_metadata` is not accepted.
- Metadata is merged (upsert): sent keys are inserted or overwritten, and omitted keys are kept.
- `acl` changes who may retrieve the source. It **replaces** rather than merges, and an `acl`-only body is a valid edit. See [Access Control](/essentials/v2/access-control).
- Edits to fields without an embedding flag stay in MongoDB and take effect for filters and listing.
- Fields with `enable_dense_embedding` or `enable_sparse_embedding` sync their vector store lane synchronously. The response reports `vector_sync_required` / `vector_synced` (deprecated aliases `milvus_sync_required` / `milvus_synced` are still emitted). These fields reject `null`, which would leave stale vectors.
- A `400` means an unknown key, a wrong type, an over-size payload ([Size limits](#size-limits)), too-deep nesting, a reserved key, or a missing `collection`.

To replace the whole document, re-ingest with `upsert: true` and the same `id`. That replaces the payload and its ingest-time metadata.

## 8. Listing with metadata filters

Use [`POST /context/list`](/api-reference/v2/endpoint/list-documents) to browse or page sources instead of running semantic retrieval:

```json
{
  "database": "acme_corp",
  "collection": "default",
  "type": "knowledge",
  "filters": {
    "metadata": { "department": "legal" },
    "additional_metadata": { "author": "alice" },
    "source_fields": { "type": "slack" }
  }
}
```

`/context/list` also accepts the legacy aliases `tenant_metadata` for `metadata` and `document_metadata` for `additional_metadata`.

## 9. Common mistakes

- **An `additional_metadata` filter returns nothing:** the key was sent top-level, so it was matched against `metadata`. Nest it: `metadata_filters: { additional_metadata: { author: "alice" } }`.
- **0 results after adding a scope:** the combined constraints exclude everything. Start with the minimum, then add scopes one at a time.

---

## 10. Advanced patterns

- **Published vs draft:** declare a `status` field, set `metadata.status` to `"draft"` or `"published"`, and pass `metadata_filters: { status: "published" }` on user-facing queries.
- **Multi-language corpora:** declare a `language` field and pass `metadata_filters: { language: detect_language(query) }`.
