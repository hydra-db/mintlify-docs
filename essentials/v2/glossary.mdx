## Scope and access

### Database

An isolated store for your context, typically one per customer or environment. A
query searches only the database you specify.

### Collection

A named group of context within a database. Omit it and HydraDB uses the
database's default collection, which is created on the first write. A query that
names another collection does not read the default one. See
[Databases and Collections](/essentials/v2/multi-tenant).

### ACL and principal

An access-control list (ACL) names who may retrieve a source. Each entry is a
principal: a person, group, or domain written as a string, such as
`grace@acme.com`. A query enforces ACLs only when it sends the caller's
principals. See [Access Control](/essentials/v2/access-control).

### Metadata schema and metadata filter

The metadata schema is the set of filterable fields you declare on a database.
Values for those fields go in `metadata` at ingest; free-form fields go in
`additional_metadata`. A metadata filter (`metadata_filters` on a query) keeps
only the sources whose values match. See [Metadata](/essentials/v2/metadata).

## Context

Everything you store in HydraDB: knowledge and memories.

### Knowledge

Documents, app sources, and facts your AI reasons over. Knowledge can be private:
the collection it lives in and its ACL decide who reads it. See
[Knowledge](/essentials/v2/knowledge).

### Memory

Preferences, decisions, and past conversations your application saves to carry
between sessions. See [Memories](/essentials/v2/memories).

### Source

One stored unit: a file, an app source, or a memory. Each source has an `id` you
use to check status, update, or delete it.

### App source

A record your application or a connector already parsed, such as a Slack message
or a Jira ticket, sent with typed fields instead of as a file. The request field
is `app_knowledge`. See [App Sources](/essentials/v2/app-sources).

<a id="class"></a>

### Kind

The type of an app source, set in its `kind` field: `message`, `ticket`,
`comment`, `knowledge_base`, `email`, `meeting`, or `custom`. Older docs called
this a class. See
[App Sources](/essentials/v2/app-sources#2-classes-tell-hydradb-what-each-item-is).

### Connector

A HydraDB-managed sync from a third-party app into your database, stored as app
sources. The provider is the app type, such as Slack or GitHub. A resource is
what you choose to sync from it: a channel, a repository, a folder, a page. See
[Connectors](/essentials/v2/connectors).

### Ingest and indexing

You ingest context with `POST /context/ingest`. HydraDB then indexes it in the
background: parsing, chunking, embedding, and graph building. A source is
searchable once its status reaches `graph_creation`; `completed` means its graph
work is done too. See [Knowledge](/essentials/v2/knowledge#3-wait-for-indexing).

### Chunk

A passage of a source, sized for search. A query returns ranked chunks, and you
pass them to your model.

### Infer

A memory flag. With `infer: true`, HydraDB extracts the preference or fact from raw
input such as dialogue or event logs. With `infer: false` (the default), it stores
exactly what you send.

## Query

The operation behind `POST /query`. See [Query](/essentials/v2/query).

### Hybrid search

The default `query_by` value: matching by meaning and by keywords at once, blended
by `alpha`. `query_by: "text"` uses keyword matching (BM25) alone. See
[Semantic Search](/essentials/v2/semantic-search).

### Fast, thinking, and auto

Query `mode` values. `fast` is one low-latency pass. `thinking` expands the query,
reranks, and pulls in forceful relations. `auto`, the default, picks one per query.

### Context graph

The entities (people, teams, services, topics) and relationships HydraDB extracts
from your context, returned with query results as `graph_context`. Following a
chain of relationships is multi-hop traversal. See
[Context Graphs](/essentials/v2/context-graphs).

### Triplet

One edge of the context graph: a source entity, a relation, and a target entity,
such as "billing policy, governs, failed payment handling".

### Forceful relations

Links between sources that you declare at ingest with `relations.ids`, for when
two sources belong together but their text does not say so. They are returned in
`additional_context` when a query runs in thinking mode.

## Deprecated aliases

`database` and `collection` were previously called `tenant_id` and
`sub_tenant_id`. Wherever you meet an old name (a request field, a route, a
query parameter), it is a deprecated alias, and it keeps working. A request that
sends both names with different values is rejected with `400`.

<Warning>
One exception: in the **indexing webhook payload**, `tenant_id` and `database` do
not carry the same value. `database` is the name you ingested into; `tenant_id` is
an identifier for it. Everywhere else, they remain interchangeable. See
[Webhooks](/essentials/v2/webhooks#payload).
</Warning>

| Deprecated | Canonical |
|---|---|
| `tenant_id` | `database` |
| `sub_tenant_id` | `collection` |
| `sub_tenant_ids` | `collections` |
| `/tenants/` routes | `/databases/` routes |

Prefer the canonical names in new integrations. See
[Databases and Collections](/essentials/v2/multi-tenant#4-migrate-from-the-legacy-tenant-and-sub-tenant-fields)
for the full compatibility contract.
