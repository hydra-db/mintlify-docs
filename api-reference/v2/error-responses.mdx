## Response envelope

HydraDB core endpoints (`/databases`, `/context/*`, `/query`, `/feedback`, and `/webhooks/indexing*`) use the same top-level envelope for successful and failed requests. Connector endpoints (`/connectors*`) and `PATCH /databases/{database}/metadata-schema` return their success body without this envelope, but their errors use it too.

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed"
  },
  "meta": {
    "request_id": "9d13aef4-02f4-4e73-8c62-4c2601d04f9d",
    "latency_ms": 4.8
  }
}
```

| Field | Description |
|---|---|
| `success` | `false` for errors. |
| `data` | Usually `null`. Some `DELETE /context` errors include per-ID results. |
| `error.code` | Machine-readable code for programmatic handling. |
| `error.message` | Human-readable explanation of what failed. |
| `meta.request_id` | Request identifier. Include it when contacting support. |
| `meta.api_version` | The API version that answered, for example `2.0.1`. |
| `meta.latency_ms` | Server-side processing time in milliseconds. |
| `detail` | Legacy copy of the message and code, plus endpoint-specific fields where the status has one: a `402` carries `detail.upgrade_url`, and a monthly allowance also carries `detail.resets_at`. |

Use `error.code` for branching and log `meta.request_id` for every failed request. The HTTP status tells you the class of failure; the error code tells you what to do.

## HTTP status codes

| Code | Meaning | Retry? |
|---|---|---|
| `400` | Invalid parameters or malformed request | No |
| `401` | Missing, expired, or invalid API key | No |
| `402` | A plan allowance is used up: the monthly enrichment tokens or storage of the Free plan (`PLAN_LIMIT_REACHED`), the plan's connector count (`PAYMENT_REQUIRED`), or the workspace is on the retired Free plan (`FREE_PLAN_DEPRECATED`) | No. The message says when the allowance resets or what clears it; `detail.upgrade_url` is the upgrade page |
| `403` | Authenticated, but not permitted for the resource, the plan's database limit is reached, or the key's workspace has no plan on record yet (`PLAN_UNRESOLVED`) | No. `PLAN_UNRESOLVED` clears once workspace setup is finished |
| `404` | Database, source, memory, or related resource was not found, or the path is not an endpoint (`NOT_FOUND`, answered before authentication) | No |
| `409` | Conflict: the database already exists, a source is still indexing when you delete it, or a schema field conflicts | Only `SOURCE_PROCESSING`, after `Retry-After` |
| `410` | A retired v1 endpoint (`ENDPOINT_RETIRED`). The message names the v2 route that replaces it | No. Call the replacement |
| `413` | One item, or the request as a whole, is over your plan's per-request allowance. The message names the item, the plan's allowance and the [limits table](#limits-per-plan); the transport caps (50 MiB multipart, 16 MiB JSON) answer here too | No. Send smaller items or split the request |
| `415` | Unsupported `Content-Type`, such as a `POST /context/ingest` body that is neither a multipart form nor JSON | No |
| `422` | Well-formed request that failed validation, or a query sent before the database finished provisioning | Only `TENANT_INFRA_NOT_READY`, once the database is ready |
| `429` | A per-second or per-minute allowance is spent for the moment (`RATE_LIMITED`). `Retry-After` is always set | Yes, after `Retry-After` |
| `500` | Internal server error | Yes, with backoff; honour `Retry-After` when it is set |
| `503` | Temporary service unavailability | Yes, with backoff |

## Common error codes

| Code | Typical status | Meaning |
|---|---|---|
| `INVALID_INPUT` | `400` | The default for a bad request: a required parameter is missing, malformed, or mutually incompatible with another parameter. Also the code of every `413` (the message names the plan's per-request allowance) and `415`. |
| `UNAUTHORIZED` | `401` | The `Authorization: Bearer <your_api_key>` header is missing or invalid. |
| `PLAN_LIMIT_REACHED` | `402` | A plan allowance is used up: the Free plan's monthly enrichment tokens (the message names the usage and the reset date, `detail.resets_at` and `Retry-After` carry it) or storage (delete data or upgrade). `detail.upgrade_url` is the upgrade page. Never retried by the SDKs. |
| `PAYMENT_REQUIRED` | `402` | A plan limit refused the write, for example the connector count. |
| `FREE_PLAN_DEPRECATED` | `402` | The organization is on the deprecated Free plan. The message and `detail.upgrade_url` carry the upgrade link. |
| `FORBIDDEN` | `403` | The API key is valid but does not have access to the requested route or resource, or the plan's database limit prevents the operation. |
| `PLAN_UNRESOLVED` | `403` | The key's workspace has no plan on record yet, so the request is refused the same way every time until one is set. Finish workspace setup in the dashboard, or contact support with `meta.request_id`. |
| `DATABASE_ALREADY_EXISTS` | `409` | `POST /databases` received a `database` (formerly `tenant_id`) that is already in use. |
| `DATABASE_NOT_FOUND` | `404` | The requested database does not exist or is not visible to the current API key. |
| `NOT_FOUND` | `404` | The requested resource does not exist, for example a source ID in `DELETE /context`; or the path is not an endpoint at all, in which case the message names the request and links the endpoint list. |
| `ENDPOINT_RETIRED` | `410` | A v1 route that no longer exists. The message names the v2 route that does the same job, and `Link` carries its documentation. |
| `SOURCE_PROCESSING` | `409` | `DELETE /context` hit a source that is still indexing. Retry after `Retry-After`. |
| `VALIDATION_ERROR` | `400` or `422` | A field has an invalid value. Query filter errors return `400`. Invalid connector credentials return `422`. |
| `TENANT_INFRA_NOT_READY` | `422` | `POST /query` reached a database that is still provisioning. Poll [Database Status](/api-reference/v2/endpoint/tenant-status) until `ready_for_ingestion` is `true`, then retry. |
| `CORPUS_TYPE_UNSUPPORTED` | `400` | The `type` value does not fit this endpoint or database, for example `type: "all"` on ingest. |
| `RATE_LIMITED` | `429` | A per-second or per-minute allowance is spent for the moment. The message names the allowance and the wait; `Retry-After` carries the wait in seconds. A monthly allowance is `402 PLAN_LIMIT_REACHED`, never this code. |
| `INTERNAL_ERROR` | `500` | HydraDB hit an unexpected server-side error. A store failure while validating the API key reports `INTERNAL_SERVER_ERROR` with `Retry-After` instead. |
| `SERVICE_UNAVAILABLE` | `503` | A dependency is temporarily unavailable or the service is under load. |

Endpoint pages list the most common codes for that operation. New codes may be added over time, so clients should handle unknown `error.code` values gracefully.

`PATCH /databases/{database}/metadata-schema` currently returns `INTERNAL_ERROR` for its `400` and `409` errors too, so branch on the HTTP status there.

For legacy route and field behavior, see [Migrating from tenant fields](/essentials/v2/multi-tenant#7-migrating-from-the-legacy-tenant-and-sub-tenant-fields).

## Limits per plan

Every limit is enforced per workspace, so all the API keys of one workspace draw on the same allowance. The response says which allowance you reached and what to do; this table says what the numbers are.

| Limit | Free | Ship | Scale | Enterprise and BYOC |
|---|---|---|---|---|
| `POST /query` requests (shared with `/byog*`, `/context/{id}/subgraph` and `/context/profile`) | 600 per minute | 1,200 per minute | 3,000 per minute | no platform ceiling; capacity is sized in your agreement |
| `POST /context/ingest` requests | 5 per second, 120 per minute | 25 per second, 600 per minute | 100 per second, 3,000 per minute | no platform ceiling |
| Items per ingest request (documents plus `app_knowledge` entries) | 1,000 per request, 60 per minute | 1,000 per request, 300 per minute | no item limit | no item limit |
| Document upload volume | 10 MiB per file and per request, 20 MiB per minute | 50 MiB per file and per request, 250 MiB per minute | 100 MiB per file and per request, 1 GiB per minute | no platform ceiling |
| Context volume (`memories`, counted in words) | 5,000 words per item and per request, 25,000 per minute | 20,000 words per item and per request, 100,000 per minute | 40,000 words per item and per request, 400,000 per minute | no platform ceiling |
| Enrichment tokens | 5,000,000 per calendar month (UTC) | metered | metered | metered |
| Storage | 1,000 MB | metered | metered | metered |
| Connectors | 3 | no limit | no limit | no limit |
| Databases | per plan; the `403` names the allowance | | | |
| `POST /feedback` | 100 per minute on every plan | | | |

Two transport caps apply to every plan: a multipart body of 50 MiB and a JSON body of 16 MiB. Larger uploads go in several requests.

What each refusal looks like:

| You reached | Status and code | The response carries | What to do |
|---|---|---|---|
| A per-second or per-minute allowance | `429 RATE_LIMITED` | `Retry-After` in seconds; the message names the allowance | Wait `Retry-After`, then retry. The SDKs do this for you |
| A per-item or per-request size allowance | `413 INVALID_INPUT` | The item's size, the plan's allowance and a link to this table | Send smaller items or split the request; a plan with a higher allowance also clears it |
| The monthly enrichment tokens or the storage allowance | `402 PLAN_LIMIT_REACHED` | `detail.upgrade_url`; for the monthly meter also `detail.resets_at` and `Retry-After` to the reset | Wait for the reset, delete data (storage), or upgrade |
| The connector count | `402 PAYMENT_REQUIRED` | The allowance in the message | Remove a connector or upgrade |
| The database count | `403 FORBIDDEN` | The allowance in the message | Delete a database or upgrade |

## Ingestion error codes

Asynchronous ingestion failures surface a numeric `E####` code in the `error_code` field of [`GET /context/status`](/api-reference/v2/endpoint/source-status) responses and `indexing.status_changed` [webhook](/essentials/v2/webhooks) payloads. Unlike the HTTP `error.code` values above (which describe why a *request* was rejected), these describe why a specific *item* failed to index.

Many storage- and capacity-related ingestion errors are **transient**: the pipeline retries them automatically with backoff, and they typically self-resolve within minutes. A code appearing in `error_code` does not by itself mean the item has failed permanently; only treat an item as a real failure once it reaches the terminal `errored` status.

| Code | Meaning | What to do |
|---|---|---|
| `E1002` | Unsupported file format. Read this code in the upload response. The file is not queued. | Upload a supported format. |
| `E2002` | The file contains no readable text. | Upload a version with text. |
| `E6001` | Processed data could not be stored. | Retried automatically. |

Files rejected with `E1002` have no ingestion status record. Handle this code from the upload response. See [Supported file formats](/api-reference/v2/endpoint/ingest-context#supported-file-formats).

## Retry pattern

Retry only transient failures: `429`, `500`, and `503`. Use exponential backoff with jitter and keep retries bounded, and honour `Retry-After` when it is set (every `429` sets it). Two other codes clear on their own, so wait instead of backing off blindly: `409 SOURCE_PROCESSING` (wait for `Retry-After`) and `422 TENANT_INFRA_NOT_READY` (wait until the database is ready).

Retrying does not clear a `402`, `403`, `410` or `413`: each message says what does, whether that is a smaller request, the replacement route, finishing workspace setup, or a plan with a higher allowance.

**The SDKs already retry:** both retry `408`, `429`, and `5xx` responses twice with exponential backoff before raising, and the Python SDK also retries `409`. Raise the count with `request_options={"max_retries": 5}` on a Python call, or `maxRetries` on the TypeScript client or call. The SDK examples below increase that limit. The raw HTTP example implements retries directly. Retry writes only when repeating the operation is safe.

<CodeGroup>
```python Python SDK
result = client.query(
    database="my_first_database",
    query="What are the pricing tiers?",
    type="knowledge",
    request_options={"max_retries": 5},
)
```
```typescript TypeScript SDK
const result = await client.query({
  database: "my_first_database",
  query: "What are the pricing tiers?",
  type: "knowledge",
}, { maxRetries: 5 });
```
```typescript fetch
async function hydraRequest(url: string, options: RequestInit, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    const response = await fetch(url, options);
    if (response.ok) return response.json();

    const retryable = [429, 500, 503].includes(response.status);
    if (!retryable || attempt === maxRetries) {
      throw await response.json();
    }

    const baseDelayMs = 2 ** attempt * 1000;
    const jitterMs = Math.floor(Math.random() * 250);
    await new Promise((resolve) => setTimeout(resolve, baseDelayMs + jitterMs));
  }
}
```
</CodeGroup>

## Handling errors

<CodeGroup>
```typescript TypeScript SDK
import { HydraDBError } from "@hydradb/sdk";

try {
  await client.context.ingest({
    type: "knowledge",
    database: "my_first_database",
    documents: [{ path: "policy.pdf", filename: "policy.pdf" }],
  });
} catch (error) {
  if (error instanceof HydraDBError) {
    // error.body is typed `unknown`; it holds the raw snake_case error envelope.
    const body = error.body as
      | { error?: { code?: string }; meta?: { request_id?: string } }
      | undefined;
    const code = body?.error?.code;
    const requestId = body?.meta?.request_id;

    if (code === "DATABASE_NOT_FOUND") {
      // Create or select a valid database before ingesting.
    } else if (error.statusCode === 429) {
      // Retry with backoff.
    } else {
      console.error({ code, requestId });
      throw error;
    }
  } else {
    throw error;
  }
}
```
```python Python SDK
from hydra_db.core.api_error import ApiError

try:
    client.context.ingest(
        type="knowledge",
        database="my_first_database",
        documents=[("policy.pdf", open("policy.pdf", "rb"), "application/pdf")],
    )
except ApiError as exc:
    # The machine-readable code lives in the response envelope, not on the
    # exception: ApiError carries status_code, headers and the parsed body.
    error_code = (exc.body or {}).get("error", {}).get("code")

    if error_code == "DATABASE_NOT_FOUND":
        # Create or select a valid database before ingesting.
        pass
    elif exc.status_code == 429:
        # Retry with backoff.
        pass
    else:
        raise
```
</CodeGroup>

## Troubleshooting

### Authentication failures

Send exactly one `Authorization` header:

```http
Authorization: Bearer <your_api_key>
```

Also send `API-Version: 2` on raw HTTP requests. The official SDKs set the version header automatically.

### Database not found after creation

Database creation is asynchronous. After `POST /databases`, poll [`GET /databases/status`](/api-reference/v2/endpoint/tenant-status) until `infra.scheduler_status`, `infra.graph_status`, `infra.vectorstore_status.knowledge`, and `infra.vectorstore_status.memories` are all `true` (`infra.ready_for_ingestion` combines them). A query sent earlier returns `422 TENANT_INFRA_NOT_READY`.

### Ingestion validation errors

Common causes:

- `document_metadata` length does not match the `documents` array length.
- `app_knowledge`, `memories`, or `document_metadata` was sent as an object instead of a JSON-stringified multipart field.
- A memory item has neither `text` nor `user_assistant_pairs`.
- A typed metadata value does not match the database metadata schema.

### Empty query results

Empty results are not always errors. Check these first:

- Context status may still be `queued` or `processing`; poll [`GET /context/status`](/api-reference/v2/endpoint/source-status).
- `metadata_filters` may be too restrictive or may target the wrong metadata namespace.
- The query may be scoped to the wrong `database` or `collection` (formerly `tenant_id` / `sub_tenant_id`).
- The `type` value may exclude the store you need. Use `type: "all"` when combining knowledge and memories in `POST /query`.
