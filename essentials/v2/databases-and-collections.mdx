Every write and read is scoped with two fields: `database`, an isolated store for one environment (for eg - one enterprise could be one database), and `collection`, a group separated by logic, not infrastructure, inside a database. Most products need one database and multiple collections.

## One database, one body of context

A new database is **unified**: everything you ingest into it, in any collection, is one body of context. You send items in one `context` list and query without choosing a store. Create one with just a name.

```bash
curl -X POST 'https://api.hydradb.com/databases' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{"database": "acme_corp"}'
```

Databases are unified. Everything you ingest goes into one store, and knowledge and memory are internal to HydraDB now, so no call takes a `type`.

## Choose how to scope your data

Some examples of goals and outcomes to help shape up your mental model

| Goal | Use |
|---|---|
| A company brain: one query across all your files and connectors | One `database` and one collection for everything. Isolate results inside it with metadata filters and access control |
| Separate enterprise customers on your platform | A different `database` per customer |
| Keep each person's memories apart | One `database`, and a collection per person, such as `user_123` |

<a id="1-put-each-user-in-their-own-collection"></a>

## How writes and reads scope

**Writes:** Send the `collection` you will query the context from. John's memories go in John's collection; shared documents go in the shared one. When you omit `collection`, HydraDB uses a universal default collection, which is automatically created.

**Reads:** A query containing one `collection` reads only that collection. To read several collections at once, send `collections` as a list, or as an object that maps each collection to a relative ranking weight, as in `{"company_docs": 1.5, "user_123": 0.8}`.

**Deleting a collection:** `DELETE /databases/collections` permanently deletes that collection and everything in it. The parent database and its other collections are unaffected.

## Deprecation signals

When a request uses a deprecated route or field, HydraDB adds a deprecation notice. It is never an error, and the status code is unchanged:

**Response headers:** `Deprecation: true`, plus a `Warning` header carrying the migration message.

The deprecated names map one to one: `tenant_id` is `database`, `sub_tenant_id` is `collection`, `sub_tenant_ids` on `/query` is `collections`, and the `/tenants/*` routes are the `/databases/*` routes.

## Common mistakes

**Mismatched `collection` between write and read:**
Context written under one collection does not surface when queried under another. Use the same `collection` for the same logical scope on every call.

**Sharing a `database` across environments:**
Do not use one database for both production and staging. Create a database per environment.

**Confusing `database` with `collection`:**
Use `database` for primary boundaries such as customers or environments. Use `collection` for groups inside a database, such as users or workspaces.

**Writing shared context under a user's collection by accident:**
Context written with one user's `collection` is invisible to every other user. Choose the write scope from where it should be queried later.
