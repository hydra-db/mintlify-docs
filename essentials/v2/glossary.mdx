HydraDB renamed its two scoping concepts in v2: **database** (formerly `tenant_id`)
and **collection** (formerly `sub_tenant_id`). The rename is user-facing only - no
data moved, and the old names are accepted forever.

The catch is that the rename reaches different surfaces at different speeds. The
API accepts both spellings, the webhook payload sends both, and the CLI and plugin
environment variables still use the original ones. This page is the map, so a name
you meet in one place is never a mystery in another.

For how scoping actually behaves - what a database isolates, when to reach for a
collection, and the full compatibility contract - see
[Multi tenancy](/essentials/v2/multi-tenant).

## The two scopes

**Database** - the top-level isolation boundary, typically one per customer,
environment, or workspace. Data in one database is fully separated from every
other; nothing is shared across them.

**Collection** - a partition *within* a database, typically one per end-user, team,
or agent. Collections keep each subject's documents, memories, and graph cleanly
separated inside a single database. Omit it and HydraDB uses the database's default
collection.

## Where each name appears

| Surface | Database | Collection |
|---|---|---|
| API request/response fields | `database` | `collection` |
| API fields (deprecated aliases, still accepted) | `tenant_id` | `sub_tenant_id` |
| API routes | `/databases/…` | - |
| API routes (deprecated, still routed) | `/tenants/…` | - |
| `/query` multi-scope selector | - | `collections` (alias: `sub_tenant_ids`) |
| Webhook payload | `database` **and** `tenant_id` | `collection` **and** `sub_tenant_id` |
| Dashboard sidebar | **Databases** (`/databases`) | - |
| Dashboard topbar scope picker | **Database** | **Collections** |
| CLI environment | `HYDRADB_TENANT_ID` | `HYDRADB_SUB_TENANT_ID` |
| CLI commands | `hydradb tenant …` | `hydradb tenant list-sub-tenants` |
| MCP server environment | `HYDRA_DB_TENANT_ID` | `HYDRA_DB_SUB_TENANT_ID` |
| Claude Code plugin | `HYDRADB_TENANT_ID` / `tenantId` | `HYDRADB_SUB_TENANT_ID` / `subTenantId` |
| OpenClaw plugin | `HYDRA_OPENCLAW_TENANT_ID` / `tenantId` | `subTenantId` |

<Note>
The CLI and plugin configuration keys have not been renamed. `HYDRADB_TENANT_ID`
takes a database ID, and `subTenantId` takes a collection ID - the value you copy
from the dashboard's **Databases** page goes into the `…TENANT_ID` variable
unchanged.
</Note>

## Reading the webhook payload

Delivered payloads carry all four keys. `database`/`collection` are the canonical
names; `tenant_id`/`sub_tenant_id` are the pre-rename spellings, kept because
receivers built against them would stop finding the scope if they disappeared.
Signature verification is unaffected either way - the HMAC covers whatever bytes
are delivered.

```json
{
  "event": "indexing.status_changed",
  "delivery_id": "<delivery_id>",
  "id": "<id>",
  "tenant_id": "<database>",
  "database": "<database>",
  "sub_tenant_id": "<collection>",
  "collection": "<collection>",
  "status": "completed",
  "timestamp": "<ISO-8601 timestamp>"
}
```

Read `database` and `collection` in new integrations. See
[Webhooks](/essentials/v2/webhooks) for the rest of the delivery contract.

## Other names you may meet

| Term | What it means |
|---|---|
| **Source** | One ingested item - a document, a memory, or an app record. Identified by `id` (older examples call it `doc_id`). |
| **Knowledge** | Ingested documents and files, searched with the knowledge retrieval modes. |
| **Memory** | Short, user-scoped facts and preferences, searched separately from knowledge. |
| **Workspace / team** | Dashboard-level account grouping. It sits *above* databases and is not a query scope - it never appears on the wire. |
