Permanently deletes one collection and all knowledge, memories, embeddings, and graph data stored under it. The parent database and its other collections are not affected.

<Warning>
This action is irreversible. There is no soft-delete and no recovery window.
</Warning>

Deleting a collection also stops every connector route that writes to it. What happens to each connector depends on its default route and its other resources:

- If the connector's default route is active and writes to this collection, and all of its resources also write to this collection, the connector is deleted.
- If the connector's default route writes to this collection but some resources write elsewhere, the default route is disabled and the connector stays.
- Resources that write to this collection are removed. The connector stays when its default route writes elsewhere or is already disabled.

## While cleanup is running

Deletion is asynchronous: a `200` means cleanup was accepted, not that it finished. From the moment the API accepts the call, the collection is fenced:

- Every ingest, query, and read addressed to it returns `404`, so nothing can write into a collection that is being purged. Other collections in the same database, and the database itself, keep serving normally.
- Ingestion already in flight for this collection is cancelled before any store is purged, so a job that started before the delete cannot repopulate it afterwards. The cancelled ingestion is reported as failed.
- The collection disappears from [List Collections](/api-reference/v2/endpoint/list-collections) once its records are dropped, which happens before the slower vector, graph, and object-store cleanup completes.

There is no collection-level completion endpoint, and a repeated `DELETE` returning `200` is not a completion signal either.

**Reusing the collection name:** Ingest the new context. While cleanup is running, the API returns `404`, so retry later. Writes succeed only after cleanup finishes in every store. A successful write also creates the collection, so use it to ingest context, not to check deletion status.

**Repeat calls are the retry path:** Deleting the same collection again is idempotent. A duplicate call while cleanup is still running joins the delete in progress and does not start a second one. If a cleanup fails part-way, the collection stays fenced and re-issuing the same `DELETE` re-runs it.

**Dashboard:** Owners can also expand a database on the Databases page and delete a collection from the inline list.

## Errors

Common codes: `400 INVALID_INPUT` (`database` or `collection` is missing), `404 DATABASE_NOT_FOUND` (a database that is itself being deleted returns `404 NOT_FOUND`), `401 UNAUTHORIZED`, `503 SERVICE_UNAVAILABLE` (an earlier failed deletion of this collection is still releasing its lock; the collection stays fenced, so retry in a few seconds), and `500 INTERNAL_ERROR` (transient; retry the same `DELETE`). See [Error Responses](/api-reference/v2/error-responses) for the full list.
