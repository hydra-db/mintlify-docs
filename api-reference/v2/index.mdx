## The four calls

Create a database, ingest context, wait for indexing, then query it.

1. [Create Database](/api-reference/v2/endpoint/create-database): `POST /databases`. Isolates context for a customer, environment, or product. Creation runs in the background, so poll [Database Status](/api-reference/v2/endpoint/database-status) until `ready_for_ingestion` is `true`.
2. [Ingest Context](/api-reference/v2/endpoint/ingest-context): `POST /context/ingest`. Files, app sources, or memories, in one multipart request.
3. [Ingestion Status](/api-reference/v2/endpoint/source-status): `GET /context/status`. Poll the returned IDs until `indexing_status` is `completed`, or [register a webhook](/api-reference/v2/endpoint/webhooks-overview) instead.
4. [Query](/api-reference/v2/endpoint/query): `POST /query`. Retrieve the context your model needs, from knowledge, memories, or both.

## Conventions

**Authentication:** Every endpoint requires `Authorization: Bearer <your_api_key>`. Get your key at [dashboard.hydradb.com](https://dashboard.hydradb.com). The [SDKs](/api-reference/v2/sdks) set it, and the version header, for you.

**Versioning:** Send `API-Version: 2` with every request.

```bash
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer <your_api_key>" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "my_first_database",
    "query": "What are the pricing tiers?",
    "type": "knowledge",
    "query_by": "hybrid"
  }'
```

**Response envelope:** Core v2 endpoints (`/databases`, `/context/*`, `/query`, `/feedback`, and `/webhooks/indexing*`) return the same envelope, with the resource-specific payload under `data`. Connector endpoints (`/connectors*`) and `PATCH /databases/{database}/metadata-schema` are the exception: they return their success body without the envelope.

```json
{
  "success": true,
  "data": {},
  "error": null,
  "meta": {
    "request_id": "request-id",
    "latency_ms": 12.3
  }
}
```

**Errors:** Every endpoint returns errors in the same envelope, with `success: false` and an `error` object containing `code` and `message`. Most errors have `data: null`. Some [Delete Context](/api-reference/v2/endpoint/delete-source) errors include per-ID results under `data`. See [Error Responses](/api-reference/v2/error-responses) for error codes and retry rules.

**Status codes:** `200` for success and `202` when an asynchronous operation is queued.

**Database scoping:** Use `database` to select a database and `collection` to scope context within it. Omitting `collection` uses the default collection. Requests that use the deprecated tenant field names can include deprecation notices. See [Migrating from tenant fields](/essentials/v2/databases-and-collections#7-migrating-from-the-legacy-tenant-and-sub-tenant-fields).

**Asynchronous operations:** Database creation, database and collection deletion, and context ingestion are asynchronous. They return immediately after queuing. Use the relevant status endpoint to confirm completion before downstream operations.

**Pagination:** Listing endpoints (`/context/list`) return pagination fields for browsing large result sets.

**Parameter casing:** The REST API uses snake_case (`database`, `max_results`). The TypeScript SDK uses camelCase keys and method names (`maxResults`, `deleteCollection`) and ignores request keys it does not recognize, including snake_case ones. The Python SDK uses snake_case throughout. See [SDKs](/api-reference/v2/sdks#naming-conventions).

## Rate limits

Rate limits apply per API key. Both SDKs retry `429` responses automatically. For raw HTTP, use exponential backoff; see [Error Responses](/api-reference/v2/error-responses#retry-pattern). Contact [founders@hydradb.com](mailto:founders@hydradb.com) for current limit values.
