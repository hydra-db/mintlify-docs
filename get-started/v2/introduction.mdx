HydraDB stores the context your agents need, links it in a graph, and returns what is useful to the person asking.

You store two kinds of data:

- **Knowledge:** documents, files, and content from tools like Slack, Notion, Drive, and email. Shared across your users.
- **Memories:** one user's preferences, history, and past conversations. They grow as that user keeps using your product.

As content comes in, HydraDB extracts the people, projects, and other entities in each source and links them in a context graph. A query matches knowledge, memories, or both by meaning and keyword, then follows graph links to related material.

## Why not only a vector database

A vector database returns the text closest to the query. That breaks in three ways:

- **It cannot tell meanings apart:** "Python" the language and "Python" the snake look alike as vectors. A question like "who owns this escalation?" needs relationships, not similarity.
- **Everyone gets the same results:** asked about "Project Acme", an account executive needs the latest deck and an engineer needs the changelog. HydraDB keeps each person's memories, so the same query returns different context to each.
- **You run five systems:** a vector store, a graph database, a relational store, file storage, and a cache, glued together by your code. HydraDB is one API for all of it.

You get the parts (graph, memory, retrieval, and ranking controls) and decide how to combine them, from 10K documents to 10M.

## Performance and isolation

- **Accuracy:** 90%+ on LongMemEval, a long-context memory benchmark.
- **Latency:** retrieval in under 200 ms.
- **Isolation:** one database can never read another's data. There is no cross-database query or aggregation, so your access rules always hold.

Full numbers: [benchmarks](https://benchmarks.hydradb.com/).

## How it works

1. Create a database.
2. Send content through the API, or connect a source with a [connector](/essentials/v2/connectors).
3. Wait while HydraDB parses, chunks, embeds, and builds the graph.
4. Call `POST /query` and pass the chunks to your own model. Your app writes the prompt and the answer.

## What people build

- Support agents grounded in a customer's history
- Coding agents that remember a codebase and its conventions
- Clinical companions that track patient context across visits
- Research copilots across papers, authors, and findings
- Internal assistants over Slack, Notion, Drive, and email
- Consumer apps where each user's memory grows over time

Longer examples: [Cookbooks](/cookbooks/v2/index).
