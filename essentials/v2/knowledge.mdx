## 1. What it is

Knowledge is context shared across users: product docs, wikis, policy PDFs, Slack threads, Notion pages, CSVs, and email. [Memories](/essentials/v2/memories), the other store, hold context about one user. How the two differ: [Core Concepts](/get-started/v2/core-concepts#how-knowledge-and-memories-differ).

Read knowledge with [`POST /query`](/api-reference/v2/endpoint/query) and `type: "knowledge"`, or `type: "all"` to rank it together with memories from the same scope. Store readiness is `vectorstore_status.knowledge` on [`GET /databases/status`](/api-reference/v2/endpoint/tenant-status) (`vectorstore_status.memories` for memories).

---

## 2. What it does

[`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) with `type=knowledge` does this for each source:

1. Parses the input: PDF, DOCX, Markdown, CSV, plain text, or app-source JSON.
2. Splits it into semantically coherent chunks.
3. Extracts entities and relationships as graph nodes and edges. See [Context Graphs](/essentials/v2/context-graphs).
4. Embeds each chunk into the dense and sparse vector stores.
5. Indexes the result so [`POST /query`](/api-reference/v2/endpoint/query) can read it.

The work runs in the background. Ingest returns `202 Accepted` with an `id` per source. To know when it is queryable, see [Verifying processing](#5-verifying-processing).

---

## 3. When to use it

Use knowledge when another user in the same database should retrieve it: docs, policies, runbooks, wikis, threads, pages. Use a [memory](/essentials/v2/memories) when only one user should.

Knowledge is versioned by replacement. When a source changes, ingest it again with the same `id` (`upsert` is on by default) or delete it. Do not append a second copy.

---

## 4. Two ingestion paths

[`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) with `type=knowledge` takes files (Path A), app sources (Path B), or both in one request. Send the fields as `multipart/form-data`. A JSON body is read as a different request shape, and a body that is neither form data nor JSON returns `415`.

### Path A: files

Binary files HydraDB parses and chunks: PDF, DOCX, Markdown, CSV, TXT.

<CodeGroup>
```python Python SDK
import json

with open("/path/to/policy.pdf", "rb") as f1, open("/path/to/runbook.pdf", "rb") as f2:
    result = client.context.ingest(
        type="knowledge",
        database="acme_corp",
        documents=[
            ("policy.pdf", f1, "application/pdf"),
            ("runbook.pdf", f2, "application/pdf"),
        ],
        document_metadata=json.dumps([
            {"id": "policy_v2", "metadata": {"document_type": "policy", "status": "approved"}},
            {"id": "runbook_deploy", "metadata": {"document_type": "runbook"}},
        ]),
    )
```
```typescript TypeScript SDK
const result = await client.context.ingest({
  type: "knowledge",
  database: "acme_corp",
  documents: [
    { path: "/path/to/policy.pdf", filename: "policy.pdf", contentType: "application/pdf" },
    { path: "/path/to/runbook.pdf", filename: "runbook.pdf", contentType: "application/pdf" },
  ],
  documentMetadata: JSON.stringify([
    { id: "policy_v2", metadata: { document_type: "policy", status: "approved" } },
    { id: "runbook_deploy", metadata: { document_type: "runbook" } },
  ]),
});
```
```bash cURL
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=knowledge" \
  -F "database=acme_corp" \
  -F "documents=@/path/to/policy.pdf" \
  -F "documents=@/path/to/runbook.pdf" \
  -F 'document_metadata=[
    { "id": "policy_v2", "metadata": { "document_type": "policy", "status": "approved" } },
    { "id": "runbook_deploy", "metadata": { "document_type": "runbook" } }
  ]'
```
</CodeGroup>

### Path B: app sources

Pre-extracted records from an app or connector: Slack messages, Notion pages, Gmail messages, tickets, or CRM records. You supply app-native fields (`kind`, `provider`, `external_id`, and `fields`), [metadata](/essentials/v2/metadata), and optional attachments and comments. HydraDB skips parsing and keeps the app structure instead of treating the item as plain text. App sources also get app-aware query behavior (`query_apps` in [Query](/essentials/v2/query)).

<CodeGroup>

## 5. Verifying processing

Query reads only indexed sources. Poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) with the `id`s from the ingest response until every item reaches `completed` or `errored`:

<CodeGroup>
```python Python SDK
import time

ids = ["policy_v2", "runbook_deploy"]
terminal = {"completed", "errored"}

while True:
    status = client.context.status(
        database="acme_corp",
        collection="default",
        ids=ids,
    )
    if all(s.indexing_status in terminal for s in status.data.statuses):
        break
    time.sleep(5)
```
```typescript TypeScript SDK
const ids = ["policy_v2", "runbook_deploy"];
const terminal = new Set(["completed", "errored"]);

let status;
while (true) {
  status = await client.context.status({
    database: "acme_corp",
    collection: "default",
    ids: ids,
  });

  const allDone = status.data.statuses.every((s) => terminal.has(s.indexingStatus));
  if (allDone) break;

  await new Promise((r) => setTimeout(r, 5_000));
}
```
```bash cURL
while true; do
  response=$(curl -s -G 'https://api.hydradb.com/context/status' \
    -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
    -H "API-Version: 2" \
    --data-urlencode "database=acme_corp" \
    --data-urlencode "collection=default" \
    --data-urlencode "ids=policy_v2" \
    --data-urlencode "ids=runbook_deploy")

  statuses=$(echo "$response" | jq -r '.data.statuses[].indexing_status')
  if echo "$statuses" | grep -qv '^\(completed\|errored\)$'; then
    sleep 5
    continue
  fi
  echo "$response" | jq
  break
done
```
</CodeGroup>

```json
{
  "statuses": [
    {
      "id": "policy_v2",
      "indexing_status": "completed",
      "success": true
    }
  ]
}
```

Status moves from `queued` to `processing` to `graph_creation` to `completed`, or ends in `errored`. Most documents complete in 1 to 5 minutes. Full table: [Ingestion Status](/api-reference/v2/endpoint/source-status).

<Info>
**`graph_creation` is already queryable:** [`POST /query`](/api-reference/v2/endpoint/query) can retrieve the source. Wait for `completed` only when you need full graph traversal (`graph_context: true`).
</Info>

## 6. Key parameters

The fields you use most, by where they go. Full schema: [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context).

### File metadata (`document_metadata` array items)

Send one item per file in `documents`, in the same order. The item count must match the file count.

| Field | Description |
|---|---|
| <Field name="id" type="string" /> | Optional stable ID. The upsert key when `upsert: true`. |
| <Field name="metadata" type="object" /> | Filterable fields. Keys must match the database metadata schema. Up to 16 KiB as compact JSON. |
| <Field name="additional_metadata" type="object" /> | Free-form fields. Filterable only when nested under `additional_metadata` in `metadata_filters`. Up to 1 KiB as compact JSON. |
| <Field name="relations" type="object" /> | Forcefully connect this source to others with `{ "ids": [...] }`. |

Any other key, including `title`, `type`, `url`, and `timestamp`, returns `400`. Those fields exist only on app sources.

### App source model (`app_knowledge` array items)

| Field | Description |
|---|---|
| <Field name="id" type="string" recommended /> | Stable ID. The upsert, delete, and status key. |
| <Field name="database" type="string" recommended /> | Owning database. Must match form-level `database` (formerly `tenant_id`) when present. |
| <Field name="collection" type="string" recommended /> | Must match form-level `collection` when present. |
| <Field name="title" type="string" recommended /> | Short title, subject, ticket title, or page name. |
| <Field name="type" type="string" recommended /> | Source category for display and analytics, such as `slack`, `notion`, `gmail`, or `jira`. |
| <Field name="kind" type="email, message, ticket, knowledge_base, comment, custom" recommended /> | App object kind. Selects the parser for `fields`. |
| <Field name="provider" type="string" recommended /> | App namespace such as `slack`, `gmail`, `jira`, `notion`, `salesforce`, or `linear`. |
| <Field name="external_id" type="string" recommended /> | Stable provider ID for this item. Enables exact lookup and relation resolution. |
| <Field name="fields" type="object" required /> | App-native content. Put primary text in `body`, `description`, `title`, or `data`, depending on `kind`. |
| <Field name="url" type="string" /> | Canonical URL. |
| <Field name="timestamp" type="ISO-8601 datetime" /> | Creation, sent, or last-updated time. |
| <Field name="metadata" type="object" /> | Filterable fields matching the database schema. |
| <Field name="additional_metadata" type="object" /> | Free-form fields. Filterable only when nested under `additional_metadata` in `metadata_filters`. |
| <Field name="attachments" type="array" /> | Related attachments. Put extracted text in `attachments[].content.text` or `.markdown`. |
| <Field name="comments" type="array" /> | Embedded snapshot comments. For live incremental comments, prefer a separate `kind: "comment"` source. |
| <Field name="relations" type="array" /> | App-native relation array: `[{ "predicate": "linked_to", "target": { "external_id": "AUTH-123", "provider": "jira" } }]`. |

### Request-level fields

| Field | Default | Description |
|---|---|---|
| <Field name="database" type="string" required /> | None | Target database. |
| <Field name="collection" type="string" /> | default collection | Target collection (formerly `sub_tenant_id`). If omitted, the source goes to the default collection, which a query naming another `collection` does not read. |
| <Field name="upsert" type="boolean" /> | `true` | Replace existing items with the same `id`. |

## 7. Forceful relations

Forceful relations are links between whole sources that you declare at ingest. When a query matches a source, HydraDB returns its linked sources in the response `additional_context`, next to the primary chunks. Use them when two documents belong together (a contract and its addendum) but the text does not say so. The [context graph](/essentials/v2/context-graphs), by contrast, is derived from content. To declare the full entity graph inside one document instead of extracting it, use [Bring Your Own Graph](/essentials/v2/bring-your-own-graph).

For files, set `relations.ids` on the matching `document_metadata` item. For app sources, prefer the app-native `relations[]` shape, so each link carries a predicate and a provider-aware target:

```json
{
  "relations": [
    {
      "predicate": "linked_to",
      "target": {
        "id": "auth-troubleshooting"
      }
    },
    {
      "predicate": "related_to",
      "target": {
        "external_id": "AUTH-FAQ",
        "provider": "notion"
      }
    }
  ]
}
```

<CodeGroup>
```python Python SDK
client.context.ingest(
    type="knowledge",
    database="acme_corp",
    app_knowledge=json.dumps([
        {
            "database": "acme_corp",
            "collection": "default",
            "id": "auth-guide",
            "title": "Authentication Guide",
            "type": "notion",
            "kind": "knowledge_base",
            "provider": "notion",
            "external_id": "AUTH-GUIDE",
            "fields": {"kind": "knowledge_base", "title": "Authentication Guide", "body": "..."},
            "relations": [
                {"predicate": "linked_to", "target": {"id": "auth-troubleshooting"}},
                {"predicate": "related_to", "target": {"external_id": "AUTH-FAQ", "provider": "notion"}},
            ],
        }
    ]),
)
```
```typescript TypeScript SDK

      id: "auth-guide",

      kind: "knowledge_base",
      provider: "notion",
      external_id: "AUTH-GUIDE",
      fields: { kind: "knowledge_base", title: "Authentication Guide", body: "..." },
      relations: [
        { predicate: "linked_to", target: { id: "auth-troubleshooting" } },
        { predicate: "related_to", target: { external_id: "AUTH-FAQ", provider: "notion" } },
      ],
    },
  ]),
});
```
```bash cURL

  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \

  -F "database=acme_corp" \

    {
      "id": "auth-guide",
      "title": "Authentication Guide",
      "type": "notion",
      "kind": "knowledge_base",
      "provider": "notion",
      "external_id": "AUTH-GUIDE",
      "fields": { "kind": "knowledge_base", "title": "Authentication Guide", "body": "..." },
      "relations": [
        { "predicate": "linked_to", "target": { "id": "auth-troubleshooting" } },
        { "predicate": "related_to", "target": { "external_id": "AUTH-FAQ", "provider": "notion" } }
      ]
    }
  ]'
```
</CodeGroup>

On the [query request](/api-reference/v2/endpoint/query), `query_forceful_relations` defaults to `true`. Send `false` to turn expansion off.

<Warning>
- **Same store only:** a knowledge item that points at a memory ID, or the reverse, silently returns nothing at query time.
- **`thinking` mode only:** linked sources are fetched only with `mode: "thinking"`, or `mode: "auto"` when it routes to thinking. In `fast` mode, `query_forceful_relations` is ignored even if `true`.
</Warning>

## 8. Metadata on knowledge

Attach [`metadata`](/essentials/v2/metadata) at ingest to filter on it at query time:

```json
{
  "metadata": { "document_type": "runbook", "environment": "production" }
}
```

Then at query time:

```json
{
  "query": "How do I rotate API keys?",
  "metadata_filters": { "document_type": "runbook", "environment": "production" }
}
```

- **Top-level filters:** declare each `metadata` key in the database schema with `enable_match: true`. A filter on an undeclared key is not ignored: in a database with a schema, ingest rejects undeclared keys, so the filter returns no results.
- **`additional_metadata`:** to filter on it, nest the keys under `additional_metadata` in `metadata_filters`, for example `{"metadata_filters": {"additional_metadata": {"author": "Alice"}}}`. Nested filters are slower than schema-backed ones, so put keys you filter on often in `metadata`. `document_metadata` is accepted only as a legacy alias for that nested namespace.

Schema design and filter examples: [Metadata](/essentials/v2/metadata). Schema field options (`enable_match`, `enable_dense_embedding`, `enable_sparse_embedding`): [Create Database](/api-reference/v2/endpoint/create-tenant).

## 9. Common mistakes

- **`document_metadata` sent as an object:** form validation fails. Send it as a JSON string in the `-F` field.
- **Omitting `database`:** returns `400` (`database is required`).
- **Querying with `type: "memory"`:** returns nothing from this store. Use `type: "knowledge"` or `"all"`.
