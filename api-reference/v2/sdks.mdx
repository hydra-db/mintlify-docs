The Python and TypeScript SDKs wrap every endpoint in the [API Reference](/api-reference/v2) with typed methods. They set the `API-Version: 2` header on every request. For a first end-to-end run, follow the [Quickstart](/get-started/v2/quickstart).

## Installation

Install version 2 of the Python or TypeScript SDK:

<CodeGroup>
```bash Python SDK
pip install "hydradb-sdk>=2.1.7,<3"
```
```bash TypeScript / Node.js
npm install @hydradb/sdk@^2.1.7
```
</CodeGroup>

BYOG SDK examples require Python `hydradb-sdk` 2.1.8 and TypeScript `@hydradb/sdk` 2.1.9 or later. Until those versions are available in your package registry, use the cURL examples on the BYOG endpoint pages.

## Client setup

<CodeGroup>
```python Python SDK
import os
from hydra_db import HydraDB

client = HydraDB(token=os.environ["HYDRADB_API_KEY"])
```
```python Python (Async)
import os
from hydra_db import AsyncHydraDB

async_client = AsyncHydraDB(token=os.environ["HYDRADB_API_KEY"])
```
```typescript TypeScript SDK
import { HydraDBClient } from "@hydradb/sdk";

const client = new HydraDBClient({
  token: process.env.HYDRADB_API_KEY,
});
```
</CodeGroup>

The Python SDK has a synchronous client (`HydraDB`) and an asynchronous one (`AsyncHydraDB`). They expose the same methods; use `AsyncHydraDB` with `await`.

## Naming conventions

The REST API and the Python SDK use snake_case. The TypeScript SDK uses camelCase for multi-word method names and for fields in typed request and response objects.

| | Method naming | Parameter field naming | Example |
|---|---|---|---|
| **Raw HTTP / cURL** | N/A | snake_case | `database`, `collection`, `query_by` |
| **Python SDK** | snake_case | snake_case | method: `query()`, params: `database`, `query_by` |
| **TypeScript SDK** | camelCase for multi-word methods | camelCase | method: `query()`, params: `database`, `queryBy` |

In TypeScript:

- **Typed fields are camelCase only.** Use `client.context.list({ database: "...", pageSize: 50 })`. The SDK sends `page_size` to the API and drops unrecognized typed fields, including a caller-supplied `page_size`.
- **JSON strings and free-form maps are sent as written.** Inside JSON strings (`context`, `documentMetadata`) and free-form maps (`metadataFilters`, and in Python a connector resource update's `request`), use REST field names such as `context_id`, `custom_attributes`, or `additional_metadata`, and preserve your own metadata keys.
- **Response fields are camelCase and optional in the types.** Read them as `status.data?.infra?.readyForIngestion`.

`database` and `collection` are the current field names. The former names, `tenant_id` and `sub_tenant_id`, are still accepted as deprecated aliases. See [Databases and Collections](/essentials/v2/databases-and-collections#7-migrating-from-the-legacy-tenant-and-sub-tenant-fields).

## Method reference

Methods are grouped under one namespace per API group: `client.context`, `client.databases`, `client.connectors`, `client.webhooks`, `client.feedback`, and `client.byog`. `client.query()` and `client.list_providers()` sit on the client itself. The tables use the Python method names. TypeScript uses camelCase for multi-word ones (`list_resources()` is `listResources()`).

## Common calls

These examples show the SDK call shape for each step of an integration, in both languages. The [Quickstart](/get-started/v2/quickstart) explains the flow end to end.

### Create a database

<CodeGroup>
```python Python SDK
response = client.databases.create(
    database="my_first_database",
    database_metadata_schema=[
        {"name": "department", "data_type": "VARCHAR"},
    ],
)
```
```python Python (Async)
import asyncio

async def create_database():
    return await async_client.databases.create(
        database="my_first_database",
        database_metadata_schema=[{"name": "department", "data_type": "VARCHAR"}],
    )

response = asyncio.run(create_database())
```
```typescript TypeScript SDK
const response = await client.databases.create({
  database: "my_first_database",
  databaseMetadataSchema: [
    { name: "department", dataType: "VARCHAR" },
  ],
});
```
</CodeGroup>

Database creation is asynchronous. Poll [`databases.status`](/api-reference/v2/endpoint/database-status) until provisioning completes:

<CodeGroup>
```python Python SDK
import time

while True:
    status = client.databases.status(database="my_first_database")
    if status.data.infra.ready_for_ingestion:
        break
    time.sleep(2)
```
```typescript TypeScript SDK
while (true) {
  const status = await client.databases.status({
    database: "my_first_database",
  });
  // Response fields are optional in the TypeScript types.
  if (status.data?.infra?.readyForIngestion) break;
  await new Promise((r) => setTimeout(r, 2000));
}
```
</CodeGroup>

### Ingest context

Send text and conversations as a list of `context` items. In the SDKs, `context` is a JSON string:

<CodeGroup>
```python Python SDK
import json

result = client.context.ingest(
    database="my_first_database",
    collection="user_alex",
    context=json.dumps([
        {
            "context_id": "alex_preferences",
            "title": "Alex's preferences",
            "text": "User prefers detailed technical explanations and dark mode",
            "user_name": "Alex",
            "custom_attributes": {"source": "onboarding"},
        }
    ]),
)
```
```typescript TypeScript SDK
const result = await client.context.ingest({
  database: "my_first_database",
  collection: "user_alex",
  context: JSON.stringify([
    {
      context_id: "alex_preferences",
      title: "Alex's preferences",
      text: "User prefers detailed technical explanations and dark mode",
      user_name: "Alex",
      custom_attributes: { source: "onboarding" },
    },
  ]),
});
```
</CodeGroup>

`enrich` defaults to `true`, so HydraDB derives implicit preferences and facts from each item. Set `enrich: false` on an item to skip that step. Send a chat as `conversation`, a list of `{ role, content }` turns, instead of `text`. See [Ingest Context](/api-reference/v2/endpoint/ingest-context#context-item-fields) for every item field.

<Note>
The `context` argument ships in the SDK release that follows 2.1.7. On an earlier SDK, send `context` with any HTTP client, or upgrade.
</Note>

### Ingest files

Upload files with the same method. `document_metadata` is a JSON string with one entry per file:

<CodeGroup>
```python Python SDK
import json

with open("contract.pdf", "rb") as f1, open("policy.pdf", "rb") as f2:
    result = client.context.ingest(
        database="my_first_database",
        collection="company_docs",
        documents=[
            ("contract.pdf", f1, "application/pdf"),
            ("policy.pdf", f2, "application/pdf"),
        ],
        document_metadata=json.dumps([
            {
                "id": "contract_q4",
                "metadata": {"department": "legal"},
                "additional_metadata": {"author": "Alice"},
            },
            {
                "id": "policy_2025",
                "metadata": {"department": "legal"},
                "additional_metadata": {"author": "Bob"},
            },
        ]),
    )
```
```typescript TypeScript SDK
const result = await client.context.ingest({
  database: "my_first_database",
  collection: "company_docs",
  documents: [
    { path: "contract.pdf", filename: "contract.pdf", contentType: "application/pdf" },
    { path: "policy.pdf", filename: "policy.pdf", contentType: "application/pdf" },
  ],
  documentMetadata: JSON.stringify([
    {
      id: "contract_q4",
      metadata: { department: "legal" },
      additional_metadata: { author: "Alice" },
    },
    {
      id: "policy_2025",
      metadata: { department: "legal" },
      additional_metadata: { author: "Bob" },
    },
  ]),
});
```
</CodeGroup>

Send files and `context` items in separate calls. `metadata` here assumes the database declares `department` in its `database_metadata_schema`.

### Wait for indexing

Items are searchable only after indexing. Check each collection separately, using the IDs supplied at ingestion or returned in `data.results`.

<CodeGroup>
```python Python SDK
import time

def wait_for_indexing(collection, ids):
    while True:
        result = client.context.status(
            database="my_first_database", collection=collection, ids=ids,
        )
        statuses = [item.indexing_status for item in result.data.statuses]
        if any(status == "errored" for status in statuses):
            raise RuntimeError("Indexing failed; check the status response for details.")
        if len(statuses) == len(ids) and all(status == "completed" for status in statuses):
            return
        time.sleep(2)

wait_for_indexing("company_docs", ["contract_q4", "policy_2025"])
wait_for_indexing("user_alex", ["alex_preferences"])
```
```typescript TypeScript SDK
async function waitForIndexing(collection: string, ids: string[]) {
  while (true) {
    const result = await client.context.status({
      database: "my_first_database", collection, ids,
    });
    const statuses = result.data?.statuses?.map((item) => item.indexingStatus) ?? [];
    if (statuses.some((status) => status === "errored")) {
      throw new Error("Indexing failed; check the status response for details.");
    }
    if (statuses.length === ids.length && statuses.every((status) => status === "completed")) return;
    await new Promise((resolve) => setTimeout(resolve, 2000));
  }
}

await waitForIndexing("company_docs", ["contract_q4", "policy_2025"]);
await waitForIndexing("user_alex", ["alex_preferences"]);
```
</CodeGroup>

## Response envelope

All responses, except those from connector endpoints and `PATCH /databases/{database}/metadata-schema`, are wrapped in the [response envelope](/api-reference/v2/error-responses#response-envelope):

```json
{
  "success": true,
  "data": {
    "message": "Success"
  },
  "error": null,
  "meta": {
    "request_id": "<uuid>",
    "latency_ms": 12.3
  }
}
```

The SDKs return the full envelope. Read the payload from the `data` field (for example, `response.data`). On failure, the SDK raises a typed exception; it does not return an envelope with `error` populated.

### Model names in the API reference

The API reference displays the SDK model names for named objects across endpoints. Expand **Show child attributes** to see each model's fields. The `object` or `object[]` annotation alongside a model name describes its JSON representation, not an untyped SDK return value. The reference does not invent separate names such as `Result object` or `Alias expansion.object`.

| Response value | Model shown in the reference and SDKs |
|---|---|
| Query `data`, for structured results | `SearchV2RetrievalResult` |
| Query `data.alias_expansions` elements | `SearchAliasExpansionNote` |
| List Context `data` | `ListV2ListResponse` |

Python exposes these models from `hydra_db.types`; TypeScript exposes them in the `HydraDB` namespace from `@hydradb/sdk`. Python fields use snake_case (`alias_expansions`), while TypeScript fields use camelCase (`aliasExpansions`). Query `data` can also be a string when `response_format` is `markdown`, so narrow that union before reading structured fields.

Maps you define, such as `metadata` and `additional_metadata`, allow arbitrary keys and values, so their contents have no fixed property autocomplete. The surrounding response and its known fields still have declared types. Improvements to the generated models reach you only when you install an SDK release that includes them.

## Error handling

Both SDKs raise an exception for a non-2xx response. The exception exposes the envelope's `error` payload:

<CodeGroup>
```python Python SDK
from hydra_db.core.api_error import ApiError
from hydra_db.errors import NotFoundError

try:
    result = client.query(
        database="my_first_database",
        query="...",
    )
except NotFoundError:
    # Handle missing database / resource (HTTP 404)
    pass
except ApiError as exc:
    if exc.status_code == 429:
        # Rate limit: retry with backoff
        pass
    else:
        raise
```

```typescript TypeScript SDK
import { HydraDBError } from "@hydradb/sdk";

try {
  const result = await client.query({
    database: "my_first_database",
    query: "...",
  });
} catch (error) {
  if (error instanceof HydraDBError) {
    // error.body is typed `unknown`; it holds the raw snake_case error envelope.
    const code = (error.body as { error?: { code?: string } } | undefined)?.error?.code;

    if (code === "DATABASE_NOT_FOUND") {
      // Handle missing database
    } else if (error.statusCode === 429) {
      // Rate limit: retry with backoff
    } else {
      throw error;
    }
  } else {
    throw error;
  }
}
```
</CodeGroup>

The Python SDK raises a typed exception per status from `hydra_db.errors`. Each subclasses `ApiError` and carries `status_code`, `headers`, and the parsed response `body`, from which you can read `body["error"]["code"]`.

Not every status has its own class: `401` and `429` do not. To handle those, catch the base `ApiError` and branch on `status_code`, as above.

Both SDKs retry some failures automatically. See [Error Responses](/api-reference/v2/error-responses#retry-pattern) for the retry rules and the full list of error codes.
