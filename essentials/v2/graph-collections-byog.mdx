This is Bring Your Own Graph (BYOG) as a graph database: you model the schema and write the Cypher, and HydraDB stores the graph and runs your queries. It suits teams moving a property-graph workload (for example from Neo4j) who want to keep their Cypher and data model. To attach your own entities and relations to one ingested document, app source, or memory instead, see [Bring Your Own Graph: per source](/essentials/v2/bring-your-own-graph).

- **Databases:** group your collections. A BYOG database shows up in your dashboard and in the standard database APIs like any other HydraDB database.
- **Collections:** independent graphs inside a database. A query runs against exactly one collection, and collections never see each other's data.
- **Full Cypher:** reads and writes (`CREATE`, `MERGE`, `MATCH`, `SET`, `DELETE`) and graph traversal. Your query is sent verbatim. HydraDB never rewrites it.
- **Structural isolation:** each collection is a separate graph owned by your organization, so `MATCH (n) RETURN n` returns *your* nodes and nothing else.

## Quickstart

```bash
BASE=https://api.hydradb.com
KEY=<your API key>

# 1. Create a database (ready immediately)
curl -X POST "$BASE/byog/databases" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"database": "crm"}'

# 2. Write data - collections auto-create on first use
curl -X POST "$BASE/byog/query" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
    "database": "crm",
    "collection": "contacts",
    "query": "UNWIND $rows AS row CREATE (p:Person) SET p = row RETURN count(p) AS created",
    "params": {"rows": [{"name": "Alice", "role": "admin"},
                        {"name": "Bob",   "role": "analyst"}]}
  }'

# 3. Read it back
curl -X POST "$BASE/byog/query" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
    "database": "crm",
    "collection": "contacts",
    "query": "MATCH (p:Person) RETURN p.name AS name, p.role AS role ORDER BY name"
  }'
```

## Authentication

Every request needs your HydraDB API key:

```
Authorization: Bearer <api key>
```

A missing or invalid key returns `401`. Databases are scoped to the organization that owns the key. Another organization's database names behave exactly like names that do not exist.

## Endpoints

### `POST /byog/databases`: create a database

```json
{ "database": "crm" }
```

Returns immediately with `{"database": "crm", "status": "ready"}`, with no provisioning wait. A name that already exists returns `409`.

It also shows up like any other database: `GET /databases` lists it, `GET /databases/status` reports it ready, `GET /databases/collections` includes its collections, and the dashboard shows it. The standard `DELETE /databases` flow removes its graph collections too.

A BYOG database holds only Cypher graphs. Sending it to `/context/ingest` or `/query` returns `400` with the error code `BYOG_DATABASE`.

### `POST /byog/query`: run Cypher

```json
{
  "database":   "crm",
  "collection": "contacts",
  "query":      "CREATE (n:Person {name: $name}) RETURN n",
  "params":     { "name": "Alice" }
}
```

- **Collections auto-create:** the first write creates the collection. There is no create-collection call. Reading a collection you never wrote to returns zero rows.
- **Names:** collection names must match `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`. Database names have no charset restriction.
- **Parameters:** pass user data through `params`, not in the query string. Parameters are bound safely and keep query plans cacheable.
- **Body size:** capped at **256 KiB** (`413` beyond that). For bulk loads, send batches of rows with `UNWIND $rows AS row CREATE ...`.

### `GET /byog/collections?database=crm`: list collections

Returns the collection names in the database. An unknown database returns `404`.

### `DELETE /byog/collections`: drop one collection

```json
{ "database": "crm", "collection": "contacts" }
```

Drops the collection and all its data. Deleting a collection that does not exist succeeds (idempotent).

### `DELETE /byog/databases`: drop a database

```json
{ "database": "crm" }
```

Drops every collection in the database. For a database created through `POST /byog/databases`, it also removes the database itself and lists what was removed:

```json
{ "database": "crm", "deleted": true, "deleted_collections": ["contacts"] }
```

For a database created through the standard database API (with only graph collections), only the collections are dropped and `deleted` is `false`. Delete the database with the standard `DELETE /databases`.

## Supported Cypher

<Note>
  Essentially all of openCypher is supported. Only server-side procedures and file loading are excluded.
</Note>

**Modelling and CRUD:** pattern matching, aggregation, `UNWIND`, `WITH` pipelines, `MERGE`, indexes (`CREATE INDEX FOR (n:Label) ON (n.prop)`), and `CALL { ... }` subqueries.

**Graph traversal:**

- **Multi-hop patterns:** chain as many hops as you need in one `MATCH`.
- **Variable-length traversal:** a bounded or unbounded number of hops with `*`, such as `[:KNOWS*1..4]` for everyone within four degrees.
- **Neighborhood expansion:** a node's edges and neighbors in one query, in any direction.
- **Path finding:** `shortestPath` returns the actual path (nodes and edges in traversal order), not just the endpoints. See [Relationships and paths](#relationships-and-paths).
- **Directed, typed, filtered traversal:** outgoing (`->`), incoming (`<-`), or either (`-`) edges, relationship type filters (`[:KNOWS]`), and node or edge property constraints anywhere along the walk.

The [traversal examples](#traversal-examples) show each pattern.

<Warning>
  Two constructs are rejected *before the query runs* with a `400` that explains why. **Nothing is executed:** no partial writes, no side effects. It is a validation error, so retrying the same query fails the same way until you change it.

  - **Procedure calls:** `CALL some.procedure(...)`. Procedures are engine-specific internals that HydraDB does not commit to supporting. (`CALL { ... }` *subqueries* are fine.)
  - **`LOAD CSV`:** server-side file or URL loading. Send data through `params` instead.
</Warning>

Dialect notes:

- **Existence checks:** use bare pattern predicates, such as `MATCH (p:Person) WHERE (p)-[:KNOWS]->() RETURN p.name AS name`. The `EXISTS { ... }` block form and the `exists()` function are not accepted.
- **`shortestPath`:** put it in a `RETURN` or `WITH` clause (not `MATCH p = …`). The traversal must be directed.

### Traversal examples

```cypher Expand a node's neighborhood
-- Every relationship on Alice and the node on the other end, in any direction.
MATCH (p:Person {name: $name})-[r]-(nbr)
RETURN type(r) AS rel, labels(nbr) AS kind, nbr.name AS neighbor
ORDER BY rel, neighbor
```

```cypher Multi-hop relationship expansion
-- Friends-of-friends up to 3 hops away, following only outgoing KNOWS edges.
MATCH (a:Person {name: $name})-[:KNOWS*1..3]->(reach:Person)
WHERE reach.name <> $name
RETURN DISTINCT reach.name AS name
ORDER BY name
```

```cypher Shortest path between two nodes
-- The actual path (nodes + edges in order), not just the endpoints.
MATCH (a:Person {name: $from}), (b:Person {name: $to})
RETURN shortestPath((a)-[:KNOWS*..8]->(b)) AS path
```

```cypher Filtered, typed traversal
-- Who does Alice know that works at a company in "fintech"?
MATCH (a:Person {name: $name})-[:KNOWS]->(f:Person)-[:WORKS_AT]->(c:Company)
WHERE c.sector = "fintech"
RETURN f.name AS person, c.name AS company
```

## Response format

Successful calls return the standard HydraDB envelope:

```json
{
  "success": true,
  "data": [ ... ],
  "error": null,
  "meta": { "request_id": "9be86a4e-…", "latency_ms": 12.4 }
}
```

For `POST /byog/query`, `data` is always a JSON **array of row objects**, one per row, keyed by your `RETURN` column names. Unaliased expressions use the expression text as the key, so **alias everything you plan to parse** (`RETURN n.name AS name`). A pure write with no `RETURN` returns `data: []`, which is a success.

### How values are rendered

- **String, boolean, null:** JSON string, boolean, null.
- **Integer:** JSON number. Graph integers are 64-bit. Values beyond 2⁵³ lose precision in languages that parse numbers as doubles, so keep your own ids inside the safe range or return them as strings.
- **Float:** JSON number.
- **List, map:** JSON array, object (rendered recursively).
- **Node:** object with all node properties, plus `id` and `labels`.
- **Relationship:** object with all relationship properties, plus `id`, `relation`, `source_node_id`, `target_node_id`.
- **Path:** `{ "nodes": [...], "edges": [...] }` in traversal order.

Example, `RETURN n` where `n` is a node:

```json
{ "data": [ { "n": { "id": 0, "labels": ["Person"], "name": "Alice", "age": 34 } } ] }
```

About ids:

- The renderer adds the `id`, `labels`, `relation`, `source_node_id`, and `target_node_id` keys. A stored property with one of those names is shadowed in the *response* (the stored value is unaffected). Avoid those names, or alias explicitly (`RETURN n.id AS my_id`).
- `id` values are internal and stable only within the life of a collection. They can be reused after deletions and do not survive an export and re-import. Treat `id` as opaque, never store it, and key your application on a property you own (`ext_id`, `email`, …).

## Using results in your code

These patterns are in Python and TypeScript, but port to any language.

### A minimal client

Wrap the endpoint once. Rows are in `data`. The examples read the error code and message from `detail`. `error.code` and `error.message` carry the same values.

```python
import requests

class HydraGraph:
    def __init__(self, base_url, api_key, database, collection="default"):
        self.base, self.db, self.col = base_url, database, collection
        self.headers = {"Authorization": f"Bearer {api_key}"}

    def query(self, cypher, params=None):
        r = requests.post(f"{self.base}/byog/query", headers=self.headers, json={
            "database": self.db, "collection": self.col,
            "query": cypher, "params": params or {},
        })
        body = r.json()
        if not r.ok:
            err = body.get("detail", {})
            raise RuntimeError(f"{r.status_code} {err.get('error_code')}: {err.get('message')}")
        return body["data"]          # always a list of row dicts

g = HydraGraph("https://api.hydradb.com", "<api key>", "crm", "contacts")
```

```typescript
async function query(cypher: string, params: object = {}): Promise<Record<string, any>[]> {
  const res = await fetch(`${BASE}/byog/query`, {
    method: "POST",
    headers: { Authorization: `Bearer ${KEY}`, "Content-Type": "application/json" },
    body: JSON.stringify({ database: "crm", collection: "contacts", query: cypher, params }),
  });
  const body = await res.json();
  if (!res.ok) throw new Error(`${res.status} ${body.detail?.error_code}: ${body.detail?.message}`);
  return body.data;                 // always an array of row objects
}
```

### Prefer aliased scalars

Shape results in the query: return exactly the fields you need, aliased, instead of whole nodes.

```python
rows = g.query("MATCH (p:Person) RETURN p.name AS name, p.role AS role ORDER BY name")
# rows == [{"name": "Alice", "role": "admin"}, {"name": "Bob", "role": "analyst"}]
names = [r["name"] for r in rows]
```

These queries keep returning the same shape as nodes gain properties.

### When you do return nodes

A returned node is one flat object, its properties merged with `id` and `labels`:

```python
rows = g.query("MATCH (p:Person {name: $n}) RETURN p", {"n": "Alice"})
alice = rows[0]["p"]        # {"id": 0, "labels": ["Person"], "name": "Alice", "role": "admin"}
props = {k: v for k, v in alice.items() if k not in ("id", "labels")}
```

### Relationships and paths

A relationship carries its endpoints as `source_node_id` / `target_node_id`, which match the `id` of nodes returned **in the same query**. Return both sides and join client-side:

```python
rows = g.query("""
    MATCH (a:Person)-[k:KNOWS]->(b:Person)
    RETURN a, k, b
""")
for row in rows:
    print(f'{row["a"]["name"]} knows {row["b"]["name"]} since {row["k"]["since"]}')
```

A path comes assembled: `nodes` and `edges` in traversal order. Follow the `shortestPath` dialect rules above (`RETURN` or `WITH`, directed `->`):

```python
rows = g.query("""
    MATCH (a:Person {name:$x}), (b:Person {name:$y})
    RETURN shortestPath((a)-[*..6]->(b)) AS p
""", {"x": "Alice", "y": "Bob"})
hops = [n["name"] for n in rows[0]["p"]["nodes"]]   # ["Alice", ..., "Bob"]
```

### Pagination

Rows past the deployment's result-set cap are silently dropped, so page any read that *could* be large. A stable `ORDER BY` keeps pages consistent:

```python
def all_rows(cypher_body, page=500, params=None):
    offset = 0
    while True:
        rows = g.query(f"{cypher_body} SKIP $offset LIMIT $limit",
                       {**(params or {}), "offset": offset, "limit": page})
        yield from rows
        if len(rows) < page:
            return
        offset += page

people = list(all_rows("MATCH (p:Person) RETURN p.name AS name ORDER BY name"))
```

### Bulk loading

Chunk rows to fit the 256 KiB body cap and the 30 s write budget. `MERGE` on your own key makes the load safe to re-run after a failure:

```python
def load(rows, chunk=500):
    for i in range(0, len(rows), chunk):
        g.query("""
            UNWIND $rows AS row
            MERGE (n:Person {ext_id: row.ext_id})
            SET n += row
        """, {"rows": rows[i:i+chunk]})
```

### Handling failures

- **`400`:** fix the Cypher, or add a `LIMIT` or an index after a budget timeout. Retrying unchanged fails the same way.
- **`429` or `500`:** transient. Back off and retry. `MERGE` writes (as above) are safe to retry. Bare `CREATE` batches are not idempotent, so a retried chunk can duplicate nodes. Key on your own id.

## Errors

Errors use the standard HydraDB error envelope, with the code and message mirrored in a `detail` object:

```json
{
  "success": false,
  "data": null,
  "error": { "code": "…", "message": "…" },
  "meta": { "request_id": "…" },
  "detail": { "success": false, "message": "…", "error_code": "…" }
}
```

- `400`: invalid request (missing fields, bad collection name), unsupported construct, **Cypher errors** (the compiler's message is passed through), or **query timeout**.
- `401`: missing or invalid API key.
- `404`: unknown database. Create it with `POST /byog/databases`.
- `409`: `POST /byog/databases` with a name that already exists.
- `413`: request body over 256 KiB.
- `429`: rate limit exceeded.
- `500`: something failed on our side. Nothing for you to fix.
- `503`: the database's dedicated graph cluster is still being provisioned. Retry after the `Retry-After` interval.

## Limits & timeouts

| Limit | Value | On exceeding |
|---|---|---|
| Request body | 256 KiB | `413` |
| Read query execution | 8 s | `400`: "query exceeded the execution time budget; simplify it, add LIMIT, or create an index" |
| Write query execution | 30 s | same `400` |
| Result set size | deployment-configured cap; rows beyond it are **silently dropped** | no error, so paginate |

A query counts as a **write**, and gets the larger budget, when it contains any write clause: `CREATE`, `MERGE`, `SET`, `DELETE`, `REMOVE`, or `FOREACH`.

- **Paginate** large reads with `ORDER BY … SKIP $offset LIMIT $page` ([Pagination](#pagination)). Without an `ORDER BY`, the rows dropped at the cap are arbitrary.
- **Chunk bulk imports** into `UNWIND $rows` batches ([Bulk loading](#bulk-loading)).
- **Create indexes** for properties you filter on, for example `CREATE INDEX FOR (n:Person) ON (n.name)`. A long-running read is usually missing one.

## Migrating from Neo4j

Most application Cypher ports directly. The differences you are most likely to notice:

- `CALL db.*` and `CALL apoc.*` procedures are not available. The equivalents are plain Cypher or outside the supported surface.
- `LOAD CSV` is not available. Batch data in through `params`.
- Internal node ids are not portable (true in Neo4j as well). Migrate on your own key properties, for example `UNWIND $rows AS row MERGE (n:Person {ext_id: row.ext_id}) SET n += row`.

One collection is a natural migration unit: export a graph, replay it into one collection, verify, repeat.
