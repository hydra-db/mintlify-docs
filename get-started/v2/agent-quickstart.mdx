HydraDB's agent documentation is designed for progressive disclosure: start with a small routing skill, then load only the ingestion, query, modeling, or debugging contract needed for the current task. This keeps context focused and reduces plausible-looking code built from the wrong API version.

```bash
npx skills add https://docs.hydradb.com
```

## Pick the right surface

| Surface | Best for | Entry point |
|---|---|---|
| Agent skills | Durable instructions your coding agent can load on demand | `npx skills add https://docs.hydradb.com` |
| Documentation MCP | Live search and page retrieval from the current docs | `https://docs.hydradb.com/mcp` |
| Markdown pages | Direct context for an agent or prompt | Add `.md` to any documentation URL |
| Full agent reference | Broad architecture and API orientation | [`https://docs.hydradb.com/AGENTS.md`](https://docs.hydradb.com/AGENTS.md) |

<Note>
  The documentation MCP server above searches these docs. It is different from the [HydraDB product MCP](/plugins/mcp), which lets an agent store and retrieve memories at runtime.
</Note>

## Give an agent live documentation access

Add the documentation MCP endpoint to a compatible coding client. For example, an HTTP-capable MCP configuration uses:

```json
{
  "mcpServers": {
    "hydradb-docs": {
      "url": "https://docs.hydradb.com/mcp"
    }
  }
}
```

Client configuration formats vary. If a client supports remote MCP servers through a command instead of a URL, use the client's documented remote-server adapter.

## The contract agents must preserve

| Layer | Request fields | Response fields | Version handling |
|---|---|---|---|
| Raw HTTP | `snake_case` | Successful envelope payloads use `snake_case` under `.data` | Send `API-Version: 2` |
| Python SDK | `snake_case` | Successful envelope payloads use `snake_case` under `.data` | SDK sends v2 automatically |
| TypeScript SDK | `camelCase` | Successful envelope payloads use `camelCase` under `.data` | SDK sends v2 automatically |

<Warning>
  Do not mechanically copy raw OpenAPI field names into TypeScript. For example, raw HTTP and Python use `max_results` and `metadata_filters`; TypeScript uses `maxResults` and `metadataFilters`.
</Warning>

## A high-signal prompt

Use this when asking an agent to implement a HydraDB feature:

<Prompt description="Give this contract to your coding agent before it changes a HydraDB integration." actions={["copy", "cursor"]}>
Use the HydraDB skills and API v2. First state the database, collection,
content type, and retrieval mode you chose. Preserve the language-specific
field naming contract. Poll database readiness and ingestion completion,
read results from .data, and treat empty context as a valid outcome.
Before finishing, verify every endpoint and field against the v2 reference.
</Prompt>

## Verify before shipping

An integration is not complete until it proves this sequence:

<Steps>
  <Step title="Scope">
    Name the database and collection used for both ingestion and retrieval.
  </Step>
  <Step title="Readiness">
    Poll database status until it is ready for ingestion.
  </Step>
  <Step title="Processing">
    Poll each ingested ID until indexing completes; stop on a terminal failure or timeout.
  </Step>
  <Step title="Retrieval">
    Query the same scope and intentionally choose `type`, `query_by`, and `mode`.
  </Step>
  <Step title="Grounding">
    Build the answer from returned chunks and graph context, preserve citations, and say when evidence is missing.
  </Step>
</Steps>

## Agent-only completion contract

Load the smallest focused HydraDB skill that covers the task. Before returning code, verify every REST method and path against the v2 API reference, preserve the language-specific field naming contract, and check that write and read scopes match. Report the chosen database, collection, content type, query mode, readiness behavior, failure behavior, and grounding behavior. If any of those are unknown, label the assumption instead of silently inventing it.
