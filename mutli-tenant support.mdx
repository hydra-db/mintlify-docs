# Multi-Tenant Support

## What it is

HydraDB is multi-tenant by default. Every piece of data — memories and knowledge — is scoped by a `tenant_id` and, optionally, a `sub_tenant_id`. In simple terms: `tenant_id` is the primary scoping unit, while `sub_tenant_id` is used to scope data to users, workspaces, or other logical partitions within a tenant.

This gives you two scoping levels: a primary scope at the tenant level, and a secondary scope for users, workspaces, or teams inside a single tenant. Isolation behavior at each level is not assumed here — see the TODOs below.

## What it does

Multi-tenancy controls what data is in scope during recall and write operations:

- `tenant_id` — the primary scoping unit in HydraDB. Required on every write and every recall.
- `sub_tenant_id` — a secondary scope within a tenant. Used for scoping and filtering memories, and optionally knowledge.

Used correctly, this lets you separate data per customer and, within a customer, per user or workspace.

---

## When to use it

Use `tenant_id` to separate:

- Different customers on your platform
- Different environments (e.g. `acme_prod` vs `acme_staging`)

Use `sub_tenant_id` to scope:

- Individual users (B2C) — `sub_tenant_id = user_id`
- Workspaces or teams (B2B) — `sub_tenant_id = workspace_id`
- Any logical scope where data should be partitioned within a tenant

---

## How it works

**Memories** are typically scoped by `sub_tenant_id`. `recall_preferences` filters memories using `sub_tenant_id`.

**Knowledge** is configurable per ingest. You can upload knowledge as:

- **Tenant-associated** — typical behavior when `sub_tenant_id` is omitted at ingest. The exact storage scope is not assumed beyond this.
- **Sub-tenant-scoped** — by passing a specific `sub_tenant_id` at ingest.

**Recall** uses these scopes as follows:

- `recall_preferences` — requires `tenant_id`; filters memories using `sub_tenant_id`.
- `full_recall` — requires `tenant_id`. `sub_tenant_id` is optional; when provided, it may be used to filter knowledge to that sub-tenant scope.

For personalized responses, call both endpoints with matching `tenant_id` and `sub_tenant_id` values and merge the results yourself. Do not assume the system will combine memory and knowledge scopes for you.

<Warning>
  Inconsistent use of `sub_tenant_id` between writes and reads can cause data to land in the wrong scope or fail to surface. Always use the same `sub_tenant_id` value across write and recall operations for the same logical scope. Do not assume the system will auto-correct or reconcile mismatched scopes.
</Warning>

## Key concepts

**`tenant_id`**
The primary scoping unit in HydraDB. Required on every write and every recall.

**`sub_tenant_id`**
Secondary scope within a tenant. Optional on writes and on `full_recall`. Used by `recall_preferences` to filter memories to a specific user or workspace.

**Memory scoping**
Memories are typically scoped by `sub_tenant_id`. Use the same `sub_tenant_id` on writes and reads to retrieve the right user's or workspace's memories.

**Knowledge scoping**
Configurable at ingest time. Knowledge can be ingested as tenant-associated or scoped to a specific `sub_tenant_id`.

## Minimal working example

> Illustrative usage patterns only. The snippets below show how to call the API with different scopes; they do not imply guarantees about storage layout, retrieval merging, or fallback behavior.

**Per-user memory (B2C)**

Write a memory scoped to a single user:

```python
client.memories.add_memory(
    tenant_id="acme_corp",
    sub_tenant_id="user_123",
    memories=[{"text": "Prefers dark mode."}],
    upsert=True,
)
```

Retrieve it back for the same user:

```python
client.recall.recall_preferences(
    tenant_id="acme_corp",
    sub_tenant_id="user_123",
    query="UI preferences",
)
```

**Tenant-associated knowledge**

Ingest knowledge intended for the whole tenant (omitting `sub_tenant_id`):

```python
client.knowledge.upload_knowledge(
    tenant_id="acme_corp",
    # sub_tenant_id omitted
    documents=[...],
)
```

Recall it without specifying a sub-tenant:

```python
client.recall.full_recall(
    tenant_id="acme_corp",
    query="refund policy",
)
```

**Sub-tenant-scoped knowledge**

Ingest knowledge scoped to a specific workspace:

```python
client.knowledge.upload_knowledge(
    tenant_id="acme_corp",
    sub_tenant_id="workspace_42",
    documents=[...],
)
```

Retrieve it by passing the same `sub_tenant_id` on recall:

```python
client.recall.full_recall(
    tenant_id="acme_corp",
    sub_tenant_id="workspace_42",
    query="internal runbook",
)
```

## Common mistakes

**Inconsistent `sub_tenant_id` between write and read**
A memory written under one `sub_tenant_id` may not surface when read under a different value. Use the same `sub_tenant_id` consistently across writes and recalls for the same logical scope. Do not rely on the system to merge or reconcile mismatched scopes.

**Confusing `tenant_id` and `sub_tenant_id`**
`tenant_id` is the primary scoping unit — use it for customers and environments. `sub_tenant_id` is a secondary scope within a tenant. Swapping them breaks scoping assumptions.

**Assuming memory and knowledge scope the same way**
Memory is typically scoped by `sub_tenant_id`. Knowledge can be tenant-associated or sub-tenant-scoped depending on how it was ingested. Do not assume symmetry.

**Assuming automatic merging across scopes**
A single recall call is not assumed to combine tenant-associated and sub-tenant-scoped data. If you need both, issue separate calls and merge the results yourself.

**Mixing environments under one tenant**
Do not share a `tenant_id` across production and staging. Use separate tenants. `sub_tenant_id` is not an environment boundary.

**Treating `sub_tenant_id` formatting as forgiving**
Until normalization rules are confirmed, treat `sub_tenant_id` as exact-match. Do not rely on case-insensitive or whitespace-tolerant matching. Normalize identifiers at your application boundary before sending them to the API.
