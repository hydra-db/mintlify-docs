Bring Your Own Graph (BYOG) lets you use **Cypher** to read and write data in
[HydraDB's core graph database](https://github.com/hydra-db/hydradb), which we
host and scale in our cloud.

<Warning>
BYOG runs a **subset of Cypher**. Every node needs an integer `id`, and writes
must use the shapes in [Supported Cypher](#supported-cypher). Read that section
before you load data.
</Warning>

Migrating from an existing graph database? Start at
[Migrating from Neo4j or another Cypher-compatible database](#migrating-from-neo4j-or-another-cypher-compatible-database).
To bring your own entities and relations without writing Cypher, attach
them to a document at ingest; see
[Using BYOG without Cypher](#using-byog-without-cypher).

## How to use Cypher with HydraDB

### Quickstart

```bash
BASE=https://api.hydradb.com
KEY="your-api-key"

# 1. Create a database (ready immediately)
curl -X POST "$BASE/byog/databases" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"database": "crm"}'

# 2. Write data - the collection is created on first write.
#    Every node has an integer id. The label goes in SET.
curl -X POST "$BASE/byog/query" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
    "database": "crm",
    "collection": "contacts",
    "query": "UNWIND $rows AS row MERGE (p {id: row.id}) SET p:Person, p.name = row.name, p.role = row.role",
    "params": {"rows": [{"id": 1, "name": "Alice", "role": "admin"},
                        {"id": 2, "name": "Bob",   "role": "analyst"}]}
  }'

# 3. Read it back
curl -X POST "$BASE/byog/query" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
    "database": "crm",
    "collection": "contacts",
    "query": "MATCH (p:Person) RETURN p.name AS name, p.role AS role ORDER BY name"
  }'
```

Agents can run the same Cypher through the [HydraDB MCP](/plugins/mcp)
graph tools (`hydradb_graph_query`, `hydradb_graph_collections`, `hydradb_graph_admin`).

### Authentication

Every request needs your HydraDB API key:

```
Authorization: Bearer <api key>
```

A missing or invalid key returns `403`. Your databases are visible only to
your organization: another organization's databases look like names that
don't exist, and `MATCH (p:Person) RETURN p.name` returns only your own nodes.

### Endpoints

#### `POST /byog/databases`: create a database

A database groups your collections. Creating a database here makes it ready
immediately; a database created with the standard `POST /databases` can also
hold graph collections. Creating a name that already exists returns `409`.

<CodeGroup>
```bash Request
curl -X POST "$BASE/byog/databases" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"database": "crm"}'
```

```json Response
{
  "success": true,
  "data": { "database": "crm", "status": "ready", "cluster": "shared" },
  "error": null,
  "meta": { "request_id": "9280b5f7-…", "api_version": "2.0.1", "latency_ms": 90.8 }
}
```
</CodeGroup>

#### `POST /byog/query`: run Cypher

<CodeGroup>
```bash Request
curl -X POST "$BASE/byog/query" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
    "database": "crm",
    "collection": "contacts",
    "query": "MATCH (p:Person {id: $id}) RETURN p.name AS name, p.role AS role",
    "params": {"id": 1}
  }'
```

```json Response
{
  "success": true,
  "data": [
    { "name": "Alice", "role": "admin" }
  ],
  "error": null,
  "meta": { "request_id": "0f345406-…", "api_version": "2.0.1", "latency_ms": 42.4 }
}
```
</CodeGroup>

- Each collection is an isolated graph. A query runs against one collection
  and cannot see data in any other.
- Collections are created automatically on the first write. Reading a
  collection that doesn't exist yet returns zero rows.
- A write returns no rows (`data: []`). Run a read to see the result.
- Pass user data through `params` instead of building it into the query string.
- Collection names can use letters, digits, `_` and `-`, must start with a
  letter or digit, and can be up to 64 characters long.

#### `GET /byog/collections`: list collections

An unknown database returns `404`.

<CodeGroup>
```bash Request
curl "$BASE/byog/collections?database=crm" \
  -H "Authorization: Bearer $KEY"
```

```json Response
{
  "success": true,
  "data": { "database": "crm", "collections": ["contacts", "sample"] },
  "error": null,
  "meta": { "request_id": "d4744632-…", "api_version": "2.0.1", "latency_ms": 55.6 }
}
```
</CodeGroup>

#### `DELETE /byog/collections`: drop one collection

Drops the collection and all its data. Deleting a collection that does not
exist also succeeds.

- When the delete succeeds, the collection is removed from
  `GET /byog/collections`.
- A very large collection can need more than one call. If the call returns
  an error, call it again. The delete continues where it stopped. Until a
  call succeeds, the collection stays in the list.
- HydraDB keeps the storage of a deleted collection. The data is not
  available through the API after the delete.
- Do not write to a collection while you delete it. In rare cases, a write
  that runs at the same time as the delete can survive it.

<CodeGroup>
```bash Request
curl -X DELETE "$BASE/byog/collections" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"database": "crm", "collection": "contacts"}'
```

```json Response
{
  "success": true,
  "data": { "database": "crm", "collection": "contacts", "deleted": true },
  "error": null,
  "meta": { "request_id": "d7b2b080-…", "api_version": "2.0.1", "latency_ms": 131.1 }
}
```
</CodeGroup>

#### `DELETE /byog/databases`: drop a database

Drops the graph collections and, if created through `POST /byog/databases`, the database itself. For a database created through the standard database API, the graph collections are dropped, `deleted` is `false`, and the database stays. Use the standard `DELETE /databases` to remove that database. The rules for deleting a collection apply to each collection.

<CodeGroup>
```bash Request

  -d '{"database": "crm"}'
```

```json Response
{
  "success": true,
  "data": {
    "database": "crm",
    "cluster": "shared",
    "deleted": true,
    "deleted_collections": ["contacts", "sample"]
  },
  "error": null,
  "meta": { "request_id": "1ba6ecb8-…", "api_version": "2.0.1", "latency_ms": 130.8 }
}
```
</CodeGroup>

### Supported Cypher

BYOG runs a subset of openCypher. Reads are broad. Writes accept only the
shapes below. A query outside this list fails with `400` before it changes
any data. Retrying the same query fails the same way.

#### Node ids

- Every node has an **integer** `id` property, which you choose. A string id
  fails with "node id property must be an integer".
- The `id` is the node's identity in the collection. Two writes with the same
  `id` change the same node, whatever label they use. Keep ids unique across
  all labels in a collection.
- To keep your own string key (an email, a UUID), store it as a second
  property, such as `ext_id`, and map it to an integer `id` in your code.

#### Writes

| To do this | Use this shape |
|---|---|
| Create or update nodes in a batch | `UNWIND $rows AS row MERGE (n {id: row.id}) SET n:Person, n.name = row.name` |
| Create an edge and its two nodes, safe to re-run | `MERGE (a:Person {id: 1, name: "Alice"})-[:KNOWS {since: 2020}]->(b:Person {id: 2, name: "Bob"})` |
| Create an edge and its two nodes, once | `CREATE (a:Person {id: 1})-[:KNOWS]->(b:Person {id: 2})` |
| Create edges in a batch | `UNWIND $rows AS row CREATE (a {id: row.src})-[:KNOWS]->(b {id: row.dst})` |
| Update a node | `MATCH (n:Person {id: 1}) SET n.age = 31` |
| Delete nodes and their edges | `MATCH (n:Person {id: 1}) DETACH DELETE n` |
| Delete one edge | `MATCH (a:Person {id: 1})-[r:KNOWS]->(b:Person {id: 2}) DELETE r` |

Rules for these shapes:

- **A write is a one-hop edge pattern or a node batch.** You cannot create a
  lone node with `CREATE` or `MERGE`. Use the node batch: it is the only way
  to write a node with no edges.
- **The node batch sets exactly one label, in `SET`** (`SET n:Person, …`),
  not in the `MERGE` pattern. Name each property you set
  (`n.name = row.name`).
- **The edge batch takes no labels and no properties in its pattern.** Load
  nodes with the node batch first, then their edges. Write one batch per
  relationship type.
- **An edge to an `id` that does not exist creates a node.** That node has
  the `id` and no label or other property. Load the nodes before their edges.
- **One `id` is one node, whatever the label.** If you write an `id` that
  exists with a different label, the node gets both labels.
- **A write `UNWIND` reads from a parameter** (`UNWIND $rows AS row`), not
  from a literal list.
- **Every row in a batch has the same fields, and no value is `null`.** A
  property value can be a boolean, an integer, a float or a string. To leave
  a property unset, leave it out of the row and the `SET`. Split rows that
  have different fields into separate batches.
- **Single `CREATE` adds a new edge each time it runs.** `MERGE` and the two
  batch shapes do not duplicate edges, so they are safe to retry.
- **A write that starts with `MATCH` needs a label, an `id` or a property**
  on the node: `MATCH (n:Person) DETACH DELETE n`, not `MATCH (n) DETACH DELETE n`.
- **A write returns no rows.** `CREATE … RETURN` and `MERGE … RETURN` are
  refused. Run a read after the write.
- **`CREATE INDEX` is refused.**

These write forms are refused:

| Refused | Use instead |
|---|---|
| `CREATE (:Person {name: "a"})` (a node without an edge) | The node batch |
| `CREATE (:Person {id: "a"})-[:KNOWS]->(:Person {id: "b"})` (string ids) | Integer ids, with the string in another property |
| `CREATE … RETURN …`, `MERGE … RETURN …` | Write, then read |
| `MATCH (a), (b) CREATE (a)-[:KNOWS]->(b)` | `MERGE (a:Person {id: 1})-[:KNOWS]->(b:Person {id: 2})` |
| `SET n = $map`, `SET n += row.props` | Name each property: `SET n.name = row.name` |
| `FOREACH`, `CALL { … }` with a write inside | `UNWIND $rows AS row` with a batch shape |
| `CREATE INDEX …` | Remove the statement |

#### Reads

Supported:

- `MATCH` with labels and properties, `WHERE` (including `IN`, `AND`/`OR`,
  `STARTS WITH`, `ENDS WITH`, `CONTAINS`) and `OPTIONAL MATCH`
- Typed traversal over one or more hops:
  `MATCH (a:Person)-[:KNOWS]->(b)-[:WORKS_AT]->(c:Company) RETURN c.name`
- Bounded variable-length typed paths: `-[:KNOWS*1..3]->`
- `WITH`, `ORDER BY`, `SKIP`, `LIMIT`, `DISTINCT`
- `UNWIND` at the start of a read, in one shape only: one `UNWIND` over a
  list of plain values (not maps), one `MATCH`, and a final `RETURN`.
  Example: `UNWIND $ids AS i MATCH (p:Person {id: i}) RETURN p.name AS name`
  with `{"ids": [1, 2]}`. This shape cannot have `WHERE`, `WITH`,
  `OPTIONAL MATCH`, `ORDER BY`, `SKIP`, `LIMIT` or `UNION`.
- Aggregates: `count`, `sum`, `avg`, `min`, `max`, `collect`
- `CASE`, `EXISTS { … }`, string functions such as `toUpper` and `toLower`
- Parameters, map and list literals, and `CALL { … }` subqueries that only read

Refused:

- Functions on graph elements: `type()`, `id()`, `elementId()`, `labels()`,
  `keys()`, `properties()`, `nodes()`, `relationships()`, `startNode()`,
  `endNode()`
- `shortestPath`
- Relationship patterns without a type: `(a)--(b)`, `(a)-[r]->(b)`,
  `()-[r]->()`. Name the type: `(a)-[:KNOWS]->(b)`.
- Procedure calls (`CALL db.*`, `CALL apoc.*`) and `LOAD CSV`

Return properties, not whole nodes. `RETURN n` gives the node's integer `id`,
not an object with its properties. Write `RETURN n.name AS name` instead.

### Common Cypher queries

**Load the sample graph:** Five people, two companies, and the `KNOWS` /
`WORKS_AT` edges between them. This is three requests: nodes first, then one
edge batch per relationship type.

```cypher
// Request 1: nodes. Run it once per label.
UNWIND $rows AS row
MERGE (n {id: row.id})
SET n:Person, n.ext_id = row.ext_id, n.name = row.name, n.role = row.role
```

```json params
{"rows": [
  {"id": 1, "ext_id": "u1", "name": "Alice", "role": "admin"},
  {"id": 2, "ext_id": "u2", "name": "Bob",   "role": "analyst"},
  {"id": 3, "ext_id": "u3", "name": "Carol", "role": "engineer"},
  {"id": 4, "ext_id": "u4", "name": "Dan",   "role": "engineer"},
  {"id": 5, "ext_id": "u5", "name": "Eve",   "role": "designer"}
]}
```

Run the same query with `SET n:Company, n.ext_id = row.ext_id, n.name = row.name, n.sector = row.sector`
and `{"rows": [{"id": 101, "ext_id": "c1", "name": "Acme", "sector": "fintech"}, {"id": 102, "ext_id": "c2", "name": "Globex", "sector": "retail"}]}`.
The company ids do not reuse a person id.

```cypher
// Request 2: KNOWS edges.
UNWIND $rows AS row
CREATE (a {id: row.src})-[:KNOWS]->(b {id: row.dst})
```

```json params
{"rows": [{"src": 1, "dst": 2}, {"src": 2, "dst": 3}, {"src": 3, "dst": 4}, {"src": 1, "dst": 5}]}
```

```cypher
// Request 3: WORKS_AT edges.
UNWIND $rows AS row
CREATE (a {id: row.src})-[:WORKS_AT]->(b {id: row.dst})
```

```json params
{"rows": [{"src": 2, "dst": 101}, {"src": 3, "dst": 101}, {"src": 4, "dst": 102}]}
```

Each request returns `data: []`.

**Update a node:** Changes Alice's role.

```cypher
MATCH (p:Person {id: 1})
SET p.role = "owner"
```

Each write returns `data: []`. To create the node when it does not exist,
use the node batch with one row.

**Connect two existing nodes:** Eve starts working at Acme. Running this
again does not add a second edge. Relationship properties are part of what
`MERGE` matches, so leave them out of a `MERGE` when the edge can already
exist with other values. After this step Acme has three people.

```cypher
MERGE (a:Person {id: 5})-[:WORKS_AT]->(b:Company {id: 101})
```

**List a node's neighbors:** There is no wildcard relationship, so ask for
each type and direction you need. Who does Bob know, and who knows Bob?

```cypher
MATCH (p:Person {name: "Bob"})-[:KNOWS]->(friend:Person)
RETURN friend.name AS friend
```

```cypher
MATCH (fan:Person)-[:KNOWS]->(p:Person {name: "Bob"})
RETURN fan.name AS fan
```

<Accordion title="Results">

```json
[{"friend": "Carol"}]
```

```json
[{"fan": "Alice"}]
```

</Accordion>

**Multi-hop expansion:** Everyone up to 3 hops from Alice along outgoing `KNOWS` edges.

```cypher
MATCH (a:Person {name: "Alice"})-[:KNOWS*1..3]->(reach:Person)
WHERE reach.name <> "Alice"
RETURN DISTINCT reach.name AS name
ORDER BY name
```

<Accordion title="Result">

```json
[
  {"name": "Bob"},
  {"name": "Carol"},
  {"name": "Dan"},
  {"name": "Eve"}
]
```

</Accordion>

A variable-length path can visit a node more than once. Use `DISTINCT` when
you want each node one time.

**Filtered, typed traversal:** Who does Alice know that works at a fintech company?

```cypher
MATCH (a:Person {name: "Alice"})-[:KNOWS]->(f:Person)-[:WORKS_AT]->(c:Company)
WHERE c.sector = "fintech"
RETURN f.name AS person, c.name AS company
ORDER BY person
```

<Accordion title="Result">

```json
[
  {"company": "Acme", "person": "Bob"},
  {"company": "Acme", "person": "Eve"}
]
```

</Accordion>

**Aggregate:** Headcount per company, largest first.

```cypher
MATCH (p:Person)-[:WORKS_AT]->(c:Company)
RETURN c.name AS company, count(p) AS headcount
ORDER BY headcount DESC
```

<Accordion title="Result">

```json
[
  {"company": "Acme", "headcount": 3},
  {"company": "Globex", "headcount": 1}
]
```

</Accordion>

**Delete one edge:** Eve leaves Acme.

```cypher
MATCH (a:Person {id: 5})-[r:WORKS_AT]->(c:Company {id: 101})
DELETE r
```

**Delete a node and its edges:** Removes Eve and every relationship attached to her.

```cypher
MATCH (p:Person {id: 5})
DETACH DELETE p
```

To delete many nodes, pass their ids as maps:
`UNWIND $rows AS row MATCH (n {id: row.id}) DETACH DELETE n` with
`{"rows": [{"id": 4}, {"id": 5}]}`. A list of plain ids
(`UNWIND $ids AS id`) is refused for a delete.

### Response format

Rows come back in `data`: one object per result row, keyed by your `RETURN`
aliases:

```json
{
  "success": true,
  "data": [
    { "name": "Alice", "role": "admin" },
    { "name": "Bob", "role": "analyst" }
  ],
  "error": null,
  "meta": { "request_id": "9be86a4e-…", "latency_ms": 12.4 }
}
```

- **Alias every column you read:** `RETURN n.name AS name`. An unaliased
  column is keyed by its expression text (`"n.name"`).
- A write succeeds with `data: []`.

What each kind of value looks like inside a row:

| You return | Example | Row in `data` |
|---|---|---|
| Scalar | `RETURN p.name AS name` | `{"name": "Alice"}` |
| List / map | `RETURN collect(p.name) AS names` | `{"names": ["Alice", "Bob"]}` |
| Node | `RETURN p` | `{"p": 1}`: the node's integer `id`, not its properties |
| Relationship or path | `RETURN k` | Not available. Return properties: `RETURN k.since AS since` |

- Integers are 64-bit. Values beyond 2⁵³ lose precision in languages that
  parse JSON numbers as doubles; return them as strings.

### Using results in your code

#### A minimal client

Wrap the endpoint once. Success puts rows in `data`; errors are wrapped in
`detail`.

```python
import requests

class HydraGraph:
    def __init__(self, base_url, api_key, database, collection="default"):
        self.base, self.db, self.col = base_url, database, collection
        self.headers = {"Authorization": f"Bearer {api_key}"}

    def query(self, cypher, params=None):
        r = requests.post(f"{self.base}/byog/query", headers=self.headers, json={
            "database": self.db, "collection": self.col,
            "query": cypher, "params": params or {},
        })
        body = r.json()
        if not r.ok:
            err = body.get("detail", {})
            raise RuntimeError(f"{r.status_code} {err.get('error_code')}: {err.get('message')}")
        return body["data"]          # always a list of row dicts

g = HydraGraph("https://api.hydradb.com", "<api key>", "crm", "contacts")
```

```typescript
async function query(cypher: string, params: object = {}): Promise<Record<string, any>[]> {
  const res = await fetch(`${BASE}/byog/query`, {
    method: "POST",
    headers: { Authorization: `Bearer ${KEY}`, "Content-Type": "application/json" },
    body: JSON.stringify({ database: "crm", collection: "contacts", query: cypher, params }),
  });
  const body = await res.json();
  if (!res.ok) throw new Error(`${res.status} ${body.detail?.error_code}: ${body.detail?.message}`);
  return body.data;                 // always an array of row objects
}
```

#### Reading rows

```python
# Scalars - project and alias exactly what you need.
rows = g.query("MATCH (p:Person) RETURN p.name AS name, p.role AS role ORDER BY name")
names = [r["name"] for r in rows]                  # ["Alice", "Bob"]

# Nodes - return the properties you need, not the node.
alice = g.query("MATCH (p:Person {name: $n}) RETURN p.id AS id, p.role AS role",
                {"n": "Alice"})[0]

# Relationships - project both ends in the same query.
for row in g.query("MATCH (a:Person)-[:KNOWS]->(b:Person) "
                   "RETURN a.name AS a, b.name AS b"):
    print(f'{row["a"]} knows {row["b"]}')
```

#### Pagination

Result sets past the deployment cap are silently truncated, so page any read
that *could* be large. A stable `ORDER BY` keeps pages consistent:

```python
def all_rows(cypher_body, page=500, params=None):
    offset = 0
    while True:
        rows = g.query(f"{cypher_body} SKIP $offset LIMIT $limit",
                       {**(params or {}), "offset": offset, "limit": page})
        yield from rows
        if len(rows) < page:
            return
        offset += page

people = list(all_rows("MATCH (p:Person) RETURN p.name AS name ORDER BY name"))
```

#### Bulk loading

Chunk rows to stay inside the 256 KiB body cap and the 30 s write budget.
Load nodes first, then edges. Both batch shapes are safe to re-run after a
failure:

```python
def load(people, knows, chunk=500):
    for i in range(0, len(people), chunk):
        g.query("""
            UNWIND $rows AS row
            MERGE (n {id: row.id})
            SET n:Person, n.ext_id = row.ext_id, n.name = row.name
        """, {"rows": people[i:i+chunk]})
    for i in range(0, len(knows), chunk):
        g.query("""
            UNWIND $rows AS row
            CREATE (a {id: row.src})-[:KNOWS]->(b {id: row.dst})
        """, {"rows": knows[i:i+chunk]})
```

#### Handling failures

- **`400`:** the message says what to fix: an unsupported Cypher shape (see
  [Supported Cypher](#supported-cypher)), another Cypher error, or a query
  that ran past its time budget. Retrying unchanged fails identically.
- **`429` / `500`:** transient; retry with backoff. `MERGE` and the batch
  shapes (as in [Bulk loading](#bulk-loading)) are safe to retry. A single
  `CREATE` of an edge is not: a retry can add a duplicate edge.

### Errors and limits

<AccordionGroup>
<Accordion title="Errors">

Errors come back with `success: false` and the reason in `error` (also
mirrored in `detail`):

```json
{
  "success": false,
  "data": null,
  "error": { "code": "DATABASE_ALREADY_EXISTS", "message": "database 'crm' already exists" },
  "detail": { "success": false, "error_code": "DATABASE_ALREADY_EXISTS", "message": "database 'crm' already exists" }
}
```

| Status | Meaning |
|---|---|
| `400` | Invalid request (missing fields, bad collection name), a **Cypher shape outside [Supported Cypher](#supported-cypher)**, another **Cypher error** (the message tells you what to fix), or a **query timeout** |
| `403` | Missing or invalid API key |
| `404` | Unknown database; create it with `POST /byog/databases` |
| `409` | `POST /byog/databases` with a name that already exists |
| `413` | Request body over 256 KiB |
| `429` | Rate limit exceeded; back off and retry |
| `500` | Server error. Retry reads with backoff; retry writes only when they are safe to repeat, such as `MERGE` and the batch shapes |

</Accordion>

<Accordion title="Limits and timeouts">

| Limit | Value | On exceeding |
|---|---|---|
| Request body | 256 KiB | `413` |
| Read query execution | 8 s | `400`: "query exceeded the execution time budget; …" |
| Write query execution | 30 s | same `400` |
| Result set size | deployment-configured cap; rows beyond it are **silently dropped** | no error; paginate |

A query counts as a **write** (and gets the larger budget) when it contains
any write clause: `CREATE`, `MERGE`, `SET`, `DELETE`, `REMOVE`, `FOREACH`.

- **Paginate anything potentially large:**
  `ORDER BY … SKIP $offset LIMIT $page`. Without an `ORDER BY`, rows dropped
  at the result-set cap are arbitrary.
- **Chunk bulk imports:** see [Bulk loading](#bulk-loading).
- **Make a slow read smaller:** start the `MATCH` from a label and an `id` or
  property, lower the upper bound of a variable-length path, and add `LIMIT`.
  `CREATE INDEX` is refused.

</Accordion>
</AccordionGroup>

## Migrating from Neo4j or another Cypher-compatible database

Most read queries port with small changes. Write queries need a rewrite into
the [supported write shapes](#writes). The differences you are most likely to
notice:

- **Integer ids.** Every node needs an integer `id`, unique in the collection.
  Keep your old key (for example `ext_id`) as an ordinary property, and map it
  to an integer in your migration script.
- **Write shapes.** No lone-node `CREATE` or `MERGE`, no `SET n += row`, no
  `MATCH … CREATE`, no `RETURN` after a write. Load nodes with the node batch
  and edges with the edge batch.
- **Fewer functions.** `type()`, `id()`, `labels()`, `keys()`,
  `properties()`, `nodes()`, `relationships()`, `startNode()`, `endNode()`,
  `elementId()` and `shortestPath` are not available. Every relationship
  pattern needs a type.
- **No index commands.** Remove `CREATE INDEX` statements.
- Procedure calls (for example Neo4j's `CALL db.*` / `CALL apoc.*`) and
  `LOAD CSV` are not available; batch data in through `params`.

Migrate one collection at a time: export a graph, replay it into one
collection, and verify the counts.

This script reads from Neo4j with the official driver and writes to
HydraDB with the [`HydraGraph` client](#a-minimal-client). Any source you can
read nodes and relationships from works the same way. It gives each source
node an integer `id`, loads the nodes with all their properties, and then
loads the relationships by `id`. Cypher does not allow a label or
relationship type as a parameter, so it writes one batch per label and per
type. It copies `Person` nodes and `KNOWS` relationships; repeat both steps
for every other label and relationship type, and compare each count.

Three rules keep the copy correct:

- **Key each node by its source identity.** The script uses Neo4j's
  `elementId()`, which is unique across labels, so two nodes never share an
  `id`.
- **Save the id map and reuse it.** A rerun after a failure then gives each
  node the same `id`, and edges keep their endpoints.
- **Group rows by their fields.** A batch needs the same fields in every row
  and no `null` values, so rows with different properties go in separate
  batches.

```python
import json, os, re
from neo4j import GraphDatabase

src = GraphDatabase.driver("neo4j://localhost:7687", auth=("neo4j", "<password>"))
g = HydraGraph("https://api.hydradb.com", "<api key>", "crm", "contacts")
ID_FILE = "contacts-ids.json"  # keep it: a rerun must reuse it

ids = json.load(open(ID_FILE)) if os.path.exists(ID_FILE) else {}  # elementId -> integer id

def node_id(element_id):
    if element_id not in ids:
        ids[element_id] = len(ids) + 1
    return ids[element_id]

def save_ids():
    # Write a new file, then replace the old one, so a crash never leaves a broken map.
    with open(ID_FILE + ".tmp", "w") as f:
        json.dump(ids, f)
    os.replace(ID_FILE + ".tmp", ID_FILE)

def field(name):
    # A property name in the query text must be an identifier: first-name -> first_name.
    name = re.sub(r"[^A-Za-z0-9_]", "_", name)  # ASCII only: café -> caf_
    return name if re.match(r"[A-Za-z_]", name) else "_" + name

def batches(rows, max_bytes=200_000):
    # The request limit is 256 KiB, so batch by size, not by row count.
    chunk, size = [], 0
    for row in rows:
        n = len(json.dumps(row))
        if chunk and size + n > max_bytes:
            yield chunk
            chunk, size = [], 0
        chunk.append(row)
        size += n
    if chunk:
        yield chunk

with src.session() as s:
    # 1. Nodes: every scalar property, grouped by the set of fields present.
    groups = {}
    for rec in s.run("MATCH (p:Person) RETURN elementId(p) AS eid, properties(p) AS props"):
        props = {}
        for k, v in rec["props"].items():
            if v is not None and isinstance(v, (bool, int, float, str)):
                props["source_id" if k == "id" else field(k)] = v  # keep a source id as source_id
        row = {"id": node_id(rec["eid"]), **props}
        groups.setdefault(tuple(sorted(props)), []).append(row)
    save_ids()
    for keys, rows in groups.items():
        sets = "".join(f", n.{k} = row.{k}" for k in keys)
        for chunk in batches(rows):
            g.query(f"UNWIND $rows AS row MERGE (n {{id: row.id}}) SET n:Person{sets}", {"rows": chunk})

    # 2. Relationships, one type at a time, by integer id.
    knows = s.run("MATCH (a:Person)-[:KNOWS]->(b:Person) RETURN elementId(a) AS src, elementId(b) AS dst").data()
    edges = [{"src": ids[r["src"]], "dst": ids[r["dst"]]} for r in knows]
    for chunk in batches(edges):
        g.query("UNWIND $rows AS row CREATE (a {id: row.src})-[:KNOWS]->(b {id: row.dst})", {"rows": chunk})

# 3. Verify counts match.
print(g.query("MATCH (p:Person) RETURN count(p) AS people"))
```

The script drops list and map property values, because BYOG stores scalar
values only. It renames a property whose name is not an identifier
(`first-name` becomes `first_name`, `café` becomes `caf_`), and it keeps a source property named `id`
as `source_id`, because `id` is the BYOG node identity. Two source names that
rename to the same name collide, so rename one of them first. The edge batch takes no properties. To copy relationship
properties, write each relationship with
`MERGE (a:Person {id: $src})-[:KNOWS {since: $since}]->(b:Person {id: $dst})`.

## Using BYOG without Cypher

To use your own entities and relations for a document or memory instead of
the ones HydraDB extracts, pass a `graph_payload` on
[`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context). It is a
JSON map keyed by source id (a `document_metadata` `id`, an `app_knowledge`
`id`, or a memory `id`):

```bash
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=knowledge" \
  -F "database=acme_corp" \
  -F "documents=@/path/to/billing-policy.pdf" \
  -F 'document_metadata=[{ "id": "billing-policy-doc" }]' \
  -F 'graph_payload={
    "billing-policy-doc": {
      "entities": {
        "alice":   { "name": "Alice Carter",  "type": "PERSON", "namespace": "employees" },
        "billing": { "name": "Billing Policy", "type": "POLICY", "namespace": "policies" }
      },
      "relations": [
        { "source": "alice", "target": "billing", "predicate": "OWNS",
          "context": "Alice Carter owns the billing policy.", "temporal_details": "since 2021" }
      ]
    }
  }'
```

- **Replaces extraction:** HydraDB skips extraction for each keyed source;
  the source is still chunked and embedded. Relations appear in `/query`
  `graph_context` tagged `origin: "byog"`, with no query-side changes.
- **Persists across re-ingest:** re-ingesting without a `graph_payload`
  re-applies the stored graph; sending a new one replaces it.
- **Limits:** at most 5,000 entities, 10,000 relations, and 500 relations per
  entity; oversized payloads return `400`. A key matching no source in the
  request is rejected with `400`.
- **Whole-graph only:** there are no per-triple updates, and relations link to
  their best-matching chunk even when the match is weak.

See the [`graph_payload` field reference](/api-reference/v2/endpoint/ingest-context)
for the full shape.
