The HydraDB [Model Context Protocol (MCP)](https://modelcontextprotocol.io/) server gives compatible agents tools to store, recall, inspect, and delete memories. This guide takes you from client configuration to a verified memory lifecycle.

## Before you start

You need:

- **Node.js 18 or later.** Run `node --version` to check.
- A HydraDB API key from the [API Keys page](https://app.hydradb.com/keys).
- A tenant ID from the [Tenants page](https://app.hydradb.com/tenants).
- An MCP client such as Claude Desktop, Cursor, Windsurf, or VS Code.

<Warning>
  MCP client configuration files contain your API key as plain text. Do not commit a configuration containing a real key, paste it into an issue, or share it in screenshots.
</Warning>

## Choose your memory boundary

Every HydraDB MCP tool operates inside one `tenant ID + sub-tenant ID` pair. The tenant identifies the HydraDB account boundary; the sub-tenant partitions data within it.

<Note>
  The MCP server retains the environment names `HYDRA_DB_TENANT_ID` and `HYDRA_DB_SUB_TENANT_ID`. They correspond to the `database` and `collection` concepts used by the current v2 API. See [Databases and collections](/essentials/v2/multi-tenant).
</Note>

Choose the sub-tenant before ingesting data:

| Desired boundary | Example `HYDRA_DB_SUB_TENANT_ID` | Result |
| --- | --- | --- |
| One user's private memory | `user_8f31` | Only clients configured for that user partition see the memory |
| Shared workspace memory | `support_workspace` | Clients using the same value share context |
| Separate development data | `mcp_dev_rohith` | Test memories stay out of the production partition |

If you omit `HYDRA_DB_SUB_TENANT_ID`, the server uses `hydra-db-mcp`. That default is convenient for a local test, but every client with the same tenant and default value shares one memory partition.

<Warning>
  Set a deliberate sub-tenant for multi-user or multi-environment applications. If storage succeeds but recall appears empty, first confirm that the storing and recalling clients use the exact same tenant and sub-tenant values.
</Warning>

## Install and configure the server

Add HydraDB to your client's MCP configuration. Replace the three placeholder values before restarting the client.

<Tabs>
  <Tab title="Claude Desktop">

        "hydradb": {
          "command": "npx",
          "args": ["-y", "@hydradb/mcp@latest"],

### Environment variables

| Variable | Required | Default | Purpose |
| --- | --- | --- | --- |
| `HYDRA_DB_API_KEY` | Yes | None | Authenticates requests to HydraDB |
| `HYDRA_DB_TENANT_ID` | Yes | None | Selects the tenant boundary |
| `HYDRA_DB_SUB_TENANT_ID` | No | `hydra-db-mcp` | Selects the data partition inside the tenant |
| `HYDRA_DB_LOG_LEVEL` | No | `ERROR` | Sets server logging to `DEBUG`, `INFO`, `WARN`, or `ERROR` |

## Confirm the connection

<Steps>
  <Step title="Restart the MCP client">
    Fully restart the editor or desktop client after changing its configuration. Some clients do not reload MCP servers when only a window is refreshed.
  </Step>

  <Step title="Check the tool inventory">
    Open your client's MCP tool view and confirm that the seven `hydra_db_*` tools appear. A running server without these tools usually means the client loaded a different configuration or package command.
  </Step>

  <Step title="Run a read-only check">
    Ask the client:

    ```text
    Use hydra_db_list_memories and tell me how many HydraDB memories are stored.
    ```

    An empty list is a successful connection. An authentication or configuration error means the server was discovered, but HydraDB rejected the request.
  </Step>
</Steps>

## Choose the right tool

| Tool | Use it when | Required input | Important behavior |
| --- | --- | --- | --- |
| `hydra_db_store` | You have a fact, preference, decision, note, or Markdown document | `text` | Defaults to `infer: true`, title `MCP Memory`, and `is_markdown: false` |
| `hydra_db_ingest_conversation` | You have one or more user-assistant turns | `turns`, `source_id` | Always infers memories; defaults `user_name` to `User` |
| `hydra_db_search` | You need context relevant to a question | `query` | Defaults to 10 results, `thinking` mode, and graph context enabled |
| `hydra_db_list_memories` | You need to audit stored memories or find a memory ID | None | Returns memory IDs and memory text |
| `hydra_db_list_sources` | You need to inspect sources or find a source ID | None | Can filter with an optional `source_ids` array |
| `hydra_db_fetch_content` | You need the original content for a source | `source_id` | Returns content by default; `mode` can be `content`, `url`, or `both` |
| `hydra_db_delete_memory` | You need to remove one memory | `memory_id` | Irreversible; it deletes a memory, not an entire source |

### Store text or ingest a conversation?

Use `hydra_db_store` for a standalone item. It lets you control `infer`, `source_id`, title, and Markdown handling.

Use `hydra_db_ingest_conversation` for paired dialogue such as:

```json
{
  "turns": [
    {
      "user": "I prefer release summaries with a short risk section.",
      "assistant": "I'll use that format for future release summaries."
    }
  ],
  "source_id": "conversation_onboarding_2026_07_22",
  "user_name": "Rohith"
}
```

Conversation ingestion always uses inference. Use `hydra_db_store` with `infer: false` when you have already written the exact memory that should be stored.

### Choose `infer: true` or `infer: false`

| Input | Setting | Why |
| --- | --- | --- |
| Raw dialogue, behavior, feedback, or indirect evidence | `infer: true` | HydraDB extracts the underlying preference, trait, or fact and builds graph context |
| A fact or memory already written in its final form | `infer: false` | HydraDB stores and indexes the text as written without an extraction step |

For example, store `"The user opened dark mode on 18 of the last 20 sessions"` with `infer: true`. Store `"User prefers dark mode"` with `infer: false` if your application already made that decision.

The MCP server always sends `upsert: true` for both write tools. `upsert` is not exposed as a tool argument. Use stable, application-owned `source_id` values for content that may be ingested again, such as a conversation ID or document ID.

## Verify the complete lifecycle

Use a unique phrase so you can distinguish the test from existing data. The examples below use `violet-orbit-742`.

<Steps>
  <Step title="Store one explicit memory">
    Ask your client to make this exact call:

    ```text
    Call hydra_db_store with:
    - text: "My MCP verification phrase is violet-orbit-742. I prefer concise deployment summaries."
    - title: "MCP lifecycle test"
    - source_id: "mcp_lifecycle_violet_orbit_742"
    - infer: false
    ```

    Confirm the tool reports one success and zero failures.
  </Step>

  <Step title="Recall it semantically">
    Ask:

    ```text
    Call hydra_db_search for "How should my deployment summaries be written?"
    Use mode "thinking" and graph_context true.
    ```

    The result should contain the concise-summary preference. If ingestion has not completed yet, retry after a short interval.
  </Step>

  <Step title="Inspect the memory and source">
    Call `hydra_db_list_memories` and locate the test memory. Save its `memory_id` for the deletion step.

    Then call `hydra_db_list_sources` with:

    ```json
    {
      "source_ids": ["mcp_lifecycle_violet_orbit_742"]
    }
    ```

    This confirms that both inspection tools use the same configured data partition.
  </Step>

  <Step title="Fetch the original content">
    Call `hydra_db_fetch_content` with:

    ```json
    {
      "source_id": "mcp_lifecycle_violet_orbit_742",
      "mode": "content"
    }
    ```

    Fetching by `source_id` is different from listing inferred memories by `memory_id`.
  </Step>

  <Step title="Delete the test memory">
    Pass the `memory_id` from `hydra_db_list_memories` to `hydra_db_delete_memory`, then list memories again to verify removal.

    <Warning>
      `hydra_db_delete_memory` is irreversible and accepts a `memory_id`, not a `source_id`. The MCP server does not currently expose a tool for deleting an entire source.
    </Warning>
  </Step>
</Steps>

## Tune recall

`hydra_db_search` exposes three optional controls:

| Parameter | Range or options | Default | Choose it when |
| --- | --- | --- | --- |
| `max_results` | `1`–`50` | `10` | You need a narrower prompt or broader evidence set |
| `mode` | `fast`, `thinking` | `thinking` | Use `fast` for lower-latency semantic recall; use `thinking` for deeper personalized recall |
| `graph_context` | `true`, `false` | `true` | Disable it when you only need matching chunks without relationship context |

Start with the defaults. Change one control at a time and test against representative questions so latency and answer quality remain measurable.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The HydraDB server does not appear in my client">
    Validate that the JSON uses the structure required by your client. Claude Desktop, Cursor, and Windsurf use `mcpServers`; VS Code uses `servers` and requires `"type": "stdio"`.

    Run `node --version` and confirm Node.js 18 or later is available to the application. Then fully restart the client.
  </Accordion>

  <Accordion title="The server starts and immediately exits">
    Both `HYDRA_DB_API_KEY` and `HYDRA_DB_TENANT_ID` are required. Confirm their names and values in the client configuration. Keep the values inside the `env` object rather than relying on a terminal session that the desktop application may not inherit.
  </Accordion>

  <Accordion title="The tools appear, but requests return an authentication error">
    Create or copy a valid key from the [API Keys page](https://app.hydradb.com/keys), update the client configuration, and restart the client. Check for accidental whitespace or a placeholder value.
  </Accordion>

  <Accordion title="Storage succeeds, but search returns no relevant memories">
    First run `hydra_db_list_memories` and `hydra_db_list_sources`.

    - If both are empty, compare the tenant and sub-tenant values used during storage and recall.
    - If the source exists but the expected memory does not, confirm whether the input needed `infer: true` or should have been stored directly with `infer: false`.
    - If the memory exists, search for a distinctive phrase, use `thinking` mode, and leave graph context enabled while diagnosing.
  </Accordion>

  <Accordion title="I changed configuration, but behavior did not change">
    Restart the entire MCP client. If you changed package versions, close all client processes before reopening so a previous server process is not reused.
  </Accordion>

  <Accordion title="I need request-level diagnostics">
    Set `HYDRA_DB_LOG_LEVEL` to `DEBUG`, restart the client, and inspect its MCP server logs. The server writes logs to standard error so they do not interfere with the MCP standard-input/standard-output transport.

    Debug logs can contain request content and identifiers. Return the level to `ERROR` after diagnosing the problem, and redact logs before sharing them.
  </Accordion>
</AccordionGroup>

## Implementation reference

The published `@hydradb/mcp` `1.0.0` server currently uses these compatibility endpoints internally:

| Tool | Method and endpoint |
| --- | --- |
| `hydra_db_store` | `POST /memories/add_memory` |
| `hydra_db_ingest_conversation` | `POST /memories/add_memory` |
| `hydra_db_search` | `POST /recall/recall_preferences` |
| `hydra_db_list_memories` | `POST /list/data` with `kind: "memories"` |
| `hydra_db_list_sources` | `POST /list/data` with `kind: "knowledge"` |
| `hydra_db_fetch_content` | `POST /fetch/content` |
| `hydra_db_delete_memory` | `DELETE /memories/delete_memory` |

These routes describe the MCP server implementation and are not a recommendation to bypass the MCP tools. Direct API integrations should use the current v2 lifecycle documented in [Memories](/essentials/v2/memories) and [Query](/essentials/v2/query). See the [open-source HydraDB MCP server](https://github.com/usecortex/hydradb-mcp) for the current tool schemas and implementation.
