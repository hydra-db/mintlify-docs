An **app source** is one item from an app, such as a Slack message or Jira ticket.

## Choose your app pattern

Expand a pattern to see its classes and payload.

<Accordion title="Slack / Teams: threads, replies, attachments">

**Classes: `message` for both the opening message and every reply.** A reply has its own ID and body. All messages in the thread share `fields.thread_id`; each reply also sets `fields.parent_id` to the opening message's `external_id`.

In Slack, the message ID is its `ts`, and the thread root is `thread_ts`. For the opening message, use its own `ts` as `thread_id`. The example uses one channel; keep provider IDs unambiguous across the channels and workspaces you sync (see [Item IDs](#item-ids)).

```json Root message and reply
[
  {
    "id": "slack_C01_1716213600_000100",
    "database": "acme_corp",
    "collection": "default",
    "title": "Auth rollback discussion",
    "kind": "message",
    "provider": "slack",
    "external_id": "1716213600.000100",
    "fields": {
      "kind": "message",
      "body": "The auth rollback notes are attached here.",
      "author": "alice",
      "thread_id": "1716213600.000100",
      "created_at": "2026-05-20T10:00:00Z"
    },
    "attachments": [
      {
        "id": "F012AUTH",
        "title": "auth-rollback-notes.md",
        "content": { "markdown": "# Auth rollback\nDisable the new token refresh path first." }
      }
    ]
  },
  {
    "id": "slack_C01_1716213700_000200",
    "database": "acme_corp",
    "collection": "default",
    "title": "Reply to auth rollback discussion",
    "kind": "message",
    "provider": "slack",
    "external_id": "1716213700.000200",
    "fields": {
      "kind": "message",
      "body": "Confirmed: login works after disabling token refresh.",
      "author": "carol",
      "thread_id": "1716213600.000100",
      "parent_id": "1716213600.000100",

    }
  }

```

HydraDB derives the `reply_to` connection from `parent_id`. The root has no `parent_id`. A new reply only needs a new source; the root stays as it is. Use the same structure for other messaging apps, with their own message and conversation IDs.

**Classes: `ticket` for an issue; `comment` for each independently synced comment.** The ticket's main text is `fields.description`. A comment has its own `external_id`, and its `fields.parent_id` is the ticket's `external_id` under the same provider.

    "title": "Login page returns 500",
    "kind": "ticket",
    "provider": "jira",
    "external_id": "AUTH-123",
    "fields": {
      "kind": "ticket",
      "title": "Login page returns 500",

      "status": "open",
      "assignee": "alice",
      "parent_id": "AUTH-100",
      "linked_issue_ids": ["AUTH-124"]
    }
  },
  {
    "id": "jira_comment_c123",
    "database": "acme_corp",
    "collection": "default",
    "title": "Reproduction steps for AUTH-123",
    "kind": "comment",
    "provider": "jira",
    "external_id": "c123",
    "fields": {
      "kind": "comment",

      "author": "carol",
      "parent_id": "AUTH-123",

This creates a `child_of` connection from AUTH-123 to its epic, a `linked_to` connection to AUTH-124, and a `comment_on` connection from c123 to AUTH-123. Ingest the epic and linked issue too to make their content available. For Linear or Zendesk, change the provider and use that app's item IDs.

For example, a Slack conversation has an opening message, replies, and perhaps an attached runbook. Ingest each message as its own source, group the messages into a thread, and attach the runbook's extracted text to the message that shared it. HydraDB can then retrieve the discussion with its supporting context.

The steps below show how to choose an object class, connect items, [ingest them](#3-ingest-an-app-source), keep them updated, and query them.

## 1. Choose the object's class and fields

**The object class is the starting point. Set it with `kind`.** It tells HydraDB what the item represents and how to read its fields. The app name goes in `provider`: a Slack message is `kind: "message"`, `provider: "slack"`; a Jira ticket is `kind: "ticket"`, `provider: "jira"`.

| Object class (`kind`) | One source represents | Main text | Useful connections |
|---|---|---|---|
| `message` | One Slack or Teams message, including a reply | `fields.body` | `thread_id`, `parent_id` |
| `ticket` | One issue or support ticket | `fields.title`, `fields.description` | `parent_id`, `linked_issue_ids` |
| `comment` | One comment on a ticket, page, or record | `fields.body` | `parent_id`, optional `thread_id` |
| `knowledge_base` | One wiki page | `fields.title`, `fields.body` | `parent_id` |
| `email` | One email, including a reply | `fields.subject`, `fields.body` | `thread_id`, `reply_to_id` |
| `meeting` | One recorded meeting or call | `fields.title`, `fields.body` | `parent_id` |
| `custom` | One CRM or other app record | `fields.data` | `parent_id`, optional `thread_id`, `relations` |

Repeat the class in `fields.kind`, with the same value as the top-level `kind`. Add the fields that describe that class: an author for a message, an assignee and status for a ticket, or a sender and recipients for an email.

### Item IDs

Every source has two IDs:

- **`id` is your stable HydraDB source ID.** Use it to check status, replace the source, or delete it. For example, `slack_C01_1716213600_000100`.
- **`external_id` identifies the item in the app.** For example, the Slack message timestamp `1716213600.000100` or Jira issue key `AUTH-123`. Parent and reply fields refer to this ID.

Use a consistent `provider` for items that belong together. HydraDB resolves external IDs within the provider and database/collection scope. If an app's IDs are only unique within a channel, workspace, or mailbox, make your external IDs unambiguous in that scope and apply the same mapping to every parent, reply, and relation target. Adding a channel name to metadata does not change how IDs resolve.

`database` and `collection` say where the source belongs. Include them in each item, matching the values on the ingestion request. `title` and `url` give the user a readable citation and a link back to the original item.

## 2. Connect threads, parents, and related items

Connections preserve the context around an item. A reply such as "Confirmed, that fixed it" becomes useful when HydraDB can also retrieve the message describing the fix.

### Threads and replies

A **thread** groups a conversation. A **parent** identifies the specific item that a reply or comment responds to. These fields answer different questions:

| In the Slack example | `external_id` | `fields.thread_id` | `fields.parent_id` |
|---|---|---|---|
| Alice's opening message | `1716213600.000100` | `1716213600.000100` | Omitted |
| Carol's reply | `1716213700.000200` | `1716213600.000100` | `1716213600.000100` |
| A later reply | Its own message ID | `1716213600.000100` | `1716213600.000100` |

Each message keeps its own body, author, and timestamp. A thread does not need a separate source. Ingest its opening message and replies with the shared `thread_id`.

For other apps, use their conversation IDs. Email uses `thread_id` to group the conversation and `reply_to_id` to identify the email being replied to. Ticket comments use `parent_id` to identify the ticket; they can also carry a `thread_id` when the app has a discussion thread.

### Relationships from fields

HydraDB creates these connections from the fields you send:

| Field | Class | Connection |
|---|---|---|
| `thread_id` | Message, email, comment, custom | Item belongs to the thread |
| `parent_id` | Message | Reply → parent message (`reply_to`) |
| `reply_to_id` | Email | Reply → original email (`reply_to`) |
| `parent_id` | Comment | Comment → ticket, page, or record (`comment_on`) |
| `parent_id` | Ticket, page, meeting, custom | Child → parent (`child_of`) |
| `linked_issue_ids` | Ticket | Ticket → related issues (`linked_to`) |

Parent and reply IDs use the same provider as the source. Ingest the referenced items too so their content can be retrieved.

### Explicit relations between sources

Use `relations` to describe connections beyond those fields: a Slack discussion about a Jira incident, a CRM renewal tied to a support ticket, or an issue blocking a release.

A relation reads as **this source → relationship → target**. On Carol's Slack reply, the following addition means "this message is linked to Jira ticket AUTH-123":

```json Add to the message source
{
  "relations": [
    {
      "predicate": "linked_to",
      "target": { "external_id": "AUTH-123", "provider": "jira" },
      "properties": { "reason": "Confirms the login fix" }
    }
  ]
}
```

`predicate` names the relationship. `target` identifies the other source. Optional `properties` explain the connection. The target can be identified in either of these ways:

| Target | Use when |
|---|---|
| `{ "source_id": "jira_AUTH-123" }` | You know the target's HydraDB source `id`. |
| `{ "external_id": "AUTH-123", "provider": "jira" }` | You know its app ID and provider. Include both. |

Choose the direction that matches the relationship:

| `predicate` | Example |
|---|---|
| `reply_to` | Reply → original message or email |
| `comment_on` | Comment → ticket or page |
| `child_of` | Subtask → epic; page → parent page |
| `linked_to` | Slack discussion → Jira ticket |
| `blocks` | Unresolved ticket → release it blocks |
| `caused_by` | Incident → change that caused it |
| `forwarded_from` | Forwarded email → original email |
| `related_to` | Item → another related item |

Keep both sources in the same database and collection. A relation connects sources that you ingest; it does not import the target from its app. Query with `query_apps: true` and `mode: "thinking"` when you want HydraDB to follow connections for supporting context.

### Link items across connectors

**Sources from different connectors can be linked.** A HubSpot deal can point to a Gmail email, just as a Slack message can point to a Jira ticket. Both sources must belong to the same database and collection. The target's provider identifies its app; it does not need to match the source's provider. You do not need to include a connector ID in the relation.

If you already have both HydraDB source IDs, add a `linked_to` relation to one source with the other source's ID as `target.source_id`. For example, link the HubSpot deal `hubspot_deal_789` to the Gmail source `gmail_msg_19a2b3c` from the email pattern above.

<Accordion title="Across connectors: link a HubSpot deal to a Gmail email">

Send this source through `app_knowledge`, using the ingestion request below. Replace the example IDs and business fields with your source's actual values.

```json HubSpot source with a Gmail target
{
  "id": "hubspot_deal_789",
  "database": "acme_corp",
  "collection": "default",
  "title": "Acme enterprise renewal",
  "kind": "custom",
  "provider": "hubspot",
  "external_id": "789",
  "fields": {
    "kind": "custom",
    "data": {
      "name": "Acme enterprise renewal",
      "stage": "negotiation"
    }
  },
  "relations": [
    {
      "predicate": "linked_to",
      "target": { "source_id": "gmail_msg_19a2b3c" }
    }
  ]
}
```

The source's own `id` identifies the HubSpot deal. `target.source_id` is the Gmail item's HydraDB ID, which you can obtain from ingestion results or [source listing](/api-reference/v2/endpoint/list-documents). A source-ID target does not require `provider`.

To add the link to an existing deal, send its complete updated snapshot with `upsert: true`. Retain its current fields, metadata, attachments, comments, and other relations. Include the relation in subsequent snapshots from your sync too.

</Accordion>

**When you only have the app's external ID**, use `target.external_id` and the target's stored provider name. For the same Gmail email, the target would be:

```json External-ID alternative for the relation target
{
  "external_id": "19a2b3c",
  "provider": "google"
}
```

Some app names are normalized when sources are stored. Explicit relation targets must use the resulting provider name:

| Target app | `target.provider` |
|---|---|
| Gmail | `google` |
| Outlook / Teams | `microsoft` |
| HubSpot | `hubspot` |
| Jira | `jira` |

For example, a Gmail source submitted with `provider: "gmail"` is stored under `google`. Use `google` in an external-ID relation target so it matches that source. Prefer `source_id` when you know the HydraDB ID; it avoids provider-name matching.

With `query_apps: true` and `mode: "thinking"`, HydraDB can follow a `linked_to` connection from either side: a query about the deal can retrieve the linked email, and a query about the email can retrieve the deal. You can declare the link on one source without adding a reverse relation. Ingest both items before expecting their content in query results. To connect a whole conversation, link to an ingested email in that conversation and keep its thread fields populated.

People and records have different connections. When sources identify people by email, HydraDB can recognize the same person across apps. That shared person identity does not declare that a particular deal is about a particular email conversation. Use an explicit source relation for that record-level connection.

## 3. Ingest an app source

Create the [database](/api-reference/v2/endpoint/create-tenant) first, then send your sources to [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context). `app_knowledge` is a JSON object or array, serialized as a string inside a multipart form request. The SDK handles the multipart request.

Here is the smallest Slack starting point: Alice's opening message. The full thread and attachment are in the messaging pattern above.

## 4. Keep app sources updated

Use the same endpoint for the first sync and later changes. **A new item gets a new source ID. An edited item keeps its source ID and is sent with `upsert: true`.**

For the Slack thread above:

1. Alice posts the opening message. Ingest `slack_C01_1716213600_000100`.
2. Carol replies. Ingest only `slack_C01_1716213700_000200`, with the same `thread_id` and the opening message's external ID as `parent_id`.
3. Carol edits her reply. Send the complete updated reply with the same `id` and `external_id`, and `upsert: true`.
4. Carol deletes her reply. [Delete the source](/api-reference/v2/endpoint/delete-source) using its HydraDB `id`.

<Accordion title="Incremental example: update Carol's reply">

The following call replaces just Carol's source. Keep its identity and connections, and send its current body and other fields.

```python Python SDK
import json

updated_reply = {
    "id": "slack_C01_1716213700_000200",
    "database": "acme_corp",
    "collection": "default",
    "title": "Reply to auth rollback discussion",
    "kind": "message",
    "provider": "slack",
    "external_id": "1716213700.000200",
    "fields": {
        "kind": "message",
        "body": "Confirmed on staging and production: login works again.",
        "author": "carol",
        "thread_id": "1716213600.000100",
        "parent_id": "1716213600.000100",
        "created_at": "2026-05-20T10:01:40Z",
        "edited_at": "2026-05-20T10:10:00Z",
    },
}

result = client.context.ingest(
    type="knowledge",
    database="acme_corp",
    collection="default",
    app_knowledge=json.dumps([updated_reply]),
    upsert="true",
)
```

</Accordion>

The same rule applies across apps:

| App event | What to send |
|---|---|
| New message, email, page, or ticket | A new source with its own `id` and `external_id` |
| Ticket status or page body changes | The updated source with the same IDs and `upsert: true` |
| New ticket or page comment | A new `comment` source with its own IDs and the parent's external ID in `fields.parent_id` |
| Existing comment edited | The updated comment source with the same IDs and `upsert: true` |
| Item deleted | `DELETE /context` with the item's HydraDB source ID |

`upsert: true` replaces the source snapshot. Include the current fields, metadata, attachments, comments, and relations you want to retain. For a new comment arriving on a ticket, ingest a separate `comment` source so you can update or delete that comment independently.

## 5. Include attachments and comments

### Attachments: the supporting file's text

A message can share a runbook; a ticket comment can include a diagnostic trace. Add these to the source's `attachments` array so their extracted text is searchable and connected to the item that shared them.

Extract the file's text in your connector and send it in `content.text` or `content.markdown`. `url` is a link back to the file; HydraDB does not download a file from that URL in an app-source payload. To upload the original file for HydraDB to parse, use the [file ingestion path](/essentials/v2/knowledge#path-a-files).

<Accordion title="Attachment example: add a diagnostic trace to a comment">

Add this fragment to the comment source from the ticket pattern:

```json Attachment fields
{
  "attachments": [
    {
      "id": "att-har-1",
      "title": "staging-login.har",
      "url": "https://files.example.com/staging-login.har",
      "content_type": "application/json",
      "content": {
        "text": "The trace shows repeated redirects after token refresh."
      }
    }
  ]
}
```

The trace's text can help answer "What evidence did Carol provide for AUTH-123?" Keep the attachment ID stable when syncing the same file again.

</Accordion>

### Comments: a snapshot or an independent source

There are two ways to include comments. Choose based on how your app sync works:

| Sync behavior | Representation | Example |
|---|---|---|
| You have the parent and its complete current comment list | Embed `comments` on the parent source | An initial Jira export containing the ticket and all comments |
| Comments arrive, change, or disappear individually | Ingest each as a `kind: "comment"` source | A webhook announces Carol's new comment on AUTH-123 |

Embedded comments add searchable text and authors connected to the parent. They are part of its snapshot. Independent comment sources have their own HydraDB IDs, so each can be replaced or deleted without resending the parent.

<Accordion title="Snapshot example: include the ticket's current comments">

Add this fragment to the ticket source when sending a complete snapshot:

```json Embedded comments
{
  "comments": [
    {
      "id": "c123",
      "author": "carol",
      "body": "Reproduces on staging when the refresh token expires.",
      "created_at": "2026-05-20T11:00:00Z"
    },
    {
      "id": "c124",
      "author": "alice",
      "body": "Fixed by disabling the new token refresh path.",
      "created_at": "2026-05-20T11:15:00Z"
    }
  ]
}
```

On the next parent upsert, send the complete current comment list. A payload containing only a new comment replaces the snapshot rather than appending to it. For separate comment sources, use the ticket-and-comment pattern above.

</Accordion>

Slack replies and email replies keep their `message` and `email` classes. This preserves each reply's app fields and thread connections.

## 6. Add metadata for filtering and display

Use `metadata` for shared values you want to filter on, such as Slack channel, Jira project, or department. Declare those keys in the [database metadata schema](/essentials/v2/metadata) with `enable_match: true` before ingestion.

Use `additional_metadata` for other details you want to preserve, such as a raw provider event ID or a display label.

```json Add to a Slack source
{
  "metadata": { "channel": "engineering" },
  "additional_metadata": { "workspace_name": "Acme" }
}
```

At query time, filter with `metadata_filters: { "channel": "engineering" }`. Filters on free-form values go under `metadata_filters.additional_metadata`. See [Scoping using metadata](/essentials/v2/metadata) for schema setup and complete filter examples.

## 7. Query app sources with connected context

Use [`POST /query`](/api-reference/v2/endpoint/query) with `type: "knowledge"` (or `"all"`) and `query_apps: true`. Set `mode: "thinking"` for queries that need related items, such as a thread's replies or a ticket's comments.

<Accordion title="Query example: retrieve the rollback discussion and its replies">

```json POST /query
{
  "database": "acme_corp",
  "collection": "default",
  "type": "knowledge",
  "query": "What did Alice propose for the auth rollback, and did the replies confirm it worked?",
  "query_apps": true,
  "mode": "thinking",
  "max_results": 10
}
```

</Accordion>

The fields you supplied support different questions:

| Question | Relevant fields or connections |
|---|---|
| "Find Slack messages from Alice" | `kind`, `provider`, `fields.author` |
| "Did the rollback work? Show the discussion" | Message bodies, `thread_id`, reply connections |
| "What did Carol report on AUTH-123?" | Ticket `external_id`, comment author, `comment_on` |
| "Which renewal depends on the login fix?" | The CRM record's explicit link to the Jira ticket |
| "What do the attached rollback notes say?" | Extracted attachment text |

## Field reference

Expand the source fields or the object class you are implementing. `kind` chooses the class; `provider` identifies the app.

<Accordion title="Top-level app source fields">

| Field | Why send it | Query / ingestion effect |
|---|---|---|
| <Field name="id" type="string" required /> | Stable HydraDB ID for this item. | Upsert key, delete/status/list ID, and direct relation target. |
| <Field name="database" type="string" required /> | Database that owns the item. | Must match the form-level `database` when present. |
| <Field name="collection" type="string" required /> | Logical partition. Use `"default"` if you do not partition. | Must match the form-level `collection` when present. |
| <Field name="title" type="string" recommended /> | Human-readable subject, page name, ticket title, or message label. | Improves display, citations, and semantic matching. |
| <Field name="kind" type="email, message, ticket, knowledge_base, comment, meeting, custom" recommended /> | App object kind. | Selects the app parser and query behavior. |
| <Field name="provider" type="string" recommended /> | App namespace such as `slack`, `gmail`, `jira`, `notion`, `salesforce`, or `linear`. | Prevents ID collisions and scopes relation resolution. |
| <Field name="external_id" type="string" recommended /> | Stable provider ID for this exact item. | Exact lookup and relation/hierarchy resolution. |
| <Field name="url" type="string" /> | Canonical link back to the provider item. | Improves citations and source navigation. |
| <Field name="timestamp" type="ISO-8601 datetime" /> | Creation, sent, or last-updated time. | Helps chronology, display, and recency-aware ranking. |
| <Field name="fields" type="object" required /> | Structured kind-specific content. | Primary app-native searchable payload. |
| <Field name="metadata" type="object" /> | Schema-aligned filterable fields. | Queryable with top-level `metadata_filters` keys when declared in database schema. |
| <Field name="additional_metadata" type="object" /> | Free-form display/bookkeeping metadata. | Queryable under `metadata_filters.additional_metadata`. |
| <Field name="relations" type="Relation[]" /> | Explicit app-source links. | Enables connected-context retrieval and app graph expansion. |
| <Field name="acl" type="string[]" /> | Who may retrieve this item. Emails, `group:<provider>:<id>`, `domain:<domain>`, or `__public__`. | Omit to leave it unrestricted. Enforcement is opt-in on the query side: a query that carries `acl` sees this item only with a matching principal, and a query without `acl` is not filtered at all. See [Access Control](/essentials/v2/access-control). |
| <Field name="attachments" type="Attachment[]" /> | Pre-extracted files attached to the item. | Attachment text is indexed and connected to the source. |
| <Field name="comments" type="Comment[]" /> | Embedded snapshot/backfill comments. | Comment text and authors become searchable. |
