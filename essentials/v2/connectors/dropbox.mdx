Sync the files inside the Dropbox folders you select, and in every folder below them. Each file is one document. Text from supported files is searchable when HydraDB can download and read the files. A file whose text cannot be read is still findable by its path, size and modified time.

With Enforce ACL on, a file can be read only by the members of the shared folder that holds it, or only by the connecting member for files in their own unshared space. Sharing set on a single file is not read. The first sync reaches only files modified in the last 30 days unless you raise `lookback_days`. Files deleted in Dropbox stay in HydraDB, and no author or owner is recorded.

## Permissions

Turn on **Enforce ACL** for this connector to make search follow Dropbox permissions. With Enforce ACL off, HydraDB does not enforce them. Only a workspace owner or writer signed in to HydraDB can turn it on. API-key requests must omit `enforce_acl`, including `false`. See [Enforce ACL](/essentials/v2/connectors#enforce-acl).

- **Who can read an item:** Each file follows the shared folder that contains it. The folder's members and invitees can read it, and so can members of a group the folder is shared with. A file in the connecting member's own unshared space can be read by that member only.
- **How a person is identified:** A member's or invitee's email address. A group is turned into its members' email addresses when the Dropbox Business team scopes are granted.
- **When permissions cannot be read:** If HydraDB cannot read a shared folder's members, or cannot turn a group into its members, the connector reports a permission warning. On HydraDB Cloud, with Enforce ACL on, such an item follows the access rule you set on its resource. With no rule, it is hidden from search. Self-hosted deployments can be configured differently. Permission warnings appear in [Get Connector Status](/api-reference/v2/endpoint/get-connector-status).
- Sharing set on an individual file, rather than on its shared folder, is not read.
- Without `sharing.read`, shared folder members can be unreadable.
- Without the Business team scopes, a folder shared with a group cannot be fully resolved.
- A very large folder or group membership list that cannot be read in full counts as unreadable.
- When a shared folder's members change, a later sync applies the new access to its files, including files that did not change.

You can also [set your own rule on a resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).

## Before you connect

### Credentials

Dropbox uses an app you create in Dropbox, authorized for offline access: an app key, an app secret and a refresh token.

<ResponseField name="app_key" type="secret string" required>
The Dropbox app key.
</ResponseField>

<ResponseField name="app_secret" type="secret string" required>
The Dropbox app secret.
</ResponseField>

<ResponseField name="refresh_token" type="secret string" required>
A long-lived offline refresh token for the connecting account.
</ResponseField>

**Scopes to give the Dropbox app**

- `account_info.read`: required. Identifies the account and whether it is a Business account. Without it, team folders are never picked up.
- `files.metadata.read`: required. Sees folders, files and what changed.
- `files.content.read`: required. Reads file contents. Without it, only name, location and size are known.
- `sharing.read`: required. Sees who each folder is shared with, which decides who can find its files.
- `team_info.read`: optional, Business only. Tells that the connection is to a team.
- `members.read`: optional, Business only.
- `team_data.member`: optional, Business only. Reads the team's files on behalf of the member who connected.
- `groups.read`: optional, Business only. Reads group members, so a folder shared with a group resolves to people.

### Set it up

<Steps>
  <Step title="Create a Dropbox app">
    Create a Dropbox app with the four required scopes. For a Dropbox Business team, add the four Business scopes too, so team folders are read and group shares resolve to people.
  </Step>
  <Step title="Authorize it offline">
    Authorize the app for offline access with the account to sync, and keep the refresh token.
  </Step>
  <Step title="Create the connector">
    Paste the values as `app_key`, `app_secret` and `refresh_token`.
  </Step>
  <Step title="Select folders">
    HydraDB lists your folders by path. Select the folders to sync. Every folder below a selected one is included. To reach files older than 30 days, raise `lookback_days` when you select them.
  </Step>
</Steps>

One connector reads one Dropbox account. On a Business team, it reads team files on behalf of the member who connected.

Then call [Discover Connector Resources](/api-reference/v2/endpoint/discover-connector-resources) to list the resources the connector can sync, and [Configure Connector](/api-reference/v2/endpoint/configure-connector) to choose what to sync.

## Keeping in sync

- **First sync:** Each selected folder reads back the window set by `lookback_days`, 30 days by default. Files last modified before that window are not synced.
- **New and changed items:** Later syncs pick up the changes Dropbox reports since the last sync. If Dropbox no longer accepts where the last sync stopped, the folder is listed again in full.
- **Edits:** An edited file is read again and replaces its document.
- **Deletions:** Deleted files are not removed. A file deleted in Dropbox stays searchable in HydraDB.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` on the connector to change it.

## What gets synced

### Files

- **One document:** One Dropbox file. Folders are not documents.
- **Title:** The file's path, for example `Projects/Acme/contract.pdf`. A file with no path is titled `Dropbox file` and its id.
- **Text:** The file's text when it could be read. Otherwise the title followed by `Path`, `Size` and `Modified` lines. The title is searchable in either case.
- **Date:** When the file was last modified on Dropbox's servers.
- **Link back:** Opens the file in the Dropbox web app, at its path.
- **Files:** Text from supported files is searchable when HydraDB can download and read the files. Files over 50 MiB keep only their details.

<ResponseField name="path" type="Searchable text">
The file's path in Dropbox. It is the title, so it is always searchable, and it is the `Path` line when the file's text could not be read.
</ResponseField>

<ResponseField name="size" type="Searchable text">
The size in bytes, written as the `Size` line. Searchable only on files whose text could not be read.
</ResponseField>

<ResponseField name="server_modified" type="Searchable text, Result date">
When the file was last modified on Dropbox's servers. Sets the result date. Written as the `Modified` line, so it is searchable only on files whose text could not be read.
</ResponseField>

<ResponseField name="additional_metadata.container_id" type="Query filter">
The path of the folder that directly holds the file, `/` at the top level. Limits a query to the files directly in one folder. Files in its subfolders carry their own folder's path. Not searchable.
</ResponseField>

<ResponseField name="additional_metadata.container_name" type="Query filter">
The same folder path. Another way to limit a query to one folder. Not searchable.
</ResponseField>

<ResponseField name="additional_metadata.container_type" type="Query filter">
Always `folder`. Not searchable.
</ResponseField>

<ResponseField name="connector_id" type="Query filter">
Limits a query to this connector's files. Not searchable.
</ResponseField>

<ResponseField name="provider" type="Query filter">
Always `dropbox`. Not searchable.
</ResponseField>

<ResponseField name="Shared folder members" type="Access rule">
The email addresses of the members and invitees of the file's shared folder, including members of shared groups. They decide who can read the file when Enforce ACL is on. Not searchable.
</ResponseField>

<Accordion title="Stored only, not searchable (6)">

<ResponseField name="rbac_warning" type="Stored only">
Set when the file's sharing could not be fully resolved. It explains the missing permissions and grants no access.
</ResponseField>

<ResponseField name="acl_warning" type="Stored only">
Set when the sharing of the file's folder could not be read. Explains the failed read.
</ResponseField>

<ResponseField name="acl_warning_kind" type="Stored only">
`permission_refused` when that warning is set.
</ResponseField>

<ResponseField name="rev" type="Stored only">
The Dropbox revision id the document was read from.
</ResponseField>

<ResponseField name="dropbox_hash" type="Stored only">
Dropbox's content hash, for comparing file contents outside HydraDB.
</ResponseField>

<ResponseField name="client_modified" type="Stored only">
The modified time recorded by the app that uploaded the file. The result date uses the server time instead.
</ResponseField>

</Accordion>

**Example searches**

- What does the Acme contract PDF in the Legal folder say about termination?
- Which files in the Projects/2026 folder mention the launch date?
- When was the pricing spreadsheet last changed?

## How it fits into the graph

- Files use the Record class.

[Graph classes](/essentials/v2/connector-providers#graph-classes) explains each class.

**Connections Dropbox creates**

- No links between files, and no links to items in other tools. The folder that holds a file is kept as a filter, not a graph link.

**People and groups**

- No people are attached to files. Dropbox files carry no author or owner in HydraDB.

**Found in the text**

The file's text. HydraDB identifies people, organizations, projects and other named things in this text. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Not synced

- Folders you did not select.
- Files last modified before the `lookback_days` window on the first sync.
- Folders themselves, as documents.
- File comments, version history and Dropbox Paper structure.
- Who created or last edited a file.
- Sharing set on an individual file.
- Text of files over 50 MiB.
- Deletions: deleted files stay in HydraDB.
