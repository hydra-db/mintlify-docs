HydraDB keeps context correct across millions or billions of documents, memories, and information nodes. It replaces vector, SQL, and FTS stores (and combinations of them) with one universal context layer: a single database that uses context graphs to materialize views over structured and unstructured data. Store emails, spreadsheets, chats, memories, and other knowledge in one place.

## Problems and objections with agents at scale

- **Vector databases weren't built for durable, persistent memory:** A vector database finds what is similar; an agent needs what is useful. A useful answer may depend on who made a decision, how a project changed, and who is asking. As you ingest more context, you generate more embeddings, and similarity search degrades because similarity isn't relevance. If you retrieve a single document from a trillion-document store, chances are that document is similar, but not the one your agent actually needs.
- **Why not use Postgres and Apache AGE (pgGraph)?** Most developers start (and should start) with Postgres, mapping CDPs and data dictionaries into a pseudo-context graph over their tables. But as data volume, query complexity, workloads, and users grow, Postgres with pgGraph slows down, and you eventually need a dedicated service for petabyte-scale retrieval. It's the same reason high-growth companies move off pgVector.
- **How about Markdown files?** Markdown is a useful starting point for agent memory, and the workflow is familiar: agents read, write, and search files with ordinary tools. But as memory grows, a plain folder of files isn't enough: filename search and literal grep become expensive and less effective. The problem isn't Markdown as a format; it's relying on files and basic search alone for agent memory at scale.

## Why graphs?

Graphs express data in the most flexible, free-form way possible: an interconnected web your agent can crawl until it finds every node needed for a complete response.

When mobile apps took off in the 2010s, developers adopted NoSQL over SQL because they couldn't predict the shape of user data two weeks out. AI has the same problem, plus interlinked memories, agent traces, and versioned context. All of it must form one web the AI can traverse until it finds every relevant node. Call it a "mind map," an "investigation board," or simply a "context graph."

## Improving agent accuracy with context graphs

Graphs make room for new information effortlessly. As new information arrives, older versions are temporally versioned: each node is the latest snapshot, while the history of how a doc, memory, user preference, or decision trace evolved is preserved.

A context (knowledge) graph organizes knowledge, chats, emails, and other data, maps how it connects, and gives that structure to agents at run time so they deliver high quality, personalized responses. You complete tasks without the back and forth of asking and searching for more information.

Consider a legal agent. Its work goes beyond reading the latest case or draft: it's highly relational, and the agent must navigate those relationships to be accurate. A single credit agreement arrives with drafts, amendments, and side letters, and the agent must know which version controls before answering anything about it. The same applies to most agents: knowledge, coding, sales, browser, and more.

## So, what is HydraDB?

HydraDB is a fast agent database that gives you every primitive you need to build the best context and memory layer for your agents. It should be the last database or context store your agents ever need.

## Benchmarks

These benchmarks show the baseline performance of a context graph compared to vanilla vector or Postgres search:

- **Memory recall:** 90.79% on [LongMemEval-S](https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned).
- **Company knowledge:** 88.7 overall on [EnterpriseRAG-Bench](https://github.com/onyx-dot-app/EnterpriseRAG-Bench), retrieval across more than half a million documents from nine enterprise systems.
- **Coding harness:** 90.73 on [CodeWikiBench](https://github.com/FSoft-AI4Code/CodeWikiBench) for nlohmann/json, against 66.06 for DeepWiki and 61.28 for CodeWiki.
- **Long-term memory at scale:** 82% overall on [BEAM 1M](https://github.com/mohammadtavakoli78/BEAM), across ten dimensions.
- **Financial AI:** 91.4% recall@10 on [FinanceBench](https://github.com/patronus-ai/financebench), over dense filings and enterprise data.
- **Low latency:** sub-200 ms retrieval.

See the full technical breakdown of each run in our [benchmarks](https://benchmarks.hydradb.com/).

## Primitives

- **RBAC-aware connectors:** 70+ providers, including Slack, Gmail, Google Drive, Notion, GitHub, Jira, and Teams, synced on a schedule. Source app permissions carry over as access control, so a query that sends a user's identity as `acl` returns only what that user may see. This is the easiest way to start extracting memories or building a context graph from these apps.
- **SLMs that learn after every run:** Typhon-1 and Minion-1, our SLMs, are trained specifically to identify, build, and output relationships, and they learn from every run.
- **SDK, MCP, plugins, CLI:** Tooling for your HydraDB development lifecycle. Plugins are available for OpenClaw, Hermes, Codex, and more.
