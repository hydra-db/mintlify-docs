One endpoint, two modes:

- **Without `id`**  -  returns the catalog of connectable providers, with availability, maturity, and category for each.
- **With `id=<provider>`**  -  returns that provider's contract: which streams get indexed, which field values are reachable by search, which keys can filter a query, and the JSON Schema for the credentials the provider needs.

Call it before [Create Connector](/api-reference/v2/endpoint/create-connector) to pick a provider and fetch its credential shape, and again at query time to look up the exact `filter_key` values accepted inside a query's `metadata_filters`.

<RequestExample>

```bash List all providers
curl 'https://api.hydradb.com/connectors/providers' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

```bash Inspect one provider
curl 'https://api.hydradb.com/connectors/providers?id=slack' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

</RequestExample>

## Query parameters

| Name | Description |
| --- | --- |
| <Field name="id" type="string" /> | Provider identifier (e.g. `slack`, `gmail`). Omit to list all providers. Returns `404` if the provider is unknown. |

<ResponseExample>

```json 200 (catalog)
{
  "providers": [
    {
      "provider": "slack",
      "category": "Communication",
      "supported": true,
      "moveit_support": false,
      "is_alpha": false,
      "is_beta": false,
      "rank": 1
    }
  ]
}
```

```json 200 (single provider)
{
  "provider": "slack",
  "connector_type": "slack",
  "indexed_object_types": ["messages", "threads"],
  "searchable_fields": [
    {
      "name": "author",
      "data_type": "string",
      "description": "Display name of the message author."
    }
  ],
  "filterable_fields": [
    {
      "name": "resource_id",
      "data_type": "string",
      "filter_key": "additional_metadata.resource_id",
      "description": "Channel the message belongs to."
    }
  ],
  "credential_schema": {
    "type": "object",
    "properties": { "...": "JSON Schema for the provider's credential inputs" }
  }
}
```

</ResponseExample>

## Catalog response (no `id`)

Each entry in `providers` describes one connectable provider:

| Property | Meaning |
| --- | --- |
| `provider` | Provider identifier. This is exactly the value accepted by the `id` parameter here and by the `provider` field in [Create Connector](/api-reference/v2/endpoint/create-connector) |
| `category` | Display grouping for the provider |
| `supported` | Whether the provider can be connected today |
| `moveit_support` | Whether the provider syncs through the MOVEIT pipeline |
| `is_alpha` / `is_beta` | Maturity flags for the connector |
| `rank` | Catalog display order (lower ranks first) |

## Single-provider response (`id=<provider>`)

| Property | Meaning |
| --- | --- |
| `indexed_object_types` | The provider streams whose records become searchable documents |
| `searchable_fields` | Field values rendered into the indexed document text. Semantic and full-text queries find them as part of the document  -  they cannot be targeted individually |
| `filterable_fields` | Keys that support exact-match filtering. Each entry carries `filter_key`, the literal key to pass inside a query's `metadata_filters` |
| `credential_schema` | JSON Schema describing the credentials the provider needs to connect. Omitted if the schema source is unavailable |

Each entry in `searchable_fields` and `filterable_fields` includes:

| Property | Meaning |
| --- | --- |
| `name` | The normalized field or metadata key stored by HydraDB |
| `data_type` | Its JSON type: `string`, `number`, `boolean`, `array`, `object`, or `null` |
| `filter_key` | Filterable fields only  -  the exact key to use in `metadata_filters` |
| `description` | Optional provider-specific context |

<Note>
  You cannot search over a single searchable field on its own. All `searchable_fields` are combined into one indexed document text, and queries run over that combined text as a whole. To narrow results, pass a `filter_key` from `filterable_fields` inside the query's `metadata_filters`  -  that is the only per-field targeting mechanism.
</Note>

## Using `filter_key` in a query

A dotted key like `additional_metadata.resource_id` nests under `additional_metadata`; tenant-scoped keys like `provider` are passed top-level. To scope by a specific connector, filter on `additional_metadata.connector_id`  -  it is provider-populated document metadata, not a tenant-scoped key:

```json Filtering by a provider's filterable field
{
  "database": "acme_corp",
  "query": "deployment checklist",
  "query_apps": true,
  "metadata_filters": {
    "additional_metadata": { "resource_id": "C_GENERAL" }
  }
}
```

```json Filtering by tenant-scoped keys
{
  "metadata_filters": { "provider": "slack" }
}
```

<Note>
  Connector contracts come from the same normalizers that prepare synced data. Query this endpoint instead of relying on a static field list: it covers the complete connector catalog and stays current as connector normalization changes.
</Note>

The dashboard's connector catalog is served by a separate `GET /connector-catalog` control-plane endpoint. API integrations should use `GET /connectors/providers`, which returns the same catalog plus the per-provider contract mode documented here.
