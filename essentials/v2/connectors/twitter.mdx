Use the twitter connector to bring the following content into HydraDB.

## What syncs

The provider description lists these indexed object types:

- `posts`
- `dms`

## Connect

Create one connector per account, using that account's credentials where required. Use a separate connector for a different account; see [account scopes](/essentials/v2/connectors#6-connect-several-accounts-from-one-provider). Shared destinations are allowed, but collection names do not authorize access.

1. You bring your own X developer app: X bills API reads per record to the app owner ($0.005/post, $0.010/user read), so the connector never fronts a shared app.
2. Posts only (recommended): in the X developer portal open Projects &amp; Apps → your app, and complete 'User authentication settings' once if it is empty; that is what creates the app's OAuth 2.0 client. Then on the Keys and tokens page, in the 'OAuth 2.0 Client ID and Client Secret' section, copy the Client ID and Generate the Client Secret (X shows it only once); pass them as client_id and client_secret. Do NOT use the API Key and API Key Secret listed above them: those are OAuth 1.0a keys and will not work. The connector mints its own app-only token from them on every sync; nothing expires, so this connection never needs reconnecting. Add the handles to follow (any public account).
3. Direct messages additionally need an OAuth2 user-context token; X serves DMs to no other auth scheme. First set the app's permissions to 'Read and write and Direct message' (User authentication settings): that setting is what allows the dm.read scope to be granted at all, and changing it later invalidates tokens already issued. Set the app type to the confidential-client option (Web App, Automated App or Bot) so the app has a client secret; both the app-only mint and token refresh require one.
4. Then, for your own account, generate the token pair straight from the portal: the Keys and tokens page has an OAuth 2.0 token generator; pick the scopes (dm.read tweet.read users.read offline.access) and it returns the access token and refresh token together. offline.access is the scope that produces the refresh token. To read a DIFFERENT account's inbox, that account must instead complete the authorization-code flow against your app once, since the portal only issues tokens for the logged-in account.
5. Pass the resulting tokens as access_token AND refresh_token, alongside client_id and client_secret. The access token expires after ~2 hours; the refresh token is what lets the platform renew it indefinitely. A DM connector without refresh_token stops syncing when the access token expires.
6. DM ingest is an explicit opt-in: even with a user token, the inbox appears as its own resource in the selection step and is never synced unless selected.
7. History limits are X's, not ours: the DM API serves only the most recent 30 days of events, so a DM backfill reaches back at most 30 days (the dashboard caps the history window accordingly); post timelines reach roughly the 3,200 most recent posts per account.
8. Spend guards: max_posts_per_account_per_sync (default 500) and max_dms_per_sync (default 1000) cap billed reads per sync and log a warning when hit; sync_profiles is off by default because a user read costs double a post read.

Use provider `twitter` with [Create Connector](/api-reference/v2/endpoint/create-connector), then [discover resources](/api-reference/v2/endpoint/discover-connector-resources) and [configure the resources](/api-reference/v2/endpoint/configure-connector) you want to sync. The [provider description](/api-reference/v2/endpoint/list-connector-providers) supplies the credential fields for your deployment.

## Common mistakes

- A provider page describes indexed content, not the access granted to your credentials. Select resources the connected account can read.
- Synced content is not automatically private to each person. Review [ACL enforcement](/essentials/v2/connectors#enforce-acl) and set resource access rules where needed.
- API-key requests must omit `enforce_acl`, including `false`. Only a signed-in human workspace owner or writer can change **Enforce ACL** in dashboard connector settings, and enabling it requires `acl_supported: true`.
