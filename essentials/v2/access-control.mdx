---
title: "Access Control"
description: "Restrict who can retrieve a document. Declare permissions yourself, or let connectors capture them from the source app."
---

By default every document in a collection is visible to every query against it. With access control, a document can carry an **ACL**: an allow-list of principals who may retrieve it. A query carries the identity it acts for, and HydraDB returns only documents that identity may see.

Use this for internal search where one employee's query must not surface another person's private Slack channel or a restricted Drive file.

<Note>
Access control is opt-in per request. A query with no `acl` field is not filtered, so ACLs on your documents change nothing until your queries send `acl`.
</Note>

## 1. Both halves are required

Either half alone does nothing.

- **Stamp the document:** put an ACL on it at ingest, in a metadata edit, in a connector resource rule, or by letting the connector capture permissions from the source app.
- **Say who is asking:** send `acl` on `POST /query` and `POST /context/list`.

---

## 2. Principals

A principal is one string identifying who may retrieve a document. There are five forms:

- **`user_email:grace@acme.com`:** one person, by email. A bare `grace@acme.com` is accepted and normalized to this form.
- **`domain:acme.com`:** everyone whose email is under that domain. It matches any caller who queries with an email at that domain, without declaring it on the query side.
- **`group:<provider>:<id>`:** a group in the source app, for example `group:slack:C0123` or `group:google:eng@acme.com`.
- **`__public__`:** every identified caller in the collection.
- **`__private__`:** nobody. The stored form of an explicitly empty allow-list.

Principals are lowercased, trimmed, and deduplicated on the way in. `__public__` overrides everything else in the same list. A list containing `__private__` alongside real principals keeps the real principals and drops the sentinel, so `__private__` only means something on its own.

<Warning>
**An absent ACL and an empty ACL are not the same thing.** A document with no `acl` is *unrestricted*. Every document ingested before you adopted access control behaves this way, so adopting it never silently hides existing content. Sending `"acl": []` on a document means "nobody", not "everybody", and is stored as `__private__`.
</Warning>

Limits: 1000 principals per document, 256 characters per principal. For larger audiences, use a `group:` or `domain:` principal.

## 3. Set an ACL

### At ingest, on an app source

Each item in `app_knowledge` accepts an `acl` list:

```json
{
  "id": "slack-C0123-1712345678",
  "kind": "message",
  "provider": "slack",
  "external_id": "1712345678.000100",
  "fields": { "kind": "message", "body": "Q3 comp bands are attached." },
  "acl": ["user_email:grace@acme.com", "group:slack:C0123"]
}
```

Omit `acl` and the document is unrestricted. A malformed principal rejects the whole request with `400` rather than ingesting the document unprotected.

### On an existing source, without re-ingesting

`PATCH /context/{id}/metadata` accepts `acl` and **replaces** the stored list:

```bash
curl -X PATCH 'https://api.hydradb.com/context/slack-C0123-1712345678/metadata' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "collection": "engineering",
    "acl": ["user_email:grace@acme.com", "user_email:hopper@acme.com"]
  }'
```

Replace, not merge: to add a third person, send all three. The three wire states differ:

- **No `acl` key:** the stored ACL is left untouched.
- **`"acl": [...]`:** replaced with exactly that list.
- **`"acl": []` or `"acl": null`:** revoked. Nobody can retrieve it.

An `acl`-only body is a valid edit. You do not have to send metadata with it.

### On a connector resource

Every object synced from a resource inherits the resource's rule. Set it when you configure the connector:

```json
{
  "resources": [
    {
      "resource_id": "C_LEADERSHIP",
      "resource_type": "channel",
      "name": "leadership",
      "acl": ["user_email:grace@acme.com", "user_email:hopper@acme.com"]
    }
  ]
}
```

Or change it later, on its own:

```bash
curl -X PATCH 'https://api.hydradb.com/connectors/:id/resources/C_LEADERSHIP' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{ "acl": ["user_email:grace@acme.com"] }'
```

This applies to **every already-synced document from that resource on the next query**, with no re-sync or re-index, however many documents it has. Use `["__public__"]` to open a resource back up.

## 4. Let connectors capture permissions for you

For supported providers, HydraDB reads the source app's own permissions on every sync and applies them as ACLs, so you do not maintain a parallel permission model.

- **Slack:** public channels are visible workspace-wide. Private channels are visible only to their members, resolved to member emails.
- **Google Drive:** per-file sharing, covering user, group, domain, and public grants. Permission-only changes (a share with no edit to the file) are picked up through the Drive changes feed, which content sync alone cannot see.
- **GitHub:** repository visibility. Private repos also capture the collaborator list when every collaborator has a visible public email. Otherwise your resource rule governs.
- **Confluence:** space-level view permissions, with groups expanded to member emails, plus per-page view restrictions.
- **Jira:** who holds Browse access per project, plus per-issue security levels.

Capture is also built for other providers, including GitLab, Linear, Dropbox, Zendesk and PagerDuty, and is switched on per provider. Capture can be turned off without a deploy. For a provider without capture, set a rule per resource with `acl`, as described [above](#on-a-connector-resource). Its documents stay unrestricted until you do.

If HydraDB cannot read a resource's permissions from the provider, a resource with no rule of yours is readable by everyone until the next successful read, while a rule you set still applies. [Get Connector Status](/api-reference/v2/endpoint/get-connector-status) reports an `acl_warning` on the resource meanwhile.

Precedence, when both exist:

- A **per-document** permission from the provider (a Drive file's own sharing) wins over everything.
- A provider verdict of "this resource is public" will **not** override a rule you set. Restricting a public channel is deliberate, and enabling capture never widens it back.
- Otherwise the provider's resource-level verdict wins over your rule, because the provider is the fresher source of truth.

## 5. Query on behalf of someone

Pass the caller's identity as `acl` on `POST /query`. `POST /context/list` takes the same field with the same meaning.

```bash
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "what are the Q3 comp bands",
    "database": "acme_corp",
    "collection": "engineering",
    "acl": ["grace@acme.com"]
  }'
```

A document is returned when **any** of these holds:

- it has no stored ACL (unrestricted),
- it is `__public__`,
- its ACL contains one of the caller's principals.

An email is usually enough. `__public__` is added for you, and the domain principal is derived from the email, so querying as `grace@acme.com` also matches anything shared with `domain:acme.com`. Group membership is not derived, so send group principals explicitly: `"acl": ["grace@acme.com", "group:slack:C0123"]`.

What each query-side value does:

- **No `acl` field:** no filtering. Everything in scope is retrievable.
- **`"acl": []`:** same as omitting it. On a query, an empty list does not mean "nobody".
- **`"acl": ["*"]`:** same as omitting it. An explicit "search as an administrator".
- **`"acl": ["grace@acme.com"]`:** filtered to what Grace may see.
- **`"acl": ["__private__"]`:** public and unrestricted content only.

<Warning>
An entry that is neither an email nor a recognized principal is kept as-is and matches nothing but public content. A typo narrows results and never widens them. If a caller sees less than you expect, check the principal spelling first.
</Warning>

Access control is independent of [metadata filters](/essentials/v2/metadata), and the two combine. Filters express *what you are looking for*. ACLs express *what you are allowed to find*. A caller cannot widen their own visibility with a filter.

## 6. Revoking access

When each change takes effect:

- **`PATCH /context/{id}/metadata` with a new `acl`:** immediately, on the next query.
- **`PATCH /connectors/{id}/resources/{resource_id}` with a new `acl`:** immediately, on the next query, for every document from that resource.
- **A permission change in the source app** (a channel goes private, a Drive share is removed): on the connector's next sync cycle.

Deleting a rule does **not** widen access on its own. Visibility only widens from a value you positively set. To open a restricted resource back up, set its ACL to `["__public__"]` rather than clearing it.

---

## 7. Common mistakes

- **ACLs are set but every query still returns everything:** the queries send no `acl`. Add `"acl": ["<caller email>"]`.
- **A provider-side permission change has not applied yet:** it lands on the next sync cycle. See [Revoking access](#6-revoking-access).
- **A caller who should see a document sees nothing:** check principal forms and spelling on both sides. `group:slack:C0123` matches only a query that declares that group, and emails match exactly after lowercasing and trimming.
