---
title: "Connected Subgraph"
openapi: "api-reference/v2/openapi.json GET /context/{id}/subgraph"
description: "Retrieve the thread, parent and child sources, and declared links around one source."
---

Use this endpoint when a query result needs more context, such as the replies to a Slack message. Pass an `id` returned by [Query](/api-reference/v2/endpoint/query), [List Context](/api-reference/v2/endpoint/list-context), or [Ingest Context](/api-reference/v2/endpoint/ingest-context) to retrieve the starting source, the sources connected to it, and their relationships.

The endpoint follows threads, parent-child relationships, and forceful relations (links you declare between sources). For relationships extracted from text, such as service dependencies, use [Inspecting Context Relations](/api-reference/v2/endpoint/source-relations).

<RequestExample>

```python Python SDK
subgraph = client.context.subgraph(
    id="slack_C0BE77_1788320073",
    database="acme_corp",
    collection="eng_slack",
    depth=3,
)
```

```typescript TypeScript SDK
const subgraph = await client.context.subgraph({
  id: "slack_C0BE77_1788320073",
  database: "acme_corp",
  collection: "eng_slack",
  depth: 3,
});
```

```bash cURL
curl -G 'https://api.hydradb.com/context/slack_C0BE77_1788320073/subgraph' \
  -H "Authorization: Bearer <your_api_key>" \
  -H "API-Version: 2" \
  --data-urlencode "database=acme_corp" \
  --data-urlencode "collection=eng_slack" \
  --data-urlencode "depth=3"
```

</RequestExample>

## Reading the response

- `sources[]` contains the starting source and the connected sources. Pass a `source_id` to [Inspect Context](/api-reference/v2/endpoint/fetch-content) to read its content.
- Each source includes its distance from the starting source in `depth`. The starting source has `depth: 0`.
- `discovered_via` identifies the source that led to this one. `discovered_relation` describes the connection, such as `same_thread`, `parent`, `child`, or a link declared at ingestion.
- `relations[]` describes links between those sources, such as thread membership and parent-child relationships.
- `auxiliary_relations[]` includes related people, comments, and attachments.
- `is_truncated` and `auxiliary_truncated` indicate that response limits were reached. `is_truncated` is `true` when `max_sources` clips the traversal.

## Behavior notes

- **IDs with reserved characters:** URL-encode the `id` if it contains reserved characters. An ID containing a literal `/` cannot be written as one path segment; pass it as `GET /context/subgraph?id=...` instead. Python and TypeScript SDK 2.1.7 use this form for every ID.
- **Knowledge and memory graphs:** `type` selects which graph the `id` belongs to (default `"knowledge"`). The two graphs are completely separate.
- **Collection:** Omit `collection` to use the database's default collection.
- **Limits:** `depth` is the maximum traversal depth in hops, from `1` to `10` (default `5`). `max_sources` caps the sources returned, from `1` to `1000` (default `200`).
- **Access control:** `acl` lists the principals to answer as. Only sources those principals may see are returned, filtered at every hop. Repeat or comma-separate values, or omit `acl` for no caller-supplied ACL filtering. For enforced connectors, the authenticated caller is used instead; see [ACL enforcement](/essentials/v2/connectors#enforce-acl).

## Errors

Common codes: `400 INVALID_INPUT` (missing `database` or `id`, `depth` outside `1` to `10`, or `max_sources` outside `1` to `1000`), `404 DATABASE_NOT_FOUND`, `500 INTERNAL_ERROR` (a transient graph read failure; retry the request). See [Error Responses](/api-reference/v2/error-responses) for the full list.
