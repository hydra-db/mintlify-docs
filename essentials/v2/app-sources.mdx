An app source is one record your connector already parsed: an email, a chat message, a ticket, a wiki page, a CRM object, a comment, or an attachment.

Send app sources to [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) in the `app_knowledge` multipart field. The body uses the same app-native model as v1, not a generic `content` object: `kind`, `provider`, `external_id`, `fields`, metadata, attachments, comments, and typed relations.

<Info>
  App sources land in the [Knowledge](/essentials/v2/knowledge) store. Query them with [`POST /query`](/api-reference/v2/endpoint/query) and `type: "knowledge"` or `type: "all"`. **`query_apps`** is on by default and turns on the app-aware lane, so do not send `query_apps: false` for app data. Use `mode: "thinking"` for app relation expansion and connected context. See [How app sources affect query](#9-how-app-sources-affect-query).
</Info>

## 1. App source or file upload

- **App source:** you already have the item's text and fields, such as a Slack message, Jira description, Notion page, or email body. Send it in `app_knowledge` as a stringified JSON object or array. HydraDB normalizes app identity, extracts searchable text from `fields`, indexes attachments and comments, and builds app graph links. Best for connectors and live app syncs.
- **File upload:** HydraDB should parse a file (PDF, DOCX, MD, CSV, TXT). Send it in `documents`, plus optional `document_metadata`. HydraDB parses, chunks, and indexes it.

Both feed the same Knowledge retrieval. App sources add provider IDs, object kinds, actors, threads, parents, and explicit relations for app-aware recall.

---

## 2. Fields

Every app source becomes one knowledge source, identified by `id`, `kind`, `provider`, and `external_id`. `external_id` is the item's own ID, not its channel, project, or space. Put those in `metadata`. The [field reference](#top-level-app-source-fields) lists every field.

The searchable text lives in `fields`, not in a top-level `content` object. `content` is the older generic knowledge payload, and it hides the actors, thread IDs, parent IDs, and typed body fields that app parsing reads. Put the text in the typed field for the item's `kind`:

- `email`: `fields.subject`, `fields.body`
- `message`: `fields.body`
- `ticket`: `fields.title`, `fields.description`
- `knowledge_base`: `fields.title`, `fields.body`
- `comment`: `fields.body`
- `meeting`: `fields.title`, `fields.body`
- `custom`: `fields.data`

Set `fields.kind` to the same value as the top-level `kind`. A mismatch is rejected.

## 3. Ingest an app source

`app_knowledge` is nested JSON in a `multipart/form-data` request, so send it as a **JSON-stringified** form value (object or array). Include the scope fields in each item too. They must match the form-level `database` and `collection`.

## 4. Incremental ingestion

Use the same endpoint for backfill and live updates. Each provider event either updates a source or creates one.

- **Ticket title, description, or status changed:** re-ingest the `kind: "ticket"` item with the same `id` and `external_id`, and `upsert: true`.
- **New Linear, Jira, or Zendesk ticket comment:** ingest a **new** `kind: "comment"` source with its own `id` and `external_id`. Put the parent ticket's provider ID in `fields.parent_id`.
- **Edited ticket comment:** re-ingest it with the same `id` and `external_id`.
- **Deleted ticket comment:** call [`DELETE /context`](/api-reference/v2/endpoint/delete-source) with the comment source `id`.
- **New Slack or Teams message:** ingest a **new** `kind: "message"` source with `fields.thread_id` and, when available, `fields.parent_id`. Do not re-ingest the whole thread per reply: that loses message-level authorship and timestamps and wastes indexing.
- **New email reply:** ingest a **new** `kind: "email"` source with `fields.thread_id` and `fields.reply_to_id`.
- **New Notion or Confluence page:** ingest a **new** `kind: "knowledge_base"` source. The space belongs in metadata.
- **Notion or Confluence page edited:** re-ingest it with the same `id` and `external_id`.

<Warning>
  `upsert: true` replaces the whole source with the same `id`. Upserting a parent ticket or page with only a new `comments[]` item can drop existing content. For live events, ingest each new comment as its own `kind: "comment"` source.
</Warning>

## 5. Per-app patterns

### Slack message with thread reply and attachment

A Slack thread is several `message` sources connected by `thread_id`, `parent_id`, and optional explicit relations.

```json
{
  "id": "slack_C01_1716213600_000100",
  "database": "acme_corp",
  "collection": "default",
  "title": "Auth rollback - thread root",
  "type": "slack",
  "kind": "message",
  "provider": "slack",
  "external_id": "1716213600.000100",
  "url": "https://acme.slack.com/archives/C01/p1716213600000100",
  "timestamp": "2026-05-20T10:00:00Z",
  "fields": {
    "kind": "message",
    "body": "The auth rollback notes are attached here.",
    "author": "alice",
    "thread_id": "1716213600.000100",
    "created_at": "2026-05-20T10:00:00Z",
    "url": "https://acme.slack.com/archives/C01/p1716213600000100"
  },
  "metadata": { "channel": "engineering", "workspace": "acme" },
  "attachments": [
    {
      "id": "F012AUTH",
      "title": "auth-rollback-notes.md",
      "url": "https://files.slack.com/files-pri/T01-F012AUTH/auth-rollback-notes.md",
      "content_type": "text/markdown",
      "content": { "markdown": "# Auth rollback\nRollback starts by disabling the new token refresh path." }
    }
  ]
}
```

For a reply, ingest a second source. `fields.parent_id` points to the parent's provider `external_id`. An explicit relation can point to the parent's HydraDB ID or its provider ID.

```json
{
  "id": "slack_C01_1716213700_000200",
  "database": "acme_corp",
  "collection": "default",
  "title": "Re: Auth rollback - reply",
  "type": "slack",
  "kind": "message",
  "provider": "slack",
  "external_id": "1716213700.000200",
  "timestamp": "2026-05-20T10:01:40Z",
  "fields": {
    "kind": "message",
    "body": "Looking now - will pair with Bob in 10.",
    "author": "carol",
    "thread_id": "1716213600.000100",
    "parent_id": "1716213600.000100",
    "created_at": "2026-05-20T10:01:40Z"
  },
  "metadata": { "channel": "engineering", "workspace": "acme" },
  "relations": [
    {
      "predicate": "reply_to",
      "target": { "external_id": "1716213600.000100", "provider": "slack" }
    }
  ]
}
```

### Jira ticket with linked issues

The ticket body goes in `fields.description` and workflow fields in `fields`. Scope and filter values, such as project and environment, go in `metadata`.

```json

  "database": "acme_corp",
  "collection": "default",
  "title": "Login page returns 500",
  "type": "jira",
  "kind": "ticket",
  "provider": "jira",
  "external_id": "AUTH-123",
  "url": "https://jira.example.com/browse/AUTH-123",
  "timestamp": "2026-05-20T10:00:00Z",
  "fields": {
    "kind": "ticket",
    "title": "Login page returns 500",
    "description": "Invalid credentials return HTTP 500 instead of 401. Reproduces on staging and prod.",
    "status": "open",
    "priority": "high",
    "assignee": "alice",
    "reporter": "bob",
    "parent_id": "AUTH-100",
    "linked_issue_ids": ["AUTH-124", "AUTH-125"],
    "created_at": "2026-05-20T10:00:00Z",
    "url": "https://jira.example.com/browse/AUTH-123"
  },
  "metadata": { "project": "AUTH", "environment": "production" },
  "relations": [
    { "predicate": "child_of", "target": { "external_id": "AUTH-100", "provider": "jira" } },
    { "predicate": "linked_to", "target": { "external_id": "AUTH-124", "provider": "jira" } },
    { "predicate": "linked_to", "target": { "external_id": "AUTH-125", "provider": "jira" } }

}
```

Comments are first-class app sources. Use `fields.parent_id` for the parent ticket's provider ID, and `relations[]` for a cross-provider link or an explicit relation.

  "collection": "default",
  "title": "Comment on AUTH-123",
  "type": "linear_comment",
  "kind": "comment",
  "provider": "linear",
  "external_id": "c123",
  "url": "https://linear.app/acme/issue/AUTH-123#comment-c123",
  "timestamp": "2026-05-25T07:00:00Z",
  "fields": {
    "kind": "comment",
    "body": "I found the repro steps. Attaching HAR.",
    "author": "alice@acme.com",
    "parent_id": "AUTH-123",
    "thread_id": "AUTH-123",
    "created_at": "2026-05-25T07:00:00Z",

## 6. Relations

Use `relations[]` for a link that matters for search and cannot be safely inferred from the text.

```json
{
  "relations": [
    {
      "predicate": "blocks",
      "target": {
        "external_id": "RELEASE-2026-05",
        "provider": "jira"
      },
      "properties": {
        "reason": "release blocker"
      }
    },
    {
      "predicate": "related_to",
      "target": {
        "id": "src_existing_source"
      }
    }
  ]
}
```

The target takes either shape:

- `{ "id": "..." }`: you know the HydraDB ID.
- `{ "external_id": "...", "provider": "..." }`: HydraDB resolves the provider ID in that provider's namespace.

Useful predicates, with direction:

- `reply_to`: from a reply, message, or email to its parent message or email.
- `comment_on`: from a comment to its parent ticket, page, or source.
- `forwarded_from`: from a forwarded email to the original email.
- `child_of`: from a child ticket, page, or custom record to its parent.
- `linked_to`: from a source to a related peer source.
- `blocks`: from the blocker to the blocked item.
- `caused_by`: from the effect to the cause.
- `related_to`: a generic association.

<Warning>
  External IDs are only unique inside a provider namespace, so a target with `target.external_id` and no `target.provider` is rejected.
</Warning>

<Note>
  For app sources, prefer the `relations[]` shape above. `relations.ids` is the forceful-relation shortcut for files and legacy payloads, and carries no predicate or provider.
</Note>

## 7. Attachments and comments

Attachments and embedded `comments[]` add searchable child content to the app source. Send `attachments[].content` only when you already extracted the text. An attachment URL is metadata: HydraDB does not fetch arbitrary URLs from app-source payloads.

```json
{
  "attachments": [
    {
      "id": "att-har-1",
      "title": "staging-login.har",
      "url": "https://...",
      "content_type": "application/json",
      "content": { "text": "HAR trace shows repeated 302 redirects after token refresh." },
      "properties": { "source": "linear", "comment_id": "c123" }
    }
  ],
  "comments": [
    {
      "id": "c-1",
      "author": "carol",
      "body": "Confirmed on staging.",
      "created_at": "2026-05-20T11:00:00Z"
    }
  ]
}
```

Use embedded `comments[]` for full backfill snapshots. For live updates, use first-class `kind: "comment"` sources, so you can add, edit, or delete one comment without replacing the parent. See [Incremental ingestion](#4-incremental-ingestion).

## 8. Metadata: scoping vs display

- **`metadata`:** the canonical filterable field, for deterministic filtering with `metadata_filters`. Declare the key in `database_metadata_schema`. Examples: `department`, `channel`, `project`, `space`, `pipeline`, `environment`, `region`.
- **`additional_metadata`:** the canonical free-form field, for display, citation, debugging, per-source bookkeeping, or keys not worth adding to the schema. Examples: `slack_ts`, `ticket_key`, `comment_id`, `raw_provider_payload_id`, `golden_run`. Filters on it are slower and need nested syntax, so put hot filters in `metadata`.

Some request shapes accept legacy aliases: `tenant_metadata` for `metadata`, `document_metadata` for `additional_metadata`. Filter with top-level keys for `metadata` and a nested `additional_metadata` object:

```json
{
  "query": "auth rollback discussion",
  "metadata_filters": {
    "channel": "engineering",
    "additional_metadata": { "slack_ts": "1716213600.000100" }
  }
}
```

See [Scoping using metadata](/essentials/v2/metadata) for the full schema and filter rules.

## 9. How app sources affect query

With `query_apps: true` (the default), an app-aware lane runs alongside normal semantic and lexical retrieval. `query_apps: false` leaves only text and vector retrieval, with no app-aware ID or relation expansion. The app lane uses signals raw text lacks:

- **`kind`, `provider`:** route queries such as "Slack messages", "Jira tickets", or "ticket comments".
- **`external_id`:** exact ID lookup, such as `AUTH-123`, `1716213600.000100`, or `page_abc`.
- **Workflow fields:** `status`, `priority`, `assignee`, `reporter`, and similar, when the query implies them.
- **Actors:** queries like "emails from Alice", "tickets assigned to Bob", or "comments by Carol".
- **Thread and parent fields:** expansion around replies, parents, children, epics, subtasks, accounts, deals, and pages.
- **`relations[]`:** traversal of explicit links like `linked_to`, `blocks`, `comment_on`, `reply_to`, and `child_of`.
- **Attachments and comments:** search over extracted attachment text and embedded comment bodies.

### Parent and child query

A child's `fields.parent_id` can match another source's `external_id` under the same `provider`. The app lane finds an initial source by text, exact ID, actor, provider, or kind. In `thinking` mode, words like "parent", "children", "epic", "subtask", "account", or "deal" can trigger expansion around it.

```json
{
  "database": "acme_corp",
  "query": "show me tickets linked to AUTH-123 and comments from Alice",
  "mode": "thinking",
  "query_apps": true,
  "max_results": 10
}
```

## 10. Field reference

### Top-level app source fields

| Field | Why send it | Query / ingestion effect |
|---|---|---|
| <Field name="id" type="string" required /> | Stable HydraDB ID for this item. | Upsert key, delete/status/list ID, and direct relation target. |
| <Field name="database" type="string" required /> | Database that owns the item (formerly `tenant_id`). | Must match the form-level `database` when present. |
| <Field name="collection" type="string" required /> | Logical partition (formerly `sub_tenant_id`). Use `"default"` if you do not partition. | Must match the form-level `collection` when present. |
| <Field name="title" type="string" recommended /> | Subject, page name, ticket title, or message label. | Improves display, citations, and semantic matching. |
| <Field name="type" type="string" recommended /> | Source category such as `slack`, `gmail`, `jira`, `notion`, `salesforce`, or `linear_comment`. | Preserved for source rendering and analytics; not the app discriminator. |
| <Field name="kind" type="email, message, ticket, knowledge_base, comment, meeting, custom" recommended /> | App object kind. | Selects the app parser and query behavior. |
| <Field name="provider" type="string" recommended /> | App namespace such as `slack`, `gmail`, `jira`, `notion`, `salesforce`, or `linear`. | Prevents ID collisions and scopes relation resolution. |
| <Field name="external_id" type="string" recommended /> | Stable provider ID for this exact item. | Exact lookup and relation/hierarchy resolution. |
| <Field name="url" type="string" /> | Canonical link back to the provider item. | Improves citations and source navigation. |
