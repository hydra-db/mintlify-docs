## The mental model

To create a unified context substrate for your AI, a connected brain for every agent, you need context, personalization, and the right scopes. We want you to build your own memory layers, context stores, and opinionated agent experiences on top.

---

## Memories

Memories are user-scoped preferences, conversation history, and inferred behavioral traits. They ensure retrieval is personalized. 

The same person searching "Project acme changelog" might expect different results than a colleague working on the same project but with a different title. HydraDB helps you factor that in.

Memories are not set once at onboarding. They compound with interactions, so your agent becomes more accurate and feels more familiar to the end user over time. 

When you ingest a memory with `infer: true`, HydraDB extracts the underlying preference. You can ship raw behavioral logs (interaction events, UI actions, dialogue), and HydraDB derives the structured insight.

When you ingest a memory with `infer: false` (the default), HydraDB stores exactly what you send - useful for deterministic facts you've already captured.

---

## Knowledge

Knowledge in HydraDB represents the entire working context you want your agents to access: PDFs, DOCX, Markdown, Slack threads, Notion pages, CSVs, emails.

HydraDB parses, relates, and stores each source into the graph. At search time, the graph traversal step surfaces structurally connected materials that vanilla search alone would miss.

---

## Why are memories & knowledge separate

Memories and Knowledge are distinct at the storage layer, not just conceptually:

|  | Memories | Knowledge |
| --- | --- | --- |
| **Content** | User preferences, conversation history, inferred traits | Documents, files, app-generated content |
| **Scope** | Per-user (scoped by `sub_tenant_id`) | Can be shared across all users in a tenant |
| **Mutability** | Dynamic - evolves with every interaction | Versioned - replaced or deleted explicitly |
| **Search `type`** | `"memory"` | `"knowledge"` |
| **Inference** | `infer` flag extracts traits automatically | Not applicable - content is parsed and chunked |
| **Search `type`** | `"memory"` | `"knowledge"` |
| **Inference** | `infer` flag extracts traits automatically | Not applicable - content is parsed and chunked |

For personalized answers grounded in shared documents, call `POST /search` with `typtype: "all"` to merge both stores in a single request.

## Querying

Querying is how agents read from HydraDB. After storing data knowing _what_ to retrieve, _when_, and _why_ is the hard part.

HydraDB's search is a multi-stage pipeline that combines graph traversal to narrow down to relevant concepts, hybrid retrieval to pinpoint exact context, and metadata filtering to reduce noise. All in a single API call, under 100ms.

Vector search asks _"what's similar to my query?"_ Graph traversal asks _"What's connected to it?"_  HydraDB does both, weighs the results by usefulness, and returns precise & personalized context for the current task.

## Tenants and Sub-Tenants

A **Tenant** is a physical isolated space for storing context. No tenant can read another tenant's data. For example, in most cases, each enterprise customer can represented by its own tenant.

A **sub-tenant** is a logical partition within a tenant - a user, team, project, or department.

- **B2B** - each customer is a tenant; their departments are sub-tenants
- **B2C** - one tenant for the organization; each end user is a sub-tenant
