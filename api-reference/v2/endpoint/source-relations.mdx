openapi: "api-reference/v2/openapi.json GET /context/relations"

---

Inspect the relationships HydraDB extracted from your content, such as `PaymentsWorker` depends on `OrdersDB`. Each relationship is a **triplet**: a starting entity (a named person, service, or topic), a relationship, and a target entity.

Pass `id` to scope to a single source, or omit it to return all relations in the collection. Set `type=memory` when `id` belongs to a memory.

<RequestExample>

```python Python SDK
relations = client.context.relations(
    database="acme_corp",
    id="billing_runbook_v3",
    limit=500,
)
```

```typescript TypeScript SDK
const relations = await client.context.relations({
  database: "acme_corp",
  id: "billing_runbook_v3",
  limit: 500,
});
```

```bash cURL
curl -G 'https://api.hydradb.com/context/relations' \
  -H "Authorization: Bearer <your_api_key>" \
  -H "API-Version: 2" \
  --data-urlencode "database=acme_corp" \
  --data-urlencode "id=billing_runbook_v3" \
  --data-urlencode "limit=500"
```

## Pagination pattern

Pass each response's `next_cursor` back as `cursor` until it is `null`. If `next_cursor` is `null` while `is_truncated` is `true`, the export is incomplete: retry the page or increase `limit`.

```python
all_relations = []
cursor = None

while True:
    page = client.context.relations(
        database="acme_corp",
        id="billing_runbook_v3",
        limit=1000,
        cursor=cursor,
    )
    all_relations.extend(page.data.relations)
    if page.data.next_cursor is None:
        if page.data.is_truncated:
            raise RuntimeError(
                "Relations export is incomplete. Retry this page or increase limit."
            )
        break
    cursor = page.data.next_cursor
```

## Behavior notes

- **Cursor opacity:** `next_cursor` is opaque (currently the timestamp, in Unix seconds, of the last group returned). Do not construct it client-side or assume meaning: pass back exactly what the server returned.
- **Full-graph exports:** Omit `id`, use a small `limit`, and paginate. `limit` counts relation groups, from `1` to `10000` (default `5000`).
- **Ordering:** `data.relations[]` comes back newest first, by each group's latest relation `timestamp`, not by relevance.
- **Unknown `id`:** Returns `200` with an empty `relations` list, not an error. So does an `id` the `acl` principals may not see.
- **`auxiliary_relations`:** The structural graph around the sources (who sent a message, which comments hang off it), in the same triplet shape. It does not count against `limit`; `auxiliary_truncated` is `true` when it was clipped.
- **Graph completeness:** A source's relations are fully populated only once its `indexing_status` reaches `completed`. Sources in `graph_creation` are searchable, but their relations may still be in flight.
- **`timestamp` format differs by endpoint:** On this endpoint each relation's `timestamp` is an ISO-8601 string (for example `2026-05-12T08:14:00Z`). The same relations surfaced as passthrough on [Query](/api-reference/v2/endpoint/query) (in `graph_context`) and [List Context](/api-reference/v2/endpoint/list-context) carry `timestamp` as a Unix epoch float (seconds) instead. Normalize before comparing relation timestamps across endpoints.
- **Access control:** `acl` lists the principals to answer as. Only relations from sources those principals may see are returned. Repeat or comma-separate values, or omit `acl` for no caller-supplied ACL filtering. For enforced connectors, the authenticated caller is used instead; see [ACL enforcement](/essentials/v2/connectors#enforce-acl).

## Errors

Common codes: `400 INVALID_INPUT` (missing `database`, a `limit` outside `1` to `10000`, or a non-numeric `cursor`), `404 DATABASE_NOT_FOUND`, `500 INTERNAL_ERROR` (a transient graph read failure; retry the request). See [Error Responses](/api-reference/v2/error-responses) for the full list.
