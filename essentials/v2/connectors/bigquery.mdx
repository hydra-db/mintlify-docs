Use the BigQuery connector to bring the following content into HydraDB.

## What syncs

The provider description does not enumerate fixed indexed object types. Use the setup notes below when available; the resource picker shows what your connection can select.

## Connect

Create one connector per account, using that account's credentials where required. Use a separate connector for a different account; see [account scopes](/essentials/v2/connectors#6-connect-several-accounts-from-one-provider). Shared destinations are allowed, but collection names do not authorize access.

1. Connect with a service-account key: paste the downloaded key file as credentials_json (grant the account the BigQuery Data Viewer and BigQuery Job User roles). client_email + private_key, or client_id + client_secret + refresh_token, also work.
2. Pick which tables to sync in the resource-selection step; each table's rows become searchable documents.
3. Replication is configured PER TABLE, alongside the selection: pass table_configs on POST /connectors/&#123;id&#125;/configure; the same request that selects the tables; with exactly one mode per table. The dashboard collects this on the table-selection screen.
4. Tables with a timestamp column that changes on every insert/update (updated_at, modified_ts, …): make it the sync cursor; table_configs: [&#123;"table": "dataset.table", "replication_key": "updated_at"&#125;]; and each sync reads only new and changed rows.
5. Append-only tables with no such column: use &#123;"table": "dataset.table", "change_history": "appends"&#125;. New rows stream from BigQuery's own change log; no schema change, no setup.
6. Tables that also receive UPDATEs but have no cursor column: use &#123;"table": "dataset.table", "change_history": "changes"&#125; instead, and run this once in BigQuery (no schema change, does not touch your data): ALTER TABLE dataset.table SET OPTIONS(enable_change_history=true).
7. Change-history backfill never blocks live syncing: changes are captured from the moment you connect, while existing rows backfill in the background in bounded slices per sync cycle. On a very large table the full backfill can take many cycles; expect it to be slow. To skip it, add "snapshot": "none" to that table's table_configs entry (only rows that change after connecting are indexed), or "snapshot": 10000 to cap the backfill at that many rows.
8. Fleet-wide fallbacks (optional, credential fields): a top-level "replication_key" applies that cursor to every synced table that has the column; "change_history" ("appends" | "changes") covers tables that still have no cursor. Per-table table_configs override both.
9. A table with no cursor and no change_history re-reads in full every sync cycle; fine for small reference tables, expensive for large ones. The dashboard requires a mode per table; API/SDK consumers should always send table_configs (or the fleet-wide fields).

Use provider `bigquery` with [Create Connector](/api-reference/v2/endpoint/create-connector), then [discover resources](/api-reference/v2/endpoint/discover-connector-resources) and [configure the resources](/api-reference/v2/endpoint/configure-connector) you want to sync. The [provider description](/api-reference/v2/endpoint/list-connector-providers) supplies the credential fields for your deployment.

## Common mistakes

- A provider page describes indexed content, not the access granted to your credentials. Select resources the connected account can read.
- Synced content is not automatically private to each person. Review [ACL enforcement](/essentials/v2/connectors#enforce-acl) and set resource access rules where needed.
- API-key requests must omit `enforce_acl`, including `false`. Only a signed-in human workspace owner or writer can change **Enforce ACL** in dashboard connector settings, and enabling it requires `acl_supported: true`.
