Supabase sends each insert, update and delete on the tables you choose to HydraDB, through Database Webhooks you add in Supabase. Each row is one document, with one searchable line per content column. HydraDB needs no Supabase credentials and does not read your database.

Rows that existed before you added the webhooks do not come across. Row-level security is not imported, so every row is visible to everyone who can query the collection unless you set an access rule. Deleting a row in Supabase asks HydraDB to remove its document, which can stay if the row is still being indexed or a newer change has replaced it. Changes sent while the connector is paused are lost.

<Note>
Supabase is in beta.
</Note>

## Permissions

<Warning>
Supabase permissions are not imported, so **Enforce ACL** is unavailable for this connector. Every synced item is visible to everyone who can query the collection, unless you [set an access rule on the resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).
</Warning>

- Supabase row-level security policies are not reproduced.

API-key requests must omit `enforce_acl`, including `false`. See [ACL on synced content](/essentials/v2/connectors#5-acl-native-rbac-awareness).

## Before you connect

<Warning>
A row is identified by its table name and primary key only. If two Supabase projects or connectors send a table with the same name to the same collection, rows with the same key overwrite each other. Send them to separate collections.
</Warning>

### Credentials

HydraDB stores no Supabase credentials. Each Supabase webhook sends its changes with a HydraDB API key and the connector id in its headers.

<ResponseField name="tables" type="string list" required>
The tables to accept, schema-qualified, one per line, for example `public.orders`. A change for any other table is refused.
</ResponseField>

### Set it up

<Steps>
  <Step title="List your tables">
    Create the Supabase connector in HydraDB and list the tables you want as `tables`, schema-qualified. A query over `information_schema.tables` can produce the list. An entry in a system schema, or an invalid entry, is rejected.
  </Step>
  <Step title="Describe each table, if needed">
    Through the API, you can send a schema for a table in `provider_metadata.schema` when you add it. A schema can name the primary key, the role of each column, a title template, the timestamp column and foreign keys. Without one, the primary key is `id` and the column rules under What gets synced apply.
  </Step>
  <Step title="Add a webhook for each table">
    In Supabase, add a Database Webhook on each table for `INSERT`, `UPDATE` and `DELETE` that sends a POST request to HydraDB's `/webhooks/supabase` endpoint.
  </Step>
  <Step title="Set the webhook headers">
    Set the `Authorization` header to `Bearer` followed by a HydraDB API key, and the `X-HydraDB-Connector` header to the connector id.
  </Step>
</Steps>

One connector covers the tables you list in it.

<Accordion title="Connect through the API">

Use provider `supabase` with [Create Connector](/api-reference/v2/endpoint/create-connector). Then call [Discover Connector Resources](/api-reference/v2/endpoint/discover-connector-resources) to list the resources the connector can sync, and [Configure Connector](/api-reference/v2/endpoint/configure-connector) to choose what to sync.

</Accordion>

## Keeping in sync

- **First sync:** Nothing is loaded when you connect. Only changes made after the webhooks exist arrive. To bring in an existing row, change it or send its change again.
- **New and changed items:** Each insert or update arrives as it happens and updates the row's document. An insert with no content columns is skipped.
- **Edits:** An update replaces the row's document. A primary-key change asks HydraDB to remove the document under the old key. An update that empties every content column asks HydraDB to remove the row's document under its current key and any replaced key. As with a delete, a document can stay if it is still being indexed or a newer change has replaced it.
- **Deletions:** A delete asks HydraDB to remove the row's document. The document can stay if the row is still being indexed when the delete arrives, or a newer change has already replaced it.
- While the connector is paused, every change, deletes included, is refused, and Supabase does not send it again.
- A change for a table you did not list is refused with an error, so a misconfigured webhook is visible.
- Changes count against HydraDB's ingestion rate limit. A bulk update sends one request per row.

## What gets synced

### Rows

- **One document:** One row of a listed table, identified by its table and primary key.
- **Title:** The table's title template with column values filled in. Without a template, the table name and the row's primary key.
- **Text:** One `column: value` line per non-empty content column, sorted by column name. Nested JSON is written as compact JSON. Without a schema, `id` is the key, timestamp columns, status columns and columns ending in `_id` are kept out of the text, columns starting with `_` are ignored, and every other column is content. Column roles in a schema override these rules. The title is searchable too, so a title template can put a key or status value into searchable text.
- **Date:** The value of the timestamp column named in the table's schema. Without one, the row has no date.
- **Link back:** None.

<ResponseField name="Content columns" type="Searchable text">
Each content column's value, one line per column.
</ResponseField>

<ResponseField name="Timestamp column" type="Result date">
The column the schema names as the timestamp. Its value is the result date. This date is not searchable as a separate field.
</ResponseField>

<ResponseField name="Foreign keys" type="Graph connection">
Each foreign key named in the schema, when it has a value, links the row to the row it references. One declaration covers one column, so a key made of several columns cannot be linked. Not searchable.
</ResponseField>

<Accordion title="Stored only, not searchable (1)">

<ResponseField name="table, row_key, updated_at" type="Stored only">
The table name, the row's key and its timestamp value.
</ResponseField>

</Accordion>

**Example searches**

- What do our orders rows say about delayed shipments?
- Which support_tickets rows mention a refund?

## How it fits into the graph

- Rows use the Record class.

[Graph classes](/essentials/v2/connector-providers#graph-classes) explains each class.

**Connections Supabase creates**

- A row to each row its schema's foreign keys reference.
- Each row is grouped under its table.
- No links to items in other tools.

**People and groups**

No one is attached to a row as a person.

**Found in the text**

The content columns of each row. HydraDB identifies people, organizations, projects and other named things in this text. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Not synced

- Rows that existed before the webhooks were added.
- Tables not listed in the connector. Their changes are refused.
- Changes sent while the connector is paused.
- Columns with the ignore role. Columns starting with `_` are ignored unless a schema gives them another role.
- Row-level security policies.
