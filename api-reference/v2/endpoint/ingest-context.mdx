import { Field } from "/snippets/field.jsx";

Pick the form fields by what you send:

- **`type=knowledge`, files:** PDFs, Office and iWork files, spreadsheets, images, and plain text in `documents`, for HydraDB to parse. See [Supported file formats](#supported-file-formats).
- **`type=knowledge`, app sources:** JSON you already extracted (Slack threads, Notion pages, emails, tickets) in `app_knowledge`. See [App sources](/essentials/v2/app-sources).
- **`type=memory`:** per-user content in `memories`, scoped by `collection`. `infer: true` extracts preferences from raw signals; `infer: false` (the default) stores the text verbatim. See [Memories](/essentials/v2/memories).

## Form fields

| Name | Description |
| --- | --- |
| <Field name="type" type="&#x22;knowledge&#x22; or &#x22;memory&#x22;" /> | Use singular `"memory"` for memories. (default=`"knowledge"`) |
| <Field name="database" type="string" required /> | Target database. Deprecated alias: `tenant_id`. |
| <Field name="collection" type="string" /> | Logical partition inside the database. Deprecated alias: `sub_tenant_id`. (default=`""`, the default collection) |
| <Field name="upsert" type="boolean" /> | Replace existing sources with the same ID. With `false`, a document or app source whose ID exists comes back `failed` with `error_code: "E9003"`. (default=`true`) |
| <Field name="documents" type="file[]" /> | Files for HydraDB to parse, **knowledge only**. See [Supported file formats](#supported-file-formats). (default=`[]`) |
| <Field name="document_metadata" type="string (JSON array)" /> | One entry per file in `documents`, in the same order. The counts must match, or the request returns `400`. If omitted, documents index with inferred defaults such as filename and title. Item shape below. |
| <Field name="app_knowledge" type="string (JSON object or array)" /> | Pre-extracted source objects (Slack, Notion, web pages, etc.), **knowledge only**. Item shape below. |
| <Field name="graph_payload" type="string (JSON map)" /> | Map from source id to your own entities and relations, replacing LLM graph extraction for each keyed source. The key is a `document_metadata` or `app_knowledge` item id for `type=knowledge`, or a memory `id` for `type=memory`. See [Bring Your Own Graph](/essentials/v2/bring-your-own-graph) and the shape below. |
| <Field name="memories" type="string (JSON array)" /> | Memory items, **memory only**. Required and non-empty when `type=memory`. The field is plural `memories`, though `type` is singular `memory`. Item shape below. |

<Note>
1. **`id` must not contain a comma (`,`).** [Ingestion Status](/api-reference/v2/endpoint/source-status) splits ids on commas (`GET /context/status?ids=a,b`), so an `id` with a comma in any `document_metadata`, `app_knowledge`, or `memories` item is rejected with `400`.

2. **`202 Accepted` means queued, not indexed.** Before you query, poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) with the returned IDs until each source reaches `graph_creation` (searchable), `completed` (graph ready), or `errored`, or register a webhook for `indexing.status_changed` events (see [Webhooks](/essentials/v2/webhooks)).
</Note>


## Supported file formats

HydraDB parses these in `documents`:

- **Documents:** `.pdf` `.doc` `.docx` `.docm` `.dot` `.dotx` `.odt` `.ott` `.rtf`
- **Spreadsheets:** `.xls` `.xlsx` `.xlsm` `.xlsb` `.ods` `.ots` `.csv` `.tsv`
- **Presentations:** `.ppt` `.pptx` `.pptm` `.odp` `.otp`
- **Apple iWork:** `.pages` `.numbers` `.key`
- **Images:** `.png` `.jpg` `.jpeg` `.tif` `.tiff` `.webp` `.gif` `.bmp`
- **Plain text:** `.txt` `.md` `.markdown` `.json`

What gets indexed depends on the type:

- **Documents and presentations:** the text in reading order, including slide titles and body text.
- **Spreadsheets:** cell values as a table, one per sheet. Formulas index as their computed result.
- **Images and scans:** text read with OCR, from a photo or a scan of a page.
- **Plain text:** the file as is.

A scan or photo with no readable text indexes as an empty document rather than failing.

### Formats we cannot read

These are rejected at upload, before anything is queued, so you find out in the upload response.

- `.heic` `.heif` `.avif`: export the photo as JPEG or PDF. `.heic` is the iPhone default; on iOS, set **Settings**, **Camera**, **Formats** to **Most Compatible** to save JPEGs instead.
- `.svg` `.ico`: export as PNG or JPEG.
- `.html` `.htm` `.xml`: save the page as PDF.
- `.eml` `.msg`: save the message as PDF, or send it as an app source.
- `.epub` `.wpd`: convert to PDF or DOCX.
- `.zip`: upload the files one by one.

### How we decide the format

The file extension decides: `report.pdf` is a PDF because of `.pdf`, not its contents. With no extension, the part's `Content-Type` decides, so an extensionless file sent as `application/pdf` is accepted.

<Note>
Renaming a file does not convert it. A `.heic` photo renamed to `photo.pdf` passes this check, then fails during parsing and shows as `errored` on [`GET /context/status`](/api-reference/v2/endpoint/source-status). Upload files under their real extension.
</Note>

### Size limit

Each file in `documents` can be up to **50 MB**. A larger file returns `413` with a message naming the file, and none of the request is processed. Split large documents or upload them separately.

## When a file is not supported

Each file is checked on its own, so one rejected file does not stop the rest. The request still returns `202`: the rejected file comes back with `status: "failed"` and `error_code: "E1002"`, and the others are queued:

```json
{
  "success": true,
  "data": {
    "success": false,
    "message": "Upload completed with some failures.",
    "results": [
      { "id": "6cc7bcd185b044cd", "filename": "report.pdf", "status": "queued", "error": null, "error_code": null },
      { "id": "f47411c736447126", "filename": "photo.heic", "status": "failed", "error": "This file format isn't supported. Please upload a PDF, Office document (Word, Excel, PowerPoint), image, CSV or text file.", "error_code": "E1002" },
      { "id": "d0c919bdec196a8d", "filename": "notes.txt", "status": "queued", "error": null, "error_code": null }
    ],
    "success_count": 2,
    "failed_count": 1
  },
  "error": null,
  "meta": { "request_id": "bcd03673-174d-4a73-83e6-73bfcdc16061", "api_version": "2.0.1" }
}
```

<Note>
- **Two `success` flags:** `results`, `success_count`, and `failed_count` sit inside `data`. The outer `success: true` means the request was accepted; `data.success` says whether every file was queued.
- **Do not poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) for an `E1002` file.** It never entered the pipeline, so the lookup returns `FILE_NOT_FOUND`. The upload response is the only place `E1002` appears, so read `error_code` on each item in `data.results`.
</Note>

## Common use cases

Each `document_metadata` item accepts `id`, `metadata`, `additional_metadata`, `relations`, `infer`, `evidence_kind`, and `evidence_subject`, plus the legacy aliases `source_id` and `file_id` (for `id`) and `document_metadata` (for `additional_metadata`). Any other key, including `title`, `type`, `url`, and `timestamp`, returns a `400` that names it rather than being silently dropped.

[`PATCH /context/{id}/metadata`](/api-reference/v2/endpoint/update-source-metadata) cannot change it either, since it only merges `additional_metadata` and `database_metadata`. Use `additional_metadata` for your own display fields, or ingest through `app_knowledge`, whose items carry an explicit `title`.
  </Note>

  | --- | --- |
  | <Field name="<source_id>" type="object" /> | Top-level key: a `document_metadata` or `app_knowledge` item id for `type=knowledge`, or a memory `id` for `type=memory`, in the same request. The value is that source's graph. A key matching no source returns `400`. |
  | <Field name="entities" type="object (map)" /> | Map of entities keyed by a caller-local id. The key is only a handle for `relations` and is not stored. |
  | <Field name="entities[].name" type="string" required /> | Entity name, up to 256 characters. Normalized (lowercased) server-side so it matches at query time. |
  | <Field name="entities[].type" type="string" /> | Entity type (e.g. `PERSON`, `POLICY`). Stored as supplied. |
  | <Field name="entities[].namespace" type="string" /> | Logical grouping for the entity. Stored as supplied. |
  | <Field name="entities[].identifier" type="string" /> | Optional external id (email, URL, etc.), for display only. |
  | <Field name="relations" type="array" /> | Edges referencing entity-map keys. |
  | <Field name="relations[].source" type="string" required /> | Entity-map key of the source entity. |
  | <Field name="relations[].target" type="string" required /> | Entity-map key of the target entity. |
  | <Field name="relations[].predicate" type="string" required /> | Relationship label, any plain string, up to 256 characters. |
  | <Field name="relations[].context" type="string" /> | Optional sentence supporting the edge, up to 2,000 characters. |
  | <Field name="relations[].temporal_details" type="string" /> | Optional timing info (e.g. "since 2021", "in Q3"). |

  <Note>

### Upload in-memory text as a `.txt` file

Wrap in-memory text in a file-like object and send it in `documents` as a `text/plain` `.txt` file. No file on disk is needed.

<CodeGroup>
```python Python SDK
import io
import json

text = """Q4 planning notes

- Launch checklist is owned by Priya.
- Legal review is due by Friday.
"""

# Create a file-like object in memory. No local .txt file is required.
txt_file = io.BytesIO(text.encode("utf-8"))

response = client.context.ingest(
    type="knowledge",
    database="acme_corp",
    collection="team_docs",
    documents=[("meeting-notes.txt", txt_file, "text/plain")],
    document_metadata=json.dumps([
        {"id": "meeting_notes_q4", "metadata": {"department": "product"}}
    ]),
)
```

## Notes

- **Multipart form:** the fields on this page are `multipart/form-data` fields. Stringify every JSON field (`document_metadata`, `app_knowledge`, `memories`, `graph_payload`) before you put it in the form. A body that is neither a form nor JSON returns `415`.
- **Declare hot schema fields up front:** put fields you filter on often in `metadata`, and declare them in `database_metadata_schema` when you [create the database](/api-reference/v2/endpoint/create-tenant). Use `additional_metadata` for free-form fields. You can add fields later with [Update Metadata Schema](/api-reference/v2/endpoint/update-metadata-schema), but dense and sparse lanes can only be declared at creation.
- **Memory vs. knowledge:** use `type: "memory"` to ingest, list, and delete memories, and `type: "all"` on `POST /query` to search both.
- **Default collection:** omitting `collection` writes to the default collection, created on first write. See [List Collections](/api-reference/v2/endpoint/list-sub-tenants).

## Errors

Common codes: `400` (invalid field, an `id` with a comma, an unknown `document_metadata` key, a `document_metadata` count that does not match `documents`, metadata over its size limit, a graph over its caps), `413` (a file over 50 MB), `415` (a body that is neither a form nor JSON), `422` (validation error). See [Error Responses](/api-reference/v2/error-responses) for the full list.
