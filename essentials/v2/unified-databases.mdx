---
title: "Unified databases"
description: "A database created with type=unified keeps knowledge and memory in one place. What changes on the v2 API, what stays, and how to adopt it."
---

Every HydraDB database used to hold two separate corpora, knowledge and memory, and every call to the context and query endpoints took `type: "knowledge" | "memory"` to say which one you meant. A **unified** database keeps everything in one corpus. There is no third API version: the same v2 endpoints serve both kinds of database, and `type` gained one more value, `unified`.

<Note>
Existing databases are not migrated and keep working unchanged. You adopt the unified layout by creating a new database with `type: "unified"`.
</Note>

---

## 1. Create a unified database

```bash
curl -X POST https://api.hydradb.com/databases \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"database": "acme", "type": "unified"}'
```

`type` on `POST /databases` is `split` (the default, the layout every existing database has) or `unified`. The layout is fixed when the database is created and cannot be changed afterwards.

You can always tell which kind of database you are talking to:

- `GET /databases` returns `details: [{ "database": "acme", "type": "unified" }, ...]` alongside the existing `databases` list.
- `GET /databases/status?database=acme` returns `type: "unified"` alongside the readiness flags.

## 2. What `type` means on each kind of database

`type` is accepted everywhere it was before: `POST /context/ingest`, `POST /query`, `POST /context/list`, `DELETE /context`, `GET /context/relations`, `GET /context/{id}/subgraph` and `GET /context/chunks`. Which values a database accepts depends on its layout:

| `type` sent | Split database (every existing one) | Unified database |
| --- | --- | --- |
| absent | `knowledge`, as before | `unified`: the whole corpus |
| `knowledge` | the knowledge corpus | `400`, there is no separate corpus to select |
| `memory` | the memory corpus | `400`, same reason |
| `all` | as much as the endpoint can answer in one response, see below; `400` on ingest | the whole corpus; `400` on ingest |
| `unified` | `400`, there is no single corpus to name | the whole corpus |

A value outside this vocabulary is a `400` on every one of those endpoints, checked before the database is resolved.

### What `all` reaches, per endpoint

`all` predates unified databases and keeps working everywhere it worked before. What it can deliver is not the same everywhere, because "both corpora" is only answerable where the endpoint can merge two of them into one response:

| Endpoint | `all` on a split database |
| --- | --- |
| `POST /query` | both corpora, searched separately and merged into one ranked list |
| `POST /context/list` | both corpora in one listing, under one cursor |
| `DELETE /context` | both corpora: the knowledge lane runs, then the memory lane |
| `GET /context/relations` | the knowledge corpus only |
| `GET /context/{id}/subgraph` | the knowledge corpus only |
| `GET /context/chunks` | the knowledge corpus only |
| `POST /context/ingest` | `400`: a write has to name the one corpus it lands in |

The three graph and chunk reads each address one graph sub-tenant and page a cursor over it, and two cursors cannot be merged into one, so `all` reads knowledge there. That is what `/context/relations` has always done with any value other than `memory`.

Every one of these responses carries `meta.source_type`, and it reports the corpus that **answered**, not the `type` you sent. On a unified database that is always `unified`. On a split database the three single-target reads report the corpus they actually consulted, so a `type: "all"` call to relations, subgraph or chunks reports `knowledge`. `/query`, `POST /context/list` and `DELETE /context` report `all`, because for those three `all` is a truthful answer: they really did read or delete from both.

`DELETE /context` with `type: "all"` runs both lanes and returns one response for the pair. `results[]` carries one entry per id, the lane that deleted it winning over the lane that did not find it; `deleted_count` is the two lanes summed; `user_memory_deleted` still counts the memory lane alone. An id lives in at most one corpus of a split database, so finding it in one lane and missing in the other is the ordinary case and the request reports `deleted`, not a partial failure.

The two lanes are two stores with no transaction across them. If the knowledge lane succeeds and the memory lane then hits a store error, the response is that error and the knowledge deletions have already happened. This is the same partial-failure shape `type: "memory"` already has part-way through its per-id loop. On a unified database none of this applies: `all` and `unified` both resolve to `unified` and run a single pass, because one source delete already purges the one shared collection and a second pass would count the same rows twice.

On a unified database there is one corpus, so an absent `type`, `all` and `unified` name the same target on every read and on delete, and the per-endpoint table above does not apply. Ingest is the exception on both layouts: `all` is refused there, and on a unified database you either omit `type` or send `unified`.

One case where an absent `type` does not mean `knowledge`: an ingest that carries `items[]` writes to the **memory** corpus of a split database, because items are memory-shaped. Absent and `type: "memory"` both land there, and `type: "knowledge"` alongside `items` is a `400` rather than a redirect. See [Ingest on a unified database](/essentials/v2/unified-ingest).

A caller that keeps using a split database sends the same values and gets the same answers, with one exception worth knowing about: `DELETE /context` with `type: "all"` used to delete from the knowledge corpus alone, and now deletes from both. The layout rule only bites when a client that hard-codes `type: "memory"` is pointed at a unified database, which is why the [plugins and SDK wrappers](/essentials/v2/unified-databases#5-clients) now read the database's layout first.

## 3. One list of items, one graph object

On a unified database you ingest `items[]` and query without a corpus selector. The two new pages cover each side:

- [Ingest on a unified database](/essentials/v2/unified-ingest): `items[]`, each item either `text` or a `conversation`.
- [Query on a unified database](/essentials/v2/unified-query): one ranked list, `graph.paths[]`, `forceful_relations`, and the `attributes` filter with `is_memory`.

The query response is **additive**. Two new top-level fields appear, and nothing you read today is removed:

| Field | Status | Notes |
| --- | --- | --- |
| `chunks[]`, `sources[]` | unchanged | same field names as before (`id`, `metadata`, `additional_metadata`, `relevancy_score`, ...) |
| `graph.paths[]` | new | one ordered list; each path carries its own `chunk_ids`. Built from `graph_context`, and dropped alongside it when the request sends `graph_context: false` |
| `forceful_relations` | new | `{ declared: [{ via: { from, to }, chunk }], inferred: [] }`, always present |
| `graph_context` | deprecated | still returned; prefer `graph.paths[]` |
| `additional_context` | deprecated | still returned; prefer `forceful_relations.declared` |

Both pairs are two renderings of one result, never two different results: see [the response section](/essentials/v2/unified-query#3-the-response).

Because the response is one shape with optional additions, every generated SDK keeps a single response type and no client breaks on a field it does not know.

## 4. Field names

Unified ingest items use the names the redesign settled on. The old names are still accepted on the existing fields and appear in responses, so nothing you have written stops working; the docs use the new names.

| Existing name | Name on `items[]` | Notes |
| --- | --- | --- |
| `memories[]`, `app_knowledge[]`, `documents` | `items[]` | one array, each item `text` or `conversation` |
| `id` | `context_id` | your identifier; generated if omitted |
| `text` (memory) / `content.text` (app knowledge) | `text` | plain text |
| `user_assistant_pairs` | `conversation` | `[{ role, content, name }]` |
| `metadata` | `attributes` | structured, filterable |
| `additional_metadata` | `custom_attributes` | free-form |
| `observation_date` | `happened_at` | when the item is about |
| `infer` | `enrich` | per item, default `true` |
| `query_paths` + `chunk_relations` + `chunk_id_to_group_ids` | `graph.paths[]` | response |
| `additional_context` | `forceful_relations.declared` | response |

Responses keep the v2 chunk and source field names (`id`, `metadata`, `additional_metadata`, `timestamp`) and the `{ "success": true, "data": ... }` envelope. `query_forceful_relations` keeps its name on the query request.

The left column is where each name lives today, not a second name `items[]` will answer to. An item is read for the right-hand names only, and a key it does not recognise is dropped without an error, so an item that still carries `metadata` or `observation_date` ingests with neither. The three names `items[]` does accept twice are the drafted spellings `contexts`, `content` and `messages`, for `items`, `text` and `conversation`.

## 5. Clients

<Warning>
None of this has shipped yet. Unified support is written but unreleased in all four wrappers, so the version you have installed today does not know what a unified database is. The table describes what each will do, and it lands with the rollout that registers these pages.
</Warning>

| Client | Behaviour on a unified database |
| --- | --- |
| MCP server | `kind: "unified"` is the default when the database reports `type: "unified"`; ingest sends `items[]`. The layout comes from one memoised `GET /databases`, and a refused kind is retried |
| CLI (`hydradb`) | `hydradb database create --type unified`; `query`, `list`, `delete` and `relations` default `--kind` to `unified`; `ingest --text` sends `items[]`. The layout is read once per process, and a probe that fails reads as split. File ingest is refused, since a unified database is text-only |
| Claude Code plugin | `searchMode: "unified"` and `ingestionMode: "unified"`; auto-detected from `GET /databases`, probed once and ahead of the first call |
| OpenClaw plugin | `layout: "unified"` in config, or `auto` to read it from `GET /databases` once; recall and capture go through `/query` and `items[]` |

None of the four can declare a forceful relation on a unified database, because no client can: `items[]` has no field for it.

If you call the API directly, read `GET /databases` once and branch on `details[].type`.

---

## 6. What breaks, and for whom

One thing changes on a split database: `DELETE /context` with `type: "all"` now deletes from both corpora rather than from knowledge alone. If you send `all` to that endpoint and relied on your memory corpus surviving it, send `type: "knowledge"` instead. Nothing else changes for anyone who does not create a unified database.

For a unified database:

- Sending `type: "knowledge"` or `type: "memory"` returns `400` instead of half the data.
- The split-era ingest fields (`documents`, `app_knowledge`, `memories`) return `400` pointing at `items[]`. Files are text-only on a unified database: extract the text and send it as an item.
- `is_memory` is filterable in `attributes` (it is not on a split database, where the column is absent from rows written before this change).

There is no in-place conversion from split to unified. Create a unified database, re-ingest, and repoint your client.
