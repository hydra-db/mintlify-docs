HydraDB accepts content, processes it in the background, and makes it searchable. You **ingest** content; **indexing** makes it searchable; **retrieval** finds relevant passages when you query. This page follows that sequence and ends with what to check when results are empty.

## The big picture

The API has three jobs:

| Job | What it handles | Endpoints |
|---|---|---|
| **Manage databases** | API authentication, database lifecycle, provisioning, and status | [`/databases`](/api-reference/v2/endpoint/tenants-overview) family |
| **Ingestion** | File and app-source uploads, memory writes, parsing, chunking, embedding, and graph construction | [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context), [`GET /context/status`](/api-reference/v2/endpoint/source-status) |
| **Search** | Hybrid query, metadata filtering, graph context, BM25 keyword search, and response shaping | [`POST /query`](/api-reference/v2/endpoint/query), [`GET /context/relations`](/api-reference/v2/endpoint/source-relations) |

Two details to notice in the diagram:

- **Two stores, one ingest endpoint:** [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) routes to the [Knowledge](/essentials/v2/knowledge) store when `type=knowledge` and to the [Memories](/essentials/v2/memories) store when `type=memory`. Same endpoint, different bucket.
- **One query endpoint, every retrieval method:** [`POST /query`](/api-reference/v2/endpoint/query) is the only retrieval entry point. Its `type` field picks the store and `query_by` picks the matching method. [Query](/essentials/v2/query) covers every parameter.

## Ingestion lifecycle

Ingestion is asynchronous. A successful upload means HydraDB accepted the work and queued it, not that the content is already searchable. Each source moves through these statuses:

Poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) with the returned `id` to follow each source, or [register a webhook](/essentials/v2/webhooks) to be told instead. Two practical notes:

- **`graph_creation` is already searchable:** chunks become retrievable as soon as embedding finishes. Wait for `completed` only when you need full graph traversal.
- **Failures come with a reason:** an `errored` status carries an `error_code` and `error_message`, so you can tell a parse failure from a validation problem or an infrastructure issue.

## From upload to query

The end-to-end flow, with the endpoint that owns each step:

1. **Create a database** with [`POST /databases`](/api-reference/v2/endpoint/create-tenant), optionally declaring a [metadata schema](/essentials/v2/metadata) up front.
2. **Wait for it to be ready** by polling [`GET /databases/status`](/api-reference/v2/endpoint/tenant-status) until `infra.ready_for_ingestion` is `true`.
3. **Ingest content** with [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context): `type=knowledge` for documents and app sources, `type=memory` for per-user context.
4. **Wait for indexing** by polling [`GET /context/status`](/api-reference/v2/endpoint/source-status) until each `id` reaches `completed`, or `graph_creation` if you do not need graph traversal.
5. **Query** with [`POST /query`](/api-reference/v2/endpoint/query), choosing `type` and the collection scope. Pass the result to your model with the helper in [How to Use API Results](/essentials/v2/api-results).

## Database isolation

A `database` (formerly `tenant_id`, still accepted as a deprecated alias) is the top-level isolation boundary: no database can read another database's data. Within a database, a `collection` (formerly `sub_tenant_id`) is a partition for a user, team, workspace, or project. Omitting `collection` on any call resolves to the database's default collection, which is created on the first write.

| Product shape | Database pattern | Collection pattern |
|---|---|---|
| **B2B SaaS** | One database per customer organization | One collection per team, workspace, or end user |
| **B2C app** | One database for your application | One collection per end user |
| **Internal tools** | One database per company or environment | One collection per department or project |

[Multi-tenancy](/essentials/v2/multi-tenant) covers when to create a new database rather than a new collection, and how scoping interacts with [Memories](/essentials/v2/memories) and [metadata filters](/essentials/v2/metadata).

## Retrieval pipeline

Every [`POST /query`](/api-reference/v2/endpoint/query) call runs the same steps:

1. **Authenticate and scope:** validate `database` and apply the requested `collection` or `collections` (the default collection when neither is sent).
2. **Filter before ranking:** apply `metadata_filters` to narrow the candidate set.
3. **Retrieve:** run hybrid retrieval over the semantic vector store and the BM25 keyword index, blended by `alpha`, or BM25 only when `query_by: "text"`.
4. **Enrich:** attach the relevant slice of the [context graph](/essentials/v2/context-graphs) when `graph_context` is on. In thinking mode, also expand the query, rerank, and pull in author-declared linked sources. `mode: "auto"`, the default, picks fast or thinking per query.
5. **Shape the response:** return ranked `chunks`, deduplicated `sources`, the `graph_context` slice, and any `additional_context`.

The response is retrieved context, not a model-written answer. You pass the chunks and any graph context into your own prompt.

## When results are empty

HydraDB separates write-time work from query-time work: uploads return quickly and run in the background, while a query is synchronous and reads only indexed content. When results look incomplete, walk the chain in order:

1. **Status first:** did every `id` reach `completed`, or at least `graph_creation`? Check [`GET /context/status`](/api-reference/v2/endpoint/source-status).
2. **Scope second:** is the `database` correct? Did you write under one `collection` and read under another? See [Multi-tenancy](/essentials/v2/multi-tenant).
3. **Filters third:** are you using the right namespace? Top-level `metadata_filters` keys match `metadata`; free-form fields belong under `additional_metadata`, and top-level filter keys must be declared in the database schema. See [Metadata](/essentials/v2/metadata).
