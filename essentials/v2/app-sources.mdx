Use [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) in **bring your own connectors** mode. **Your connector fetches and parses the app data, then maps each item to a supported class (`kind`) and its fields.** Send those items in `app_knowledge` as **multipart/form-data**, with `type=knowledge`.

**HydraDB provides the ontology engine and retrieval:** it organizes the content and relationships, indexes the sources, and retrieves them through [`POST /query`](/api-reference/v2/endpoint/query).

## Choose the class for each item

An **app source** is one mapped item. **Choose its class with `kind`, identify its app with `provider`, and put its content in `fields`.**

| Object class (`kind`) | Use for | Main text |
|---|---|---|
| `message` | Slack / Teams messages and replies | `fields.body` |
| `ticket` | Issues and support tickets | `fields.title`, `fields.description` |
| `comment` | Comments on tickets, pages, or records | `fields.body` |
| `knowledge_base` | Wiki pages | `fields.title`, `fields.body` |
| `email` | Emails and email replies | `fields.subject`, `fields.body` |
| [`custom`](#map-your-data-to-the-custom-class) | CRM records, meeting transcripts, and other app records | `fields.body`, `fields.data` |


A connector can produce more than one class: your Jira connector sends tickets as `ticket` and their comments as `comment`. Repeat the class in `fields.kind`, matching the top-level `kind`.

## Choose your app pattern

These five patterns show how to map the app data your connector has fetched. Expand one, replace its example values with your app's data, and save the JSON as `app-sources.json`. Send it with the [ingestion request](#2-ingest-an-app-source). Use the same pattern for later snapshots, adding `upsert=true` to the form request when replacing an existing item.

<Accordion title="Slack / Teams: threads, replies, attachments">

**Classes: `message` for both the opening message and every reply.** A reply has its own ID and body. All messages in the thread share `fields.thread_id`; each reply also sets `fields.parent_id` to the opening message's `external_id`.

In Slack, the message ID is its `ts`, and the thread root is `thread_ts`. For the opening message, use its own `ts` as `thread_id`. The example uses one channel; keep provider IDs unambiguous across the channels and workspaces you sync (see [Item IDs](#item-ids)).

```json Root message and reply
    "collection": "default",
    "title": "Auth rollback discussion",
    "kind": "message",
    "provider": "slack",
    "external_id": "1716213600.000100",
    "fields": {
      "kind": "message",
      "body": "The auth rollback notes are attached here.",
      "author": "alice",
      "thread_id": "1716213600.000100",
      "created_at": "2026-05-20T10:00:00Z"
    },
    "attachments": [
      {
        "id": "F012AUTH",
        "title": "auth-rollback-notes.md",
        "content": { "markdown": "# Auth rollback\nDisable the new token refresh path first." }
      }
    ]
  },
  {
    "id": "slack_C01_1716213700_000200",
    "database": "acme_corp",
    "collection": "default",
    "title": "Reply to auth rollback discussion",
    "kind": "message",
    "provider": "slack",
    "external_id": "1716213700.000200",
    "fields": {
      "kind": "message",

```

HydraDB derives the `reply_to` connection from `parent_id`. The root has no `parent_id`. A new reply only needs a new source; the root stays as it is. Use the same structure for other messaging apps, with their own message and conversation IDs.

```json Ticket and comment
    "external_id": "AUTH-123",

      "title": "Login page returns 500",

      "status": "open",
      "assignee": "alice",
      "parent_id": "AUTH-100",
      "linked_issue_ids": ["AUTH-124"]
    }
  },
  {
    "id": "jira_comment_c123",
    "database": "acme_corp",
    "collection": "default",
    "title": "Reproduction steps for AUTH-123",
    "kind": "comment",
    "provider": "jira",
    "external_id": "c123",
    "fields": {
      "kind": "comment",
      "body": "Reproduces on staging when the refresh token expires.",
```

This creates a `child_of` connection from AUTH-123 to its epic, a `linked_to` connection to AUTH-124, and a `comment_on` connection from c123 to AUTH-123. Ingest the epic and linked issue too to make their content available. For Linear or Zendesk, change the provider and use that app's item IDs.

## 1. Map your app data

Your connector translates the app's API response into the fields for the class you chose above. Fetch the item and extract its text, authors, timestamps, and app IDs before building the source. Extract attachment text too if you want it searched. For example, a Slack API message maps like this:

| Slack API value | App-source field |
|---|---|
| Message `ts` | `external_id` |
| Message `text` | `fields.body` |
| Sender `user` | `fields.author` (resolve the user ID to a name or email when available) |
| Reply's `thread_ts`, or the root's own `ts` | `fields.thread_id` |
| Reply's `thread_ts` | `fields.parent_id`; omit on the opening message |
| File text extracted by your connector | `attachments[].content.text` or `attachments[].content.markdown` |

Set `kind: "message"` and `fields.kind: "message"` for this mapping. For a ticket, map its title and description to `fields.title` and `fields.description`; for an email, map its subject, body, sender, and recipients to the email fields. Keep the original item's ID so later updates and relationships refer to the same item.

### Map your data to the custom class

**Use the `custom` class for records that do not fit another class**, such as CRM deals, contacts, invoices, meeting transcripts, or records from your internal app. Set both `kind` and `fields.kind` to `custom`. Your business record type, such as `opportunity` or `invoice`, goes in `fields.data.record_type`.

Your connector maps the record's properties to `fields.data` and its readable text to `fields.body`. For a meeting transcript, put the transcript in `fields.body` and details such as participants in `fields.data`.

<Accordion title="Salesforce opportunity: map to custom and link to Jira">

The ingestion request still uses **`type=knowledge`**. `custom` is the source's class; `opportunity` is the business record type in this example.

Map the app's properties into **`fields.data`**, a JSON object that can contain strings, numbers, booleans, arrays, and nested objects. HydraDB renders the values as text for indexing, omitting empty values, `0`, and `false`. Add **`fields.body`** for a readable description or notes, including any zero or false values that need to be searchable.

Map the Salesforce opportunity's fields to these app-source fields, and connect the resulting source to its account and a Jira ticket:

| App value | App-source field |
|---|---|
| Opportunity ID | `external_id`; derive a stable HydraDB `id` from it |
| Opportunity name | Top-level `title` and `fields.data.name` |
| Opportunity notes | `fields.body` |
| Stage, amount, owner, and other business properties | Keys in `fields.data` |
| Associated account's app ID | `fields.parent_id` |
| Related Jira source's HydraDB ID | `relations[].target.source_id` |

Save this source in `app-sources.json` and send it with the [ingestion request](#2-ingest-an-app-source). Your connector supplies the mapped text, properties, and IDs.

```json Custom opportunity source
{
  "id": "salesforce_opp_789",
  "database": "acme_corp",
  "collection": "default",
  "title": "Acme enterprise renewal",
  "kind": "custom",
  "provider": "salesforce",
  "external_id": "opp_789",
  "fields": {
    "kind": "custom",
    "body": "Acme is negotiating its enterprise renewal. The renewal depends on resolving the login issue in the linked Jira ticket.",
    "parent_id": "account_456",
    "data": {
      "record_type": "opportunity",
      "name": "Acme enterprise renewal",
      "stage": "negotiation",
      "amount": 50000,
      "owner": "morgan"
    }
  },
  "relations": [
    {
      "predicate": "linked_to",
      "target": { "source_id": "jira_AUTH-123" }
    }
  ]
}
```

Ingest the account as another Salesforce source with `external_id: "account_456"`. For the direct source-ID relation shown here, ingest the Jira ticket and wait for `completed` before ingesting the opportunity. HydraDB uses the account as the opportunity's parent and the ticket as a linked source.

Keep connection fields outside `data`: `fields.parent_id` creates a same-provider parent connection, `fields.thread_id` groups a conversation, and top-level `relations` connects other sources, including across apps. A business property such as `fields.data.account_id` alone does not create a connection. The [connection examples](#3-connect-app-sources) include Gmail linked to Notion and a CRM field mapped to a Postgres row.

For filters such as deal stage, also map the property into `metadata` and declare it in your [metadata schema](/essentials/v2/metadata) with `enable_match: true`. Keys in `fields.data` provide searchable content; they do not automatically become metadata filters.

After ingestion, query with `type: "knowledge"` and `query_apps: true`, just as for other app classes. For example, ask "What is blocking Acme's renewal?" with `mode: "thinking"` to retrieve connected context. When the deal changes, send its complete updated snapshot with the same IDs and `upsert: true`; retain its relationships and other content. See [incremental ingestion](#4-incremental-ingestion).

</Accordion>

### Item IDs

Every source has two IDs:

- **`id` is your stable HydraDB source ID.** Use it to check status, replace the source, or delete it. For example, `slack_C01_1716213600_000100`.
- **`external_id` identifies the item in the app.** For example, the Slack message timestamp `1716213600.000100` or Jira issue key `AUTH-123`. Parent and reply fields refer to this ID.

Use a consistent `provider` for items that belong together. HydraDB resolves external IDs within the provider and database/collection scope. If an app's IDs are only unique within a channel, workspace, or mailbox, make your external IDs unambiguous in that scope and apply the same mapping to every parent, reply, and relation target. Adding a channel name to metadata does not change how IDs resolve.

`database` and `collection` say where the source belongs. Include them in each item, matching the values on the ingestion request. `title` and `url` give the user a readable citation and a link back to the original item.

## 2. Ingest an app source

Send your mapped sources to [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context), using an existing [database](/api-reference/v2/endpoint/create-tenant) and collection. The request is **multipart/form-data**. `app_knowledge` is your mapped source object or array, serialized as a JSON string in one form field.

| Form field | What to send |
|---|---|
| `type` | `knowledge` |
| `database` | The existing database that should own these sources |
| `collection` | Your collection, or `default` |
| `app_knowledge` | Your mapped source object or array, serialized as a JSON string |

Include the same `database` and `collection` in every source and in the form fields. With an SDK, use `json.dumps(...)` in Python or `JSON.stringify(...)` in TypeScript; the SDK constructs the multipart request.

The example below sends Alice's opening Slack message. To send another app pattern, replace this JSON with the source or array you mapped above.

<Accordion title="Ingest a Slack message: JSON, cURL, Python, or TypeScript">

For cURL, save the JSON in the first tab as `app-sources.json` in your current directory, then run the request in the next tab. The request reads that JSON into the `app_knowledge` form value.

Set up your [SDK client](/api-reference/v2/sdks#client-setup) before running Python or TypeScript. These examples build and serialize the same message directly. The TypeScript SDK names the form property `appKnowledge`; the JSON source fields keep their snake_case names.

**For edits, use this same endpoint and add `upsert=true` to the form request.** Send the item's complete current snapshot with the same IDs. See [Incremental ingestion](#4-incremental-ingestion) for the updated JSON and cURL request.

The call returns `202 Accepted`. Check each item's entry in `data.results` for its source `id`, `status`, and any `error`. A `queued` item has been accepted for processing.

Use [`GET /context/status`](/api-reference/v2/endpoint/source-status) with that ID to follow ingestion. The source is queryable when `indexing_status` reaches `graph_creation` or `completed`.

At `graph_creation`, text can already be searchable while the graph is still being built. Before checking thread or relation expansion, wait for the involved sources to reach `completed`. Use the [connected subgraph endpoint](/api-reference/v2/endpoint/subgraph) to confirm that the expected source IDs and links are present.

`errored` is also a terminal state. Stop waiting, inspect `error_code`, correct the source payload or address the reported failure, and retry ingestion with `upsert: true`. You can also delete a failed source for cleanup. A relation target that failed ingestion must be corrected and successfully ingested before you expect its content in results.

## 3. Connect app sources

Connect replies to their conversations, link records across apps, or request linked text alongside search hits. Expand a topic to see the fields and examples.

<AccordionGroup>
<a id="threads-and-replies"></a>
<Accordion title="Threads and replies">

A **thread** groups a conversation. A **parent** identifies the specific item that a reply or comment responds to. These fields answer different questions:

| In the Slack example | `external_id` | `fields.thread_id` | `fields.parent_id` |
|---|---|---|---|
| Alice's opening message | `1716213600.000100` | `1716213600.000100` | Omitted |
| Carol's reply | `1716213700.000200` | `1716213600.000100` | `1716213600.000100` |
| A later reply | Its own message ID | `1716213600.000100` | `1716213600.000100` |

Each message keeps its own body, author, and timestamp. A thread does not need a separate source. Ingest its opening message and replies with the shared `thread_id`.

For other apps, use their conversation IDs. Email uses `thread_id` to group the conversation and `reply_to_id` to identify the email being replied to. Ticket comments use `parent_id` to identify the ticket; they can also carry a `thread_id` when the app has a discussion thread.

</Accordion>
<a id="relationships-from-fields"></a>
<Accordion title="Relationships from fields">

HydraDB creates these connections from the fields you send:

| Field | Class | Connection |
|---|---|---|
| `thread_id` | Message, email, comment, custom | Item belongs to the thread |
| `parent_id` | Message | Reply → parent message (`reply_to`) |
| `reply_to_id` | Email | Reply → original email (`reply_to`) |
| `parent_id` | Comment | Comment → ticket, page, or record (`comment_on`) |
| `parent_id` | Ticket, page, custom | Child → parent (`child_of`) |
| `linked_issue_ids` | Ticket | Ticket → related issues (`linked_to`) |

Parent and reply IDs use the same provider as the source. Ingest the referenced items too so their content can be retrieved.

</Accordion>
<a id="explicit-relations-between-sources"></a>
<Accordion title="Explicit relations between sources">

Use `relations` to describe connections beyond those fields: a Slack discussion about a Jira incident, a CRM renewal tied to a support ticket, or an issue blocking a release.

A relation reads as **this source → relationship → target**. On Carol's Slack reply, the following addition means "this message is linked to Jira ticket AUTH-123":

```json Add to the message source
{
  "relations": [
    {
      "predicate": "linked_to",
      "target": { "external_id": "AUTH-123", "provider": "jira" },
      "properties": { "reason": "Confirms the login fix" }
    }
  ]
}
```

`predicate` names the relationship. `target` identifies the other source. Optional `properties` explain the connection. The target can be identified in either of these ways:

| Target | Use when |
|---|---|
| `{ "source_id": "jira_AUTH-123" }` | You know the target's HydraDB source `id`. |
| `{ "external_id": "AUTH-123", "provider": "jira" }` | You know its app ID and provider. Include both. |

For `source_id` targets, ingest the target and wait for `completed` before submitting the relation.

Choose the direction that matches the relationship:

| `predicate` | Example |
|---|---|
| `reply_to` | Reply → original message or email |
| `comment_on` | Comment → ticket or page |
| `child_of` | Subtask → epic; page → parent page |
| `linked_to` | Slack discussion → Jira ticket |
| `blocks` | Unresolved ticket → release it blocks |
| `caused_by` | Incident → change that caused it |
| `forwarded_from` | Forwarded email → original email |
| `related_to` | Item → another related item |

Keep both sources in the same database and collection. A relation connects sources that you ingest; it does not import the target from its app. Query with `query_apps: true` and `mode: "thinking"` when you want HydraDB to follow connections for supporting context.

</Accordion>
<a id="return-linked-content-with-query-results"></a>
<Accordion title="Return linked content with query results">

**Use a forceful retrieval link when linked content should accompany a search hit.** For example, a CRM contact can request its linked account row as supporting context even when only the contact matches the question.

| What you need | What to send on the app source |
|---|---|
| Describe a relationship, such as `reply_to` or `linked_to` | A typed `relations` array, as above |
| Retrieve linked content alongside a search hit | A `relations` object with `ids`, containing the targets' HydraDB source IDs |
| Both the relationship and retrieval link | The typed array in `app_relations`, and the retrieval object in `relations` |

```json Add a retrieval link to the source
{
  "relations": { "ids": ["postgres:public.users:123"] }
}
```

On [`POST /query`](/api-reference/v2/endpoint/query), use `mode: "thinking"` and `query_forceful_relations: true` (the default). `query_apps: true` also enables app-specific retrieval. **Fast mode ignores `query_forceful_relations`.** The flag applies to retrieval links declared with the object form; setting it does not turn a typed relation array into a forceful link.

<Warning>
**Current limitation:** Retrieval links can be lost while ingestion rebuilds the graph. After ingestion completes, verify the links with the [connected subgraph endpoint](/api-reference/v2/endpoint/subgraph) and check the query's linked context. A `202` response or `relations_created` count alone does not prove that linked content will be returned.
</Warning>

Read linked text from `data.additional_context`, alongside the primary hits in `data.chunks`. `data.forceful_relations.declared` identifies the returned links with `via.from`, `via.to`, and each linked chunk. Include this supporting text when presenting results or building an answer.

Forceful retrieval follows direct links from the sources represented in the returned primary chunks. For example, `max_results: 4` selects up to four primary chunks whose sources can supply linked context. It does not mean four traversal hops: a chain `A → B → C` can return B as context for a hit on A, but this path does not recursively fetch C. Linked context is bounded, and metadata filters, source scopes, and access controls still apply.

</Accordion>
<a id="link-app-sources-across-apps"></a>
<Accordion title="Link app sources across apps">

**An app source can link to another app source from a different app.** Map and ingest each item, then connect them with a relation. For example, link a Gmail email approving an auth rollback to the Notion runbook that describes the procedure.

Both sources must belong to the same database and collection. The target's provider identifies its app; it does not need to match the source's provider.

For a `source_id` target, ingest the target first and wait for its ingestion to reach `completed`. Then add a `linked_to` relation to the referring source with the target's HydraDB ID as `target.source_id`. For example, link `gmail_msg_19a2b3c` to `notion_page_abc` from the patterns above.

Save this source as `app-sources.json` and send it through `app_knowledge` using the [ingestion request](#2-ingest-an-app-source). If you already ingested the email from the pattern above, add `-F 'upsert=true'` to update it. Replace the example IDs and business fields with your source's actual values.

```json Gmail source with a Notion target
{
  "id": "gmail_msg_19a2b3c",
  "database": "acme_corp",
  "collection": "default",
  "title": "Re: Auth rollback plan",
  "kind": "email",
  "provider": "gmail",
  "external_id": "19a2b3c",
  "fields": {
    "kind": "email",
    "subject": "Re: Auth rollback plan",
    "body": "Approved. Please share the verification results after rollback.",
    "from": "alice@acme.com",
    "to": ["team@acme.com"],
    "thread_id": "thread_19a2",
    "reply_to_id": "19a1a00",
    "created_at": "2026-05-20T11:00:00Z"
  },
  "relations": { "ids": ["notion_page_abc"] },
  "app_relations": [
    {
      "predicate": "linked_to",
      "target": { "source_id": "notion_page_abc" }
    }
  ]
}
```

The source's own `id` identifies the Gmail email. `target.source_id` is the Notion page's HydraDB ID, which you can obtain from ingestion results or [source listing](/api-reference/v2/endpoint/list-documents). A source-ID target does not require `provider`.

To add the link to an existing email, send its complete updated snapshot with `upsert: true`. Retain its current fields, metadata, attachments, comments, and other relations. Include the relation in subsequent snapshots from your sync too.

**When you only have the app's external ID**, use `target.external_id` and the target's stored provider name. To target the Gmail email from the Notion page instead, the target would be:

```json External-ID alternative for the relation target
{
  "external_id": "19a2b3c",
  "provider": "google"
}
```

Some app names are normalized when sources are stored. You can use the stored provider name for an external-ID target:

| Target app | `target.provider` |
|---|---|
| Gmail | `google` |
| Outlook / Teams | `microsoft` |
| HubSpot | `hubspot` |
| Jira | `jira` |

For example, a Gmail source submitted with `provider: "gmail"` is stored under `google`. Gmail external-ID targets accept `gmail` as well as `google`; the example uses the stored name. Prefer `source_id` when you know the HydraDB ID; it avoids provider-name matching.

The example declares both the typed connection and a forceful retrieval link. With `query_apps: true`, `mode: "thinking"`, and `query_forceful_relations: true`, direct linked content can accompany a hit from either side: a query about the email can retrieve the runbook, and a query about the runbook can retrieve the email. You can declare the link on one source without adding a reverse relation. Ingest both items before expecting their content in query results. To connect a whole conversation, link to an ingested email in that conversation and keep its thread fields populated.

People and records have different connections. When sources identify people by email, HydraDB can recognize the same person across apps. That shared person identity does not declare that a particular email is about a particular page. Use an explicit source relation for that record-level connection.

</Accordion>
<a id="link-a-crm-field-to-a-postgres-row"></a>
<Accordion title="Link a CRM field to a Postgres row">

**You can represent a foreign-key link between app sources.** Suppose a HubSpot contact has a custom field `psql_user_id: "123"` referring to row `123` in your Postgres `public.users` table. Ingest the contact and the row as `custom` app sources. Your mapping code reads the field and adds a relation to the row's HydraDB source ID.

| Input | Your mapping |
|---|---|
| Postgres row `public.users`, primary key `123` | Source `id: "postgres:public.users:123"`, `provider: "postgres"`, `external_id: "public.users:123"` |
| Contact's `psql_user_id: "123"` | `app_relations[].target.source_id: "postgres:public.users:123"` describes the link; `relations.ids` includes that same source ID for retrieval |
| User ID for exact filtering | `metadata.user_id: "123"` on both sources |

The source-ID format above is a convention you define in your mapping. Include the schema and table so rows with the same primary key in different tables remain distinct. If the row already has a HydraDB source ID, use that actual ID instead. Apply the same mapping to references from Salesforce or any other app.

**The relation comes from your mapping, not from storing the ID in `fields.data`.** Read each non-empty `psql_user_id`, compute or look up the matching row's source ID, and declare the typed link in `app_relations` plus the retrieval link in `relations.ids`, as shown below. This creates a graph connection; it does not enforce a SQL foreign-key constraint or read from Postgres during a query.

Declare `user_id` as a `VARCHAR` field with `enable_match: true` in your [database metadata schema](/essentials/v2/metadata). The array below shows both mapped snapshots. Save the row object by itself as `app-sources.json`, send it with the [ingestion request](#2-ingest-an-app-source), and wait for `completed`. Then save and send the contact object, which refers to that row.

```json Contact linked to a user row
[
  {
    "id": "postgres:public.users:123",
    "database": "acme_corp",
    "collection": "default",
    "title": "User 123: Morgan Lee",
    "kind": "custom",
    "provider": "postgres",
    "external_id": "public.users:123",
    "fields": {
      "kind": "custom",
      "body": "Morgan Lee is Acme's renewal contact and has an enterprise account.",
      "data": {
        "record_type": "user",
        "table": "public.users",
        "user_id": "123",
        "name": "Morgan Lee",
        "plan": "enterprise"
      }
    },
    "metadata": { "user_id": "123" }
  },
  {
    "id": "hubspot_contact_456",
    "database": "acme_corp",
    "collection": "default",
    "title": "Morgan Lee: renewal contact",
    "kind": "custom",
    "provider": "hubspot",
    "external_id": "456",
    "fields": {
      "kind": "custom",
      "body": "Morgan Lee asked for the login issue to be resolved before renewing.",
      "data": {
        "record_type": "contact",
        "name": "Morgan Lee",
        "psql_user_id": "123"
      }
    },
    "metadata": { "user_id": "123" },
    "relations": { "ids": ["postgres:public.users:123"] },
    "app_relations": [

        "predicate": "linked_to",
        "target": { "source_id": "postgres:public.users:123" }
      }
    ]
  }

```

Keep both sources in the same database and collection. For the `source_id` link shown here, first ingest the row by itself and wait for `completed`, then ingest the contact. The array above shows both mapped payloads; it does not define ingestion order. For the typed `app_relations` target, the external-ID form is `{ "external_id": "public.users:123", "provider": "postgres" }`. The retrieval link in `relations.ids` still uses the row's HydraDB source ID.

**For connected context**, query with `query_apps: true`, `mode: "thinking"`, and `query_forceful_relations: true`. The `relations.ids` declaration requests the user row's text in `additional_context` alongside a contact hit; read that field alongside `chunks`. Fast mode ignores this forceful retrieval flag.

**For an exact user-ID constraint**, use `metadata_filters`. The shared `metadata.user_id` makes both sources eligible for the same lookup. Filters also apply to connected context, so put the value on every source you want included. Retrieval still ranks the matching content.

Send this JSON body to [`POST /query`](/api-reference/v2/endpoint/query):

```json Query linked sources with an exact user-ID filter
{
  "database": "acme_corp",
  "collection": "default",
  "type": "knowledge",
  "query": "What is blocking Morgan Lee's renewal, and what account plan do they have?",
  "query_apps": true,
  "mode": "thinking",
  "query_forceful_relations": true,
  "max_results": 4,
  "metadata_filters": {
    "user_id": { "equals": "123" }
  }
}
```

See [Scoping using metadata](/essentials/v2/metadata) for schema setup and filter semantics.

When the contact's `psql_user_id` changes, ingest the new target row and wait for it to complete, then send the contact's complete snapshot with `upsert: true`, updating `app_relations[].target.source_id`, `relations.ids`, and `metadata.user_id`. Keep row IDs stable when updating the row's other fields. After the contact completes, verify the changed link with the [connected subgraph endpoint](/api-reference/v2/endpoint/subgraph).

## 4. Incremental ingestion

Send new and changed items to the same [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) endpoint. **A new item gets a new source ID. An edited item keeps its source ID and is sent with `upsert=true` as a form field.** You only need to send the items that changed.

For the Slack thread above:

1. Alice posts the opening message. Ingest `slack_C01_1716213600_000100`.
2. Carol replies. Ingest only `slack_C01_1716213700_000200`, with the same `thread_id` and the opening message's external ID as `parent_id`.
3. Carol edits her reply. Send the complete updated reply with the same `id` and `external_id`, and `upsert: true`.
4. Carol deletes her reply. [Delete the source](/api-reference/v2/endpoint/delete-source) using its HydraDB `id`.

<Accordion title="Update a Slack reply: JSON snapshot, cURL request, and Python SDK">

Wait for Carol's previous ingestion to reach `completed` or `errored` before sending another snapshot. If it errored, inspect `error_code` and correct the failure before retrying. Save the complete updated reply below as `reply-update.json`, then run the cURL request in the next tab. This replaces only Carol's source, retaining its identity and thread connections.

<CodeGroup>
```json reply-update.json

  "provider": "slack",

  "fields": {
    "kind": "message",

```


The same rule applies across apps:

| App event | What to send |
|---|---|
| New message, email, page, or ticket | A new source with its own `id` and `external_id` |
| Ticket status or page body changes | The updated source with the same IDs and `upsert: true` |
| New ticket or page comment | A new `comment` source with its own IDs and the parent's external ID in `fields.parent_id` |
| Existing comment edited | The updated comment source with the same IDs and `upsert: true` |
| Item deleted | `DELETE /context` with the item's HydraDB source ID, after ingestion reaches `completed` or `errored` |

`upsert: true` replaces the source snapshot. Include the current fields, metadata, attachments, comments, and relations you want to retain. Process updates for the same source in order: wait for its current ingestion to reach a terminal state (`completed` or `errored`) before submitting another snapshot. If it errored, inspect `error_code` and correct the failure before retrying. For a new comment arriving on a ticket, ingest a separate `comment` source so you can update or delete that comment independently.

For deletion, check the response's `data.results[].deleted` value. An HTTP 200 alone can include a failed deletion when the source is still processing; wait for `completed` or `errored` and retry. Set `X-HydraDB-Delete-Status: strict` to receive an HTTP error for a failed deletion. See [Delete source](/api-reference/v2/endpoint/delete-source).

## 5. Include attachments and comments

### Attachments: the supporting file's text

A message can share a runbook; a ticket comment can include a diagnostic trace. Add these to the source's `attachments` array so their extracted text is searchable and connected to the item that shared them.

Extract the file's text in your connector and send it in `content.text` or `content.markdown`. `url` is a link back to the file; HydraDB does not download a file from that URL in an app-source payload. To upload the original file for HydraDB to parse, use the [file ingestion path](/essentials/v2/knowledge#path-a-files).

<Accordion title="Attachment example: add a diagnostic trace to a comment">

Add this fragment to the comment source from the ticket pattern:

```json Attachment fields
{
  "attachments": [
    {
      "id": "att-har-1",
      "title": "staging-login.har",
      "url": "https://files.example.com/staging-login.har",
      "content_type": "application/json",
      "content": {
        "text": "The trace shows repeated redirects after token refresh."
      }
    }
  ]
}
```

The trace's text can help answer "What evidence did Carol provide for AUTH-123?" Keep the attachment ID stable when syncing the same file again.

</Accordion>

### Comments: a snapshot or an independent source

There are two ways to include comments. Choose based on how your app sync works:

| Sync behavior | Representation | Example |
|---|---|---|
| You have the parent and its complete current comment list | Embed `comments` on the parent source | An initial Jira export containing the ticket and all comments |
| Comments arrive, change, or disappear individually | Ingest each as a `kind: "comment"` source | A webhook announces Carol's new comment on AUTH-123 |

Embedded comments add searchable text and authors connected to the parent. They are part of its snapshot. Independent comment sources have their own HydraDB IDs, so each can be replaced or deleted without resending the parent.

<Accordion title="Snapshot example: include the ticket's current comments">

Add this fragment to the ticket source when sending a complete snapshot:

```json Embedded comments
{
  "comments": [
    {
      "id": "c123",
      "author": "carol",
      "body": "Reproduces on staging when the refresh token expires.",
      "created_at": "2026-05-20T11:00:00Z"
    },
    {
      "id": "c124",
      "author": "alice",
      "body": "Fixed by disabling the new token refresh path.",
      "created_at": "2026-05-20T11:15:00Z"
    }
  ]
}
```

On the next parent upsert, send the complete current comment list. A payload containing only a new comment replaces the snapshot rather than appending to it. For separate comment sources, use the ticket-and-comment pattern above.

</Accordion>

Slack replies and email replies keep their `message` and `email` classes. This preserves each reply's app fields and thread connections.

## 6. Add metadata for filtering and display

Use `metadata` for shared values you want to filter on, such as Slack channel, Jira project, or department. Declare those keys in the [database metadata schema](/essentials/v2/metadata) with `enable_match: true` before ingestion.

Use `additional_metadata` for other details you want to preserve, such as a raw provider event ID or a display label.

```json Add to a Slack source
{
  "metadata": { "channel": "engineering" },
  "additional_metadata": { "workspace_name": "Acme" }
}
```

At query time, filter with `metadata_filters: { "channel": "engineering" }`. Filters on free-form values go under `metadata_filters.additional_metadata`. See [Scoping using metadata](/essentials/v2/metadata) for schema setup and complete filter examples.

## 7. Query app sources with connected context

Use [`POST /query`](/api-reference/v2/endpoint/query) with `type: "knowledge"` (or `"all"`) and `query_apps: true`. Set `mode: "thinking"` for queries that need related items, such as a thread's replies or a ticket's comments. For explicitly declared retrieval links, also use `query_forceful_relations: true` and read `additional_context`. Expand "Return linked content with query results" under [Connect app sources](#3-connect-app-sources) for the declaration, response fields, and current limitations.

<Accordion title="Query example: retrieve the rollback discussion and its replies">

```json POST /query
{
  "database": "acme_corp",
  "collection": "default",
  "type": "knowledge",
  "query": "What did Alice propose for the auth rollback, and did the replies confirm it worked?",
  "query_apps": true,
  "mode": "thinking",
  "max_results": 10
}
```

</Accordion>

The fields you supplied support different questions:

| Question | Relevant fields or connections |
|---|---|
| "Find Slack messages from Alice" | `kind`, `provider`, `fields.author` |
| "Did the rollback work? Show the discussion" | Message bodies, `thread_id`, reply connections |
| "What did Carol report on AUTH-123?" | Ticket `external_id`, comment author, `comment_on` |
| "Which renewal depends on the login fix?" | The CRM record's explicit link to the Jira ticket |
| "What do the attached rollback notes say?" | Extracted attachment text |
