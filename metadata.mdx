# Metadata

## What it is

Metadata in HydraDB is structured data attached to knowledge and memories that enables deterministic filtering during recall.

It operates in two tiers:

- **Tenant metadata schema** — typed, indexed fields declared at tenant creation
- **Document metadata** — flexible JSON attached at ingest time

The schema tier is what makes filtering work. Document metadata is flexible storage.

---

## What it does

Metadata lets you narrow recall candidates before retrieval runs.

When you pass `metadata_filters` to `full_recall`, HydraDB filters the candidate set deterministically using indexed schema fields, then runs retrieval on what remains. This may be exact-match filtering, not semantic similarity.

The result: faster, more predictable recall when you need it scoped to known dimensions like environment, customer tier, or document type.

---

## When to use it

Use metadata filtering when:

- Recall must be scoped to a known attribute (e.g. `compliance_framework: "SOC2"`)
- You need deterministic narrowing alongside semantic search
- You want to enforce strict filtering constraints that vector similarity cannot guarantee

Do not use metadata filtering for fuzzy matches or conceptual filtering — that is what semantic recall is for.

---

## How it works

**1. Define the schema at tenant creation**

Filterable fields may be declared in `tenant_metadata_schema` when the tenant is created. The schema is treated as immutable after creation — plan to declare fields upfront rather than relying on later modification.

Each field needs `enable_match: true` to be usable in `metadata_filters`.

**2. Attach metadata at ingest**

When ingesting knowledge or memories, pass metadata as native JSON objects (`tenant_metadata`, `document_metadata`, `metadata`, `additional_metadata`). These are stored alongside the content.

**3. Filter at recall**

Pass `metadata_filters` on `full_recall`. HydraDB applies the filter as a deterministic filter on the candidate set prior to retrieval stages.

---

## Key concepts

**Tenant metadata schema**
An array of typed field definitions declared at tenant creation. Defines which metadata fields are indexed and filterable. Treated as immutable after creation.

**`enable_match`**
Per-field flag. Must be `true` for the field to be usable in `metadata_filters`. Without it, the field may be stored but not filterable.

**`data_type`**
Field type. Supports multiple typed fields (e.g. string, integer, float, boolean, array). Friendly aliases such as `string`, `integer`, `float`, `boolean`, `array`, `object` may also be accepted. Default is `VARCHAR`.

**Document metadata**
Per-document JSON attached at ingest. Native JSON objects, not stringified. Flexible — does not need to match the schema. Not filterable unless its keys are also declared in the tenant schema with `enable_match: true`.

**`metadata_filters`**
The filter object passed to `full_recall`. Treated as **exact-match** on declared fields. Operators beyond exact-match: `Needs verification`.

**Filtering vs semantic search**
Filtering is deterministic and runs as a candidate-set filter prior to retrieval stages. Semantic retrieval and graph traversal run on the filtered candidate set. The two may be complementary, not interchangeable.

## Minimal working example

**1. Define the schema at tenant creation**

```python
client.tenants.create(
    tenant_id="acme_corp",
    tenant_metadata_schema=[
        {
            "name": "compliance_framework",
            "data_type": "VARCHAR",
            "max_length": 255,
            "enable_match": True,
            "enable_dense_embedding": False,
            "enable_sparse_embedding": False,
        }
    ],
)
```

**2. Ingest with metadata**

```python
client.knowledge.upload_knowledge(
    tenant_id="acme_corp",
    app_knowledge=[
        {
            "text": "...",
            "metadata": {"compliance_framework": "SOC2"},
            "additional_metadata": {},
        }
    ],
)
```

**3. Recall with `metadata_filters`**

```python
client.recall.full_recall(
    tenant_id="acme_corp",
    query="How does auth work?",
    metadata_filters={"compliance_framework": "SOC2"},
)
```

Only chunks whose `compliance_framework` equals `"SOC2"` enter the recall pipeline.

## Common mistakes

**Filtering on fields not declared in the schema**
`metadata_filters` typically only works on fields defined in `tenant_metadata_schema`. Filtering on an undeclared key may return no results or fail validation — it should not be assumed to silently fall through to document metadata.

**Forgetting `enable_match: true`**
A field declared without `enable_match` may be stored but not filterable. This is a common cause of "my filter returns nothing" issues.

**Trying to modify the schema after tenant creation**
The tenant metadata schema is treated as immutable after creation. Plan your filterable fields upfront. If you need new fields, plan to use a new tenant.

**Confusing metadata filtering with semantic search**
Metadata filtering is exact-match and deterministic. It does not understand synonyms, partial matches, or intent. Use it to scope, not to search.

**Stringifying metadata on ingest**
`tenant_metadata`, `document_metadata`, `metadata`, and `additional_metadata` may accept native JSON objects on the knowledge ingestion endpoint. Do not stringify them.

**Assuming document metadata is filterable by default**
Document metadata is flexible storage. To filter on a key, that key must also be declared in the tenant schema with `enable_match: true`.
