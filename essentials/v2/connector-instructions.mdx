---
title: "Custom Ingestion Instructions"
description: "Free text, per connector or per resource, that tells HydraDB what synced content means before it is indexed."
---

Custom ingestion instructions are free text on a connector or one of its resources. HydraDB adds the text to the extraction and inference stages of ingestion for every document the connector syncs, so you can say what the content means before it is indexed, including facts the documents never state.

Example: the product was renamed from Aurora to Nimbus. Old documents only say Aurora and never state the rename, so a search for Nimbus misses them. One instruction fixes that:

```text
Aurora was renamed to Nimbus in January 2025; they are the same product.
Index all Aurora content under the canonical name Nimbus and record
Aurora as a former name.
```

From the next sync, documents that mention only Aurora are extracted under the Nimbus entity, with alias links to the old name, so new-name queries reach old-name content through the knowledge graph.

Other uses:

- **Focus:** "prioritize decisions, owners, and deadlines; ignore social chatter".
- **Interpretation:** "threads in this workspace are incident retros; extract root cause and remediation".
- **Domain vocabulary:** "SEV1/SEV2 are incident severities, not product names".

---

## Works with every existing connector

Every existing connector supports instructions with a single `PATCH`, with no reconnection, reconfiguration or migration:

```bash
curl -X PATCH 'https://api.hydradb.com/connectors/CONNECTOR_ID' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{ "custom_instructions": "Aurora was renamed to Nimbus in January 2025; they are the same product." }'
```

Configuration is re-read at the start of every sync cycle, so the instruction applies from the next sync. A connector with no instructions behaves as before.

## Two levels: connector default and per-resource override

- **Connector level:** applies to every resource without instructions of its own. Set it with `custom_instructions` on `POST /connectors` or `PATCH /connectors/{id}`.
- **Resource level:** applies to documents from that one resource. Set it with `PATCH /connectors/{id}/resources/{resource_id}`, or with `custom_instructions` on a resource in configure.

A resource uses its own instructions, otherwise the connector's, otherwise none. A resource-level value **replaces** the connector default for that resource. It does not add to it. An empty or absent resource value inherits the default. Per-resource database and collection overrides resolve the same way.

Use a resource override when one connector spans different kinds of content, such as a channel of incident retros and a channel of release notes.

### Set the connector default at creation

```bash
curl -X POST 'https://api.hydradb.com/connectors' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "slack",
    "database": "acme_corp",
    "collection": "engineering",
    "credentials": { "access_token": "xoxp-..." },
    "custom_instructions": "Prioritize decisions and owners; treat threads as engineering discussions."
  }'
```

### Set a resource override

At configure time, per entry:

```bash
curl -X POST 'https://api.hydradb.com/connectors/CONNECTOR_ID/configure' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "resources": [
      { "resource_id": "C_INCIDENTS", "resource_type": "channel", "name": "incidents",
        "custom_instructions": "These are incident retros; extract root cause, impact, and owner." },
      { "resource_id": "C_RELEASES", "resource_type": "channel", "name": "releases" }
    ]
  }'
```

`C_RELEASES` carries no value, so it inherits the connector default. Or on an already-configured resource:

```bash
curl -X PATCH 'https://api.hydradb.com/connectors/CONNECTOR_ID/resources/RESOURCE_ID' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{ "custom_instructions": "These are incident retros; extract root cause, impact, and owner." }'
```

### Clear instructions

Send an explicit empty string. Omitting the field leaves the stored value unchanged:

```bash
curl -X PATCH 'https://api.hydradb.com/connectors/CONNECTOR_ID/resources/RESOURCE_ID' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{ "custom_instructions": "" }'
```

Clearing a resource override returns that resource to the connector default. A configure request without the field keeps an existing override, so reconfiguring never silently strips one.

### Read them back

`GET /connectors/{id}` returns the connector's `custom_instructions`. `GET /connectors/{id}/resources` returns each resource's, and omits it when the resource inherits.

## From the dashboard

- **At connect time:** the connect wizard has an *Instructions* step between resource selection and review. Set the connector default there, and click any selected resource to give it its own instructions before ingestion starts.
- **After connecting:** open the connector and click **Instructions**, or the instructions icon on any resource row. The dialog lists the connector default and every resource, showing which override and which inherit, so you can edit them in one place. Resources with their own instructions are badged in the resource table.

## Semantics and limits

- **Future syncs only:** instructions are read at sync time and stamped onto each document as it is ingested. Already-indexed documents are not re-processed. Each document keeps the instructions it was ingested under, in its stored metadata.
- **Length limit:** 4,000 characters, counted in characters rather than bytes, so multi-byte scripts get the same budget. Longer values are rejected with a `400`, and the stored value is left unchanged.
- **Cost:** the text rides the extraction and inference prompts for every synced document, so a long value on a high-volume connector is a recurring cost. Say what matters and stop.
- **Steering, not string rewriting:** instructions guide the language models that build the knowledge graph. Explicit, unambiguous rules ("X was renamed to Y; they are the same product; index under Y") get the strongest adherence, and vague guidance gets vague results. Name the exact terms, and keep unrelated rules as separate sentences.
- **No filtering or routing:** instructions do not change which documents sync, where they are stored, or who can access them. Use resource selection, [multi-tenant routing](/essentials/v2/multi-tenant), and [ACLs](/essentials/v2/access-control) for those.
