## What a memory is

A memory is one piece of context about a user: a stated preference, a trait inferred from behavior, a past conversation, a decision, feedback, or a fact you want back later. Memories carry that context across sessions, and HydraDB links them in a [context graph](/essentials/v2/context-graphs) so related preferences come back together.

Store it as a memory when only that user, workspace, or session should retrieve it, and as [knowledge](/essentials/v2/knowledge) when other users should too. Full comparison: [Core Concepts](/get-started/v2/core-concepts#how-knowledge-and-memories-differ).

---

## What happens when you ingest a memory

[`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) with `type=memory`:

1. Parses the input: raw text, markdown, or user and assistant pairs.
2. With `infer: true`, extracts the preference, trait, or fact. With `infer: false`, keeps the text you sent.
3. Indexes the result for [`POST /query`](/api-reference/v2/endpoint/query) with `type: "memory"` or `type: "all"`.

Ingestion is asynchronous. Before you query, poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) until the memory reaches at least `graph_creation` (`completed` for full indexing), or [register a webhook](/essentials/v2/webhooks).

## Minimal working example

Store a preference for one user, scoped by `collection`:

<CodeGroup>

```python Python SDK
import json
import os
from hydra_db import HydraDB

client = HydraDB(token=os.environ["HYDRA_DB_API_KEY"])

result = client.context.ingest(
    type="memory",
    database="acme_corp",
    collection="user_john_123",
    upsert=True,
    memories=json.dumps([
        {
            "text": "Prefers short, direct answers with no preamble.",
            "infer": True,
            "user_name": "John",
        }
    ]),
)
```

```typescript TypeScript SDK
import { HydraDBClient } from "@hydradb/sdk";

const client = new HydraDBClient({
  token: process.env.HYDRA_DB_API_KEY,
});

const result = await client.context.ingest({
  type: "memory",
  database: "acme_corp",
  collection: "user_john_123",
  upsert: true,
  memories: JSON.stringify([
    {
      text: "Prefers short, direct answers with no preamble.",
      infer: true,
      user_name: "John",
    },
  ]),
});
```

```bash cURL
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=memory" \
  -F "database=acme_corp" \
  -F "collection=user_john_123" \
  -F "upsert=true" \
  -F 'memories=[
    {
      "text": "Prefers short, direct answers with no preamble.",
      "infer": true,
      "user_name": "John"
    }
  ]'
```

</CodeGroup>

Each memory gets an `id` and an initial `status` of `queued`. Read them from the envelope's `data` (`response.data.results`):


## Choose whether HydraDB should infer the memory

`infer` sets how much extraction your application does before it sends content.

### Use `infer: true` when the input is raw signal

You send messy or indirect evidence, and HydraDB extracts the preference, trait, or fact. Use it for dialogue where the preference is implicit, behavior logs and event streams, and feedback like "the last summary was too long." Do not extract preferences yourself first: send the raw signal.

`custom_instructions` guides extraction, for example `"Focus on UI and notification preferences only"`. It takes effect only when `infer: true`.

### Use `infer: false` when the input is already the memory

The default. HydraDB stores and indexes exactly what you send, with no extraction step. It is faster and deterministic. Use it for facts you already captured (`"User's plan tier is Pro"`), pre-structured notes, and content you want back as written. With `infer: true`, HydraDB may re-derive such a fact and change its phrasing.

### Example: infer a preference from behavior

A user has been toggling dark mode. Instead of writing logic to decide what they prefer, send the raw log with `infer: true`.

<CodeGroup>

```python Python SDK
import json

client.context.ingest(
    type="memory",
    database="acme_corp",
    collection="user_john_123",
    memories=json.dumps([
        {
            "text": (
                "User opened the app 14 times in the last week. "
                "Switched to dark mode on first session. "
                "Toggled back to light once on 2026-04-12 at 3pm, "
                "then switched back to dark within 4 minutes. "
                "Has not changed theme since."
            ),
            "infer": True,
            "user_name": "John",
            "custom_instructions": "Focus on display and theme preferences.",
        }
    ]),
)
```


A later query with `type: "memory"` and `"what UI settings does the user prefer?"` can return the inferred `"prefers dark mode"` instead of the log. With `infer: false`, HydraDB would index the log verbatim.

## Choose the right input shape

Each memory item takes either `text` or `user_assistant_pairs`, not both.

### Text

Use `text` for prose: observations, captured facts, preference statements, meeting notes, or semi-structured records. Set `is_markdown: true` to keep markdown structure (headings, lists, code blocks) during chunking and embedding. Leave it unset or `false` for plain prose.

```json
{
  "text": "# Meeting Notes\n\n## Key Points\n- Budget approved",
  "is_markdown": true,
  "infer": false
}
```

```json
{
  "text": "Prefers detailed technical explanations and works in PST.",
  "infer": true
}
```

### User and assistant pairs

Use `user_assistant_pairs` when the signal comes from dialogue. Set `infer: true` with it, or HydraDB stores the raw dialogue without extracting a preference.

```json
{
  "user_assistant_pairs": [
    { "user": "Remember I like dark mode", "assistant": "Noted." }
  ],
  "infer": true
}
```

## Memory fields

For `type=memory`, send a JSON-stringified `memories` array. Full schema: [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context).

### Request-level fields

| Field | Default | Description |
|---|---|---|
| <Field name="type" type="memory" required /> | None | Selects the Memories store. Use singular `memory`. |
| <Field name="database" type="string" required /> | None | Target database. Deprecated alias: `tenant_id`. Omitting it returns `400` (`database is required`). |
| <Field name="collection" type="string" recommended /> | default collection | User, workspace, or session scope, such as the user's ID. Deprecated alias: `sub_tenant_id`. Without it, the memory lands in the default collection and can surface in the wrong scope. |
| <Field name="upsert" type="boolean" /> | `true` | Replace existing memories with the same `id`. |
| <Field name="memories" type="string (JSON array)" required /> | None | JSON-stringified array of memory items. |

### `memories` item fields

| Field | Description |
|---|---|
| <Field name="id" type="string" /> | Optional stable ID. The upsert key and relation target. |
| <Field name="title" type="string" /> | Short label shown in `/context/list` and query results. |
| <Field name="text" type="string" recommended /> | Raw text or Markdown. Required unless `user_assistant_pairs` is set. |
| <Field name="user_assistant_pairs" type="array" recommended /> | Pairs shaped `{ "user": "...", "assistant": "..." }`. Required unless `text` is set. |
| <Field name="is_markdown" type="boolean" /> | Treat `text` as Markdown for chunking and indexing. |
| <Field name="infer" type="boolean" /> | `true` extracts the underlying preference, trait, or fact. `false` (the default) stores the input as written. |
| <Field name="custom_instructions" type="string" /> | Guides extraction when `infer: true`. Ignored when `infer: false`. |
| <Field name="user_name" type="string" /> | User name used during inference. A wrong name can bias extraction, so pass the real one. |
| <Field name="expiry_time" type="integer" /> | TTL in seconds. The memory stops surfacing after expiry. |
| <Field name="metadata" type="object" /> | Database-schema fields for filtering, for example `"metadata": { "department": "support" }`. Up to 16 KiB as compact JSON. |
| <Field name="additional_metadata" type="object" /> | Free-form per-memory fields for display or bookkeeping. Up to 1 KiB as compact JSON. |
| <Field name="relations" type="object" /> | Forcefully connect this memory to other memories with `{ "ids": [...] }`. |

<Note>
  `memories` is a JSON-stringified multipart field. Inside each item, `metadata` and `additional_metadata` are plain objects. Do not stringify them again.
</Note>

```json
{
  "id": "pref_dark_mode",
  "text": "User prefers dark mode and concise answers.",
  "infer": true,
  "metadata": { "department": "support", "workspace": "docs" },
  "additional_metadata": { "source": "onboarding" }
}
```

## Query memories

On [`POST /query`](/api-reference/v2/endpoint/query), `type: "memory"` reads this store (readiness: `vectorstore_status.memories`). `type: "knowledge"` does not return memories. `type: "all"` reads both stores from the same scope and returns one re-ranked result set, for personalized answers grounded in shared documents.

Query under the `collection` the memory was written to. If shared documents live in another collection, send both in `collections`, for example `["company_docs", "user_john_123"]`. See [Query](/essentials/v2/query) and [Multi-tenant support](/essentials/v2/multi-tenant#shared-knowledge-plus-user-personalization).

## Connect related memories with forceful relations

The context graph comes from your content. Forceful relations are links you declare, for when two memories belong together but the text does not say so, such as a tone preference and a format preference. Set an `id` on each memory you want to link, then add `relations` to any item in `memories`:

```json
{
  "relations": {
    "ids": ["memory-id-1", "memory-id-2"]
  }
}
```

<CodeGroup>
```python Python SDK
import json

client.context.ingest(
    type="memory",
    database="acme_corp",
    collection="user_alex",
    memories=json.dumps([
        {
            "text": "User prefers concise answers",
            "id": "pref-concise",
            "infer": True,
            "relations": {"ids": ["pref-tone", "pref-format"]},
        }
    ]),
)
```
```typescript TypeScript SDK
await client.context.ingest({
  type: "memory",
  database: "acme_corp",
  collection: "user_alex",
  memories: JSON.stringify([
    {
      text: "User prefers concise answers",
      id: "pref-concise",
      infer: true,
      relations: { ids: ["pref-tone", "pref-format"] },
    },
  ]),
});
```
```bash cURL
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=memory" \
  -F "database=acme_corp" \
  -F "collection=user_alex" \
  -F 'memories=[
    {
      "text": "User prefers concise answers",
      "id": "pref-concise",
      "infer": true,
      "relations": { "ids": ["pref-tone", "pref-format"] }
    }
  ]'
```
</CodeGroup>

Linked memories come back in the `additional_context` field of the [query response](/api-reference/v2/endpoint/query). Expansion is on by default. Send `query_forceful_relations: false` to turn it off.

<Warning>
- **Same store only:** a memory item that points at a knowledge ID, or the reverse, silently returns nothing at query time.
- **`thinking` mode only:** linked memories are fetched only with `mode: "thinking"`, or `mode: "auto"` when it routes to thinking. With `mode: "fast"`, `query_forceful_relations: true` is not an error. It is silently ignored.
</Warning>

## Common mistakes

- **Sending `"memory": "..."`:** validation fails. Use `"memories": [ { "text": "..." } ]`, always an array of objects.
- **Storing shared docs as memories:** they do not surface for `type: "knowledge"`. Ingest them with `type=knowledge`.
