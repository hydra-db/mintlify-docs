## Ingesting Knowledge

There are two ways to ingest knowledge/context

1. Directly using the ingest API. You have to set your own ACLs with multi tenancy features within the database
2. Connectors API - programmatically ingest data from slack, gmail, linear, and 70+ connectors with all RBAC aware. Read more in  [Connectors](/essentials/v2/connectors).

### Upload with metadata

| Property | What it is |
|---|---|
| `id` | Your stable ID for the file, and the upsert key. Send the same `id` later to replace the file, or use it to check status and delete. Leave it out to have one generated; the response returns it either way. |
| `metadata` | Values you filter on at query time, such as `document_type`. Declare the keys in the database's [metadata schema](/essentials/v2/metadata). Up to 16 KiB as compact JSON. |
| `additional_metadata` | Free-form values for display and bookkeeping. Filterable only when nested under `additional_metadata` in `metadata_filters`. Up to 1 KiB as compact JSON. |
| `relations` | Other sources this file belongs with, as `{ "ids": [...] }`. See [Link documents that belong together](#6-link-sources-that-belong-together). |

## Ingesting memory

HydraDB does not capture memories on its own: your application saves one when a user states a preference, makes a decision in a specific way, finishes a task, or corrects the agent.

1. **Let HydraDB infer**: `infer` controls whether HydraDB extracts memories and preferences from what you send.
   1. `infer: true`(default): Extracts the preferences, trait, or fact from messy or indirect evidence.
   2. `infer: false`: Stores and indexes exactly what you send. No preprocessing step.
2. **Ingest memory**: It can be via `text` or `user_assistant_pairs`, not both.
   - `text`: Any prose, such as observations, facts, meeting notes, or semi-structured records. Set `is_markdown: true` for Markdown content so HydraDB keeps its structure when chunking and embedding.
   - `user_assistant_pairs`: Dialogue, especially when a preference is implied rather than stated. Each pair is `{ "user": "...", "assistant": "..." }`.

        }

| Form field | What to send |
| --- | --- |
| `type` | `memory` |
| `database` | An existing [database](/api-reference/v2/endpoint/create-database) |
| `collection` | The user's own collection, such as `user_john_123`. |
| `memories` | One item or a list of items, as a JSON string |
| `upsert` | Leave it out. It defaults to `true`, so sending an item again with the same `id` replaces the saved memory. |

## Wait for indexing

Use polling or webhooks for verify indexing status:

- **Webhooks:** register a [webhook](/api-reference/v2/endpoint/webhooks-overview) and HydraDB notifies you when indexing finishes, so you don't need to poll.
- **Polling:** call [`GET /context/status`](/api-reference/v2/endpoint/source-status) with those ids and the same `collection` every few seconds until `indexing_status` is `completed` or `errored`.
  - At `graph_creation`, the source becomes searchable but its graph is still building. Queries sent right away can miss it, and a new collection can still be reported as not existing.
  - At `completed`, the source and its graph are ready to query.

[Ingestion Status](/api-reference/v2/endpoint/source-status) lists every status.

## Upsert or Delete

To change a source, send it again with the same `id`. `upsert` defaults to `true`, so the saved one is replaced; include everything you want to keep. Wait for the previous ingestion to reach `completed` or `errored` before sending the next update for the same `id`.

To remove one, call [`DELETE /context`](/api-reference/v2/endpoint/delete-source) with its `id` and the same `collection`.

## Link sources explicitly/pragmatically/deterministically

You can declare links and relations between sources using `explicit_relations` that you want to explicitly link together. HydraDB returns these explicitly linked sources in the `additional_context` field of the response, alongside the primary response.

This is separate from the relations in the context graph HydraDB builds on its own.

On a file, set `relations.ids` on its `document_metadata` item. On an app source, set `relations.ids` the same way, and name the relationship in `app_relations` so the link also carries a predicate. `relations.ids` is what makes the linked text come back with query results; a named relationship alone connects the sources without requesting their text.

`query_explicit_relations` defaults to `true`; set it to `false` to skip the linked sources.
