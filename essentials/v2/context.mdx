## Ingesting files

There are two ways to ingest context

1. Directly using the ingest API. You have to set your own ACLs with multi tenancy features within the database
2. Connectors API - programmatically ingest data from slack, gmail, linear, and 70+ connectors with all RBAC aware. Read more in  [Connectors](/essentials/v2/connectors).

### Upload with metadata

| Property | What it is |
|---|---|
| `id` | Your stable ID for the file, and the upsert key. Send the same `id` later to replace the file, or use it to check status and delete. Leave it out to have one generated; the response returns it either way. |
| `metadata` | Values you filter on at query time, such as `document_type`. Declare the keys in the database's [metadata schema](/essentials/v2/metadata). Up to 16 KiB as compact JSON. |
| `additional_metadata` | Free-form values for display and bookkeeping. Filterable only when nested under `additional_metadata` in `metadata_filters`. Up to 1 KiB as compact JSON. |
| `relations` | Other sources this file belongs with, as `{ "ids": [...] }`. See [Link sources deterministically](#link-sources-deterministically). |

### Spreadsheets become queryable tables

A CSV, TSV or Excel workbook (`.xlsx`, `.xlsm`, `.xlsb`, `.xls`, `.ods`) uploaded here, or delivered by a file connector such as Google Drive, Dropbox, Box, SharePoint or Nextcloud, is ingested two ways at once. Its cells are rendered as text and indexed like any other document, and its rows are kept as a typed table: HydraDB infers a column type for every column and records the row ranges each chunk came from. A workbook yields one table per sheet.

Nothing changes in how you upload. The difference shows at query time: a question that needs filtering, grouping or arithmetic over the rows is answered by SQL that HydraDB writes and runs over the complete table, with the result returned under `tabular_data`. See [Ask questions over spreadsheets](/essentials/v2/query#ask-questions-over-spreadsheets).

Replacing the file with the same `id` replaces the table too; the previous version is no longer queried once the new one is indexed. A table is bounded at 4,096 columns; a file with more columns is ingested as text only.

## Ingesting context

HydraDB does not capture conversations on its own: your application saves one when a user states a preference, makes a decision in a specific way, finishes a task, or corrects the agent.

Give each user their own collection, such as `user_john_123`, and send it on every ingest, status check, and query. Your backend picks the collection from the signed-in session, never from untrusted client input; the collection name itself does not authenticate anyone.

Apply the same server-derived scope and authorization to updates and deletes. Before any operation, authorize the signed-in user's access to the source in that collection; knowing a source ID or collection name is not permission to read or change it.

1. **Let HydraDB enrich**: `enrich` controls whether HydraDB extracts facts and preferences from what you send.
   1. `enrich: true` (default): Extracts the preferences, trait, or fact from messy or indirect evidence. Omitting `enrich` means `true`.
   2. `enrich: false`: Disables additional enrichment for that item. Ingestion, indexing, and entity/graph extraction may still run.
2. **Ingest context**: It can be via `text` or `conversation`, not both.
   - `text`: Any prose, such as observations, facts, meeting notes, or semi-structured records.
   - `conversation`: Dialogue, especially when a preference is implied rather than stated. Each turn is `{ "role": "...", "content": "..." }`, with `role` set to `user`, `assistant`, or `system`.

Set up your [SDK client](/api-reference/v2/sdks#client-setup) before running the Python or TypeScript example.

The `verified_session` / `verifiedSession` objects and `SESSION_MEMORY_COLLECTION` below stand in for scope already resolved by your backend from a verified session.
```python Python SDK
import json
import os
from hydra_db import HydraDB

client = HydraDB(token=os.environ["HYDRADB_API_KEY"])
verified_session = {"memory_collection": "user_john_123"}

result = client.context.ingest(
    database="acme_corp",
    collection=verified_session["memory_collection"],
    context=json.dumps([
        {
            "text": "Prefers short, direct answers with no preamble.",
            "enrich": True,
            "user_name": "John",
        }
    ]),
)
```


## Wait for indexing

Use polling or webhooks to check indexing status:

- **Webhooks:** register a [webhook](/api-reference/v2/endpoint/webhooks-overview) and HydraDB notifies you when indexing finishes, so you don't need to poll.
- **Polling:** call [`GET /context/status`](/api-reference/v2/endpoint/source-status) with those ids and the same `collection` every few seconds until `indexing_status` is `completed` or `errored`.
  - At `graph_creation`, the source becomes searchable but its graph is still building. Queries sent right away can miss it, and a new collection can still be reported as not existing.
  - At `completed`, the source and its graph are ready to query.

[Ingestion Status](/api-reference/v2/endpoint/source-status) lists every status.

## Upsert or Delete

To change a source, send it again with the same `id`, or the same `context_id` for a `context` item. `upsert` defaults to `true`, so the saved one is replaced; include everything you want to keep. Wait for the previous ingestion to reach `completed` or `errored` before sending the next update for the same `id`.

To remove one, call [`DELETE /context`](/api-reference/v2/endpoint/delete-source) with its `id` and the same `collection`.

## Link sources deterministically

Deterministic relations are links you declare between sources at ingestion. When a query matches one of those sources, HydraDB returns the linked sources in the response list `data.forceful_relations`, alongside the primary chunks.

This is separate from the relations in the context graph HydraDB builds on its own.

On a file, set `relations.ids` on its `document_metadata` item. On a `context` item, set `forceful_relations.context_ids`. These IDs are what make the linked text come back with query results.

`query_explicit_relations` defaults to `true`; set it to `false` to skip the linked sources. Linked-source retrieval runs only in `thinking` mode.
