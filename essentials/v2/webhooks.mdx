title: "Webhooks"
description: "Receive indexing status events when ingested content finishes processing."
---

Webhooks send your application an HTTP callback when HydraDB finishes processing a document or memory. Use them to update your own database when content is ready for query, notify users that an upload finished, trigger downstream jobs, or track indexing failures without polling.

---

## 1. How it works

When an ingested item reaches a terminal indexing state, HydraDB creates a delivery record and sends a `POST` to your URL. For progress updates before that, use [Ingestion Status](/api-reference/v2/endpoint/source-status). A failed delivery is retried in the background, and you can also retry it yourself. See [Delivery and retries](#7-delivery-and-retries).

The only event today is `indexing.status_changed`. It fires when an item reaches `completed`, `errored`, or `success` (a legacy alias for `completed`).

## 2. Register a webhook

Open the HydraDB dashboard and go to **Webhooks**.

1. Click **Register Webhook**.
2. Enter your public HTTPS endpoint.
3. Select `indexing.status_changed`.
4. Save the webhook.
5. Enable signing and copy the generated secret. It is shown once and cannot be retrieved later.
6. Use **Send Test** to confirm your endpoint receives a request.

Signing is optional, but turn it on. Without it, your endpoint cannot tell a real HydraDB delivery from any other request. See [Verifying signatures](#5-verifying-signatures).

<Warning>
Your webhook URL must be reachable from the public internet. Localhost and private network addresses are blocked.
</Warning>

<Info>
Management endpoints (`/webhooks/indexing` and the routes under it) return the standard v2 `{ success, data, error, meta }` envelope, like `/databases`, `/context/*`, and `/query`. The examples below show only `data`. The event sent to your URL is not wrapped. See [Request format](#3-request-format).
</Info>

### Register with cURL

```bash cURL
curl -X POST 'https://api.hydradb.com/webhooks/indexing' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://api.example.com/webhooks/hydradb",
    "event_types": ["indexing.status_changed"],
    "signing_secret": "replace-with-at-least-16-characters"
  }'
```

**Response:**

```json
{
  "registered": true,
  "url": "https://api.example.com/webhooks/hydradb",
  "event_types": ["indexing.status_changed"],
  "signing_secret_configured": true,
  "message": "Webhook registered."
}
```

`signing_secret` is optional. If you send one, it must be at least 16 characters.

Or send `generate_signing_secret` to register and enable signing in one call. The generated secret comes back once, in this response:

**Response:**

```json
{
  "registered": true,
  "url": "https://api.example.com/webhooks/hydradb",
  "event_types": ["indexing.status_changed"],

  "signing_secret": "whsec_Yk8sQ2pWc0xuNGRIeUZ0UmJKZ1B3WHZNaTdaYUUxcW8",
```

### Edit a webhook

`POST /webhooks/indexing` also replaces an existing registration.

```bash cURL
curl -X POST 'https://api.hydradb.com/webhooks/indexing' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \

```

Omitting `signing_secret` while editing **preserves** your current secret. Editing the URL or the event list never changes your signing configuration. To turn signing off, call `DELETE /webhooks/indexing/signing-secret`.

### Manage the signing secret

You can enable signing when you register, with `generate_signing_secret` or `signing_secret`. To enable, rotate, or disable it later, use `/webhooks/indexing/signing-secret`.

**Generate a secret:** send no body. HydraDB returns a strong secret once, in plain text.

```bash cURL
curl -X POST 'https://api.hydradb.com/webhooks/indexing/signing-secret' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

**Response:**

```json
{
  "signing_secret": "whsec_Yk8sQ2pWc0xuNGRIeUZ0UmJKZ1B3WHZNaTdaYUUxcW8",
  "generated": true,
  "message": "Signing secret generated. Copy it now - it cannot be retrieved later, and it takes effect immediately."
}
```

**Supply your own:** deploy the secret to your receiver first, then give it to HydraDB, so no delivery is signed with a secret your endpoint lacks.

```bash cURL
curl -X POST 'https://api.hydradb.com/webhooks/indexing/signing-secret' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{ "signing_secret": "at-least-16-characters" }'
```

**Disable signing:** removes the stored secret. Deliveries stop carrying `X-HydraDB-Signature`.

```bash cURL
curl -X DELETE 'https://api.hydradb.com/webhooks/indexing/signing-secret' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

<Warning>
Rotating takes effect immediately, with no overlap period. Deliveries in flight are signed with the new secret, so a receiver that only knows the old one rejects them. See [Zero-downtime key rotation](#zero-downtime-key-rotation).
</Warning>

## 3. Request format

HydraDB sends a `POST` request with a JSON body.

### Headers

- `Content-Type`: always `application/json`.
- `X-HydraDB-Delivery-ID`: stable delivery ID for this event.
- `X-HydraDB-Event`: event name, such as `indexing.status_changed`.
- `X-HydraDB-Signature`: `sha256=<hex>`, the HMAC-SHA256 of the raw request body keyed by your signing secret. Present only when signing is configured.

The signature scheme in full:

```
X-HydraDB-Signature: sha256=<lowercase hex digest>

digest = HMAC-SHA256(key = signing_secret, message = raw request body bytes)
```

Three details decide whether your verifier works:

- The `sha256=` prefix is **part of the header value**. Compare against the whole string.
- The digest is **lowercase hex**, not base64.
- The HMAC covers the **raw body bytes exactly as received**. Parsing and re-serialising the JSON produces different bytes, and the signature will not match.

### Payload

```json
{
  "event": "indexing.status_changed",
  "delivery_id": "<delivery_id>",
  "id": "<id>",
  "tenant_id": "<database_id>",
  "database": "<database>",
  "sub_tenant_id": "<collection>",
  "collection": "<collection>",
  "status": "completed",
  "timestamp": "<ISO-8601 timestamp>"
}
```

For failed indexing, the payload can include `error_code` and `error_message`:

```json
{
  "event": "indexing.status_changed",
  "delivery_id": "<delivery_id>",
  "id": "<id>",
  "tenant_id": "<database_id>",
  "database": "<database>",
  "sub_tenant_id": "<collection>",
  "collection": "<collection>",
  "status": "errored",
  "timestamp": "<ISO-8601 timestamp>",
  "error_code": "<error_code>",
  "error_message": "<error_message>"
}
```

- `event`: event type, currently `indexing.status_changed`.
- `delivery_id`: stable ID for this event. Store it to deduplicate retries.
- `id`: the document, memory, or app item ID you supplied at ingestion. Older examples call it `doc_id`. New payloads use `id`.
- `database`: the database name you ingested into, the value you sent as `database` (or `tenant_id`). Empty only for items ingested before this field existed.
- `collection`: collection scope for the indexed item.
- `status`: terminal indexing status, usually `completed` or `errored`.
- `timestamp`: time the payload was created.
- `error_code`, `error_message`: present, when available, for failed processing.
- `tenant_id`: deprecated. An identifier for the database, not its name. Always present.
- `sub_tenant_id`: deprecated exact alias for `collection`.

<Note>
**`tenant_id` and `database` do not carry the same value.** `database` is the name you ingested into (`marketing-docs`), the only field that matches what you sent, so route and filter on **`database`**. `tenant_id` is an identifier for it (`kv3qz7mabx`), unchanged so existing integrations keep working. Read it only if you need a scope that is always set.
</Note>

## 5. Verifying signatures

Verification is one function of your signing secret, the raw request body, and the `X-HydraDB-Signature` header. The official SDKs include it:

<CodeGroup>

```python Python SDK
from hydra_db.helpers import verify_webhook_signature

if not verify_webhook_signature(secret, raw_body, signature):
    ...  # reject
```

```typescript TypeScript SDK
import { verifyWebhookSignature } from "@hydradb/sdk/helpers";

if (!verifyWebhookSignature(secret, rawBody, signature)) {
  // reject
}
```

</CodeGroup>

Without an SDK, copy `verify_webhook_signature` (Python) or `verifyWebhookSignature` (TypeScript) from the [receiver examples](#6-receiver-examples). Both compare in constant time: a plain `==` leaks timing information that can be used to forge a signature byte by byte. In Node, compare lengths first, because `timingSafeEqual` throws on a mismatch.

<Warning>
Fail closed. If the signing secret is missing from your environment, reject the request instead of skipping verification. A verifier that accepts everything when a variable is unset gives no protection.
</Warning>

## 6. Receiver examples

Return a `2xx` quickly and do slow work after you acknowledge the request. Both handlers read the **raw** body before parsing.

<CodeGroup>

```python Python
import hashlib
import hmac
import json
import os

from fastapi import FastAPI, Header, Request, Response

app = FastAPI()

# Fail fast at startup when the secret is missing, rather than accepting
# unverified deliveries at request time.
SIGNING_SECRET = os.environ["HYDRADB_WEBHOOK_SECRET"]


def verify_webhook_signature(secret: str, raw_body: bytes, signature: str | None) -> bool:
    if not secret or not signature:
        return False
    digest = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(signature, f"sha256={digest}")


@app.post("/webhooks/hydradb")
async def hydradb_webhook(
    request: Request,
    delivery_id: str | None = Header(default=None, alias="X-HydraDB-Delivery-ID"),
    signature: str | None = Header(default=None, alias="X-HydraDB-Signature"),
):
    raw_body = await request.body()

    if not verify_webhook_signature(SIGNING_SECRET, raw_body, signature):
        return Response(status_code=401)

    event = json.loads(raw_body)

    # Store delivery_id and skip it if you have already processed it.
    print("HydraDB webhook", delivery_id, event["id"], event["status"])

    return Response(status_code=204)
```

```typescript TypeScript
import crypto from "node:crypto";
import express from "express";

const app = express();

// Fail fast at startup when the secret is missing, rather than accepting
// unverified deliveries at request time.
const signingSecret = process.env.HYDRADB_WEBHOOK_SECRET;
if (!signingSecret) {
  throw new Error("HYDRADB_WEBHOOK_SECRET is required");
}

function verifyWebhookSignature(
  secret: string,
  rawBody: Buffer,
  signature: string | undefined,
): boolean {
  if (!secret || !signature) {
    return false;
  }
  const expected =
    "sha256=" + crypto.createHmac("sha256", secret).update(rawBody).digest("hex");

  const expectedBuffer = Buffer.from(expected);
  const signatureBuffer = Buffer.from(signature);

  if (signatureBuffer.length !== expectedBuffer.length) {
    return false;
  }
  return crypto.timingSafeEqual(signatureBuffer, expectedBuffer);
}

app.post(
  "/webhooks/hydradb",
  // express.raw is essential: the signature covers the raw bytes, so the body
  // must not be parsed before verification.
  express.raw({ type: "application/json" }),
  (req, res) => {
    const deliveryId = req.header("X-HydraDB-Delivery-ID");
    const signature = req.header("X-HydraDB-Signature");
    const rawBody = req.body as Buffer;

    if (!verifyWebhookSignature(signingSecret, rawBody, signature)) {
      return res.status(401).send("Invalid signature");
    }

    const event = JSON.parse(rawBody.toString("utf8"));

    // Store deliveryId and skip it if you have already processed it.
    console.log("HydraDB webhook", deliveryId, event.id, event.status);

    return res.status(204).send();
  }
);

app.listen(3000);
```

</CodeGroup>

## 7. Delivery and retries

HydraDB records every delivery attempt. See the history on the dashboard Webhooks page or with the API below.

Delivery states:

- `pending`: the event was recorded and is waiting to be sent.
- `sweeping`: HydraDB has claimed the event for delivery or retry.
- `delivered`: your endpoint returned a successful status code.
- `failed`: the current send attempt failed and will be retried.
- `permanently_failed`: HydraDB stopped retrying this event. On HydraDB Cloud this happens after 16 attempts.

Failed deliveries retry in the background, and the sweep process recovers events from a worker that shut down mid-delivery. To resend a `failed` or `permanently_failed` delivery yourself, see [Retry a failed delivery](#retry-a-failed-delivery).

Make your receiver idempotent: store `delivery_id`, return `2xx` without repeating side effects on a repeat, and do not depend on exactly-once delivery.

### List deliveries with cURL

```bash cURL
curl 'https://api.hydradb.com/webhooks/indexing/deliveries?limit=20' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

**Response:**

```json
{
  "deliveries": [
    {
      "delivery_id": "<delivery_id>",
      "doc_id": "<id>",
      "status": "delivered",
      "indexing_status": "completed",
      "event_type": "indexing.status_changed",
      "attempts": 1,
      "error_code": null,
      "error_message": null,
      "created_at": "<ISO-8601 timestamp>",
      "updated_at": "<ISO-8601 timestamp>"
    }
  ],
  "count": 1,
  "next_cursor": null
}
```

Delivery history uses `doc_id` internally. The outbound webhook payload uses `id`.

### Filter deliveries

```bash cURL
curl 'https://api.hydradb.com/webhooks/indexing/deliveries?limit=20&status=failed' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

`status` accepts any delivery state above: `pending`, `sweeping`, `delivered`, `failed`, or `permanently_failed`.

### Paginate deliveries

When `next_cursor` is not `null`, pass it back as `cursor`. `limit` can be between `1` and `100`.

```bash cURL
curl 'https://api.hydradb.com/webhooks/indexing/deliveries?limit=20&cursor=<next_cursor>' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

### Get one delivery

Replace `<delivery_id>` with a value from a webhook payload or the delivery list.

```bash cURL
curl 'https://api.hydradb.com/webhooks/indexing/deliveries/<delivery_id>' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

### Retry a failed delivery

Only `failed` and `permanently_failed` deliveries can be retried manually.

```bash cURL
curl -X POST 'https://api.hydradb.com/webhooks/indexing/deliveries/<delivery_id>/retry' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2"
```

**Response:**

```json
{
  "delivery_id": "<delivery_id>",
  "queued": true,
  "message": "Delivery queued for retry."
}
```

## 8. Advanced patterns

### Zero-downtime key rotation

HydraDB signs each delivery with exactly one secret, so a plain rotation leaves a window where your receiver rejects deliveries signed with a secret it does not have yet. The overlap has to live in your receiver, which accepts both secrets during the changeover. So you need the new secret before HydraDB uses it: supply it yourself instead of generating one.

<Steps>
  <Step title="Choose the new secret yourself">
    Generate a high-entropy value with your own tooling, for example `openssl rand -base64 32`. Do not use the generate option: a generated secret is only revealed after it is already in effect.
  </Step>
  <Step title="Teach your receiver both secrets">
    Deploy your receiver so it accepts either secret, reading both from your environment. Deliveries still verify against the old one.
  </Step>
  <Step title="Rotate in HydraDB, supplying that secret">
    In the dashboard, open **Rotate**, tick **I'll use my own secret**, and paste the value. Over the API, `POST /webhooks/indexing/signing-secret` with a `signing_secret` body. Deliveries switch immediately, and your receiver already accepts the new secret.
  </Step>
  <Step title="Retire the old secret">
    Once deliveries verify against the new secret, remove the old one from your receiver and redeploy. Keep this window short.
  </Step>
</Steps>

A receiver that accepts either secret:

<CodeGroup>

```python Python
import hashlib
import hmac
import os

# During a rotation both are set. Afterwards, drop HYDRADB_WEBHOOK_SECRET_OLD.
SECRETS = [
    s for s in (
        os.environ["HYDRADB_WEBHOOK_SECRET"],
        os.environ.get("HYDRADB_WEBHOOK_SECRET_OLD"),
    ) if s
]


def verify_webhook_signature(raw_body: bytes, signature: str) -> bool:
    if not signature:
        return False
    for secret in SECRETS:
        digest = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
        if hmac.compare_digest(signature, f"sha256={digest}"):
            return True
    return False
```

```typescript TypeScript
import crypto from "node:crypto";

// During a rotation both are set. Afterwards, drop HYDRADB_WEBHOOK_SECRET_OLD.
const secrets = [
  process.env.HYDRADB_WEBHOOK_SECRET,
  process.env.HYDRADB_WEBHOOK_SECRET_OLD,
].filter((s): s is string => Boolean(s));

export function verifyWebhookSignature(rawBody: Buffer, signature: string | undefined): boolean {
  if (!signature) {
    return false;
  }
  return secrets.some((secret) => {
    const expected =
      "sha256=" + crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
    const expectedBuffer = Buffer.from(expected);
    const signatureBuffer = Buffer.from(signature);
    if (signatureBuffer.length !== expectedBuffer.length) {
      return false;
    }
    return crypto.timingSafeEqual(signatureBuffer, expectedBuffer);
  });
}
```

</CodeGroup>

## 9. Security checklist

- Use HTTPS for your webhook URL.
- Enable signing and let HydraDB generate the secret. An invented secret is usually far weaker than one from a CSPRNG.
- Verify `X-HydraDB-Signature` over the raw body with a constant-time comparison, and fail closed.
- Keep the secret in your secret manager, not in source control.
- Return `2xx` only after you accept the event, and queue slow work.
- Deduplicate using `delivery_id`.

## 10. Common issues

- **Test delivery fails:** confirm your endpoint is public and returns a `2xx` status.
- **Signature check fails:** check the [three signature details](#3-request-format): raw body, the whole header value including `sha256=`, and lowercase hex.
- **Signature header is missing:** signing is not configured. Call `POST /webhooks/indexing/signing-secret` to enable it.
- **Signatures started failing after a rotation:** rotation applies immediately. Deploy the new secret to your receiver. See [Zero-downtime key rotation](#zero-downtime-key-rotation).
- **Event arrives more than once:** expected during retries. Deduplicate with `delivery_id`.
- **Event never arrives:** check the delivery history for `failed` or `permanently_failed`.
- **`id` is unexpected:** it is the ID you supplied at ingestion: a document ID, memory ID, or app item ID.
