[`POST /query`](/api-reference/v2/endpoint/query) searches your [context](/essentials/v2/context): knowledge, memories, or both. It returns ranked passages, called **chunks**, with their source details and the context graph around them. Your application puts them in the model's prompt; the model writes the answer.

The defaults work without tuning.

## 1. Run a query

This request searches the `acme_corp` database for knowledge about rotating API keys. Every query starts from this request; later sections add fields. The body is JSON; ingestion is multipart.

<Accordion title="Run a query: Python, TypeScript, or cURL">

Set up your [SDK client](/api-reference/v2/sdks#client-setup) before running the Python or TypeScript example.

<CodeGroup>
```python Python SDK
result = client.query(
    database="acme_corp",
    collection="company_docs",
    query="How do I rotate API keys?",
    type="knowledge",
    max_results=5,
)

for chunk in result.data.chunks:
    print(chunk.source_title, chunk.chunk_content)
```
```typescript TypeScript SDK
const result = await client.query({
  database: "acme_corp",
  collection: "company_docs",
  query: "How do I rotate API keys?",
  type: "knowledge",
  maxResults: 5,
});

if (!result.data || typeof result.data === "string") throw new Error("Expected structured query results");
for (const chunk of result.data.chunks ?? []) {
  console.log(chunk.sourceTitle, chunk.chunkContent);
}
```
```bash cURL
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "collection": "company_docs",
    "query": "How do I rotate API keys?",
    "type": "knowledge",
    "max_results": 5
  }'
```
</CodeGroup>

The response is wrapped in the standard envelope, so read the result from `data`. Trimmed to the fields you use most, it looks like this:

```json

### What each property means

| Property | What it is |
|---|---|
| `database` | The [database](/api-reference/v2/endpoint/create-database) to search. Required on every call. A query never reads another database. |
| `collection` | The collection to search, the same one you ingested into. Leave it out to search the database's default collection. [Section 4](#4-choose-what-to-search) covers searching several at once. |
| `query` | The question or search terms, in natural language. Cannot be empty. |
| `type` | What to search: `"knowledge"` (the default) for documents and content synced by connectors, `"memory"` for saved preferences and conversations, or `"all"` for both. |
| `max_results` | How many chunks to return. Default `10`, maximum `250`. |

### What comes back

- **`data.llm_prompt`:** the question, the matching chunks, and citation instructions as one Markdown string, ready for a model.
- **`data.chunks`:** the matching chunks, ranked by relevance, each with its source `id`, `chunk_content`, `source_title`, `relevancy_score`, and `metadata`. Keep the order.
- **`data.graph_context`** and **`data.additional_context`:** relationships and linked chunks, covered in [section 5](#5-add-relationships).

[Section 7](#7-use-the-results) shows how to pass the result to a model. New context is searchable within seconds of its [indexing status](/api-reference/v2/endpoint/source-status) reaching `graph_creation`; wait for `completed` when you query straight after ingesting.

## 2. Pick a recipe

Start from the row that matches your goal. Leave everything else at its default.

| I want to | `type` | `query_by` | `mode` | Notes |
| --- | --- | --- | --- | --- |
| Answer questions from documents | `"knowledge"` | `"hybrid"` | `"thinking"` | Keep `graph_context` on (the default) to include relationships between the people, topics, or services the documents mention |
| Match an exact keyword or phrase | `"knowledge"` | `"text"` | Not used | Set `operator` to `"and"` or `"phrase"` to control how the keywords must match. |
| Personalize a response | `"memory"` | `"hybrid"` | `"thinking"` | Search the collection the memories were saved in |
| Personalize and ground in documents | `"all"` | `"hybrid"` | `"thinking"` | One call reads both stores from the same scope. If the documents live in another collection, list both in `collections` |
| Search content synced from Slack, Jira, Gmail, and other apps | `"knowledge"` | `"hybrid"` | `"thinking"` | Leave `query_apps` on (the default) so threads, replies, and linked records expand along with the matching source |
| Serve mixed traffic with one setting | `"knowledge"` | `"hybrid"` | `"auto"` | HydraDB scores each query and routes it to `"fast"` or `"thinking"`. This is also what you get when `mode` is omitted |

`query_by` picks how the text is matched: `"hybrid"` (the default) matches by meaning and by keyword together, and `"text"` matches keywords only. `mode` picks how much work the query does. [Section 3](#3-tune-the-ranking) explains `mode`.

## 3. Tune the ranking

When the defaults are not right, start here:

- **`mode`:** `"fast"` is one retrieval pass, for chat and autocomplete. `"thinking"` expands the query, reranks, and pulls in [forceful relations](#5-add-relationships), for answers where quality matters more than latency. `"auto"`, the default, scores each query and routes it to one of the two, choosing thinking when unsure; the response does not say which it chose. Applies to `query_by: "hybrid"` only.
- **`alpha`:** the balance between meaning (`1.0`) and keywords (`0.0`) in a hybrid query. Default `0.8`, which `"auto"` also resolves to. Lower it toward `0.3` to `0.5` for error codes, SKUs, and product names; raise it toward `0.9` for conceptual questions.
- **`recency_bias`:** how much newer context is favored, from `0.0` to `1.0`. Default `0.4`, a mild tilt that only reorders close results. Send `0` for policies and other context that rarely changes, and `0.6` to `0.8` for changelogs and status updates.
- **`max_results`:** drop to `5` for tight context windows; raise to `20` when you rerank downstream.
- **`additional_context`:** a short factual hint, such as `"user is on the billing page"`, that sharpens retrieval. It is not a filter.

In production:

- **Timeouts:** 3 to 5 s for thinking, 500 ms or less for fast. Budget `"auto"` like thinking.
- **Literal token plus intent:** run `query_by: "hybrid"` and `query_by: "text"` in parallel, dedupe by `chunk_uuid`, and keep the text hits.
- **Recall, then rerank:** ask for `max_results: 20` and apply your own rules before picking the final set.
- **Caching:** key on the database, the collections, the caller's `acl`, and every query parameter, and expire entries when context or permissions change.

## 4. Choose what to search

To search beyond one collection:

- **Several collections:** send `collections` instead, as a list, or as an object of weights to rank one collection over another. Up to 100; every listed collection must exist, or the call returns `400`. `max_results` caps the merged list.
- **Knowledge and memories together:** `type: "all"` reads both from the same collections and ranks them together. When shared documents and memories live in different collections, list both.
- **A slice you already know:** `metadata_filters` narrows results before ranking, such as only runbooks or only one team's documents. [Metadata](/essentials/v2/metadata) covers the operators.

    query="How do I reset my password?",
    type="all",
    mode="thinking",
    max_results=8,
)
```

```json

  "collections": {
    "user_john_123": 2,
    "company_docs": 1
  }
}
```

## 5. Add relationships

Three fields bring in context beyond the chunks that matched. All three are on by default.

- **`graph_context`:** the relationships HydraDB extracted from your context, such as "Payments team owns billing service", in `data.graph_context`. `false` drops it, but only in fast mode; thinking always includes it. The [Query API reference](/api-reference/v2/endpoint/query) describes its fields.
- **`query_forceful_relations`:** forceful relations (links you declare between sources at ingest with `relations.ids`), such as a contract and its addendum, returned in `data.additional_context`. Thinking mode only; fast mode skips it without an error. [Context](/essentials/v2/context#6-link-sources-that-belong-together) shows how to declare the links.
- **`query_apps`:** for content synced by [connectors](/essentials/v2/connectors), an extra lane that rebuilds Slack threads, follows ticket and parent links, and matches exact ids and people. It still searches everything else, and has no effect on memories.

## 6. Query on behalf of a user

Which identity a query runs as depends on where the content came from:

- **Directly ingested knowledge, and connectors without ACL enforcement:** send the caller's email in `acl`, such as `"acl": ["grace@acme.com"]`, to filter results to documents that person may retrieve, plus public and unrestricted ones. Without `acl`, this content is not filtered by caller identity.
- **Connectors with `enforce_acl` enabled:** HydraDB uses the authenticated caller and ignores a request `acl` for that connector's content. API keys use the key creator's email; MCP OAuth and dashboard requests use the signed-in user. If you send `acl` anyway, a successful response includes one `meta.warnings` entry with code `acl_ignored_by_connector_enforcement`.

An `acl` entry on a source or a query is a **principal**:

| Principal | Meaning |
|---|---|
| `grace@acme.com` | One person, by email. |
| `domain:acme.com` | Everyone whose email is under that domain. A query as `grace@acme.com` matches it automatically. |
| `group:<provider>:<id>` | A group in the source app, such as `group:slack:C0123`. Group membership is never derived from an email; send it on the query. |
| `__public__` | Every identified caller. |

A source with no `acl` is unrestricted. On a query, omitting `acl`, sending `[]`, or sending `["*"]` all mean no caller filtering. See [ACL on synced content](/essentials/v2/connectors#enforce-acl) for connectors.

## 7. Use the results

HydraDB returns context, not answers: your application passes the result to a model. `build_string(result)` in Python and `buildString(result)` in TypeScript return `data.llm_prompt`, which numbers the ranked results `[1]`, `[2]`, and so on, so ask the model to cite by those numbers. Tell the model to answer only from the context, and keep the chunks in the order returned. To format the prompt yourself, read `data.chunks`; set `response_format` to `"structured"` to leave `llm_prompt` out, or to `"markdown"` to get only the prompt text as `data`.

<CodeGroup>
```python Python SDK
import os
from hydra_db import HydraDB
from hydra_db.helpers import build_string
from openai import OpenAI

hydra = HydraDB(token=os.environ["HYDRADB_API_KEY"])
openai_client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

question = "How does authentication work?"

result = hydra.query(
    database="your-database",
    collection="your-collection",
    query=question,
    type="knowledge",
    query_by="hybrid",
    mode="fast",
    graph_context=True,
)

context = build_string(result)

completion = openai_client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {
            "role": "system",
            "content": "You are a helpful assistant. Answer the user's question using only the context provided. If the answer is not in the context, say you don't know.",
        },
        {
            "role": "user",
            "content": f"Context:\n{context}\n\nQuestion: {question}",
        },
    ],
)

print(completion.choices[0].message.content)
```
```typescript TypeScript SDK
import { HydraDBClient } from "@hydradb/sdk";
import { buildString } from "@hydradb/sdk/helpers";
import OpenAI from "openai";

const hydra = new HydraDBClient({ token: process.env.HYDRADB_API_KEY });
const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

const question = "How does authentication work?";

const result = await hydra.query({
  database: "your-database",
  collection: "your-collection",
  query: question,
  type: "knowledge",
  queryBy: "hybrid",
  mode: "fast",
  graphContext: true,
});

const context = buildString(result);

const completion = await openai.chat.completions.create({
  model: "gpt-4o",
  messages: [
    {
      role: "system",
      content: "You are a helpful assistant. Answer the user's question using only the context provided. If the answer is not in the context, say you don't know.",
    },
    {
      role: "user",
      content: `Context:\n${context}\n\nQuestion: ${question}`,
    },
  ],
});

console.log(completion.choices[0].message.content);
```
</CodeGroup>

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Empty `query_paths` or `chunk_relations` | `graph_context` set to `false`, or no relationships exist for the result set | Leave `graph_context` on (the default). Empty arrays are normal when there is nothing to return. |
| Recent uploads do not appear in results | Indexing not finished | Poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) with the source ids. Chunks are invisible until indexing reaches at least `graph_creation`. |
| `metadata_filters` does not narrow results | Filter key is in the wrong namespace, the value does not match exactly, or the top-level field was not declared in the metadata schema | Top-level keys match `metadata`; free-form per-source fields must be nested under `additional_metadata`. Declare hot filter keys in `database_metadata_schema` before production ingest. |
| Memories missing from a `type: "knowledge"` query | Wrong store selected | Use `type: "memory"` or `type: "all"`. |
| Knowledge missing from a `type: "all"` query | The documents live in a different collection from the one you sent | List both collections in `collections`. |
| Recency does not seem to matter | `recency_bias` was sent as `0`, or the default `0.4` tilt is too mild | Raise it toward `1.0`. |
| `operator: "phrase"` returns `400` | `query_by` not set to `"text"` | `"and"` and `"phrase"` only apply to BM25 text queries: switch `query_by` to `"text"`. |
| `query_forceful_relations` ignored | Request runs in `mode: "fast"` (or `auto` routed to fast) | Forceful relations are fetched only in thinking mode. Set `mode: "thinking"`. |
| `graph_context: false` ignored | Request runs in thinking mode (`mode: "thinking"`, or `auto` routed to thinking) | Thinking always includes the graph slice; `false` takes effect only in fast mode. Set `mode: "fast"` to drop it. |
| Expected a deterministic `fast` or `thinking` pipeline, got auto-routed instead | `mode` was omitted | Omitting `mode` means `"auto"`. Set `mode` explicitly to `"fast"` or `"thinking"`. |
