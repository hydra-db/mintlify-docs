title: "Query"

---

`POST /query` reads what you stored. `type` picks the store: [knowledge](/essentials/v2/knowledge), [memories](/essentials/v2/memories), or both. Ranking uses meaning (vectors), keywords (BM25), and the [context graph](/essentials/v2/context-graphs). Full request and response schema: [Query API](/api-reference/v2/endpoint/query-overview).

## 1. Starting points

- **Shared documents:** `type: "knowledge"`, `query_by: "hybrid"`, `mode: "thinking"`.
- **Exact tokens (error codes, IDs, names):** `type: "knowledge"`, `query_by: "text"`, optionally with `operator`.
- **One user's memory:** `type: "memory"`, `query_by: "hybrid"`, `mode: "thinking"`.
- **Shared documents plus that user's memory:** `type: "all"`, `query_by: "hybrid"`, `mode: "thinking"`. If the two live in different collections, list both in `collections`.
- **App data (Slack, mail, tickets):** leave `query_apps` on (the default).

---

## 2. Parameter reference

When to send `database` and `collection`: [Multi-tenant](/essentials/v2/multi-tenant#2-when-to-use-each). The older `tenant_id` and `sub_tenant_id` still work as deprecated aliases.

### Retrieval

- `type`: `"knowledge"` (default), `"memory"`, or `"all"`. `"all"` reads both stores from the same scope and ranks the results together.
- `query_by`: `"hybrid"` (default) combines vector similarity and BM25 keyword scores. `"text"` is BM25 only.
- `operator`: `"or"` (default), `"and"`, or `"phrase"`. How BM25 matches query terms, with `query_by: "text"` only. `"and"` or `"phrase"` with any other `query_by` returns `400`: "operator is only valid with query_by=text".
- `alpha`: `0.0` (pure BM25) to `1.0` (pure semantic), or `"auto"`. Weights the two scores in `query_by: "hybrid"`. Default `0.8`, and `"auto"` also resolves to `0.8`.
- `mode`: how much work the query does.
  - `"fast"`: a single low-latency pass.
  - `"thinking"`: expands the query into several, reranks, and fetches the relations you declared at ingest.
  - `"auto"`: the default. HydraDB scores the query and routes it to `"fast"` or `"thinking"`, choosing `"thinking"` when unsure. Set `"fast"` or `"thinking"` explicitly for a deterministic pipeline.

### Scope

| Parameter | Type / values | Purpose |
| --- | --- | --- |
| `collections` | `string[]` or `{ [collection]: positive number (max one decimal place) }` | Preferred scope selector. A list fans out with equal normalized weights. An object sets relative ranking weights. HydraDB runs the whole query in each collection and merges the results. Every listed collection must exist. Maximum 100 collections. |
| `collection` | string | One collection to query. If you send neither field, the query reads the database's default collection. |

### Graph

| Parameter | Type / values | Purpose |
| --- | --- | --- |
| `graph_context` | boolean | Includes the entity and relation graph slice. Default `true`. `false` takes effect only in fast mode (explicit, or `auto` routed to fast). Thinking always includes it. See [Context Graphs](/essentials/v2/context-graphs). |
| `query_forceful_relations` | boolean | Fetches the sources you linked with [`relations` on ingest](/api-reference/v2/endpoint/ingest-context) into the response `additional_context`. Default `true`. **Takes effect only in thinking mode** (explicit, or `auto` routed to thinking). In fast mode it is silently ignored. |

### Shaping results

| Parameter | Type / values | Purpose |
| --- | --- | --- |
| `max_results` | integer | Maximum chunks to return. Default `10`, maximum `250`. |
| `recency_bias` | float, `0.0` to `1.0` | Boost for newer content. Omitted, it applies a mild `0.4` tilt. Raise it toward `1.0` for a stronger boost, or send `0` to turn it off. |
| `query_apps` | boolean | Default `true`. Adds an app-aware lane for ingested app data (Slack, Gmail, Confluence, Jira, Salesforce): exact ID and actor lookups, reconstructed threads, and parent/child traversal. It does not restrict the query to app sources. Knowledge only. Pair with `mode: "thinking"`. Send `false` to turn it off. See [App Sources](/essentials/v2/app-sources). |
| `additional_context` | string | Short request-time hint, such as known page, feature, or role ("user is on the billing page"). Not the response `additional_context`, which carries forceful-relation results. Default `null`. |
| `metadata_filters` | object | Exact narrowing before ranking. See [Metadata](/essentials/v2/metadata). Default `null`. |

### Access control

| Parameter | Type / values | Purpose |
| --- | --- | --- |
| `acl` | `string[]` | Query on behalf of an identity, restricting results to documents it may retrieve. Send the caller's email (`["grace@acme.com"]`). `__public__` and the caller's `domain:` principal are added automatically. Omitted (the default `null`), empty, or `["*"]` disables filtering. See [Access Control](/essentials/v2/access-control). |

## 3. Tuning heuristics

The defaults usually work. When they do not:

- **`mode`:** leave it unset (`"auto"`) for mixed traffic.
- **`alpha`:** lower it toward `0.3` to `0.5` for literal tokens (error codes, SKUs, product names). Raise it toward `0.9` for conceptual questions.
- **`max_results`:** drop to `5` for tight context windows. Raise to `20` if you rerank or summarize downstream.
- **`graph_context`:** for multi-hop questions ("how does X relate to Y"), pair it with `mode: "thinking"`, because the `"fast"` graph slice is shallow. Send `false` with `mode: "fast"` when you only need ranked chunks.
- **Timeouts:** generous for `thinking` (3 to 5 s), tight for `fast` (500 ms or less). Size `"auto"` for `thinking`, because it can pick either.

## 4. Minimal working example

A personalized answer takes one call with `type: "all"`. If shared knowledge lives in its own collection, list it next to the user's in `collections`. See [Multi-tenant](/essentials/v2/multi-tenant#shared-knowledge-plus-user-personalization).

### Setup

```bash
# Set your key as an environment variable - used in every request below
export HYDRA_DB_API_KEY="your_api_key"
# All requests: -H "Authorization: Bearer $HYDRA_DB_API_KEY" -H "API-Version: 2"
```

```typescript
import { HydraDBClient } from "@hydradb/sdk";

const client = new HydraDBClient({
  token: process.env.HYDRA_DB_API_KEY,
});
```

```python
import os
from hydra_db import HydraDB

client = HydraDB(token=os.environ["HYDRA_DB_API_KEY"])
```

### One call for knowledge and memories

```bash
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "collection": "user_john_123",
    "query": "How do I reset my password?",
    "type": "all",
    "query_by": "hybrid",
    "mode": "thinking",
    "max_results": 8,
    "graph_context": true
  }'
```

```typescript
const result = await client.query({
  database: "acme_corp",
  collection: "user_john_123",
  query: "How do I reset my password?",
  type: "all",
  queryBy: "hybrid",
  mode: "thinking",
  maxResults: 8,
  graphContext: true,
});
```

```python
result = client.query(
    database="acme_corp",
    collection="user_john_123",
    query="How do I reset my password?",
    type="all",
    query_by="hybrid",
    mode="thinking",
    max_results=8,
    graph_context=True,
)
```

### Merge into the LLM prompt

The response is one `RetrievalResult` with `chunks[]`, `sources[]`, and, when present, `graph_context` and `additional_context`. Knowledge and memory chunks arrive already ranked together. The helper in [How to Use API Results](/essentials/v2/api-results) turns the result into a prompt string:

```typescript
const context = buildContextString(result);

const completion = await openai.chat.completions.create({
  model: "gpt-4o",
  messages: [
    {
      role: "system",
      content: "Answer using only the provided context. Match the user's preferred style.",
    },
    {
      role: "user",
      content: `${context}\n\nQuestion: How do I reset my password?`,
    },
  ],
});
```

To query several scopes at once, pass `collections` (see [Scope](#scope)). Weights apply before the final merged ranking, and `max_results` caps the merged response, not each collection:

```json
{
  "database": "acme_corp",
  "collections": {
    "workspace_42": 2,
    "user_john_123": 1
  },
  "query": "What context matters for this renewal?",
  "type": "all"
}
```

To format knowledge and memories differently in the prompt, call `/query` twice in parallel with `type: "knowledge"` and `type: "memory"`, then merge client-side.

## 5. Common mistakes

- **Empty `query_paths` or `chunk_relations`:** `graph_context` is off, or no relations exist for the results. Empty arrays are normal when there is nothing to return.
- **Recent uploads missing:** chunks are invisible until indexing reaches at least `graph_creation`. Poll `GET /context/status?ids=...&database=...`.
- **`metadata_filters` does not narrow results:** top-level keys match `metadata`, and values must match exactly. Nest free-form fields under `additional_metadata`. Declare frequent filter keys in `database_metadata_schema` before production ingest.

---

## 6. Advanced patterns

- **Hybrid and text in parallel:** when a query mixes a literal token (error code, SKU, function name) with natural-language intent, run `query_by: "hybrid"` and `query_by: "text"` in parallel, dedupe by chunk ID, and always include the text hits.
- **Recall, then rerank:** ask for more chunks than you need (`max_results: 20`) and apply your own reranker (recency windows, compliance filters, business rules) before picking the final top-k.
- **Cache the prompt context:** if a query repeats inside a session, cache the `RetrievalResult` keyed by `(database, collection, query, type, query_by)`.
