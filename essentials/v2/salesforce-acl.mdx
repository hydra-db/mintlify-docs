Use this guide to prepare for optional Salesforce permission enforcement. It describes pending behavior, not a feature you can rely on in production today.

## Choose whether to enforce Salesforce permissions

Salesforce uses the existing **Enforce ACL** control and `enforce_acl` setting. There is no second Salesforce-specific toggle. An omitted setting means `false`.

With **Enforce ACL off**, synced Salesforce content stays visible to everyone who can query its HydraDB collection. Optional Salesforce ACL enforcement adds no permission-inventory or viewer-verification prerequisites in this mode. The integration user still needs the ordinary permissions required to authenticate and sync the selected content. Do not enable ACL enforcement merely to make a connection work.

With **Enforce ACL on**, HydraDB restricts reads to supported records it can positively authorize for the authenticated viewer. A workspace owner or writer signed in to the dashboard can select the setting during creation or change it on an existing connector. API-key requests must omit `enforce_acl`, including `false`; an API key cannot change this setting. See the shared [Enforce ACL contract](/essentials/v2/connectors#enforce-acl).

## Check the supported records and grants

The pending enforced-read path supports exactly these Salesforce object types:

- `Account`
- `Contact`
- `Opportunity`
- `Case`
- `Lead`

For each supported object, the viewer needs positive **Read** and **View All Fields** grants from a directly assigned permission set or the viewer's profile. **View All Fields** requires Salesforce API v63 or later. HydraDB uses this conservative lower bound rather than attempting to redact individual unreadable fields from an already indexed record.

These grants are necessary, not sufficient. HydraDB must also verify that the active Salesforce user can read each requested record. A grant that this path cannot positively resolve does not become an allow decision, even if a different Salesforce permission mechanism might permit access in Salesforce itself.

Custom objects, files, activities, and objects that can carry restriction rules are outside this enforced-read coverage. They stay denied with enforcement on. Unknown object types, missing field access, unresolved identities or permissions, and failed verification also deny access. Selecting an object for sync does not make it supported for ACL-enforced reads.

## Separate OAuth scopes from Salesforce user permissions

OAuth scopes allow the External Client App to call Salesforce APIs. They do not grant object access, field access, or administrative access to the actual **Run As** integration user. Assign that user's permissions in Salesforce separately; a broad OAuth scope does not repair a missing grant.

The integration user's ability to sync a record is also not evidence that a different viewer may read it. Enforced reads require permission evidence for the viewer, obtained through the connection's actual authorized Salesforce access. If the connection cannot read the permission information needed for verification, fix the reported Salesforce grant rather than widening an OAuth scope and assuming access is proved.

## Verify the viewer on every read

HydraDB verifies the viewer against a unique, active Salesforce user and checks fresh record visibility on every enforced read. It does not treat a previous successful check, a stored email alone, or the integration user's access as an enduring viewer grant. Missing or ambiguous user matches, unavailable permission information, and incomplete verification fail closed.

Dashboard requests use the signed-in person's identity. API requests use the API key creator's identity; a caller-supplied `acl` cannot widen that access. This is not a way to serve many different viewers through one shared API key. See [querying on behalf of a user](/essentials/v2/query#6-query-on-behalf-of-a-user).

## Activate without exposing old content

The pending transition contract hides previously indexed workspace-visible Salesforce content immediately when you turn enforcement on. It must remain hidden until a sanitized replacement is fully committed and eligible for enforced reads. Starting a sync, preparing a replacement, or writing permission metadata alone is not enough to make old content readable.

The next sync prepares sanitized record content without borrowing cross-record names or owner emails. Only a safely committed replacement can be considered for access, and it still has to pass the live viewer and record checks. Do not apply the shared connector guide's no-reingestion behavior to this Salesforce Off-to-On transition, and do not treat this unreleased guide as evidence that the transition-safety implementation has shipped.

## Common mistakes

- **Expecting Off to require ACL grants:** Off keeps the existing workspace-visible behavior and ordinary sync requirements. Optional permission verification runs only when enforcement is on.
- **Treating OAuth scopes as Run As grants:** check the actual Salesforce user's permissions and the API's actionable error. Scopes do not assign object or field permissions.
- **Granting Read without View All Fields:** the enforced-read path requires both grants through supported direct or profile evidence, as well as live record access.
- **Expecting every selected object to be queryable with enforcement on:** only the five named object types are supported. Unsupported or uncertain access stays denied.
- **Assuming a started reindex is safe to serve:** the sanitized replacement must be committed before it becomes eligible for authorization.
