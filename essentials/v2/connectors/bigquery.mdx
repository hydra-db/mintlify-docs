The BigQuery connector reads the tables you select in one Google Cloud project. Each row becomes one document. Its text lists every non-empty column as a label and a value, and the document is grouped under its table.

You decide, table by table, how HydraDB finds new and changed rows: a timestamp column, BigQuery's change history, or a full read of the table on every sync.

<Note>
BigQuery is in beta.
</Note>

## Before you connect

<Warning>
Set a primary key for every table you select. HydraDB updates a row's document by its key. If a table has no real unique key, different rows can be treated as the same document and replace each other.
</Warning>

BigQuery uses a Google Cloud service account. There is no sign-in flow: you paste credentials. Supply one complete set: a service-account key file, a service-account email with its private key, or an OAuth client id, client secret and refresh token.

**Credentials**

<ResponseField name="credentials_json" type="secret string">
The service account's JSON key file, pasted whole. This is the recommended option.
</ResponseField>

<ResponseField name="client_email" type="secret string">
The service account's email. Use it together with `private_key` instead of the key file.
</ResponseField>

<ResponseField name="private_key" type="secret string">
The service account's private key. Use it together with `client_email`.
</ResponseField>

<ResponseField name="client_id" type="secret string">
An OAuth client id. Valid only together with `client_secret` and `refresh_token`.
</ResponseField>

<ResponseField name="client_secret" type="secret string">
An OAuth client secret. Valid only together with `client_id` and `refresh_token`.
</ResponseField>

<ResponseField name="refresh_token" type="secret string">
An OAuth refresh token you issued beforehand. It is required in the OAuth option, because a client id and secret alone cannot reach BigQuery.
</ResponseField>

Each credential field is optional on its own, but one of the three options must be complete.

**Connector settings**

<ResponseField name="project_id" type="string">
The Google Cloud project to read. Required unless the key file already names a project.
</ResponseField>

<ResponseField name="location" type="string">
The BigQuery location to run query jobs in.
</ResponseField>

<ResponseField name="datasets" type="string list">
Limits discovery and sync to these datasets.
</ResponseField>

<ResponseField name="replication_key" type="string">
A timestamp column to use as the sync cursor for every selected table that has it. A table's own setting overrides it.
</ResponseField>

<ResponseField name="change_history" type="string">
`appends` or `changes`, used for tables that still have no cursor column. A table's own setting overrides it.
</ResponseField>

<ResponseField name="detect_replication_from_partitioning" type="boolean">
Off by default. When on, column-partitioned tables sync incrementally on their partition column.
</ResponseField>

**What the service account needs**

- `BigQuery Data Viewer`: role on the project.
- `BigQuery Job User`: role on the project.
- `https://www.googleapis.com/auth/bigquery`: scope, in the OAuth option. Google rejects query jobs under the read-only BigQuery scope.

**Set it up**

<Steps>
  <Step title="Create a service account">
    In Google Cloud, create a service account. Give it the BigQuery Data Viewer and BigQuery Job User roles on the project, and download its JSON key.
  </Step>
  <Step title="Create the connector">
    Paste the key as `credentials_json`. Add `project_id` only if the key file does not name a project. To narrow what discovery shows, list `datasets`.
  </Step>
  <Step title="Select tables">
    Discover lists the tables in the project, narrowed by `datasets` when you set it. Select the tables to sync. Each selected table becomes its own set of documents, one per row.
  </Step>
  <Step title="Choose a sync mode for each table">
    If the table has a timestamp column that changes on every insert and update, such as `updated_at`, make it the table's `replication_key`. If rows are only ever inserted, set `change_history` to `appends`. If rows are also updated and there is no such column, set `change_history` to `changes`. A table with none of these is read in full on every sync. If a table has both a cursor and change history, change history wins.
  </Step>
  <Step title="Turn on change history for tables set to changes">
    Run `ALTER TABLE dataset.table SET OPTIONS(enable_change_history=true)` once in BigQuery for that table. It changes no data.
  </Step>
  <Step title="Set each table's primary key">
    Add `primary_keys` with the column or columns that identify one row, unless the table already declares a primary key.
  </Step>
  <Step title="Send the settings when you configure">
    Through the API or SDK, send the per-table settings as `table_configs` on the same Configure Connector request that selects the tables. The dashboard collects them on the table-selection screen.
  </Step>
</Steps>

One `table_configs` entry per table, for each sync mode:

<CodeGroup>
```json Timestamp cursor
{"table": "sales.orders", "replication_key": "updated_at", "primary_keys": ["order_id"]}
```
```json Inserts only
{"table": "web.page_views", "change_history": "appends", "primary_keys": ["event_id"]}
```
```json Inserts and updates
{"table": "crm.accounts", "change_history": "changes", "primary_keys": ["account_id"]}
```
```json Changes only, no backfill
{"table": "crm.accounts", "change_history": "changes", "snapshot": "none", "primary_keys": ["account_id"]}
```
```json Full read
{"table": "ref.countries", "primary_keys": ["code"]}
```
</CodeGroup>

Use provider `bigquery` with [Create Connector](/api-reference/v2/endpoint/create-connector). Then call [Discover Connector Resources](/api-reference/v2/endpoint/discover-connector-resources) to list what the credentials can reach, and [Configure Connector](/api-reference/v2/endpoint/configure-connector) to choose what to sync.

Create one connector per account, each with that account's own credentials. One connector reads one Google Cloud project.

## What gets synced

**What the labels mean**

- **Title:** names the item in results.
- **Searchable:** part of the text a query matches.
- **Date:** the time HydraDB uses for recency.
- **Filter:** a key a query can filter on, typed exactly as shown.
- **Link:** connects this item to another item.
- **Person or group in the graph:** a person or group the knowledge graph attaches the item to.
- **Access:** decides who can read the item.
- **Stored with results:** kept on the document, and shown when you open or inspect it. A search does not match it.
- **Not kept:** the provider has it, and HydraDB does not keep it.

### Table rows

- **One document:** One row of a selected table, as long as the table's key is unique. Rows that share a key replace one another.
- **Title:** The first non-empty column named `name`, `title`, `subject`, `summary` or `email`. Otherwise the first non-empty column that is not a number, in alphabetical column order, then the first number column. A row with none of these is titled with its table and row key.
- **Text:** The title on the first line. Then every non-empty column in alphabetical order, as `Column Name: value`: underscores become spaces and words are capitalised. Lists of values are joined with commas. Nested records are written as compact JSON.
- **Date:** The first of `updated_at`, `modified_at`, `last_modified`, `updated`, `created_at`, `created`, `timestamp`, `event_time` and `inserted_at` that holds a TIMESTAMP or epoch-seconds value. A row with none has no date. DATETIME columns carry no time zone and are not used.
- **Link back:** None.
- **Files:** None. Column values are kept as text only.

**Title**

<ResponseField name="title" type="Title, Searchable">
Names the row in results. It is also the first line of the row text, so a query matches it.
</ResponseField>

**Searchable**

<ResponseField name="Row text" type="Searchable">
Every non-empty column of the row, written as described above. This is what a query matches.
</ResponseField>

**Date**

<ResponseField name="updated_at" type="Date">

</ResponseField>

</ResponseField>

<ResponseField name="additional_metadata.container_id" type="Filter">

</ResponseField>

<ResponseField name="additional_metadata.container_type" type="Filter">
Always `table`.
</ResponseField>

<ResponseField name="connector_id" type="Filter">

</ResponseField>

<ResponseField name="provider" type="Filter">
Always `bigquery`. Limits a query to BigQuery documents.
</ResponseField>

The table as `dataset.table`, so you can see where a result came from.
</ResponseField>

The key the row was matched on. Together with the table, it decides which document a later sync updates.
</ResponseField>

## How it fits into the graph

**What each item becomes**

- Table rows: a record, an item that does not fit one of the specialised kinds, searched through its text.

**Connections BigQuery creates**

None. Rows are not linked to each other or to items in other tools, even when a column holds another table's key.

**People and groups it names**

- None are declared. Each row is grouped under its table.
- A column such as `email` or `user_id` is part of the row text only. It does not make the row a person in the graph.

**What HydraDB reads from the text**

Everything else. Customers, people, products and references between rows are found only by HydraDB reading the row text.

There is no per-connector setup for this. Every connector maps its items onto the same shared model, and HydraDB finds people, organizations, projects, products and other entities in the text the same way for every source. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Permissions

<Warning>
This connector does not carry BigQuery permissions into search. Every synced item is visible to everyone who can query the collection, unless you [set an access rule on the resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).
</Warning>

- BigQuery dataset, table, row-level and column-level access controls are not reproduced.
- Every column of a selected table becomes searchable text, including sensitive ones. Select tables with that in mind.

**Enforce ACL** cannot be turned on for BigQuery, because it needs a provider that reports `acl_supported: true`. API-key requests must omit `enforce_acl`, including `false`. See [ACL on synced content](/essentials/v2/connectors#5-acl-native-rbac-awareness).

Database and collection names decide where content lands; collection names do not authorize access.

## Keeping in sync

- **First sync:** A table with a cursor column reads back the window set by `lookback_days`, 30 days by default. A change-history table starts capturing changes at its first sync, not when you create the connector, and then loads its existing rows in slices of 1,000 per sync. Set `snapshot` to `none` to skip existing rows, or to a number to load at most that many rows, in no particular order. With `none`, changes between creating the connector and its first sync are not recovered.
- **New and changed items:** A cursor table picks up rows whose cursor value moved past the last sync. A `changes` table reads BigQuery's change history, about 11 minutes behind the current time. An `appends` table sees new rows only. A table with neither is read in full on every sync, and rows whose content did not change are skipped.
- **Edits:** An edited row updates the same document, as long as its key is unique. In `appends` mode, edits to existing rows are never seen.
- **Deletions:** Deleted rows are not removed. A row deleted in BigQuery stays searchable in HydraDB.
- BigQuery keeps change history for its time-travel window, 2 to 7 days. If a change-history table is not synced within that window, for example while the connector is paused, the table is skipped with an error on each sync until it is loaded again from the start.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` to change it.

## Not synced

- Tables you did not select.
- Rows deleted in BigQuery: they stay in HydraDB.
- Updates to existing rows in tables set to `appends`.
- BigQuery dataset, table, row-level and column-level access controls.
- Table and column descriptions and other schema details. Only row values are kept.

## Questions this lets you answer

- What does the `sales.orders` table say about order 10432?
- Which rows in `crm.accounts` mention Acme Corp?
- Which rows in `support.tickets` were updated most recently?
- What plan and region are recorded for jane@example.com in `billing.customers`?

## Good to know

- **Large tables need a sync mode.** A table with no cursor column and no change history is read in full on every sync, which is expensive on large tables.
- **Change-history rows carry two extra lines.** In change-history mode, each row also has `_change_type` and `_change_timestamp` columns, and both appear in the row text.
- **A cursor column does not always set the date.** Recency uses only the time column names listed above. A cursor with another name drives sync without setting the document date.
- **Backfill is best effort.** Deleting rows while existing rows are still loading can make other rows be missed.
