HydraDB stores the context your agents need, links it in a graph, and returns the part that is useful to the person asking.

You store two kinds of data:

- **Knowledge:** documents, files, and content from the tools your company already uses, such as Slack, Notion, Drive, and email. It is shared across your users.
- **Memories:** preferences, history, and past conversations for one user. They grow as that user keeps using your product.

As content comes in, HydraDB builds a context graph. It extracts the people, projects, and other entities in each source and links them. A query can search knowledge, memories, or both. It matches by meaning and by keyword, then follows graph links to pull in related material.

## Why not only a vector database

A vector database returns the text closest to the query. That breaks in three common ways:

- **It cannot tell meanings apart:** "Python" the language and "Python" the snake look alike as vectors. Questions like "who owns this escalation?" or "how has this project changed over three years?" need relationships, not similarity.
- **Everyone gets the same results:** an account executive asking about "Project Acme" needs the latest deck and competitor notes. An engineer asking the same thing needs the changelog and design decisions. HydraDB keeps each person's memories, so the same query can return different context to each of them.
- **You end up running five systems:** a vector store, a graph database, a relational store, file storage, and a cache, glued together by code you maintain. HydraDB is one API for all of it.

HydraDB gives you the parts (graph, memory, retrieval, and ranking controls), and you decide how to combine them. It is built for teams going from 10K documents to 10M.

## Performance and isolation

- **Accuracy:** 90%+ on LongMemEval, a long-context memory benchmark.
- **Latency:** retrieval in under 200 ms.
- **Isolation:** one database can never read another database's data. There is no cross-database query or aggregation, so your access rules always hold.

Full numbers: [benchmarks](https://benchmarks.hydradb.com/).

## How it works

1. Create a database.
2. Send content through the API, or connect a source with a [connector](/essentials/v2/connectors).
3. Wait for indexing. HydraDB parses, chunks, and embeds the content, and builds the graph.
4. Call `POST /query` and pass the returned chunks to your own model. Your app writes the prompt and generates the answer.

## What people build

- Support agents grounded in a customer's history and preferences
- Coding agents that remember a codebase and team conventions
- Clinical companions that track patient context across visits
- Research copilots that reason across papers, authors, and findings
- Internal assistants over Slack, Notion, Drive, and email
- Consumer apps where each user's memory grows over time

Longer examples: [Cookbooks](/cookbooks/v2/index).

Coding agents should follow the [agent guide](/AGENTS) and the [v2 OpenAPI spec](/api-reference/v2/openapi.json). On `POST /query`, `type` selects `knowledge`, `memory`, or `all`.
