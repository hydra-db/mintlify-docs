This is the complete, maintained agent guide. Continue with the sections below; no separate documentation-index fetch is needed.

### TL;DR: Critical endpoints

1. **`POST /databases`** (`client.databases.create()`): Create an isolated database. Creation is asynchronous.
2. **`GET /databases/status`** (`client.databases.status()`): Poll until `infra.ready_for_ingestion` is true before you ingest or query.
3. **`POST /context/ingest`** (`client.context.ingest()`): Ingest files, app sources, or memories with `type="knowledge"` or `type="memory"`. Indexing is asynchronous.
4. **`GET /context/status`** (`client.context.status()`): Poll by `ids` until `indexing_status` is `graph_creation` (searchable, graph still building) or `completed` before you query. `errored` means indexing failed: read `error_code` and `error_message`. Details in [7. Context status and lifecycle](#7-context-status-and-lifecycle).
5. **`POST /query`** (`client.query()`): Retrieve chunks with `type: "knowledge"`, `"memory"`, or `"all"`.
6. **`POST /feedback`** (`client.feedback.submit()`): Tell us when a query did not give you what you needed, and once the task is done, how the context held up. See [Sending feedback](#sending-feedback).

Every other endpoint and SDK method is in [15. SDK method reference](#15-sdk-method-reference).

## 1. Critical rules for LLMs

### API versioning and auth

- Base URL: `https://api.hydradb.com`
- Raw HTTP calls must include:
  - `Authorization: Bearer <api_key>`
  - `API-Version: 2`
- Official SDKs set `API-Version: 2` automatically.
- Use `HYDRADB_API_KEY` as the environment variable in examples.

### Response envelope

Raw HTTP responses are wrapped:

```json
{
  "success": true,
  "data": {},
  "error": null,
  "meta": {
    "request_id": "...",
    "latency_ms": 12.3
  }
}
```

- Read the payload from `data`, never from the top level. This applies to `/databases`, `/context/*`, `/query`, `/feedback`, and the webhook management endpoints (`/webhooks/indexing*`).
- The SDKs do not unwrap it: they return the full envelope object, so read `response.data` (for example `response.data.infra`, `response.data.statuses`, `response.data.results`). On failure they raise a typed exception instead of returning an envelope with `error` set.
- Exceptions: connector endpoints (`/connectors*`) and `PATCH /databases/{database}/metadata-schema` return their success body directly, without the envelope. In the SDKs that is every `connectors.*` method, `list_providers()`, and `update_metadata_schema()`. Their errors still use the envelope.
- Log `meta.request_id` for failed requests.
- Treat `meta` as an open object: ignore keys you do not recognize.
- `meta` carries an optional `deprecation` list (with a `Deprecation: true` response header) when a request uses a legacy tenants route (any path under /tenants) or a deprecated field (`tenant_id`/`sub_tenant_id`, or `sub_tenant_ids` on `/query`). It is a non-breaking nudge: the status code is unchanged. Every entry has `deprecated`, `message`, and `deprecated_since`. `deprecated_field` and `preferred_field` are **optional**: the `sub_tenant_ids` notice on `/query` carries them, the `tenant_id`/`sub_tenant_id` notice does not. Read `message` for the migration, and do not key logic off the two optional fields. To avoid the notice, use the `/databases` routes and the `database`/`collection`/`collections` fields.

### Query parameter naming

`type` selects the store on `POST /query` and on the context lifecycle APIs, with the same values: `"knowledge"` or `"memory"`. `POST /query` also accepts `"all"` to query knowledge and memories together.

### Metadata naming

- `metadata`: schema-aligned fields, declared at database creation; the fast filter path. Filter on them with top-level `metadata_filters` keys.
- `additional_metadata`: free-form fields; anything not in the `metadata` schema. Filter on them with `metadata_filters.additional_metadata`.
- Set both per source on `/context/ingest`: on each `document_metadata[]` item (file uploads), each `app_knowledge[]` item, or each memory item. There is no top-level `metadata` or `additional_metadata` form field.

Schema fields, placement, and filter operators are in [10. Metadata guide](#10-metadata-guide).

### Do not mix scopes accidentally

- `database` (formerly `tenant_id`) is the hard isolation boundary.
- `collection` (formerly `sub_tenant_id`) is an optional group inside a database. Use separate collections only for context that must never meet in one query, such as each user's memories. Otherwise (for example, a company brain) keep all knowledge and connectors in one collection and isolate results with `metadata_filters` and `acl`. Patterns are in [Databases and collections](#databases-and-collections).
- Use the same `collection` on writes, status checks, and reads. Context written under one collection does not appear in a query that names another.

### Send `acl` on user queries

- If your application answers on behalf of signed-in users, send the caller's identity as `acl` on every `POST /query`, for example `"acl": ["grace@acme.com"]`.
- A query with no `acl`, `[]`, or `["*"]` is not filtered: it returns everything in scope, including sources restricted to other people.
- Derive `acl` from your authenticated session, never from client input. See [Access control](#access-control).

### Sending feedback

`POST /feedback` (`client.feedback.submit()`) records how a query performed. It is optional, and there is no penalty for skipping it. You are the only party that knows whether the retrieved context answered the question, and that judgement is what tunes retrieval.

Send it when you have something specific to report:

- **A query did not give you what you needed:** nothing relevant came back, the top result was wrong, or you had to fall back to another source. One report on a query that disappointed you is worth far more than a stream of routine ones.
- **A query worked well:** `rating: "positive"` tells us what to preserve.
- **The task is finished (recommended):** send one short report on how the context performed. See [End-of-task report](#end-of-task-report).

Rules:

- **Take `request_id` from the query's own response. Never invent one.** It is in `meta.request_id` and in the `X-Request-ID` response header. Send it back **verbatim**: an ID you made up, or one from another query, correlates to nothing.
- Set `source: "agent"`. It separates your reports from human ones, which fail in different ways.
- Say **what** was wrong, not that something was wrong. "Returned the 2023 policy, current one is in the Q3 handbook" is actionable; "bad results" is not.
- Do not block the user on it. Feedback is fire-and-forget: if the **feedback call itself** fails, drop it and carry on. Never retry in a loop, and never surface that error to the user.
- Catch broadly, so that **nothing** escapes. Narrowing to the SDK error type would still let a timeout or a DNS failure surface an error the user cannot act on, from a call they did not ask for.
- Feedback never changes the query's result. It is a signal, not a correction, and you cannot read it back.
- Each submission is its own record. A second report about the same query adds to the first instead of replacing it, so refine as you learn more.

```python
result = client.query(database="acme_corp", query="What is our refund policy?")

# ... use result.data.chunks to answer the user ...

try:
    client.feedback.submit(
        request_id=result.meta.request_id,
        feedback="Top chunk was the 2023 policy; the current one is in the Q3 handbook.",
        rating="negative",
        source="agent",
        database="acme_corp",
    )
except Exception:
    pass  # fire-and-forget: a failed report must never reach the user
```

#### End-of-task report

At the end of the task you know what you could not know at query time: whether a chunk that looked plausible turned out to be stale, contradicted by another source, or never used at all. A single report then is worth more than one per query, and `rating: "positive"` is as valuable as a negative one, because you know which part of the context did the work.

Make the report stand on its own. We see only a `request_id` and the prose you send, nothing about what you were doing. Worth a sentence each:

- What the user was trying to do.
- Which chunks carried the answer, and which you discarded and why.
- Whether you had to go outside HydraDB to finish, and what was missing when you did.

```python
try:
    client.feedback.submit(
        request_id=result.meta.request_id,   # from the query you are reporting on
        source="agent",
        rating="positive",
        feedback=(
            "Task: user asked which refund window applies to EU orders. "
            "Chunks 1 and 3 (Q3 handbook) carried the answer. Chunk 2 was the "
            "2023 policy and was discarded as superseded. No outside sources needed."
        ),
        database="acme_corp",
    )
except Exception:
    pass  # fire-and-forget, exactly as above
```

#### Ground truth

**If you know the right answer, send it as `ground_truth`.** When you run against a labelled set, or you know which source should have been returned, that is a far stronger signal than a comment, because it can be scored without a human reading it. With `ground_truth` present, `feedback` prose is optional:

```python
try:
    client.feedback.submit(
        request_id=result.meta.request_id,
        source="agent",
        ground_truth={
            "answer": expected_answer,          # what a correct response looks like
            "source_ids": ["policy_2024"],      # sources that actually contain it
        },
    )
except Exception:
    pass
```

Send `answer`, `source_ids`, or both. Do **not** guess: only send ground truth you have. A fabricated answer key is worse than none, because it is scored as if it were true.

#### Failed requests are not feedback

**"Did not give me what I needed" is not the same as "errored".** A query that returned `200` with unhelpful results is what this endpoint is for. A query that never returned (`4xx`/`5xx`, or the SDK raised) is not: a failed request has no retrieval result to judge. Fix the request instead: a `404` means the database name is wrong, a `429` means back off, a `400` means the body was malformed.

#### Request fields and limits

| Field | Required | Notes |
|---|---|---|
| `request_id` | yes | The UUID from that query's `meta.request_id`, verbatim |
| `feedback` | yes* | What was right or wrong, up to 8000 chars. *Optional if `ground_truth` is sent |
| `rating` | no | `positive`, `negative`, `neutral`. Omitting it is not the same as `neutral` |
| `source` | no | `user` (default) or `agent`. Agents set `"agent"` |
| `database` / `collection` | no | Optional scoping; `collection` requires `database` |
| `ground_truth` | no | `{ answer, source_ids }`: what the right answer was, when you know it. Makes `feedback` optional |
| `metadata` | no | Up to 20 string pairs of your own context (agent name, conversation id) |

Limit: 100 submissions per minute per organization, far above what reporting only the queries that fell short reaches. If you do hit `429`, honour `Retry-After` or skip that report. Never spin.

## 2. Core primitives

### Databases and collections

Scoping rules are in [Do not mix scopes accidentally](#do-not-mix-scopes-accidentally). Recommended patterns:

| Use case | Pattern |
|---|---|
| Company brain | one `database`, one collection for all documents and connectors; isolate with `metadata_filters` and `acl` |
| B2B SaaS | one `database` per customer; one collection for that customer's knowledge; isolate teams with `metadata_filters` and `acl` |
| B2C app | one `database`; shared knowledge in one collection; `collection = user_id` for each user's memories |
| Environment isolation | separate `database`s for prod/staging |
| User memories | `collection = user_id`, and the same collection on every read |

### Knowledge

Knowledge is the documents, app sources, and facts your AI reasons over: PDFs, Markdown, CSVs, Slack threads, Notion pages, Gmail threads, tickets, webpages, and so on. Ingest and query it with `type: "knowledge"`.

- It can be private: restrict sources with `acl` (see [Access control](#access-control)).
- Mutability is explicit: re-ingest with the same ID and `upsert: true`, edit metadata in place with `PATCH /context/{id}/metadata`, or delete.

### Memories

Memories are preferences, decisions, past conversations, behavioral signals, and inferred traits. Ingest them with `type: "memory"` into the collection you will query them from, and query with `type: "memory"` or `type: "all"`. Item fields, including `infer`, are in [6. Source ingestion](#6-source-ingestion).

### Query

`POST /query` is the single retrieval endpoint for knowledge, memories, or both. Fields, recommended configurations, and the response shape are in [8. Query API](#8-query-api).

### Context graph

HydraDB builds a graph of entity/relation triplets from ingested content. When `graph_context: true` (default), a query can return:

- `graph_context.query_paths`
- `graph_context.chunk_relations`
- `graph_context.chunk_id_to_group_ids`

Graph context augments the result; it does not replace `chunks`.

### Forceful relations

Forceful relations are links you declare between sources at ingest:

```json
{
  "relations": {
    "ids": ["related-item-1", "related-item-2"],
    "properties": { "reason": "same thread" }
  }
}
```

- Use `ids`.
- Declare `relations` on `document_metadata[]` and `app_knowledge[]` items. They link knowledge sources; memory items do not take `relations`.
- A query pulls the related chunks into `additional_context` only in `mode: "thinking"` with `query_forceful_relations: true` (the default).

### Access control

A source's `acl` lists who may retrieve it; a query's `acl` says who is asking. The query-side rule is in [Send `acl` on user queries](#send-acl-on-user-queries).

- Set `acl` on `app_knowledge[]` items at ingest, or on any existing source with `PATCH /context/{id}/metadata`, where it replaces the stored list.
- Connectors copy permissions from Slack, Google Drive, GitHub, Confluence, Jira, and other providers on every sync.
- Principals: an email (`grace@acme.com`), `domain:acme.com`, `group:<provider>:<id>`, or `__public__`.
- On a query, the caller's email also matches its `domain:` principal and `__public__` automatically. Group membership is never derived from an email; send `group:` principals yourself.
- A source with no `acl` is unrestricted.

Example: a source with `"acl": ["grace@acme.com"]` comes back for a query with `"acl": ["grace@acme.com"]` and stays hidden from `"acl": ["bob@acme.com"]`. A source with `"acl": ["domain:acme.com"]` comes back for both.

### Connectors

Connectors sync context from 70 apps, including Slack, Gmail, Google Drive, Notion, Jira, Confluence, GitHub, Linear, HubSpot, and Zendesk, into a database on a schedule, with no ingestion code. Prefer a connector over hand-written `app_knowledge` ingestion when the app is in the catalog; `GET /connectors/providers` lists it.

Setup is four calls, made once:

1. `GET /connectors/providers?id={provider}`: read `credential_schema`, the credentials it needs.
2. `POST /connectors`: store the credentials, with `database` and `collection`.
3. `GET /connectors/{id}/discover`: list the channels, repositories, or pages the credentials reach.
4. `POST /connectors/{id}/configure`: choose resources; the first sync starts right away.

Then poll `GET /connectors/{id}/status` until `lifecycle` is `active`, and query as usual. Syncs repeat every `sync_interval_seconds` (one hour by default).

```python
connector = client.connectors.create(
    provider="slack",
    database="acme_corp",
    collection="company_docs",
    provider_account_scope="T12345ACME",
    credentials={"access_token": "xoxp-..."},
)
found = client.connectors.discover(connector.connector_id)
client.connectors.configure(
    connector.connector_id,
    resources=[
        {"resource_id": r.id, "resource_type": r.resource_type, "name": r.name}
        for r in found.resources
    ],
)
status = client.connectors.status(connector.connector_id)
```

```ts
const connector = await client.connectors.create({
  provider: "slack",
  database: "acme_corp",
  collection: "company_docs",
  providerAccountScope: "T12345ACME",
  credentials: { access_token: "xoxp-..." },
});
const id = connector.connectorId!;
const found = await client.connectors.discover({ id });
await client.connectors.configure({
  id,
  resources: (found.resources ?? []).map((r) => ({
    resourceId: r.id!,
    resourceType: r.resourceType,
    name: r.name,
  })),
});
const status = await client.connectors.status({ id });
```

Rules:

- To change one resource, use `PATCH /connectors/{id}/resources/{resource_id}`. `POST /connectors/{id}/resources` adds new resources only: on an existing resource it returns `409` and changes nothing.
- Every synced source carries `connector_id` and `provider` in `metadata`, and `connector_id` and `resource_id` in `additional_metadata`; filter on them to scope a query.
- `custom_instructions` on the connector or one resource tells HydraDB how to read its documents, from the next sync on.

## 4. Minimal end-to-end flow

### Python

```python
import json
import os
import time
from hydra_db import HydraDB

client = HydraDB(token=os.environ["HYDRADB_API_KEY"])
database = "my_first_database"

# 1. Create database.
client.databases.create(database=database)

# 2. Wait until the database can accept data.
while True:
    status = client.databases.status(database=database)
    if status.data.infra.ready_for_ingestion:
        break
    time.sleep(5)

# 3. Ingest a user memory.
ingest = client.context.ingest(
    type="memory",
    database=database,
    collection="user_alex",
    memories=json.dumps([
        {
            "id": "user_alex_pref_001",
            "text": "User prefers detailed technical explanations and dark mode.",
            "infer": True,
            "user_name": "Alex",
        }
    ]),
)

ingest_id = ingest.data.results[0].id

# 4. Wait until searchable.
while True:
    status = client.context.status(
        database=database,
        collection="user_alex",
        ids=[ingest_id],
    ).data.statuses[0]

    if status.indexing_status in ("graph_creation", "completed"):
        break
    if status.indexing_status in ("errored", "failed"):
        # A wrong database/collection reports "errored" too, with FILE_NOT_FOUND.
        # error_message is "" in that case, so branch on the code, not the text.
        if status.error_code == "FILE_NOT_FOUND":
            raise RuntimeError("No such id in this scope: check database/collection match ingestion")
        raise RuntimeError(status.error_message or status.message or "Indexing failed")
    time.sleep(2)

# 5. Search memories.
result = client.query(
    database=database,
    collection="user_alex",
    query="What does the user prefer?",
    type="memory",
    query_by="hybrid",
    mode="thinking",
)

print(result.data.chunks)
```

### TypeScript

```ts
import { HydraDBClient } from "@hydradb/sdk";

const client = new HydraDBClient({
  token: process.env.HYDRADB_API_KEY,
});

const database = "my_first_database";

await client.databases.create({ database: database });

while (true) {
  const status = await client.databases.status({ database: database });
  if (status.data.infra.readyForIngestion) break;
  await new Promise((resolve) => setTimeout(resolve, 5_000));
}

const ingest = await client.context.ingest({
  type: "memory",
  database: database,
  collection: "user_alex",
  memories: JSON.stringify([
    {
      id: "user_alex_pref_001",
      text: "User prefers detailed technical explanations and dark mode.",
      infer: true,
      user_name: "Alex",
    },
  ]),
});

const ingestId = ingest.data.results[0].id;

while (true) {
  const status = (await client.context.status({
    database: database,
    collection: "user_alex",
    ids: [ingestId],
  })).data.statuses[0];

  if (["graph_creation", "completed"].includes(status.indexingStatus as string)) break;
  if (["errored", "failed"].includes(status.indexingStatus as string)) {
    // || rather than ??: errorMessage is "" (not null) on some failures, and ??
    // would pass the empty string through and throw an error with no message.
    throw new Error(status.errorMessage || status.message || "Indexing failed");
  }

  await new Promise((resolve) => setTimeout(resolve, 2_000));
}

const result = await client.query({
  database: database,
  collection: "user_alex",
  query: "What does the user prefer?",
  type: "memory",
  queryBy: "hybrid",
  mode: "thinking",
});

if (!result.data || typeof result.data === "string") throw new Error("Expected structured query results");
console.log(result.data.chunks);
```

## 5. Databases API

### Create database

`POST /databases` · `client.databases.create()`

```json
{
  "database": "acme_corp",
  "database_metadata_schema": [
    {
      "name": "department",
      "data_type": "VARCHAR",
      "enable_dense_embedding": false,
      "enable_sparse_embedding": false,
      "max_length": 1024
    }
  ]
}
```

Notes:

- `database` should be stable. Use lowercase letters, numbers, and underscores for portability.
- Plan `database_metadata_schema` before ingestion. What you can change later is in [10. Metadata guide](#10-metadata-guide).
- `POST /databases` may return `409 DATABASE_ALREADY_EXISTS` for duplicate database IDs and `403 FORBIDDEN` when the API key or plan cannot create more databases.

### Check readiness

`GET /databases/status?database=...` · `client.databases.status()`

The database is ready when `infra.ready_for_ingestion` is true. The response also carries the underlying signals:

- `infra.scheduler_status`
- `infra.graph_status`
- `infra.vectorstore_status.knowledge`
- `infra.vectorstore_status.memories`

### Other database endpoints

The collections, stats, and delete routes also take `database` as a query parameter, for example `GET /databases/collections?database=...`. `DELETE /databases?database=...` deletes the database and all its data. The full list is in [15. SDK method reference](#15-sdk-method-reference).

## 6. Source ingestion

`POST /context/ingest` is the single write endpoint for knowledge and memories. It takes multipart form data.

### Common form fields

| Field | Description |
|---|---|
| `type` | `"knowledge"` or `"memory"`; default is `"knowledge"` |
| `database` | target database |
| `collection` | optional; the default collection if omitted |
| `upsert` | default `true`; replaces existing sources with the same ID |
| `documents` | binary file uploads for knowledge |
| `document_metadata` | JSON-stringified array, one item per uploaded file; see [Knowledge from files](#knowledge-from-files) |
| `app_knowledge` | JSON-stringified object/array of pre-extracted app sources |
| `memories` | JSON-stringified array of memory items |

### Knowledge from files

Use for PDFs, DOCX, Markdown, CSV, TXT, and other files HydraDB should parse.

```python
import json

with open("policy.pdf", "rb") as f:
    result = client.context.ingest(
        type="knowledge",
        database="acme_corp",
        documents=[("policy.pdf", f, "application/pdf")],
        document_metadata=json.dumps([
            {
                "id": "policy_v2",
                "metadata": {"department": "support", "status": "approved"},
                "additional_metadata": {"author": "Alice", "version": 2},
            }
        ]),
    )
```

`document_metadata` is how you attach anything to an uploaded file. Send one item per file, in the same order as `documents`. The item count must match the file count, and an unrecognized key returns `400`.

| `document_metadata` item field | Purpose |
|---|---|
| `id` | stable source ID / upsert key for the uploaded file; HydraDB assigns one if omitted |
| `metadata` | schema-aligned fields for this file (max 16 KiB compact JSON) |
| `additional_metadata` | free-form fields for this file (max 1 KiB compact JSON) |
| `relations` | relations you declare to other sources, e.g. `{ "ids": [...] }` |

### Knowledge from app sources

Use `app_knowledge` when you already extracted the text from Slack, Gmail, Jira, Linear, Zendesk, Notion, Confluence, Salesforce, webpages, and so on.

```ts
await client.context.ingest({
  type: "knowledge",
  database: "acme_corp",
  appKnowledge: JSON.stringify([
    {
      id: "slack_C123_1715012345_000100",
      database: "acme_corp",
      collection: "default",
      title: "Pricing discussion - Slack #product",
      type: "slack",
      url: "https://slack.com/archives/C123/p1715012345000100",
      timestamp: "2025-01-15T12:30:00Z",
      content: {
        text: "We agreed on three tiers: Starter, Pro, and Enterprise."
      },
      tenant_metadata: {
        channel: "product",
        workspace: "acme"
      },
      additional_metadata: {
        author: "alice",
        slack_ts: "1715012345.000100"
      },
      relations: {
        ids: ["slack_thread_root_001"]
      }
    }
  ]),
});
```

Recommended app-source fields:

| Field | Why send it |
|---|---|
| `id` | stable HydraDB ID and upsert key |
| `title` | readable result/citation title |
| `type` | category such as `slack`, `gmail`, `jira`, `notion`, `webpage` |
| `content.text` / `content.markdown` | primary searchable content |
| `metadata` | fast filters such as channel, project, region, workspace. `tenant_metadata`, used in the example, is a still-accepted older alias |
| `additional_metadata` | provider IDs, author, status, assignee, timestamps |
| `url` | citation / navigation link |
| `timestamp` | freshness and chronology |
| `relations.ids` | thread, parent/child, linked issue, related source expansion |

An app source takes either the generic `content` shape above or a richer app shape with `kind`, `provider`, `external_id`, `fields`, `attachments`, `comments`, and `relations`. Kinds in OpenAPI include `email`, `message`, `ticket`, `knowledge_base`, `comment`, and `custom`. Use the richer shape for app-aware retrieval (see [App sources](https://docs.hydradb.com/essentials/v2/context#send-app-sources.md)); at minimum provide stable IDs, content, source type, metadata, and relations.

### Memories

Use `type="memory"` and a JSON-stringified `memories` array.

```python
import json

client.context.ingest(
    type="memory",
    database="acme_corp",
    collection="user_alex",
    memories=json.dumps([
        {
            "id": "pref_dark_mode",
            "title": "Dark mode preference",
            "text": "User prefers dark mode and concise answers.",
            "infer": True,
            "user_name": "Alex",
            "metadata": {"team": "engineering"},
            "additional_metadata": {"source": "onboarding"}
        }
    ]),
)
```

Memory item fields:

| Field | Description |
|---|---|
| `id` | optional stable upsert key |
| `title` | label for listing and result display |
| `text` | raw text or Markdown; required unless `user_assistant_pairs` provided |
| `user_assistant_pairs` | dialogue pairs `{ user, assistant }`; useful for implied preferences |
| `is_markdown` | preserve Markdown structure during chunking |
| `infer` | `true`: the input is raw signal and HydraDB extracts the durable preference or fact. `false`: the memory is already structured and is stored verbatim |
| `custom_instructions` | guide inference when `infer: true` |
| `user_name` | helps inference |
| `metadata` | schema-aligned fields, as an object (do not stringify it again inside `memories`). `tenant_metadata` is not read on memory items. |
| `additional_metadata` | free-form fields; keep as objects |

## 7. Context status and lifecycle

### Poll indexing

`GET /context/status` · `client.context.status()`

Parameters:

- `database`: required.
- `ids`: required array.
- `collection`: **required if you ingested into one.** The lookup is scoped: omitting `collection`, or sending the wrong one, returns `indexing_status: "errored"` with `error_code: "FILE_NOT_FOUND"` and `message: "ID not found"` for a source that exists and is fully searchable. That is a scope miss, not an indexing failure, and you can tell the two apart only by reading `error_code`.

| Status | Searchable? | Meaning |
|---|---:|---|
| `queued` | No | accepted, not picked up |
| `processing` | No | parsing/chunking/embedding |
| `graph_creation` | Yes | chunks indexed; graph still building |
| `completed` | Yes | fully indexed and graphed |
| `errored` / `failed` | No | terminal failure; read `error_code` and `error_message` |

`error_message` is `""`, not null, on some failures (including a scope miss), so branch on `error_code`, and in TypeScript fall back with `||`, not `??`.

```ts
while (true) {
  const status = (await client.context.status({
    database: "acme_corp",
    collection: "support_docs", // must match the ingestion scope, or you get FILE_NOT_FOUND
    ids: ["policy_v2"],
  })).data.statuses[0];

  if (["graph_creation", "completed"].includes(status.indexingStatus as string)) break;
  if (["errored", "failed"].includes(status.indexingStatus as string)) {
    // A scope miss reports errored too, so name the cause rather than guessing.
    if (status.errorCode === "FILE_NOT_FOUND") {
      throw new Error(`No such id in this scope: check database/collection match ingestion`);
    }
    // Use ||, not ??: errorMessage comes back as "" (not null) on some failures,
    // and ?? passes an empty string straight through to an empty error.
    throw new Error(status.errorMessage || status.message || "Indexing failed");
  }
  await new Promise((r) => setTimeout(r, 2_000));
}
```

### Webhooks instead of polling

Register a webhook on `/webhooks/indexing` to receive terminal indexing events instead of polling. The management endpoints and SDK methods are in [15. SDK method reference](#15-sdk-method-reference).

Supported event: `indexing.status_changed`. Payload shape:

```json
{
  "event": "indexing.status_changed",
  "delivery_id": "<delivery_id>",
  "id": "<id>",
  "database": "<database>",
  "collection": "<collection>",
  "status": "completed",
  "timestamp": "<ISO-8601 timestamp>",
  "error_code": null,
  "error_message": null
}
```

Headers: `X-HydraDB-Delivery-ID`, `X-HydraDB-Event`, and `X-HydraDB-Signature` when a signing secret is configured.

Signature scheme:

```
X-HydraDB-Signature: sha256=<lowercase hex digest>

digest = HMAC-SHA256(key = signing_secret, message = raw request body bytes)
```

The `sha256=` prefix is part of the header value. The digest is lowercase hex, not base64. The HMAC covers the raw body bytes as received; re-serialising the parsed JSON produces different bytes and will not match.

Managing the secret:

- `POST /webhooks/indexing` with `{"generate_signing_secret": true}` registers and enables signing in one call, returning the secret once. Mutually exclusive with `signing_secret`; sending both is a `422`.
- `POST /webhooks/indexing/signing-secret` with no body generates one and returns the secret once. Send `{"signing_secret": "..."}` to supply your own (minimum 16 characters).
- `DELETE /webhooks/indexing/signing-secret` disables signing.
- Omitting `signing_secret` on `POST /webhooks/indexing` preserves the existing secret. It does not disable signing.

Rules:

- The webhook URL must be public HTTPS; localhost and private networks are blocked.
- Store `delivery_id` to deduplicate retries.
- Verify `X-HydraDB-Signature` with a constant-time comparison. Use `verify_webhook_signature` (Python SDK) or `verifyWebhookSignature` (TypeScript SDK) from the SDK helpers module.
- Fail closed: reject the request when the signing secret is absent from the environment, instead of skipping verification.

## 8. Query API

`POST /query` · `client.query()`

### Request fields that matter

| Field | Values | Notes |
|---|---|---|
| `database` | string | required |
| `collection` | string/null | the collection the context was saved in; default collection if omitted |
| `collections` | list of collection IDs | query several collections at once; every listed collection must exist |
| `query` | string | required |
| `type` | `knowledge`, `memory`, `all` | store selector for knowledge, memories, or both |
| `acl` | list of principals | who is asking; see [Send `acl` on user queries](#send-acl-on-user-queries) |
| `query_by` | `hybrid`, `text` | default `hybrid` (semantic + BM25); `text` is BM25 keyword/phrase search |
| `operator` | `or`, `and`, `phrase` | only for `query_by: "text"` |
| `mode` | `fast`, `thinking`, `auto` | applies to hybrid; omitted means `auto`, which picks fast or thinking per query (thinking when unsure). `fast` is low latency. `thinking` adds query expansion, reranking, richer graph traversal, and forceful-relation expansion; it improves quality but adds latency |
| `max_results` | integer/null | default 10; max 250 |
| `alpha` | `0.0` to `1.0`, or `auto` | hybrid weight; `1.0` semantic, `0.0` BM25 |
| `recency_bias` | `0.0` to `1.0` | boost newer content; omitted means `0.4`, send `0` to disable |
| `graph_context` | boolean | default true; include graph slice; `false` only takes effect in fast mode, thinking always includes it |
| `query_forceful_relations` | boolean | only effective in `thinking` mode |
| `additional_context` | string | short factual hint; not a hard filter |
| `metadata_filters` | object | deterministic filters before/around ranking |
| `query_apps` | boolean | app-aware retrieval lane for app sources; still searches the full selected knowledge scope; defaults to `true` on `/query`, send `false` to disable |

`type: "all"` reads both stores from the same scope. When shared knowledge lives in its own collection, send `collections: ["<shared>", "<user>"]`.

### Recommended configurations

| Goal | Request shape |
|---|---|
| Fast document RAG | `type: "knowledge"`, `query_by: "hybrid"`, `mode: "fast"`, `graph_context: false`, `max_results: 5-10` |
| Highest-quality document RAG | `type: "knowledge"`, `query_by: "hybrid"`, `mode: "thinking"`, `graph_context: true`, `alpha: "auto"` |
| Personalized grounded answer | `type: "all"`, include `collection`, `query_by: "hybrid"`, `mode: "thinking"` |
| User preferences only | `type: "memory"`, include `collection`, `query_by: "hybrid"` |
| Exact keyword / phrase | `type: "knowledge"`, `query_by: "text"`, `operator: "phrase"` |
| Recent operational updates | `query_by: "hybrid"`, `recency_bias: 0.2-0.4`, metadata filter to doc type/status |
| App search | `type: "knowledge"`, `query_by: "hybrid"`, `mode: "thinking"`, `query_apps: true`; still searches non-app knowledge too |

## 9. Turning query results into LLM prompts

- Do not pass raw result JSON to the LLM if token budget matters. Use the SDK formatting helper to produce a compact context string: `build_string(result)` from `hydra_db.helpers` (Python) or `buildString(result)` from `@hydradb/sdk/helpers` (TypeScript).
- Include a grounding instruction: answer only from the provided context, and say when the context is insufficient.
- Start with `max_results: 10`; reduce it for tight context windows.
- Use graph context only when it helps the question.
- Use `additional_context` to attach forcefully related chunks by `chunk_uuid` / `extra_context_ids`.
- For personalized answers, `type: "all"` is simplest: one result set already merges knowledge and memories.

Python:

```python
import os
from hydra_db import HydraDB
from hydra_db.helpers import build_string
from openai import OpenAI

hydra = HydraDB(token=os.environ["HYDRADB_API_KEY"])
openai = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

question = "How does authentication work?"

result = hydra.query(
    database="your-database",
    collection="your-collection",
    query=question,
    type="knowledge",
    query_by="hybrid",
    max_results=5,
)

context = build_string(result)

messages = [
    {
        "role": "system",
        "content": "Answer using only the provided HydraDB context. If the answer is not in the context, say so. Cite source titles or URLs when available.",
    },
    {
        "role": "user",
        "content": f"{context}\n\nQuestion: {question}",
    },
]
```

TypeScript:

```ts
import { HydraDBClient } from "@hydradb/sdk";
import { buildString } from "@hydradb/sdk/helpers";
import OpenAI from "openai";

const hydra = new HydraDBClient({ token: process.env.HYDRADB_API_KEY });
const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

  database: "your-database",
  collection: "your-collection",
  query: question,
  type: "knowledge",
  queryBy: "hybrid",
  maxResults: 5,
});

const messages = [
  {
    role: "system",
    content: "Answer using only the provided HydraDB context. If the answer is not in the context, say so. Cite source titles or URLs when available.",
  },
  {
    role: "user",
    content: `${context}\n\nQuestion: ${question}`,
  },
];
```

## 10. Metadata guide

### Metadata schema

Declared at `POST /databases`:

```json
{
  "database_metadata_schema": [
    {
      "name": "department",
      "data_type": "VARCHAR",
      "enable_dense_embedding": false,
      "enable_sparse_embedding": false,
      "max_length": 1024
    }
  ]
}
```

Field options:

| Field | Purpose |
|---|---|
| `name` | metadata key; must be valid and non-reserved |
| `data_type` | friendly names like `string`, `integer`, `float`, `boolean`, or backend types like `VARCHAR`, `INT*`, `JSON` |
| `enable_dense_embedding` | semantically embed `VARCHAR` field |
| `enable_sparse_embedding` | BM25 index `VARCHAR` field |
| `max_length` | max string length |

### Where metadata belongs

| Need | Put it in | Filter with |
|---|---|---|
| Hot-path exact filters: department, region, environment, status | `metadata` | top-level `metadata_filters` |
| Free-form display/bookkeeping: author, provider IDs, version | `additional_metadata` | `metadata_filters.additional_metadata` |
| Provider app fields for UI/citations | `additional_metadata` or app `fields` | usually not filtered unless needed |
| User/workspace partition | `collection` | not metadata |

Rules:

- Plan hot filter fields before the first ingest. `PATCH /databases/{database}/metadata-schema` can add fields later, but cannot rename, retype, or reflag existing ones, and rejects `enable_dense_embedding` / `enable_sparse_embedding` (declare those at database creation). Changing an existing field definition requires a new database and re-ingestion.
- Top-level `metadata_filters` keys must be declared in the metadata schema. They support `equals`, `contains`, and `contains_any`. Range and fuzzy matching belong in the query or a downstream reranker.
- To change metadata on an indexed source, call `PATCH /context/{id}/metadata` (merges keys), or re-ingest with the same `id` and `upsert: true`.
- Do not rename metadata keys without re-ingesting the affected sources.

## 12. Error handling

### HTTP status codes

| Code | Meaning | Retry? |
|---|---|---|
| `400` | invalid parameters / malformed request | No |
| `401` | missing/invalid API key | No |
| `403` | authenticated but not permitted | No |
| `404` | database or source not found | No |
| `409` | conflict, e.g. existing database or source ID | Usually no |
| `413` | upload too large | No |
| `422` | semantic validation failure, including `TENANT_INFRA_NOT_READY` | Only for `TENANT_INFRA_NOT_READY`, after polling readiness |
| `429` | rate limited | Yes with backoff |
| `500` | internal error | Yes with backoff |
| `502` | upstream dependency error (`BACKEND_ERROR`) | Yes with backoff |
| `503` | temporary unavailability | Yes with backoff |

Retry only `429`, `500`, `502`, and `503`, with bounded exponential backoff and jitter.

The SDKs already retry `408`, `429`, and `5xx` responses twice with exponential backoff before raising, and the Python SDK also retries `409`. Do not wrap SDK calls in a second retry loop: raise the count with `request_options={"max_retries": 5}` on a Python call, or `maxRetries` on the TypeScript client or call.

### Common error codes

| Code | Meaning |
|---|---|
| `INVALID_INPUT` | required, malformed, or conflicting parameter. This is the code for essentially every `400`. Branch on it, not on a generic name |
| `VALIDATION_ERROR` | request shape valid but failed validation |
| `UNAUTHORIZED` | missing/invalid API key |
| `FORBIDDEN` | key lacks access |
| `DATABASE_ALREADY_EXISTS` | duplicate database ID |
| `DATABASE_NOT_FOUND` | database missing/not visible |
| `TENANT_INFRA_NOT_READY` | `422`: the database exists but its infrastructure is still provisioning. This is what querying before polling readiness returns |
| `FILE_NOT_FOUND` | ID not found **in the selected scope**, usually a `collection` mismatch, not a missing source |
| `SOURCE_PROCESSING` | the source is still indexing and cannot serve this request yet |
| `NOT_FOUND` | requested resource does not exist |
| `PARSE_ERROR` | a document could not be parsed |
| `PROCESSING_FAILED` | indexing failed for a source |
| `RATE_LIMITED` | rate limit exceeded |
| `INTERNAL_ERROR` | unexpected server error |
| `BACKEND_ERROR` | `502`: an upstream dependency returned an error |
| `SERVICE_UNAVAILABLE` | dependency unavailable / under load |

There is no `INVALID_PARAMETERS` and no `SOURCE_NOT_FOUND`: no HydraDB response carries either. Match on `INVALID_INPUT` and `FILE_NOT_FOUND`.

SDK errors:

```python
from hydra_db.core.api_error import ApiError

RETRYABLE = (429, 500, 502, 503)

try:
    result = client.query(
        database="acme_corp",
        query="pricing tiers",
        type="knowledge",
    )
except ApiError as exc:
    # 500 and 503 have typed subclasses (InternalServerError,
    # ServiceUnavailableError); 429 does not, so branch on status_code to cover
    # all three uniformly. Back off and retry.
    if exc.status_code not in RETRYABLE:
        raise
```

```ts
import { HydraDBError } from "@hydradb/sdk";

try {
  const result = await client.query({
    database: "acme_corp",
    query: "pricing tiers",
    type: "knowledge",
  });
} catch (error) {
  if (error instanceof HydraDBError) {
    const body = error.body as {
      error?: { code?: string };
      meta?: { request_id?: string };
    } | undefined;
    const code = body?.error?.code;
    const requestId = body?.meta?.request_id;
    console.error({ code, requestId });
  }
  throw error;
}
```

## 13. Common integration patterns

Most integrations follow the same architecture:

1. Create a database with a metadata schema for hot filters.
2. Ingest shared knowledge and app sources with stable IDs.
3. Ingest user and session memories with `collection`.
4. Poll status or use webhooks.
5. Query with `type: "knowledge"`, `"memory"`, or `"all"`.
6. Format chunks, graph paths, and additional context into an LLM prompt.
7. Cite sources and handle missing context explicitly.

## 14. Common mistakes checklist

Each item is a rule stated in full in the section named. Check all of them before you finish.

Section 1, critical rules:

- [ ] Forgetting `API-Version: 2` in raw HTTP calls.
- [ ] Reading a payload from the top level instead of `data`, in raw HTTP or in the SDKs.
- [ ] Writing with one `collection` and reading with another, or omitting `collection` for user memories.
- [ ] Splitting a company brain into many collections instead of one collection with `metadata_filters` and `acl`.
- [ ] Querying on behalf of a user without `acl`, which returns everything in scope.

Sections 2 to 7, ingestion and lifecycle:

- [ ] Hand-writing `app_knowledge` ingestion for an app a connector already syncs.
- [ ] Editing an existing connector resource with `POST /connectors/{id}/resources`, which returns `409` and changes nothing.
- [ ] Querying right after database creation without polling readiness.
- [ ] Querying right after ingestion without polling `context.status` or using webhooks.
- [ ] Treating `processing` or `queued` context as searchable.
- [ ] Not handling both `errored` and `failed` as failure statuses.
- [ ] Omitting `collection` on `context.status` and reading the resulting `FILE_NOT_FOUND` as a genuine indexing failure.
- [ ] Using `??` on `errorMessage`, which is `""`, not null, on some failures, so the fallback never fires.
- [ ] Forgetting to verify webhook signatures when a signing secret is configured.

Sections 8 to 10, query and metadata:

- [ ] Using undeclared `metadata` keys in `metadata_filters`.
- [ ] Using `operator` without `query_by: "text"`.
- [ ] Expecting `query_forceful_relations` to work in `mode: "fast"`.
- [ ] Setting `graph_context: false` and expecting graph fields.
- [ ] Re-sorting chunks before prompting without a deliberate reranker.
- [ ] Passing raw result JSON or too many chunks to the LLM.
- [ ] Putting hot filters in free-form metadata instead of the metadata schema.

### 15.1 Minimal cURL example

The flow from [4. Minimal end-to-end flow](#4-minimal-end-to-end-flow) over raw HTTP:

```bash
export HYDRADB_API_KEY="your_api_key"
DATABASE="agent_docs_demo"
COLLECTION="user_alex"

# 1. Create a database.
curl -s -X POST 'https://api.hydradb.com/databases' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d "{\"database\":\"${DATABASE}\"}"

# 2. Check readiness. Poll this until .data.infra.ready_for_ingestion is true.
curl -s "https://api.hydradb.com/databases/status?database=${DATABASE}" \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" | jq '.data.infra'

# 3. Ingest a memory.
INGEST_ID=$(curl -s -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=memory" \
  -F "database=${DATABASE}" \
  -F "collection=${COLLECTION}" \
  -F 'memories=[{"id":"alex_pref_001","text":"Alex prefers concise technical answers.","infer":true,"user_name":"Alex"}]' \
  | jq -r '.data.results[0].id')

# 4. Poll indexing.
curl -s -G 'https://api.hydradb.com/context/status' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "database=${DATABASE}" \
  --data-urlencode "collection=${COLLECTION}" \
  --data-urlencode "ids=${INGEST_ID}" \
  | jq '.data.statuses[0]'

# 5. Search memories.
curl -s -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d "{\"database\":\"${DATABASE}\",\"collection\":\"${COLLECTION}\",\"query\":\"How should I answer Alex?\",\"type\":\"memory\",\"query_by\":\"hybrid\",\"mode\":\"thinking\"}" \
  | jq '.data.chunks'
```

### 15.2 Raw HTTP: ingest app-source knowledge

The raw HTTP form of [Knowledge from app sources](#knowledge-from-app-sources). `app_knowledge` must be a JSON string in multipart form data.

```bash
curl -s -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=knowledge" \
  -F "database=acme_corp" \
  -F 'app_knowledge=[
    {
      "id": "slack_C123_1715012345_000100",
      "database": "acme_corp",
      "collection": "default",
      "title": "Pricing discussion - Slack #product",
      "type": "slack",
      "url": "https://slack.com/archives/C123/p1715012345000100",
      "timestamp": "2025-01-15T12:30:00Z",
      "content": {
        "text": "We agreed on three tiers: Starter at $29, Pro at $79, Enterprise at $199."
      },
      "tenant_metadata": {
        "channel": "product",
        "workspace": "acme"
      },
      "additional_metadata": {
        "author": "alice",
        "slack_ts": "1715012345.000100"
      },
      "relations": {
        "ids": ["slack_thread_root_001"],
        "properties": { "relation": "same_thread" }
      }
    }
  ]'
```

Query it with app-aware retrieval:

```bash
curl -s -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "query": "What pricing tiers did product agree on?",
    "type": "knowledge",
    "query_by": "hybrid",
    "mode": "thinking",
    "query_apps": true,
    "graph_context": true
  }' | jq '.data.chunks'
```
