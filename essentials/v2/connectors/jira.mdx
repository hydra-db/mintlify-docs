Sync issues, comments and worklogs from the Jira Cloud projects you select. Each issue is one document with its description, environment, people, status, labels, issue links and linked pull requests. Each comment and each worklog entry is its own document, linked to its issue.

Project and issue-security permissions restrict search only when Enforce ACL is on and HydraDB can read them, which needs a Jira site-admin account. Issue history, watchers and most custom fields are not synced. Edits come across on the next sync. Items deleted in Jira stay in HydraDB.

## Permissions

Turn on **Enforce ACL** for this connector to make search follow Jira permissions. With Enforce ACL off, HydraDB does not enforce them. Only a workspace owner or writer signed in to HydraDB can turn it on. API-key requests must omit `enforce_acl`, including `false`. See [Enforce ACL](/essentials/v2/connectors#enforce-acl).

- **Who can read an item:** Access follows the project. An issue can be read by the active people who hold Browse Projects on its project. An issue with a security level can be read only by that level's members, and an empty level lets nobody read it. A comment or worklog follows its issue's security level.
- **How a person is identified:** A person's email address. For a security level, Jira groups are kept as groups next to their members' emails.
- **When permissions cannot be read:** If HydraDB cannot read a project's Browse holders or an issue's security level, the connector reports a permission warning. On HydraDB Cloud, with Enforce ACL on, such an item follows the access rule you set on its resource. With no rule, it is hidden from search. Self-hosted deployments can be configured differently. Permission warnings appear in [Get Connector Status](/api-reference/v2/endpoint/get-connector-status).
- Reading who can browse a project needs a Jira site-admin account.
- One Browse holder whose email is hidden by Atlassian profile visibility stops HydraDB from capturing the whole project's audience. Set an access rule on such a project.
- A project with too many readers to express cannot be captured.
- A security level held by project roles, the reporter, the assignee or a custom field cannot be captured.
- A comment or worklog whose issue security level cannot be found follows the project's access.
- If Jira returns a temporary error, the audience captured earlier stays in force.

You can also [set your own rule on a resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).

## Before you connect

### Credentials

Jira uses an Atlassian API token together with the email of the account that owns it.

<ResponseField name="domain" type="string" required>
Your Atlassian site host, for example `acme.atlassian.net`.
</ResponseField>

<ResponseField name="email" type="string" required>
The email of the Atlassian account that owns the API token.
</ResponseField>

<ResponseField name="api_token" type="secret string" required>
An Atlassian API token for that account.
</ResponseField>

**Jira permissions for the account**

- `Browse projects`: required. Lists projects and their issues.
- `Browse issues`: required. Reads issue fields, comments and worklogs.
- `Administer Jira`: optional, for permissions. Reading who can browse a project and issue security schemes needs a site-admin account.
- `Browse users and groups`: optional, for permissions. Finds each project reader's email and turns a security level's groups into member emails.

### Set it up

<Steps>
  <Step title="Create an API token">
    In your Atlassian account security settings, create an API token for the account HydraDB will use. Give that account the Jira permissions above on every project you will select.
  </Step>
  <Step title="Create the connector">
    Enter your site as `domain`, the account's `email`, and the token as `api_token`.
  </Step>
  <Step title="Select projects">
    HydraDB lists every project the account can see, with its name and key. Select the projects to sync.
  </Step>
</Steps>

One connector reads one Jira Cloud site as the account that owns the token, and sees only what that account can access.

<Accordion title="Connect through the API">

Use provider `jira` with [Create Connector](/api-reference/v2/endpoint/create-connector). Then call [Discover Connector Resources](/api-reference/v2/endpoint/discover-connector-resources) to list the resources the connector can sync, and [Configure Connector](/api-reference/v2/endpoint/configure-connector) to choose what to sync.

</Accordion>

## Keeping in sync

- **First sync:** A newly selected project reads back the window set by `lookback_days`, 30 days by default. The window is measured on when an issue was last updated, not when it was created.
- **New and changed items:** Each sync reads the issues updated since the last sync. Comments and worklogs are read again for every issue in that window.
- **Edits:** An edited issue is picked up through its last-updated time and updates its document. Comments and worklogs are read again whenever their issue is picked up.
- **Deletions:** Issues, comments and worklogs deleted in Jira stay searchable in HydraDB.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` on the connector to change it.

### Issues

- **One document:** One Jira issue. Its comments and worklogs are separate documents.
- **Title:** The issue summary, or `Jira issue` and the issue key, or the numeric id, when there is no summary.
- **Text:** A first line with the issue key and type, such as `ENG-123 (Bug)`. Then a `Parent` line and one line per issue link, such as `blocks: ENG-7`, up to 20. Then the description as plain text, with link targets kept and mentions written as names, the `Environment` text, and a `Linked pull requests` list with one pull request address per line. The status, priority, assignee, reporter, type, labels, creation date and resolution date are written as lines too. The title is searchable too.
- **Date:** When the issue was last updated, or when it was created if there is no update time.
- **Link back:** The issue's page in Jira, `https://<site>/browse/<KEY>`.
- **Files:** Files attached to the issue are downloaded with the connector's credentials and read, and their text becomes searchable with the issue. A file with no id or download address is skipped. A file that fails to download or is not a supported type keeps only its details.

<ResponseField name="priority" type="Searchable text">

## How it fits into the graph

- Issues use the Ticket class.
- Comments use the Comment class.
- Worklogs use the Comment class.

[Graph classes](/essentials/v2/connector-providers#graph-classes) explains each class.

**Connections Jira creates**

- An issue to its parent issue or epic.
- An issue to each issue it links to. `blocks`, `is blocked by` and `is caused by` keep their direction. `relates to`, `duplicates`, `clones` and `causes` become a plain related link. Other link types become a general link.
- A comment or worklog to its issue, and the comments and worklogs of one issue to each other.
- Each item to its project.
- No links to items in other tools. Linked pull requests stay addresses in the text.

**People and groups**

- The assignee and the reporter, or creator, of each issue.
- The author of each comment and worklog.
- People @mentioned in a description, comment or worklog note.

**Found in the text**

The issue description and environment, and the text of each comment and worklog note. HydraDB identifies people, organizations, projects and other named things in this text. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Not synced

- Projects you did not select.
- Issue history and watchers.
- Projects, boards, sprints, versions, components and users as items of their own.
- Jira admin configuration: screens, schemes, filters, dashboards and custom field definitions.
- Custom fields other than resolution, components and fix versions.
- Linked pull requests, when development-status capture is turned off with `include_dev_status`.
- Comments with no text, and comments or worklogs whose issue cannot be identified.
