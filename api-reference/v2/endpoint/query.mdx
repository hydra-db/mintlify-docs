The one retrieval endpoint: grounded context for an LLM, a user's preferences, or chunks ranked by relevance. Three independent choices control it:

- **`type`:** what to query. `"knowledge"` (default) for documents, files, and app sources; `"memory"` for user memories and preferences; `"all"` for both, merged and re-ranked together, for personalized answers.
- **`query_by`:** how to match. `"hybrid"` (default) is semantic plus BM25, for general retrieval. `"text"` is BM25 only, for exact terms, compliance lookups, and phrases; pair it with `operator`.
- **`mode`:** how to rank. `"fast"`, `"thinking"`, or `"auto"`. **`"auto"` is the default when you omit `mode`.** See [Modes](#decision-matrix).

To pick a configuration for your use case, see [Recommended configurations](/api-reference/v2/endpoint/query-overview#recommended-configurations).

### Querying multiple collections

Use `collections` to fan the whole query out across several user, workspace, or team scopes and merge the results. Send a list or a weighted object:

```json Equal weighting
{
  "database": "acme_corp",
  "collections": ["workspace_42", "user_alex"],
  "query": "What renewal risks should I know about?",
  "type": "all"
}
```

```json Weighted ranking
{
  "database": "acme_corp",
  "collections": {
    "workspace_42": 2,
    "user_alex": 1
  },
  "query": "What renewal risks should I know about?",
  "type": "all"
}
```

- **List:** every collection gets equal normalized weight.
- **Object:** HydraDB normalizes the weights server-side. Limits are in the `collections` row below.
- **`max_results` omitted:** HydraDB takes up to 10 results per collection, capped at 1000 fanout candidates, before shaping the final ranked response.
- **`max_results` set:** it caps the final response across the merged results.
- **Missing collections:** every listed collection must exist, or the call returns `400 INVALID_INPUT` naming the missing ones.

<Tip>
**Caching:** list order does not affect fanout selection. Sort list values, or the keys of a weighted object with weights at one decimal place, before you build cache keys, so equivalent calls share a cache entry.
</Tip>

The SDK's `build_string` (Python) or `buildString` (TypeScript) turns any `POST /query` result into a formatted plain string.


## Request body

| Name | Description |
| --- | --- |
| <Field name="database" type="string" required /> | Owning database. Deprecated alias: `tenant_id`. |
| <Field name="collection" type="string or null" /> | Single collection scope, for example one user's memories. Deprecated alias: `sub_tenant_id`. (default=default collection) |
| <Field name="collections" type="string[] or object" /> | Multi-collection scope: a list of collection IDs for equal weighting, or an object mapping each ID to a positive relative weight with at most one decimal place (e.g. `{"finance": 1.5, "legal": 0.8}`). Up to 100 collections. Do not combine with `collection`/`sub_tenant_id`. Deprecated alias: `sub_tenant_ids` (since 2.0.1). |
| <Field name="query" type="string" required /> | Query terms or natural-language question. Cannot be empty. |
| <Field name="type" type='"knowledge" or "memory" or "all"' /> | What to query. `"all"` runs knowledge and memory in parallel over the same scope and merges by `relevancy_score`. (default=`"knowledge"`) |
| <Field name="query_by" type='"hybrid" or "text"' /> | Retrieval method. (default=`"hybrid"`) |
| <Field name="query_apps" type="boolean" /> | Applies to knowledge queries only. Adds an app-aware lane for app sources (thread and relation traversal, exact IDs, actor and provider hints) on top of the full selected knowledge scope. It does **not** limit the query to app sources. Send `false` to turn the lane off. (default=`true`) |
| <Field name="operator" type='"or" or "and" or "phrase"' /> | BM25 operator for `query_by: "text"`. `"and"` or `"phrase"` with any other `query_by` returns `400`. (default=`"or"`) |
| <Field name="mode" type='"fast", "thinking", or "auto"' /> | Retrieval pipeline, for `hybrid` only (ignored for `text`). `"auto"` scores the query before retrieval and resolves it to `"fast"` or `"thinking"`, picking `"thinking"` when the signal is inconclusive. See [Modes](#decision-matrix). (default=`"auto"`) |
| <Field name="max_results" type="integer or null" /> | Maximum chunks to return. Default `10`; maximum `250`. |
| <Field name="alpha" type='float 0.0 to 1.0, or "auto"' /> | Hybrid weight (`1.0` is pure semantic, `0.0` is pure BM25), for `query_by: "hybrid"` only. `"auto"` currently resolves to `0.8`. (default=`0.8`) |
| <Field name="recency_bias" type="float 0.0 to 1.0" /> | Boost newer content. Omitted applies a mild `0.4` tilt; send `0` to turn it off. (default=`0.4`) |
| <Field name="graph_context" type="boolean" /> | Include the entity and relation graph slice under `graph_context`. `false` only takes effect in `fast` mode: `thinking`, and `auto` when it resolves to thinking, always include it. Relations from [Bring Your Own Graph](/essentials/v2/bring-your-own-graph) appear the same way as extracted ones. (default=`true`) |
| <Field name="query_forceful_relations" type="boolean" /> | Pull author-declared related sources into `additional_context`. **Only takes effect when `mode` resolves to `"thinking"`;** silently ignored in `fast`. (default=`true`) |
| <Field name="additional_context" type="string or null" /> | Request-time hint to guide retrieval (for example, "user is on the billing page"). Not the same as the response `additional_context` map. (default=`null`) |
| <Field name="metadata_filters" type="object or null" /> | Hard filters applied before ranking. See [Filters](#decision-matrix). Each list holds at most 500 values, and the object is capped at 64 KiB of compact JSON, measured after operator objects are reduced to their values. Over either returns `400`. (default=`null`) |

<Tip>
**Tuning heuristics:**

- **`alpha`:** start at `0.8`. Lower it toward `0.3` to `0.5` for literal tokens (error codes, SKUs, product names). Raise it toward `0.9` for conceptual questions.
- **`recency_bias`:** set it to `0` for static reference material. Use `0.2` to `0.4` for mixed content, and `0.6` to `0.8` for changelogs, news, or status updates.
- **`max_results`:** start at `10`. Drop to `5` for tight context windows. Raise to `20` if you rerank downstream.
</Tip>

### Decision matrix

<AccordionGroup>
  <Accordion title="Modes">
    For `query_by: "hybrid"`:

    - **`"fast"`:** a single query pass, for real-time chat, autocomplete, and simple lookups.
    - **`"thinking"`:** multi-query expansion, reranking, and forceful-relation context, for complex queries and customer-facing answers.
    - **`"auto"` (default):** routes each query to `"fast"` or `"thinking"`, for mixed or unpredictable traffic. The response does not report which pipeline it picked, so budget for thinking-level latency.
  </Accordion>

  <Accordion title="Filters">
    `metadata_filters` are hard constraints applied before ranking and re-checked after hydration. The object has two scopes:

    ```json
    {
      "metadata_filters": {
        "department": "engineering",
        "region": "us-east",
        "additional_metadata": {
          "source": "account_plan",
          "author": "alex"
        }
      }
    }
    ```

    - **Top-level keys** such as `department` and `region` match the source's schema-backed `metadata`. The filter matches stored values, not the schema. In a database with a schema, ingest rejects undeclared keys, so filtering on one returns nothing, except `connector_id` and `provider`, which connectors always write. Declare filter keys in `database_metadata_schema` with `enable_match: true`.
    - **Keys under `additional_metadata`** match free-form per-document fields, with no schema needed. `document_metadata` is a legacy alias.

    Separate keys are ANDed. Each top-level `metadata` key takes an operator object:

    | Operator | Value | Matches |
    | --- | --- | --- |
    | `equals` | a single value | sources whose field is **exactly** that value |
    | `contains` | a single value | sources whose field **holds** that value. Multi-value fields are stored comma-joined, so this matches one member of that list |
    | `contains_any` | an array | sources holding **any one** of the listed values (OR/IN) |

    ```json
    "metadata_filters": {
      "department": { "equals": "legal" },
      "attendee_emails": { "contains": "b@company.com" },
      "tags": { "contains_any": ["alpha", "beta"] }
    }
    ```

    - Adding values to `contains_any` **widens** the result set. There is no ALL/AND operator within one key, and no range or fuzzy operators; run several queries or post-process client-side.
    - Operators apply to top-level `metadata` keys only. Inside `additional_metadata`, use a bare scalar for an exact match or a bare array to match any listed value.

    <Warning>
      An operator inside `additional_metadata` is **not** rejected. It is read as an exact match against a stored object, so on a normal field it matches nothing and returns `200` with an empty result.
    </Warning>

    <Note>
      Bare values still work but are **deprecated**, because the comparison is inferred from the JSON shape. A bare scalar acts as `equals`, a bare array as `contains_any`, and a single-element array as `contains`, so `{"emails": "a@x"}` and `{"emails": ["a@x"]}` return different results.
    </Note>

    Validation rules:

    - **Types:** `contains`, `contains_any`, and lists work on `VARCHAR` fields only; on a declared field of another type they return `400 VALIDATION_ERROR`. `equals` works on every declared type, so `{"priority": {"equals": 7}}` is valid on an `INT64` field.
    - **Bad operators:** a known operator with the wrong operand type, or several operators in one object, returns `400 INVALID_INPUT`. A **misspelled** operator (`{"contian": "x"}`) does not: it reads as a filter for a stored object with that key and matches nothing.
    - **Null values:** return `400 INVALID_INPUT`.
    - **Reserved names:** `contains`, `contains_any`, and `equals` are reserved key names. An object built only from them is read as an operator, so it cannot exact-match a stored object, and one whose keys are ALL operator names is rejected with `400`. Mixing in any other key (`{"contains": "a", "other": 1}`) is unaffected. If you need the reserved shape, rename the nested key or the field.

    More examples: [Filter operators](/essentials/v2/metadata#filter-operators).
  </Accordion>
</AccordionGroup>

## Behavior notes

<Warning>
**Common mistakes:**

- **An omitted `mode` means `"auto"`, not `"fast"`:** under `auto`, `graph_context: false` and `query_forceful_relations` depend on each request's routing, and the response does not say which applied. In `fast`, forceful relations are silently skipped and `additional_context` is empty. Set `mode` to `"fast"` or `"thinking"` explicitly for a deterministic pipeline, and call `"fast"` if you never want the graph.
- **Relation `timestamp` is a Unix epoch float here:** in `graph_context`, and in the relations [List Documents](/api-reference/v2/endpoint/list-documents) returns with `include_fields: ["relations"]`, each relation's `timestamp` is in seconds (for example `1778573640.0`). [Context Relations](/api-reference/v2/endpoint/source-relations) returns an ISO-8601 string. Normalize before comparing across endpoints.
- **Query before indexing finishes:** check [Ingestion Status](/api-reference/v2/endpoint/source-status) for recently ingested documents first.
- **Wrong collection:** an omitted `collection` queries the default collection, and a query that names a collection does not read the default one. Use [List Collections](/api-reference/v2/endpoint/list-sub-tenants) to find IDs.
</Warning>

## Errors

Common codes:

- `400 INVALID_INPUT`: the request failed validation, for example an empty `query`, `operator: "and"` without `query_by: "text"`, a malformed filter operator, or a listed collection that does not exist.
- `400` for oversized filters: a `metadata_filters` list above 500 values, or an object above 64 KiB of compact JSON. The message names the offending key or reports the byte count. See [Filter size limits](/essentials/v2/metadata#filter-size-limits).
- `400 VALIDATION_ERROR`: a metadata filter does not fit the declared field type, such as `contains` on an `INT64` field.
- `404 DATABASE_NOT_FOUND`: the database does not exist.
- `422 TENANT_INFRA_NOT_READY`: the database is still provisioning. Poll [Database Status](/api-reference/v2/endpoint/tenant-status) until `ready_for_ingestion` is `true`, then retry.
- `429 RATE_LIMITED`, `500 INTERNAL_ERROR`, `503 SERVICE_UNAVAILABLE`: transient. Retry with backoff.

See [Error Responses](/api-reference/v2/error-responses) for the full list.
