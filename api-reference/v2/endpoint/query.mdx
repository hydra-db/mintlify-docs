The one retrieval endpoint. Call it whenever you need grounded context for an LLM, a user's preferences, or chunks ranked by relevance.

Three independent choices control behavior:

- **`type`:** what to query. `"knowledge"`, `"memory"`, or `"all"` (both, merged and re-ranked together).
- **`query_by`:** how to match. `"hybrid"` (semantic plus BM25, the default) or `"text"` (BM25 only; pair it with `operator`).
- **`mode`:** how to rank. `"fast"` (single pass, low latency), `"thinking"` (expands the query, reranks, and can include forceful-relation context), or `"auto"` (scores the query and routes it to `"fast"` or `"thinking"`, defaulting to `"thinking"` when the signal is inconclusive). **`"auto"` is the default when you omit `mode`.**

To pick a configuration for your use case, see [Recommended configurations](/api-reference/v2/endpoint/query-overview#recommended-configurations).

### Querying multiple collections

Use `collections` to fan one query out across several user, workspace, or team scopes. Send a list or a weighted object:

```json Equal weighting
{
  "database": "acme_corp",
  "collections": ["workspace_42", "user_alex"],
  "query": "What renewal risks should I know about?",
  "type": "all"
}
```

```json Weighted ranking
{
  "database": "acme_corp",
  "collections": {
    "workspace_42": 2,
    "user_alex": 1
  },
  "query": "What renewal risks should I know about?",
  "type": "all"
}
```

- **List:** every collection gets equal normalized weight.
- **Object:** values are positive relative ranking weights with at most one decimal place. HydraDB normalizes them server-side.
- **Limit:** at most 100 collections.
- **`max_results` omitted:** HydraDB takes up to 10 results per collection, capped at 1000 fanout candidates, before it shapes the final ranked response.
- **`max_results` set:** it caps the final response across the merged fanout result set.
- **Missing collections:** every listed collection must exist. Otherwise the call returns `400 INVALID_INPUT` naming the missing ones.

<Tip>
**Caching:** list order does not affect fanout selection. Sort list values before you build cache keys. For weighted objects, sort the keys and keep weights at one decimal place, so equivalent calls share a cache entry.
</Tip>

### Turning the response into LLM context

Use `build_string` (Python) or `buildString` (TypeScript) from the SDK. It takes any `POST /query` result and returns a formatted plain string.

<CodeGroup>
```python Python SDK
from hydra_db import HydraDB
from hydra_db.helpers import build_string

client = HydraDB(token="YOUR_API_KEY")

result = client.query(
    database="your-database",
    collection="your-collection",
    query="How does authentication work?",
    type="knowledge",
    query_by="hybrid",
    max_results=5,
    mode="fast",
    graph_context=True,
)

context = build_string(result)
```

## Request body

| Name | Description |
| --- | --- |
| <Field name="database" type="string" required /> | Owning database. Formerly `tenant_id`, which is still accepted as a deprecated alias. |
| <Field name="collection" type="string or null" /> | Single collection scope. Pass it for per-user memory queries. Formerly `sub_tenant_id`, which is still accepted as a deprecated alias. (default=default collection) |
| <Field name="collections" type="string[] or object" /> | Multi-collection scope. Send a list of collection IDs for equal weighting, or an object mapping collection ID to a positive relative weight (at most one decimal place, e.g. `{"finance": 1.5, "legal": 0.8}`) to bias ranking. Up to 100 collections. Do not combine with `collection`/`sub_tenant_id`. Formerly `sub_tenant_ids`; the `sub_tenant_ids` alias is still accepted (deprecated since 2.0.1). |
| <Field name="query" type="string" required /> | Query terms or natural-language question. Cannot be empty. |
| <Field name="type" type='"knowledge" or "memory" or "all"' /> | What collection to query. `"all"` runs knowledge and memory in parallel over the same scope and merges by `relevancy_score`. (default=`"knowledge"`) |
| <Field name="query_by" type='"hybrid" or "text"' /> | Retrieval method. See [Query methods](#decision-matrix). (default=`"hybrid"`) |
| <Field name="query_apps" type="boolean" /> | Adds an app-aware retrieval lane for app sources while still querying the full selected knowledge scope. Set `true` for better app-source matching, thread/relation traversal, exact IDs, and actor/provider hints. It does **not** limit query to only app sources. Set `false` to turn the lane off. (default=`true`) |
| <Field name="operator" type='"or" or "and" or "phrase"' /> | BM25 operator for `query_by: "text"`. `"and"` or `"phrase"` with any other `query_by` returns `400`. (default=`"or"`) |
| <Field name="mode" type='"fast", "thinking", or "auto"' /> | Retrieval pipeline. Applies to `hybrid` only; ignored for `text`. `"auto"` scores the query before retrieval and resolves it to `"fast"` or `"thinking"`, defaulting to `"thinking"` when the signal is inconclusive. When it resolves to `"thinking"`, graph context is always included. (default=`"auto"`) |
| <Field name="max_results" type="integer or null" /> | Maximum chunks to return. Default `10`; maximum `250`. See the tuning tip below. |
| <Field name="alpha" type='float 0.0 to 1.0, or "auto"' /> | Hybrid weight (`1.0` is pure semantic, `0.0` is pure BM25). Applies to `query_by: "hybrid"` only. `"auto"` currently resolves to `0.8`. (default=`0.8`) |
| <Field name="recency_bias" type="float 0.0 to 1.0" /> | Boost newer content. If omitted, a mild `0.4` tilt applies. Send `0` to turn it off. (default=`0.4`) |
| <Field name="graph_context" type="boolean" /> | When `true`, includes the entity and relation graph slice in the response under `graph_context`. Set it to `false` when you only need ranked chunks. `false` only takes effect in `fast` mode: `thinking` (and `auto` when it resolves to thinking) always includes the graph. Relations you supplied with [Bring Your Own Graph](/essentials/v2/bring-your-own-graph) appear here the same way as extracted ones. (default=`true`) |
| <Field name="query_forceful_relations" type="boolean" /> | Pull author-declared related sources into `additional_context`. **Only takes effect when `mode` resolves to `"thinking"`.** It is silently ignored in `fast` mode, and under `mode: "auto"` it depends on the routing decision. (default=`true`) |
| <Field name="additional_context" type="string or null" /> | Request-time hint to guide retrieval (for example, "user is on the billing page"). This is different from the response `additional_context` map. (default=`null`) |
| <Field name="metadata_filters" type="object or null" /> | Deterministic narrowing before ranking. See [Filters](#decision-matrix). Each list holds at most 500 values, and the whole object is capped at 64 KiB of compact JSON, measured after operator objects are reduced to their values; over either returns `400`. (default=`null`) |

<Tip>
**Tuning heuristics:**

- **`alpha`:** start at `0.8`. Lower it toward `0.3` to `0.5` when the query contains literal tokens (error codes, SKUs, product names). Raise it toward `0.9` for conceptual questions. `"auto"` currently resolves to `0.8`, the same as the default.
- **`recency_bias`:** set it to `0` for static reference material. Use `0.2` to `0.4` for mixed content, and `0.6` to `0.8` for changelogs, news, or status updates.
- **`max_results`:** start at `10`. Drop to `5` for tight context windows. Raise to `20` if you rerank downstream.
</Tip>

### Decision matrix

<AccordionGroup>
  <Accordion title="Type selection">
    - **`"knowledge"` (default):** knowledge documents, files, and app sources. Use it for document Q&A and RAG context.
    - **`"memory"`:** user memories. Use it for personalization and user preferences.
    - **`"all"`:** both, merged into one ranked result set. Use it for personalized answers grounded in shared and user-specific context.
    - **`query_apps`:** not a `type` value. It is on by default for knowledge queries and adds app-aware retrieval on top of the full selected knowledge scope. Use it for app-specific Q&A that should still query non-app knowledge documents.
  </Accordion>

  <Accordion title="Query methods">
    - **`"hybrid"` (default):** dense vectors plus BM25 keywords. Use it for general retrieval and RAG.
    - **`"text"`:** BM25 only. Use it for exact terms, compliance lookups, and phrase queries. Pair it with `operator`.
  </Accordion>

  <Accordion title="Modes">
    For `query_by: "hybrid"`:

    - **`"fast"`:** a single query pass. Use it for real-time chat, autocomplete, and simple lookups.
    - **`"thinking"`:** multi-query expansion, reranking, and forceful-relation context. Use it for complex queries, customer-facing answers, and anything where quality matters.
    - **`"auto"` (default when `mode` is omitted):** scores the query before retrieval and routes it to `"fast"` or `"thinking"`, defaulting to `"thinking"` when the signal is inconclusive. If it picks `"thinking"`, the graph slice is always included; if it picks `"fast"`, your `graph_context` value applies. Use it for mixed or unpredictable traffic.

    The response does not report which pipeline `"auto"` picked, so budget for thinking-level latency in the worst case.
  </Accordion>

  <Accordion title="Filters">
    `metadata_filters` are hard constraints applied before ranking and re-checked after hydration. The object combines two scopes:

    ```json
    {
      "metadata_filters": {
        "department": "engineering",
        "region": "us-east",
        "additional_metadata": {
          "source": "account_plan",
          "author": "alex"
        }
      }
    }
    ```

    - **Top-level keys:** keys such as `department` and `region` match the source's schema-backed `metadata`. The filter does not consult the schema: it matches each key against the metadata stored on each source. In a database with a schema, ingest rejects undeclared keys, so a filter on an undeclared key returns an empty result. `connector_id` and `provider` are the exception, because connectors always write them. Declare the keys you filter on in `database_metadata_schema` with `enable_match: true`.
    - **Keys under `additional_metadata`:** match the source's free-form per-document fields. No schema declaration needed. `document_metadata` is accepted as a legacy alias.

    Separate keys are ANDed. Each top-level `metadata` key takes an operator object that names the comparison:

    | Operator | Value | Matches |
    | --- | --- | --- |
    | `equals` | a single value | sources whose field is **exactly** that value |
    | `contains` | a single value | sources whose field **holds** that value. Multi-value fields are stored comma-joined, so this matches one member of that list |
    | `contains_any` | an array | sources holding **any one** of the listed values (OR/IN) |

    ```json
    "metadata_filters": {
      "department": { "equals": "legal" },
      "attendee_emails": { "contains": "b@company.com" },
      "tags": { "contains_any": ["alpha", "beta"] }
    }
    ```

    - Adding values to `contains_any` **widens** the result set. There is no ALL/AND operator within a single key, and range and fuzzy operators are not supported. Run several queries or post-process client-side for those cases.
    - Operators apply to top-level `metadata` keys only. Inside `additional_metadata`, use a bare scalar for an exact match or a bare array to match any listed value.

    <Warning>
      An operator used inside `additional_metadata` is **not** rejected. It is read as an exact-match filter against a stored object, so on a normal field it matches nothing and the request returns `200` with an empty result rather than an error.
    </Warning>

    <Note>
      The bare forms still work unchanged but are **deprecated** in favour of the operators, because the comparison is inferred from the JSON shape rather than stated. A bare scalar behaves as `equals`, a bare array as `contains_any`, and a bare single-element array as `contains`. So `{"emails": "a@x"}` and `{"emails": ["a@x"]}` differ by one character and return different results.
    </Note>

    Validation rules:

    - **Types:** `contains`, `contains_any`, and lists work on `VARCHAR` fields only. Passing any of them for a declared field of another type returns `400 VALIDATION_ERROR`. `equals` works on every declared type, so `{"priority": {"equals": 7}}` is valid on an `INT64` field.
    - **Bad operators:** a known operator with the wrong operand type, or several operators in one object, returns `400 INVALID_INPUT`. A **misspelled** operator does not: `{"contian": "x"}` looks like a filter for a stored object with that key, so it is left alone and matches nothing.
    - **Null values:** a `null` filter value returns `400 INVALID_INPUT`.
    - **Reserved names:** `contains`, `contains_any`, and `equals` are reserved key names. An object built only from them is read as an operator and can no longer exact-match a stored object, and an object whose keys are ALL operator names is rejected with `400`. Mixing an operator name with any other key (`{"contains": "a", "other": 1}`) is unaffected. If you need the reserved shape, rename the nested key or the field.

    More examples: [Filter operators](/essentials/v2/metadata#filter-operators).
  </Accordion>
</AccordionGroup>

## Behavior notes

<Warning>
**Common mistakes:**

- **`query_forceful_relations` needs `"thinking"`:** in `fast` mode the flag is silently ignored. The server does not error or warn; the response `additional_context` is simply empty. Under `mode: "auto"`, it depends on that request's routing decision, not on what you asked for.
- **`graph_context: false` only works in `fast`:** `thinking`, and `auto` when it routes to thinking, always include the graph slice. Under `auto` (including an omitted `mode`), `false` takes effect only on requests that route to `fast`. Call `"fast"` directly if you never want the graph.
- **An omitted `mode` means `"auto"`, not `"fast"`:** set `mode` to `"fast"` or `"thinking"` explicitly if you want a deterministic pipeline.
- **Relation `timestamp` is a Unix epoch float here:** in the `graph_context` slice returned by `/query`, and in the passthrough relations returned by [List Documents](/api-reference/v2/endpoint/list-documents) with `include_fields: ["relations"]`, each relation's `timestamp` is a Unix epoch value in seconds (a float, for example `1778573640.0`). The [Context Relations](/api-reference/v2/endpoint/source-relations) endpoint returns the same field as an ISO-8601 string. Normalize before comparing relation timestamps across endpoints.
- **Use the right metadata namespace:** top-level `metadata_filters` keys match `metadata`. Free-form per-document fields must be nested under `additional_metadata` (`document_metadata` is only a legacy alias). Declare hot top-level filter fields in `database_metadata_schema` with `enable_match: true`.
- **Query before indexing finishes:** check [Ingestion Status](/api-reference/v2/endpoint/source-status) for recently ingested documents before querying.
- **Wrong collection:** if you omit `collection`, HydraDB queries the default collection. A query that names a collection does not read the default collection. Use [List Collections](/api-reference/v2/endpoint/list-sub-tenants) to discover available IDs.
</Warning>

## Errors

Common codes:

- `400 INVALID_INPUT`: the request failed validation, for example an empty `query`, `operator: "and"` without `query_by: "text"`, a malformed filter operator, or a listed collection that does not exist.
- `400 VALIDATION_ERROR`: a metadata filter does not fit the declared field type, such as `contains` on an `INT64` field.
- `404 DATABASE_NOT_FOUND`: the database does not exist.
- `422 TENANT_INFRA_NOT_READY`: the database is still provisioning. Poll [Database Status](/api-reference/v2/endpoint/tenant-status) until `ready_for_ingestion` is `true`, then retry.
- `429 RATE_LIMITED`, `500 INTERNAL_ERROR`, `503 SERVICE_UNAVAILABLE`: transient. Retry with backoff.

See [Error Responses](/api-reference/v2/error-responses) for the full list.

`400` also covers oversized filters: a `metadata_filters` list above 500 values, or a `metadata_filters` object above 64 KiB of compact JSON. The message names the offending key or reports the actual byte count. See [Filter size limits](/essentials/v2/metadata#filter-size-limits).
