A chief of staff remembers what was decided, who committed to what, and what has changed since. This cookbook builds one from two types of context: meetings and email, and the decisions drawn from them, which HydraDB keeps current.

| Benchmark | Result | What it shows here |
| --- | --- | --- |
| [BEAM 1M](https://benchmarks.hydradb.com/beam-1m) | 82% overall across ten dimensions | Decisions, tasks, and events tracked over months, where newer information replaces older |

No benchmark tests a chief of staff end to end. BEAM 1M tests the memory underneath it.

## 1. Create a database with two collections

Work records go in one collection. The executive's own decisions and commitments go in another, so they can be queried alone or together with the records.

```python chief_of_staff.py
import json

from hydra import answer, client, create_database, source_ids, wait_indexed

DATABASE = "acme_corp"
RECORDS, EXECUTIVE = "work_records", "exec_dana"

create_database(DATABASE)
```

## 2. Ingest meetings and email

Meetings and email go in as text items. Keep participants, senders, and dates in the text, and the date in `happened_at`, which is what lets a query answer "what did Priya agree to on the September call".

```python chief_of_staff.py
records = [
    {
        "context_id": "gong_call_0912",
        "title": "Q4 planning call",
        "text": "Q4 planning call, hosted by Dana Okafor, with Priya Shah. "
        "Dana: we launch the EU region on November 3. Priya: I will "
        "have the data residency review done by October 15.",
        "happened_at": "2026-09-12",
    },
    {
        "context_id": "gmail_msg_1002",
        "title": "EU launch date",
        "text": "Email from dana@acme.com to leadership@acme.com. "
        "Legal needs two more weeks. Moving the EU launch to November 17.",
        "happened_at": "2026-10-02",
    },
]

result = client.context.ingest(
    database=DATABASE,
    collection=RECORDS,
    context=json.dumps(records),
)
wait_indexed(DATABASE, RECORDS, source_ids(result))
```

## 3. Save decisions

After each meeting or thread, save what was decided as a [text item](/essentials/v2/context). With `enrich: true`, HydraDB extracts the facts and checks them against what the collection already holds, so the October change to the launch date is reconciled with the September decision instead of sitting beside it.

```python chief_of_staff.py
def remember(text):
    result = client.context.ingest(
        database=DATABASE,
        collection=EXECUTIVE,
        context=json.dumps([{"text": text, "enrich": True, "user_name": "Dana"}]),
    )
    wait_indexed(DATABASE, EXECUTIVE, source_ids(result))


remember("2026-09-12: Decided to launch the EU region on November 3. "
         "Priya owns the data residency review, due October 15.")
remember("2026-10-02: Moved the EU launch to November 17 because legal needs two more weeks.")
```

## 4. Ask what is current

Query both collections at once. `recency_bias` favors newer context, and `thinking` mode reranks, so the current launch date ranks above the one it replaced.

```python chief_of_staff.py
def brief(question):
    result = client.query(
        database=DATABASE,
        collections=[RECORDS, EXECUTIVE],
        query=question,
        mode="thinking",
        recency_bias=0.6,
    )
    return answer(question, result, "When facts conflict, the most recent one is current. "
                                    "Name the owner and due date of each commitment.")


print(brief("When is the EU launch, and what is still open before it?"))
```

## Run it

```bash
python chief_of_staff.py
```

The answer should give November 17, note that the date moved from November 3, and list Priya's data residency review as the open commitment.

## Use real data

Connect the calendar, meeting, and email apps with [connectors](/essentials/v2/connectors) in place of step 2. Keep step 3 in your application: decide what counts as a decision, and save it when the meeting ends.

## Common mistakes

- **Saving the transcript only:** a transcript records what was said. A decision records what is true now. Save both.
- **Querying one collection:** a query that names only `RECORDS` does not read the decisions. Use `collections` with both names.
- **Leaving dates out of decisions:** write the date into the decision text. It is what lets a later change supersede an earlier one.
