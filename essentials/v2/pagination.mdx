---
title: "Paginating list responses"
description: "How HydraDB v2 paginates list endpoints: page numbers for context list, numeric cursors for graph relations, and opaque cursors with has_more for connector discovery."
---

HydraDB does **not** use one pagination scheme everywhere. List-style endpoints return pages of results, but the request parameters and stop conditions differ by endpoint. Treating every list call like offset/`limit`, or assuming every response has `has_more`, causes partial exports and broken loops.

This page documents the three contracts in the current v2 OpenAPI:

1. **Page numbers**  -  [`POST /context/list`](/api-reference/v2/endpoint/list-documents)
2. **Numeric cursor**  -  [`GET /context/relations`](/api-reference/v2/endpoint/source-relations)
3. **Opaque string cursor + `has_more`**  -  [`GET /connectors/{id}/discover`](/api-reference/v2/endpoint/discover-connector-resources) and **`POST /connector-discovery`** (credentials in the body), currently when Notion pagination is opted into

Webhook delivery listing also uses an opaque string `cursor` / `next_cursor` pair. See [Webhooks](/essentials/v2/webhooks) for that surface.

`POST /query` is **not** a paginated list API. Bound retrieval size with `max_results` instead. See [How to Use API Results](/essentials/v2/api-results).

---

## Does this endpoint paginate?

| Endpoint | Scheme | Request knobs | Continue while… |
| --- | --- | --- | --- |
| [`POST /context/list`](/api-reference/v2/endpoint/list-documents) | Page index | `page`, `page_size` | `data.pagination.has_next` is `true` |
| [`GET /context/relations`](/api-reference/v2/endpoint/source-relations) | Numeric cursor | `limit`, `cursor` | `data.next_cursor` is not `null` |
| [`GET /connectors/{id}/discover`](/api-reference/v2/endpoint/discover-connector-resources) | Opaque cursor (opt-in) | `limit`, `cursor` query params | `has_more` is `true` (Notion when opted in) |
| `POST /connector-discovery` | Opaque cursor (opt-in) | credentials body + `limit`/`cursor` query params | `has_more` is `true` (Notion when opted in) |
| Webhook delivery list | Opaque cursor | `limit`, `cursor` | `next_cursor` is not `null` |

Pagination fields live under the response payload (usually inside the envelope's `data` object), not at the top-level envelope. Always read `success` first, then inspect `data`.

---

## Scheme A - Page numbers (`POST /context/list`)

Use this to browse knowledge sources or memories. Request fields:

- `page`  -  1-indexed page number (default `1`)
- `page_size`  -  items per page, `1` to `100` (default `50`)

Response pagination lives at `data.pagination`:

```json
{
  "success": true,
  "data": {
    "sources": [],
    "total": 318,
    "pagination": {
      "page": 1,
      "page_size": 50,
      "total": 318,
      "total_pages": 7,
      "has_next": true,
      "has_previous": false
    }
  },
  "error": null
}
```

Drain pattern: start at `page: 1`, append each page's items, then increment `page` while `data.pagination.has_next` is `true`. Keep `page_size` fixed for the whole walk.

<CodeGroup>
```bash cURL
# Page 1
curl -X POST 'https://api.hydradb.com/context/list' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "collection": "team_docs",
    "type": "knowledge",
    "page": 1,
    "page_size": 50
  }'

# Page 2 when data.pagination.has_next is true
curl -X POST 'https://api.hydradb.com/context/list' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme_corp",
    "collection": "team_docs",
    "type": "knowledge",
    "page": 2,
    "page_size": 50
  }'
```

```python Python
import os
import requests

headers = {
    "Authorization": f"Bearer {os.environ['HYDRA_DB_API_KEY']}",
    "API-Version": "2",
    "Content-Type": "application/json",
}

page = 1
page_size = 50
all_sources = []

while True:
    response = requests.post(
        "https://api.hydradb.com/context/list",
        headers=headers,
        json={
            "database": "acme_corp",
            "collection": "team_docs",
            "type": "knowledge",
            "page": page,
            "page_size": page_size,
        },
    )
    envelope = response.json()
    if not envelope.get("success"):
        raise RuntimeError(envelope.get("error") or "list failed")

    data = envelope["data"]
    all_sources.extend(data.get("sources") or [])

    pagination = data.get("pagination") or {}
    if not pagination.get("has_next"):
        break
    page += 1
```

```typescript TypeScript
const headers = {
  Authorization: `Bearer ${process.env.HYDRA_DB_API_KEY}`,
  "API-Version": "2",
  "Content-Type": "application/json",
};

let page = 1;
const pageSize = 50;
const allSources: unknown[] = [];

while (true) {
  const response = await fetch("https://api.hydradb.com/context/list", {
    method: "POST",
    headers,
    body: JSON.stringify({
      database: "acme_corp",
      collection: "team_docs",
      type: "knowledge",
      page,
      page_size: pageSize,
    }),
  });

  const envelope = await response.json();
  if (!envelope.success) {
    throw new Error(envelope.error?.message ?? "list failed");
  }

  const data = envelope.data;
  allSources.push(...(data.sources ?? []));

  if (!data.pagination?.has_next) {
    break;
  }
  page += 1;
}
```
</CodeGroup>

Stop on `has_next: false`. Do not invent a stop condition from `sources.length < page_size` alone when `has_next` is present.

## Scheme B - Numeric cursor (`GET /context/relations`)

Use this to export graph relations for a source or an entire collection. Request query parameters:

- `limit`  -  max relation groups per call, `1` to `10000` (default `5000`)
- `cursor`  -  number from a previous response's `data.next_cursor` (omit on the first call)

Response fields under `data`:

- `relations`  -  this page of triplet groups
- `next_cursor`  -  number to pass back as `cursor`, or `null` when finished
- `is_truncated`  -  `true` when the result was cut by `limit`

`next_cursor` is opaque even though it is typed as a number. Pass back exactly what the server returned. Do not construct it, increment it, or treat it as an offset.

<CodeGroup>
```bash cURL
curl -G 'https://api.hydradb.com/context/relations' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "database=acme_corp" \
  --data-urlencode "collection=team_docs" \
  --data-urlencode "id=billing_runbook_v3" \
  --data-urlencode "limit=1000"

# Next page when data.next_cursor is not null
curl -G 'https://api.hydradb.com/context/relations' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "database=acme_corp" \
  --data-urlencode "collection=team_docs" \
  --data-urlencode "id=billing_runbook_v3" \
  --data-urlencode "limit=1000" \
  --data-urlencode "cursor=0.88"
```

```python Python
import os
import requests

headers = {
    "Authorization": f"Bearer {os.environ['HYDRA_DB_API_KEY']}",
    "API-Version": "2",
}

cursor = None
all_relations = []

while True:
    params = {
        "database": "acme_corp",
        "collection": "team_docs",
        "id": "billing_runbook_v3",
        "limit": 1000,
    }
    if cursor is not None:
        params["cursor"] = cursor

    response = requests.get(
        "https://api.hydradb.com/context/relations",
        headers=headers,
        params=params,
    )
    envelope = response.json()
    if not envelope.get("success"):
        raise RuntimeError(envelope.get("error") or "relations failed")

    data = envelope["data"]
    all_relations.extend(data.get("relations") or [])

    next_cursor = data.get("next_cursor")
    if next_cursor is None:
        break
    cursor = next_cursor
```

```typescript TypeScript
const headers = {
  Authorization: `Bearer ${process.env.HYDRA_DB_API_KEY}`,
  "API-Version": "2",
};

let cursor: number | null = null;
const allRelations: unknown[] = [];

while (true) {
  const params = new URLSearchParams({
    database: "acme_corp",
    collection: "team_docs",
    id: "billing_runbook_v3",
    limit: "1000",
  });
  if (cursor !== null) {
    params.set("cursor", String(cursor));
  }

  const response = await fetch(
    `https://api.hydradb.com/context/relations?${params}`,
    { headers },
  );
  const envelope = await response.json();
  if (!envelope.success) {
    throw new Error(envelope.error?.message ?? "relations failed");
  }

  const data = envelope.data;
  allRelations.push(...(data.relations ?? []));

  if (data.next_cursor == null) {
    break;
  }
  cursor = data.next_cursor;
}
```
</CodeGroup>

Keep `limit` constant across pages. Stopping because `is_truncated` is `false` alone is weaker than checking `next_cursor`; prefer `next_cursor === null` as the drain stop.

## Scheme C - Opaque cursor + `has_more` (connector discover)

Two discovery routes share the same pagination contract:

- [`GET /connectors/{id}/discover`](/api-reference/v2/endpoint/discover-connector-resources)  -  uses the connector's stored credentials
- **`POST /connector-discovery`**  -  discovers **before** a connector exists; you must send a JSON body with the provider and credentials (required). Do not call this route with `GET`.

Both can return the full resource list in one response. Passing **`cursor` or `limit`** as query parameters opts into pagination. Per the OpenAPI description, that opt-in path is **currently Notion only**.

When you opt in:

- Query params: opaque string `cursor` (from the previous page's `next_cursor`) and `limit` (`1` to `100`; values above `100` are clamped)
- For `POST /connector-discovery`, keep sending the same credentials body on every page
- Response adds `next_cursor` and `has_more`
- A page may contain fewer than `limit` resources
- Clients **must continue while `has_more` is true**

Without `cursor` or `limit`, expect the full resource list and do not assume `has_more` is present.

<CodeGroup>
```bash cURL
curl -G 'https://api.hydradb.com/connectors/conn_123/discover' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "limit=50"

# Next page when has_more is true
curl -G 'https://api.hydradb.com/connectors/conn_123/discover' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "limit=50" \
  --data-urlencode "cursor=eyJvZmZzZXQiOjUwfQ=="
```

```python Python
import os
import requests

headers = {
    "Authorization": f"Bearer {os.environ['HYDRA_DB_API_KEY']}",
    "API-Version": "2",
}

cursor = None
all_resources = []

while True:
    params = {"limit": 50}
    if cursor is not None:
        params["cursor"] = cursor

    response = requests.get(
        "https://api.hydradb.com/connectors/conn_123/discover",
        headers=headers,
        params=params,
    )
    response.raise_for_status()
    payload = response.json()

    all_resources.extend(payload.get("resources") or [])

    if not payload.get("has_more"):
        break
    cursor = payload.get("next_cursor")
    if cursor is None:
        break
```

```typescript TypeScript
const headers = {
  Authorization: `Bearer ${process.env.HYDRA_DB_API_KEY}`,
  "API-Version": "2",
};

let cursor: string | null = null;
const allResources: unknown[] = [];

while (true) {
  const params = new URLSearchParams({ limit: "50" });
  if (cursor) {
    params.set("cursor", cursor);
  }

  const response = await fetch(
    `https://api.hydradb.com/connectors/conn_123/discover?${params}`,
    { headers },
  );
  if (!response.ok) {
    throw new Error(`discover failed: ${response.status}`);
  }

  const payload = await response.json();
  allResources.push(...(payload.resources ?? []));

  if (!payload.has_more) {
    break;
  }
  if (!payload.next_cursor) {
    break;
  }
  cursor = payload.next_cursor;
}
```
</CodeGroup>

Do not decode or rebuild opaque cursors. Pass the server value through unchanged.

## Pitfalls checklist

- **Do not assume one global scheme.** Page numbers on list, numeric cursors on relations, opaque cursors on discover/deliveries.
- **Read fields under `data` (or the endpoint payload), not the top-level envelope.** Envelope fields are `success`, `data`, `error`, `meta`.
- **Keep page size / limit fixed** for a single drain. Changing `page_size` or `limit` mid-walk can skip or duplicate items.
- **Opaque cursors are not offsets.** Never invent `cursor=2` for relations or parse a base64 discover cursor.
- **For discover, honor `has_more`.** A short page does not mean you are done when `has_more` is still `true`.
- **For list, honor `has_next`.** Prefer `data.pagination.has_next` over guessing from array length.
- **For relations, stop on `next_cursor: null`.** Prefer that over stopping only on `is_truncated: false`.
- **Discover pagination is opt-in and currently Notion-focused.** Without `cursor`/`limit`, expect a full list and no `has_more` field.
- **`POST /connector-discovery` is not `GET`.** It requires a JSON body with `provider` and `credentials`. Use `GET /connectors/{id}/discover` only after a connector already exists.
- **`POST /query` is not this guide.** Use `max_results` for retrieval size, not list cursors.
