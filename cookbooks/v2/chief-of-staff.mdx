A chief of staff remembers what was decided, who committed to what, and what has changed since. This cookbook builds one from two types of context: email and chat as knowledge, and the decisions drawn from them as memories that HydraDB keeps current.

| Benchmark | Result | What it shows here |
| --- | --- | --- |
| [BEAM 1M](https://benchmarks.hydradb.com/beam-1m) | 82% overall across ten dimensions | Decisions, tasks, and events tracked over months, where newer information replaces older |

No benchmark tests a chief of staff end to end. BEAM 1M tests the memory underneath it.

## 1. Create a database with two collections

Work records go in one collection. The executive's own decisions and commitments go in another, so they can be queried alone or together with the records.

```python chief_of_staff.py
import json
import os

from hydra import answer, client, connect, create_database, source_ids, wait_indexed

DATABASE = "acme_corp"
RECORDS, EXECUTIVE = "work_records", "exec_dana"

create_database(DATABASE)
```

## 2. Connect email and chat as knowledge

Where the work happened is already written down in email and chat. A [connector](/essentials/v2/connectors) syncs each app into the records collection and keeps senders, participants, threads, and dates, which is what lets a query answer "what did Priya agree to in September".

```python chief_of_staff.py
# Each provider has its own credentials: client.list_providers(id="gmail")
# returns the shape. Gmail needs no account scope.
connect("gmail", DATABASE, RECORDS, credentials=json.loads(os.environ["GMAIL_CREDENTIALS"]))
connect(
    "slack",
    DATABASE,
    RECORDS,
    credentials={"access_token": os.environ["SLACK_TOKEN"]},
    account_scope=os.environ["SLACK_WORKSPACE_ID"],
)
```

## 3. Save decisions as memories

After each meeting or thread, save what was decided as a [memory](/essentials/v2/context#2-save-memories). With `infer: true`, HydraDB extracts the facts and checks them against what the collection already holds, so the October change to the launch date is reconciled with the September decision instead of sitting beside it.

```python chief_of_staff.py
def remember(text):
    result = client.context.ingest(
        type="memory",
        database=DATABASE,
        collection=EXECUTIVE,
        memories=json.dumps([{"text": text, "infer": True, "user_name": "Dana"}]),
    )
    wait_indexed(DATABASE, EXECUTIVE, source_ids(result))


remember("2026-09-12: Decided to launch the EU region on November 3. "
         "Priya owns the data residency review, due October 15.")
remember("2026-10-02: Moved the EU launch to November 17 because legal needs two more weeks.")
```

## 4. Ask what is current

Query both collections at once with `type: "all"`, as the executive: a connector copies the app's permissions where the provider supports it, and `acl` keeps the brief to what this person may see. `recency_bias` favors newer context, and `thinking` mode reranks, so the current launch date ranks above the one it replaced.

```python chief_of_staff.py
def brief(question):
    result = client.query(
        database=DATABASE,
        collections=[RECORDS, EXECUTIVE],
        query=question,
        type="all",
        mode="thinking",
        recency_bias=0.6,
        acl=[os.environ["EXECUTIVE_EMAIL"]],
    )
    return answer(question, result, "When facts conflict, the most recent one is current. "
                                    "Name the owner and due date of each commitment.")


print(brief("When is the EU launch, and what is still open before it?"))
```

## Run it

Set `GMAIL_CREDENTIALS`, `SLACK_TOKEN`, `SLACK_WORKSPACE_ID`, and `EXECUTIVE_EMAIL`, replace the two sample decisions and the question with your own, and run:

```bash
python chief_of_staff.py
```

With the sample decisions, the answer gives November 17, notes that the date moved from November 3, and lists Priya's data residency review as the open commitment. It adds whatever your email and chat say on the subject.

Keep step 3 in your application: decide what counts as a decision, and save it when the meeting or thread ends.

## Common mistakes

- **Saving decisions as knowledge only:** a transcript records what was said. A memory records what is true now. Save both.
- **Querying one collection:** a query that names only `RECORDS` does not read the memories. Use `collections` with both names.
- **Leaving dates out of memories:** write the date into the memory text. It is what lets a later change supersede an earlier one.
