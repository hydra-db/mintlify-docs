This is the complete, maintained agent guide. Continue with the sections below; no separate documentation-index fetch is needed.

### TL;DR: Critical endpoints

1. **`POST /databases`** (`client.databases.create()`): Create an isolated database. Creation is asynchronous. New databases are unified: one corpus for everything you store, and no `type` anywhere.
2. **`GET /databases/status`** (`client.databases.status()`): Poll until `infra.ready_for_ingestion` is true before you ingest or query.
3. **`POST /context/ingest`** (`client.context.ingest()`): Ingest a `context` list of items, each a `text` or a `conversation`, or upload files. Indexing is asynchronous.
4. **`GET /context/status`** (`client.context.status()`): Poll by `ids` until `indexing_status` is `completed` before you query. `graph_creation` means the item is becoming searchable while its graph builds, but a query sent the moment it appears can still miss the item. `errored` means indexing failed: read `error_code` and `error_message`. Details in [7. Context status and lifecycle](#7-context-status-and-lifecycle).
5. **`POST /query`** (`client.query()`): Retrieve chunks, graph paths, and linked items from the whole database, or from the collections you name.
6. **`POST /feedback`** (`client.feedback.submit()`): Tell us when a query did not give you what you needed, and once the task is done, how the context held up. See [Sending feedback](#sending-feedback).

Every other endpoint and SDK method is in [15. SDK method reference](#15-sdk-method-reference).

## 1. Critical rules for LLMs

### API versioning and auth

- Base URL: `https://api.hydradb.com`
- Raw HTTP calls must include:
  - `Authorization: Bearer <api_key>`
  - `API-Version: 2`
- Official SDKs set `API-Version: 2` automatically.
- Use `HYDRADB_API_KEY` as the environment variable in examples.

### Response envelope

Raw HTTP responses are wrapped:

```json
{
  "success": true,
  "data": {},
  "error": null,
  "meta": {
    "request_id": "...",
    "latency_ms": 12.3
  }
}
```

- Read the payload from `data`, never from the top level. This applies to `/databases`, `/context/*`, `/query`, `/feedback`, and the webhook management endpoints (`/webhooks/indexing*`).
- The SDKs do not unwrap it: they return the full envelope object, so read `response.data` (for example `response.data.infra`, `response.data.statuses`, `response.data.results`). On failure they raise a typed exception instead of returning an envelope with `error` set.
- Exceptions: connector endpoints (`/connectors*`) and `PATCH /databases/{database}/metadata-schema` return their success body directly, without the envelope. In the SDKs that is every `connectors.*` method, `list_providers()`, and `update_metadata_schema()`. Their errors still use the envelope.
- Log `meta.request_id` for failed requests.
- Treat `meta` as an open object: ignore keys you do not recognize.
- `meta` carries an optional `deprecation` list (with a `Deprecation: true` response header) when a request uses a legacy tenants route (any path under /tenants) or a deprecated field (`tenant_id`/`sub_tenant_id`, or `sub_tenant_ids` on `/query`). It is a non-breaking nudge: the status code is unchanged. Every entry has `deprecated`, `message`, and `deprecated_since`. `deprecated_field` and `preferred_field` are **optional**: the `sub_tenant_ids` notice on `/query` carries them, the `tenant_id`/`sub_tenant_id` notice does not. Read `message` for the migration, and do not key logic off the two optional fields. To avoid the notice, use the `/databases` routes and the `database`/`collection`/`collections` fields.

### Unified and split databases

- A database has a layout, `unified` or `split`, fixed when it is created. `GET /databases` reports it as `details[].type`, and `GET /databases/status` as `type`.
- New databases are unified. Everything you store goes into one corpus: send a `context` list (or files) on ingest, and do not send `type` on any call. `POST /databases` needs no `type` either.
- On a unified database, `POST /context/ingest` refuses `type: "knowledge"` and `type: "memory"`, and refuses the split upload field `memories`.
- Databases created before unified became the default are split, and keep working exactly as before. They take `type`, their own upload fields and defaults, and answer a query with different keys (`sources`, `graph_context`, `data.additional_graph_context` and the rest). If you hold one, read `https://docs.hydradb.com/essentials/v2/split-databases` instead of the examples here.
- A split database cannot be converted. To move to unified, create a new database and ingest again.

The rest of this guide describes unified databases.

### Attribute naming

- `attributes`: schema-aligned fields, declared at database creation; the fast filter path. Filter on them with the `attributes` filter on `POST /query`.
- `custom_attributes`: free-form fields; anything not in the schema.
- Set both per item on `/context/ingest`, on each `context` item. A file upload carries the same two stores under the names `metadata` and `additional_metadata`, on its `document_metadata[]` item.

Schema fields, placement, and filter operators are in [10. Metadata guide](#10-metadata-guide).

### Do not mix scopes accidentally

- `database` (formerly `tenant_id`) is the hard isolation boundary.
- `collection` (formerly `sub_tenant_id`) is an optional group inside a database. Use separate collections only for context that must never meet in one query, such as what each user tells your agent. Otherwise (for example, a company brain) keep all documents and connectors in one collection and isolate results with the `attributes` filter and `acl`. Patterns are in [Databases and collections](#databases-and-collections).
- Use the same `collection` on writes, status checks, and reads. Context written under one collection does not appear in a query that names another.

### Send `acl` on user queries

- If your application answers on behalf of signed-in users, send the caller's identity as `acl` on every `POST /query`, for example `"acl": ["grace@acme.com"]`.
- A query with no `acl`, `[]`, or `["*"]` is not filtered: it returns everything in scope, including sources restricted to other people.
- Derive `acl` from your authenticated session, never from client input. See [Access control](#access-control).
- Do not turn on a connector's `enforce_acl` for an application that serves many users through one API key. With `enforce_acl` on, HydraDB ignores the request's `acl` for that connector's content and uses the email of whoever created the API key, so every user sees what the key's creator may see. Leave it off and send `acl` yourself.
- Under `enforce_acl`, the identity comes from authentication: an API key or pasted-key MCP uses the key creator's email, and MCP OAuth and the dashboard use the signed-in user. A request `acl` still scopes content from non-enforced connectors.
- If you send `acl` and an enforced connector ignores it, a successful response includes one `meta.warnings` entry with code `acl_ignored_by_connector_enforcement`. Treat it as a signal that your `acl` did not apply to that content.

### Sending feedback

`POST /feedback` (`client.feedback.submit()`) records how a query performed. It is optional, and there is no penalty for skipping it. You are the only party that knows whether the retrieved context answered the question, and that judgement is what tunes retrieval.

Send it when you have something specific to report:

- **A query did not give you what you needed:** nothing relevant came back, the top result was wrong, or you had to fall back to another source. One report on a query that disappointed you is worth far more than a stream of routine ones.
- **A query worked well:** `rating: "positive"` tells us what to preserve.
- **The task is finished (recommended):** send one short report on how the context performed. See [End-of-task report](#end-of-task-report).

Rules:

- **Take `request_id` from the query's own response. Never invent one.** It is in `meta.request_id` and in the `X-Request-ID` response header. Send it back **verbatim**: an ID you made up, or one from another query, correlates to nothing.
- Set `source: "agent"`. It separates your reports from human ones, which fail in different ways.
- Say **what** was wrong, not that something was wrong. "Returned the 2023 policy, current one is in the Q3 handbook" is actionable; "bad results" is not.
- Do not block the user on it. Feedback is fire-and-forget: if the **feedback call itself** fails, drop it and carry on. Never retry in a loop, and never surface that error to the user.
- Catch broadly, so that **nothing** escapes. Narrowing to the SDK error type would still let a timeout or a DNS failure surface an error the user cannot act on, from a call they did not ask for.
- Feedback never changes the query's result. It is a signal, not a correction, and you cannot read it back.
- Each submission is its own record. A second report about the same query adds to the first instead of replacing it, so refine as you learn more.

```python
result = client.query(database="acme_corp", query="What is our refund policy?")

# ... use result.data.chunks to answer the user ...

try:
    client.feedback.submit(
        request_id=result.meta.request_id,
        feedback="Top chunk was the 2023 policy; the current one is in the Q3 handbook.",
        rating="negative",
        source="agent",
        database="acme_corp",
    )
except Exception:
    pass  # fire-and-forget: a failed report must never reach the user
```

#### End-of-task report

At the end of the task you know what you could not know at query time: whether a chunk that looked plausible turned out to be stale, contradicted by another source, or never used at all. A single report then is worth more than one per query, and `rating: "positive"` is as valuable as a negative one, because you know which part of the context did the work.

Make the report stand on its own. We see only a `request_id` and the prose you send, nothing about what you were doing. Worth a sentence each:

- What the user was trying to do.
- Which chunks carried the answer, and which you discarded and why.
- Whether you had to go outside HydraDB to finish, and what was missing when you did.

```python
try:
    client.feedback.submit(
        request_id=result.meta.request_id,   # from the query you are reporting on
        source="agent",
        rating="positive",
        feedback=(
            "Task: user asked which refund window applies to EU orders. "
            "Chunks 1 and 3 (Q3 handbook) carried the answer. Chunk 2 was the "
            "2023 policy and was discarded as superseded. No outside sources needed."
        ),
        database="acme_corp",
    )
except Exception:
    pass  # fire-and-forget, exactly as above
```

#### Ground truth

**If you know the right answer, send it as `ground_truth`.** When you run against a labelled set, or you know which source should have been returned, that is a far stronger signal than a comment, because it can be scored without a human reading it. With `ground_truth` present, `feedback` prose is optional:

```python
try:
    client.feedback.submit(
        request_id=result.meta.request_id,
        source="agent",
        ground_truth={
            "answer": expected_answer,          # what a correct response looks like
            "source_ids": ["policy_2024"],      # sources that actually contain it
        },
    )
except Exception:
    pass
```

Send `answer`, `source_ids`, or both. Do **not** guess: only send ground truth you have. A fabricated answer key is worse than none, because it is scored as if it were true.

#### Failed requests are not feedback

**"Did not give me what I needed" is not the same as "errored".** A query that returned `200` with unhelpful results is what this endpoint is for. A query that never returned (`4xx`/`5xx`, or the SDK raised) is not: a failed request has no retrieval result to judge. Fix the request instead: a `404` means the database name is wrong, a `429` means back off, a `400` means the body was malformed.

#### Request fields and limits

| Field | Required | Notes |
|---|---|---|
| `request_id` | yes | The UUID from that query's `meta.request_id`, verbatim |
| `feedback` | yes* | What was right or wrong, up to 8000 chars. *Optional if `ground_truth` is sent |
| `rating` | no | `positive`, `negative`, `neutral`. Omitting it is not the same as `neutral` |
| `source` | no | `user` (default) or `agent`. Agents set `"agent"` |
| `database` / `collection` | no | Optional scoping; `collection` requires `database` |
| `ground_truth` | no | `{ answer, source_ids }`: what the right answer was, when you know it. Makes `feedback` optional |
| `metadata` | no | Up to 20 string pairs of your own context (agent name, conversation id) |

Limit: 100 submissions per minute per organization, far above what reporting only the queries that fell short reaches. If you do hit `429`, honour `Retry-After` or skip that report. Never spin.

## 2. Core primitives

### Databases and collections

Scoping rules are in [Do not mix scopes accidentally](#do-not-mix-scopes-accidentally). Recommended patterns:

| Use case | Pattern |
|---|---|
| Company brain | one `database`, one collection for all documents and connectors; isolate with the `attributes` filter and `acl` |
| B2B SaaS | one `database` per customer; one collection for that customer's context; isolate teams with the `attributes` filter and `acl` |
| B2C app | one `database`; shared context in one collection; `collection = user_id` for what each user tells your agent |
| Environment isolation | separate `database`s for prod/staging |
| Per-user context | `collection = user_id`, and the same collection on every read |

### Context

Context is everything your AI reasons over, in one corpus: notes, facts, preferences, decisions, and past conversations you send as `context` items; PDFs, Markdown, and CSVs you upload as files; and Slack threads, Notion pages, Gmail threads, tickets, and other content that [connectors](#connectors) sync from your apps. A query reads all of it together. There is no `type` to choose.

- Each `context` item is a `text` or a `conversation` (a list of `{role, content}` turns). Item fields are in [6. Context ingestion](#6-context-ingestion).
- Enrichment is on by default (`enrich: true`): HydraDB extracts what the item says, including preferences implied in a conversation, and returns it beside the original content.
- It can be private: restrict items with `acl` (see [Access control](#access-control)).
- Mutability is explicit: re-ingest with the same `context_id` and `upsert: true`, edit attributes in place with `PATCH /context/{id}/metadata`, or delete.

### Query

`POST /query` is the single retrieval endpoint. Fields, recommended configurations, and the response shape are in [8. Query API](#8-query-api).

### Context graph

HydraDB builds a graph of entity/relation triplets from ingested content. When `graph_context: true` (default), a query returns them in `graph`: a list of paths, each a chain of triplets with a `path_summary`. Each path's `origin` says how it was found: `query_path` (grown from the entities in the query) or `chunk_relation` (the neighbourhood of a chunk that ranked).

The graph augments the result; it does not replace `chunks`.

### Deterministic relations

Deterministic relations are links you declare between items at ingest, by `context_id`, with optional properties stored on each link. Unlike the graph, which HydraDB extracts, these are links you assert:

```json
{
  "context_id": "billing_runbook",
  "text": "The billing runbook points to the pager escalation policy.",
  "forceful_relations": {
    "context_ids": ["pager_escalation_policy"],
    "properties": { "reason": "runbook step" }
  }
}
```

- Any `context` item can declare them in `forceful_relations`. Properties are flat scalars (string, number, boolean).
- A query follows them only in `mode: "thinking"` with `query_explicit_relations: true` (the default). The linked chunks come back in `data.forceful_relations`, separate from the ranked `chunks`, each with `via` (`from` and `to`) naming the relation that reached it.
- Do not confuse them with the request field `additional_graph_context`, which is a short text hint, not a relation.

### Access control

A source's `acl` lists who may retrieve it; a query's `acl` says who is asking. The query-side rule is in [Send `acl` on user queries](#send-acl-on-user-queries).

- Set `acl` on any existing source with `PATCH /context/{id}/metadata`, where it replaces the stored list.
- Connectors copy permissions from Slack, Google Drive, GitHub, Confluence, Jira, and other providers on every sync.
- Principals: an email (`grace@acme.com`), `domain:acme.com`, `group:<provider>:<id>`, or `__public__`.
- On a query, the caller's email also matches its `domain:` principal and `__public__` automatically. Group membership is never derived from an email; send `group:` principals yourself.
- A source with no `acl` is unrestricted.

Example: a source with `"acl": ["grace@acme.com"]` comes back for a query with `"acl": ["grace@acme.com"]` and stays hidden from `"acl": ["bob@acme.com"]`. A source with `"acl": ["domain:acme.com"]` comes back for both.

### Connectors

Connectors sync context from 70+ apps, including Slack, Gmail, Google Drive, Notion, Jira, Confluence, GitHub, Linear, HubSpot, and Zendesk, into a database on a schedule, with no ingestion code. Indexing is permission-aware: for providers with `acl_supported: true`, each synced source carries the provider's own access rules. App content reaches HydraDB through connectors; `GET /connectors/providers` lists the catalog.

Setup is four calls, made once:

1. `GET /connectors/providers?id={provider}`: read `credential_schema`, the credentials it needs.
2. `POST /connectors`: store the credentials, with `database` and `collection`.
3. `GET /connectors/{id}/discover`: list the channels, repositories, or pages the credentials reach.
4. `POST /connectors/{id}/configure`: choose resources; the first sync starts right away.

Then poll `GET /connectors/{id}/status` until `lifecycle` is `active`, and query as usual. Syncs repeat every `sync_interval_seconds` (one hour by default).

```python
connector = client.connectors.create(
    provider="slack",
    database="acme_corp",
    collection="company_docs",
    provider_account_scope="T12345ACME",
    credentials={"access_token": "xoxp-..."},
)
found = client.connectors.discover(connector.connector_id)
client.connectors.configure(
    connector.connector_id,
    resources=[
        {"resource_id": r.id, "resource_type": r.resource_type, "name": r.name}
        for r in found.resources
    ],
)
status = client.connectors.status(connector.connector_id)
```

```ts
const connector = await client.connectors.create({
  provider: "slack",
  database: "acme_corp",
  collection: "company_docs",
  providerAccountScope: "T12345ACME",
  credentials: { access_token: "xoxp-..." },
});
const id = connector.connectorId!;
const found = await client.connectors.discover({ id });
await client.connectors.configure({
  id,
  resources: (found.resources ?? []).map((r) => ({
    resourceId: r.id!,
    resourceType: r.resourceType,
    name: r.name,
  })),
});
const status = await client.connectors.status({ id });
```

Rules:

- To change one resource, use `PATCH /connectors/{id}/resources/{resource_id}`. `POST /connectors/{id}/resources` adds new resources only: on an existing resource it returns `409` and changes nothing.
- Every synced source carries `connector_id` and `provider` in its attributes, and `connector_id` and `resource_id` in its custom attributes. `POST /context/list` shows them as `metadata` and `additional_metadata`, and filters on them there.
- `custom_instructions` on the connector or one resource tells HydraDB how to read its documents, from the next sync on.

### Bring Your Own Graph (BYOG)

To build and query your own graph in Cypher, for example when migrating from Neo4j or another Cypher-compatible store, use the `/byog` endpoints instead of `/context/ingest`:

| Endpoint | Purpose |
| --- | --- |
| `POST /byog/databases` | Create a database; ready immediately. Returns `409` if the name exists |
| `POST /byog/query` | Run Cypher against one `collection`, with user data in `params` |
| `GET /byog/collections` | List a database's graph collections |
| `DELETE /byog/collections` | Drop one collection |
| `DELETE /byog/databases` | Drop a database |

- Each collection is an isolated graph, created on first write. Reading one that does not exist yet returns zero rows.
- Pass user data through `params`, never by building it into the query string.
- Procedure calls (`CALL db.*`, `CALL apoc.*`) and `LOAD CSV` are not supported.
- Limits: 256 KiB request body (`413`), 8 s for reads and 30 s for writes (`400` on timeout). Rows beyond the result-set cap are silently dropped, so paginate large reads.
- Agents can run the same Cypher through the HydraDB MCP graph tools: `hydradb_graph_query`, `hydradb_graph_collections`, and `hydradb_graph_admin`.

Full guide: `https://docs.hydradb.com/essentials/v2/bring-your-own-graph`.

## 4. Minimal end-to-end flow

### Python

```python
import json
import os
import time
from hydra_db import HydraDB

client = HydraDB(token=os.environ["HYDRADB_API_KEY"])
database = "my_first_database"

# 1. Create database.
client.databases.create(database=database)

# 2. Wait until the database can accept data.
while True:
    status = client.databases.status(database=database)
    if status.data.infra.ready_for_ingestion:
        break
    time.sleep(5)

# 3. Ingest what the user said.
ingest = client.context.ingest(
    database=database,
    collection="user_alex",
    context=json.dumps([
        {
            "context_id": "user_alex_pref_001",
            "text": "I prefer detailed technical explanations, and dark mode everywhere.",
            "user_name": "Alex",
        }
    ]),
)

ingest_id = ingest.data.results[0].id

# 4. Wait until searchable.
while True:
    status = client.context.status(
        database=database,
        collection="user_alex",
        ids=[ingest_id],
    ).data.statuses[0]

    if status.indexing_status == "completed":
        break
    if status.indexing_status == "errored":
        # A wrong database/collection reports "errored" too, with FILE_NOT_FOUND.
        # error_message is "" in that case, so branch on the code, not the text.
        if status.error_code == "FILE_NOT_FOUND":
            raise RuntimeError("No such id in this scope: check database/collection match ingestion")
        raise RuntimeError(status.error_message or status.message or "Indexing failed")
    time.sleep(2)

# 5. Search what the user said.
result = client.query(
    database=database,
    collection="user_alex",
    query="What does the user prefer?",
    query_by="hybrid",
    mode="thinking",
)

print(result.data.chunks)
```

### TypeScript

```ts
import { HydraDBClient } from "@hydradb/sdk";

const client = new HydraDBClient({
  token: process.env.HYDRADB_API_KEY,
});

const database = "my_first_database";

await client.databases.create({ database: database });

while (true) {
  const status = await client.databases.status({ database: database });
  if (status.data?.infra?.readyForIngestion) break;
  await new Promise((resolve) => setTimeout(resolve, 5_000));
}

const ingest = await client.context.ingest({
  database: database,
  collection: "user_alex",
  context: JSON.stringify([
    {
      context_id: "user_alex_pref_001",
      text: "I prefer detailed technical explanations, and dark mode everywhere.",
      user_name: "Alex",
    },
  ]),
});

const ingestId = ingest.data?.results?.[0]?.id;
if (!ingestId) throw new Error("Ingest returned no id");

while (true) {
  const status = (await client.context.status({
    database: database,
    collection: "user_alex",
    ids: [ingestId],
  })).data?.statuses?.[0];
  if (!status) throw new Error("No status returned");

  if (status.indexingStatus === "completed") break;
  if (status.indexingStatus === "errored") {
    // || rather than ??: errorMessage is "" (not null) on some failures, and ??
    // would pass the empty string through and throw an error with no message.
    throw new Error(status.errorMessage || status.message || "Indexing failed");
  }

  await new Promise((resolve) => setTimeout(resolve, 2_000));
}

const result = await client.query({
  database: database,
  collection: "user_alex",
  query: "What does the user prefer?",
  queryBy: "hybrid",
  mode: "thinking",
});

if (!result.data || typeof result.data === "string") throw new Error("Expected structured query results");
console.log(result.data.chunks);
```

## 5. Databases API

### Create database

`POST /databases` · `client.databases.create()`

```json
{
  "database": "acme_corp",
  "database_metadata_schema": [
    {
      "name": "department",
      "data_type": "VARCHAR",
      "enable_dense_embedding": false,
      "enable_sparse_embedding": false,
      "max_length": 1024
    }
  ]
}
```

Notes:

- `database` should be stable. Use lowercase letters, numbers, and underscores for portability.
- Plan `database_metadata_schema` before ingestion. What you can change later is in [10. Metadata guide](#10-metadata-guide).
- `POST /databases` may return `409 DATABASE_ALREADY_EXISTS` for duplicate database IDs and `403 FORBIDDEN` when the API key or plan cannot create more databases.

### Check readiness

`GET /databases/status?database=...` · `client.databases.status()`

The database is ready when `infra.ready_for_ingestion` is true. The response also carries `type`, the database's layout (`unified` for every new database), and the underlying signals under `infra`, such as `infra.scheduler_status` and `infra.graph_status`.

### Other database endpoints

The collections, stats, and delete routes also take `database` as a query parameter, for example `GET /databases/collections?database=...`. `DELETE /databases?database=...` deletes the database and all its data. The full list is in [15. SDK method reference](#15-sdk-method-reference).

## 6. Context ingestion

`POST /context/ingest` is the single write endpoint. Send a JSON body with a `context` list, or a multipart form with the same list as a JSON string in the `context` field (the SDKs send the form). Files go in the multipart `documents` field instead.

### Request fields

| Field | Description |
|---|---|
| `database` | target database |
| `collection` | optional; the default collection if omitted |
| `context` | the list of items to ingest; at most 100 per request |
| `upsert` | default `true`; replaces existing items with the same `context_id`. An item's own `upsert` overrides it |
| `enrich` | default `true`; the default for every item that does not set its own |
| `documents` | binary file uploads; see [Files](#files) |
| `document_metadata` | JSON-stringified array, one item per uploaded file |

Do not send `type`. A request that sends both `context` and `documents` is refused: send files in their own request.

### Context items

```python
import json

client.context.ingest(
    database="acme_corp",
    collection="user_alex",
    context=json.dumps([
        {
            "context_id": "pref_dark_mode",
            "title": "Dark mode preference",
            "text": "Alex prefers dark mode and concise answers.",
            "user_name": "Alex",
            "happened_at": "2026-11-02",
            "attributes": {"team": "engineering"},
            "custom_attributes": {"source": "onboarding"},
        },
        {
            "context_id": "onboarding_chat",
            "user_name": "Alex",
            "conversation": [
                {"role": "user", "content": "I'm on the platform team and mostly write Go."},
                {"role": "assistant", "content": "Noted. I'll use Go in examples."},
            ],
        },
    ]),
)
```

Over raw HTTP, send the same list as a JSON body:

```bash
curl -s -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{"database":"acme_corp","collection":"user_alex","context":[{"context_id":"pref_dark_mode","text":"Alex prefers dark mode and concise answers.","user_name":"Alex"}]}'
```

Item fields:

| Field | Description |
|---|---|
| `text` | the content, as raw text or Markdown. Send exactly one of `text` or `conversation` |
| `conversation` | a list of `{role, content}` turns, the shape you already send to a chat model. `role` is `user`, `assistant`, or `system`; `system` turns are read as context, never as facts, and at least one `user` or `assistant` turn is required |
| `context_id` | optional stable ID and upsert key; HydraDB assigns one if omitted. Items with identical text and no `context_id` or `title` collide, so set one of them |
| `title` | label for listing, results, and citations; up to 1024 bytes |
| `user_name` | who is speaking: the author of a `text` item, or the user in a `conversation` |
| `enrich` | defaults to `true`: HydraDB extracts what the item says, including preferences implied in a conversation, and returns it as `enrichment` beside the original content. `false` stores the item as written |
| `upsert` | overrides the request-level `upsert` for this item |
| `happened_at` | the date the content is about, `YYYY-MM-DD` |
| `attributes` | schema-aligned fields, as an object (do not stringify it again inside `context`). Keys must be declared in the metadata schema. Max 16 KiB |
| `custom_attributes` | free-form fields, as an object. Max 1 KiB |
| `context_category` | a label: `user_preference`, `business_knowledge`, or `decision_trace`. `auto` (the default) stores none. The label does not change how the item is processed; it can be filtered on in `POST /context/list` and comes back on each chunk as `enrichment_kind` |
| `forceful_relations` | deterministic relations to other items, `{ "context_ids": [...], "properties": {...} }`; see [Deterministic relations](#deterministic-relations) |
| `acl` | who may retrieve the item; see [Access control](#access-control) |

Limits: 1 MiB of text per item and 8 MiB per request. An unknown key, on the request or on an item, is refused with a `400` that names it and lists the accepted fields.

### Files

Use for files HydraDB should parse. Supported extensions:

| Type | Extensions |
|---|---|
| Documents | `.pdf` `.doc` `.docx` `.docm` `.dot` `.dotx` `.odt` `.ott` `.rtf` |
| Spreadsheets | `.xls` `.xlsx` `.xlsm` `.xlsb` `.ods` `.ots` `.csv` `.tsv` |
| Presentations | `.ppt` `.pptx` `.pptm` `.odp` `.otp` |
| Apple iWork | `.pages` `.numbers` `.key` |
| Images (text is read with OCR) | `.png` `.jpg` `.jpeg` `.tif` `.tiff` `.webp` `.gif` `.bmp` |
| Plain text | `.txt` `.md` `.markdown` `.json` |

- Any other extension, including source code (`.py`, `.ts`, `.go`), `.html`, and `.zip`, is rejected. The request still returns `202`; the rejected file comes back in `data.results` with `status: "failed"` and `error_code: "E1002"`, and has no status record to poll. Check every result item before polling.
- To ingest source code, upload it with `.txt` added to the filename (`auth.py.txt`) and keep the real path in `additional_metadata`, or send its text as a `context` item.
- The `Content-Type` of the part is used only when the filename has no extension.

```python
import json

with open("policy.pdf", "rb") as f:
    result = client.context.ingest(
        database="acme_corp",
        documents=[("policy.pdf", f, "application/pdf")],
        document_metadata=json.dumps([
            {
                "id": "policy_v2",
                "metadata": {"department": "support", "status": "approved"},
                "additional_metadata": {"author": "Alice", "version": 2},
            }
        ]),
    )
```

`document_metadata` is how you attach anything to an uploaded file. Send one item per file, in the same order as `documents`. The item count must match the file count, and an unrecognized key returns `400`.

| `document_metadata` item field | Purpose |
|---|---|
| `id` | stable ID / upsert key for the uploaded file; HydraDB assigns one if omitted |
| `metadata` | schema-aligned fields for this file (max 16 KiB compact JSON); the file's `attributes` |
| `additional_metadata` | free-form fields for this file (max 1 KiB compact JSON); the file's `custom_attributes` |
| `relations` | deterministic relations to other items, `{ "ids": [...] }` |

### Ingest response

`202` means the request was accepted, not that the items are searchable. `data.results` has one entry per item, in order, with its `id` (the `context_id` you sent, or the one HydraDB assigned), `status`, and `error_code` / `error` when that item was refused. Poll each accepted `id` with [`GET /context/status`](#7-context-status-and-lifecycle).

## 7. Context status and lifecycle

### Poll indexing

`GET /context/status` · `client.context.status()`

Parameters:

- `database`: required.
- `ids`: required array.
- `collection`: **required if you ingested into one.** The lookup is scoped: omitting `collection`, or sending the wrong one, returns `indexing_status: "errored"` with `error_code: "FILE_NOT_FOUND"` and `message: "ID not found"` for an item that exists and is fully searchable. That is a scope miss, not an indexing failure, and you can tell the two apart only by reading `error_code`.

| Status | Searchable? | Meaning |
|---|---:|---|
| `queued` | No | accepted, not picked up |
| `processing` | No | parsing/chunking/embedding |
| `graph_creation` | Within seconds | chunks are being indexed and the graph is still building; a query sent immediately can miss the item, and a new collection can still be reported as not existing |
| `completed` | Yes | fully indexed and graphed |
| `errored` | No | terminal failure; read `error_code` and `error_message` |

`error_message` is `""`, not null, on some failures (including a scope miss), so branch on `error_code`, and in TypeScript fall back with `||`, not `??`.

```ts
while (true) {
  const status = (await client.context.status({
    database: "acme_corp",
    collection: "support_docs", // must match the ingestion scope, or you get FILE_NOT_FOUND
    ids: ["policy_v2"],
  })).data?.statuses?.[0];
  if (!status) throw new Error("No status returned");

  if (status.indexingStatus === "completed") break;
  if (status.indexingStatus === "errored") {
    // A scope miss reports errored too, so name the cause rather than guessing.
    if (status.errorCode === "FILE_NOT_FOUND") {
      throw new Error(`No such id in this scope: check database/collection match ingestion`);
    }
    // Use ||, not ??: errorMessage comes back as "" (not null) on some failures,
    // and ?? passes an empty string straight through to an empty error.
    throw new Error(status.errorMessage || status.message || "Indexing failed");
  }
  await new Promise((r) => setTimeout(r, 2_000));
}
```

### Webhooks instead of polling

Register a webhook on `/webhooks/indexing` to receive terminal indexing events instead of polling. The management endpoints and SDK methods are in [15. SDK method reference](#15-sdk-method-reference).

Supported event: `indexing.status_changed`. Payload shape:

```json
{
  "event": "indexing.status_changed",
  "delivery_id": "<delivery_id>",
  "id": "<id>",
  "database": "<database>",
  "collection": "<collection>",
  "status": "completed",
  "timestamp": "<ISO-8601 timestamp>",
  "error_code": null,
  "error_message": null
}
```

Headers: `X-HydraDB-Delivery-ID`, `X-HydraDB-Event`, and `X-HydraDB-Signature` when a signing secret is configured.

Signature scheme:

```text
X-HydraDB-Signature: sha256=<lowercase hex digest>

digest = HMAC-SHA256(key = signing_secret, message = raw request body bytes)
```

The `sha256=` prefix is part of the header value. The digest is lowercase hex, not base64. The HMAC covers the raw body bytes as received; re-serialising the parsed JSON produces different bytes and will not match.

Managing the secret:

- `POST /webhooks/indexing` with `{"generate_signing_secret": true}` registers and enables signing in one call, returning the secret once. Mutually exclusive with `signing_secret`; sending both is a `422`.
- `POST /webhooks/indexing/signing-secret` with no body generates one and returns the secret once. Send `{"signing_secret": "..."}` to supply your own (minimum 16 characters).
- `DELETE /webhooks/indexing/signing-secret` disables signing.
- Omitting `signing_secret` on `POST /webhooks/indexing` preserves the existing secret. It does not disable signing.

Rules:

- The webhook URL must be public HTTPS; localhost and private networks are blocked.
- Store `delivery_id` to deduplicate retries.
- Verify `X-HydraDB-Signature` with a constant-time comparison. Use `verify_webhook_signature` (Python SDK) or `verifyWebhookSignature` (TypeScript SDK) from the SDK helpers module.
- Fail closed: reject the request when the signing secret is absent from the environment, instead of skipping verification.

## 8. Query API

`POST /query` · `client.query()`

### Request fields that matter

| Field | Values | Notes |
|---|---|---|
| `database` | string | required |
| `collection` | string/null | the collection the context was saved in; default collection if omitted |
| `collections` | list of collection IDs, or an object of weights | query up to 100 collections at once; every listed collection must exist. Send weights, such as `{"user_alex": 2, "company_docs": 1}`, to rank one collection over another |
| `query` | string | required |
| `acl` | list of principals | who is asking; see [Send `acl` on user queries](#send-acl-on-user-queries) |
| `query_by` | `hybrid`, `text` | default `hybrid` (semantic + BM25); `text` is BM25 keyword/phrase search |
| `operator` | `or`, `and`, `phrase` | only for `query_by: "text"` |
| `mode` | `fast`, `thinking`, `auto` | applies to hybrid; omitted means `auto`, which scores the query before retrieval and routes it to fast or thinking. `fast` is low latency. `thinking` adds query expansion, reranking, richer graph traversal, and deterministic relations; it improves quality but adds latency |
| `max_results` | integer/null | default 10; max 250 |
| `alpha` | `0.0` to `1.0`, or `auto` | hybrid weight; `1.0` semantic, `0.0` BM25 |
| `recency_bias` | `0.0` to `1.0` | boost newer content; omitted means `0.6`, send `0` to disable |
| `graph_context` | boolean | default true; include `graph` paths; `false` only takes effect in fast mode, thinking always includes them |
| `query_explicit_relations` | boolean | default true; follows the deterministic relations declared with `forceful_relations` and returns the linked chunks in `data.forceful_relations`; only effective in `thinking` mode |
| `additional_graph_context` | string | short factual hint that sharpens retrieval; not a hard filter |
| `titles` | list of strings | only items whose full title matches one of these, case-insensitively |
| `attributes` | object | filter on declared `attributes` with `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`, `$and`, `$or`, `$not`, `$exists`; a bare value means `$eq`. Applied to chunks, linked chunks, and graph paths |
| `query_apps` | boolean | app-aware retrieval lane for content synced by connectors; still searches everything else in scope; defaults to `true` on `/query`, send `false` to disable |

Do not send `type`. A query reads the whole database, or the collections you name. To combine shared context with one user's, send `collections: ["<shared>", "<user>"]`.

### Recommended configurations

| Goal | Request shape |
|---|---|
| Fast document RAG | `query_by: "hybrid"`, `mode: "fast"`, `graph_context: false`, `max_results: 5-10` |
| Highest-quality answer | `query_by: "hybrid"`, `mode: "thinking"`, `graph_context: true`, `alpha: "auto"` |
| Personalized grounded answer | `collections` listing the shared collection and the user's, `query_by: "hybrid"`, `mode: "thinking"` |
| One user's preferences | `collection` set to the user's collection, `query_by: "hybrid"` |
| Exact keyword / phrase | `query_by: "text"`, `operator: "phrase"` |
| Recent operational updates | `query_by: "hybrid"`, `recency_bias: 0.6-0.8`, an `attributes` filter on doc type/status |
| App search | `query_by: "hybrid"`, `mode: "thinking"`, `query_apps: true`; still searches uploaded files and items too |

### Query examples

Document RAG:

```ts
const result = await client.query({
  database: "acme_corp",
  query: "What is our refund policy?",
  queryBy: "hybrid",
  mode: "thinking",
  maxResults: 10,
  graphContext: true,
});
```

Personalized answer from shared context and one user's:

```ts
const result = await client.query({
  database: "acme_corp",
  collections: ["company_docs", "user_alex"], // shared context and what this user said
  query: "What is our refund policy, and how should I explain it to this user?",
  queryBy: "hybrid",
  mode: "thinking",
  alpha: "auto",
});
```

Exact phrase:

```python
result = client.query(
    database="acme_corp",
    query="ERROR_429 rate limit",
    query_by="text",
    operator="phrase",
)
```

Attribute-scoped query:

```json
{
  "database": "acme_corp",
  "query": "authentication control review",
  "query_by": "hybrid",
  "attributes": {
    "compliance_framework": { "$eq": "SOC2" },
    "status": { "$in": ["approved", "in_review"] }
  }
}
```

### Query response

The successful `data` object has exactly five keys:

```json
{
  "chunks": [
    {
      "chunk_id": "...",
      "context_id": "...",
      "score": 0.91,
      "content": "...",
      "enrichment": "...",
      "enrichment_kind": "user_preference",
      "received_at": "2026-11-02T09:14:00Z"
    }
  ],
  "graph": [
    {
      "origin": "query_path",
      "triplets": [
        {
          "source": { "entity_id": "...", "name": "Alex" },
          "relation": { "predicate": "prefers", "context": "...", "relationship_id": "...", "chunk_id": "..." },
          "target": { "entity_id": "...", "name": "dark mode" }
        }
      ],
      "path_summary": "..."
    }
  ],
  "forceful_relations": [
    {
      "via": { "from": "...", "to": "..." },
      "chunk": { "chunk_id": "...", "context_id": "...", "score": 0.0, "content": "..." }
    }
  ],
  "llm_prompt": "...",
  "tabular_data": null
}
```

- `chunks`: what was retrieved, in rank order. `context_id` is the item the chunk came from: cite with it. `score` is the final relevance after reranking. `content` is the original text, and `enrichment` is what HydraDB extracted from it, kept apart (omitted when there is none, as with `enrich: false`). `enrichment_kind` echoes the item's `context_category` label, when it has one. `received_at` is when HydraDB received the item, not its `happened_at`. `temporal[]` (dated facts, each with `content`, `start_date`, `end_date`) appears only when the query used temporal reasoning. `chunk_metadata` appears on rows of a table.
- `graph`: a list of paths. Each has `origin` (`query_path` or `chunk_relation`), `triplets` (each a `source`, a `relation`, and a `target`; every relation names the `chunk_id` it was extracted from), and `path_summary`, the chain as text. Empty, not absent, when `graph_context` is off or nothing was found.
- `forceful_relations`: the chunks reached through deterministic relations, each with `via` naming the relation and the `chunk` itself.
- `llm_prompt`: the whole result rendered as Markdown for a model, ready to use: instructions, numbered results, related facts, and a sources list with each item's title.
- `tabular_data`: the answer to a question over a spreadsheet, as a table, or `null`.

The three lists are always arrays, never `null`. A chunk carries no title or attributes: to show them, look the items up with `POST /context/list` and `ids` (see [List items](#list-items)).

Use `chunks` as the primary LLM context, or `llm_prompt` whole. Preserve server order, which is the ranking; do not re-sort unless you have a deliberate reranking step.

## 9. Turning query results into LLM prompts

- Do not pass raw result JSON to the LLM if token budget matters. Use the SDK formatting helper to produce a compact context string: `build_string(result)` from `hydra_db.helpers` (Python) or `buildString(result)` from `@hydradb/sdk/helpers` (TypeScript). Both return `data.llm_prompt`, which numbers the ranked results and ends with a sources list; ask the model to cite by those numbers.
- Include a grounding instruction: answer only from the provided context, and say when the context is insufficient.
- Start with `max_results: 10`; reduce it for tight context windows.
- Use `graph` paths only when they help the question; each path's `path_summary` is already prose.
- `llm_prompt` already includes the chunks reached through deterministic relations. If you build your own prompt, add `data.forceful_relations[].chunk` yourself.
- For personalized answers, name the shared collection and the user's in `collections`: one result set already merges them.

Python:

```python
import os
from hydra_db import HydraDB
from hydra_db.helpers import build_string
from openai import OpenAI

hydra = HydraDB(token=os.environ["HYDRADB_API_KEY"])
openai = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

question = "How does authentication work?"

result = hydra.query(
    database="your-database",
    collection="your-collection",
    query=question,
    query_by="hybrid",
    max_results=5,
)

context = build_string(result)

messages = [
    {
        "role": "system",
        "content": "Answer using only the provided HydraDB context. If the answer is not in the context, say so. Cite source titles.",
    },
    {
        "role": "user",
        "content": f"{context}\n\nQuestion: {question}",
    },
]
```

TypeScript:


## 10. Metadata guide

### Metadata schema

Declared at `POST /databases`:

```json
{
  "database_metadata_schema": [
    {
      "name": "department",
      "data_type": "VARCHAR",
      "enable_dense_embedding": false,
      "enable_sparse_embedding": false,
      "max_length": 1024
    }
  ]
}
```

Field options:

| Field | Purpose |
|---|---|
| `name` | attribute key; must be valid and non-reserved |
| `data_type` | friendly names like `string`, `integer`, `float`, `boolean`, or backend types like `VARCHAR`, `INT*`, `JSON` |
| `enable_dense_embedding` | semantically embed `VARCHAR` field |
| `enable_sparse_embedding` | BM25 index `VARCHAR` field |
| `max_length` | max string length; default `1024`, maximum `65535`, and it cannot be raised after the field is created |

Schema limits:

- Up to 32 fields and 6 embedding flags per database. Embedding flags are valid only on `VARCHAR` fields.
- Field names are unique, case-insensitively.
- `ARRAY` is not a supported `data_type` and is rejected with `400`. For a multi-value field, store the values as one comma-joined `VARCHAR`.
- Values must match their declared type, and undeclared `attributes` keys are rejected on ingest.

### Where metadata belongs

| Need | Put it in | Filter with |
|---|---|---|
| Hot-path exact filters: department, region, environment, status | `attributes` (`metadata` on a file) | the `attributes` filter on `POST /query` |
| Free-form display/bookkeeping: author, provider IDs, version | `custom_attributes` (`additional_metadata` on a file) | usually not filtered |
| User/workspace partition | `collection` | not metadata |

Rules:

- Plan hot filter fields before the first ingest. `PATCH /databases/{database}/metadata-schema` can add fields later, but cannot rename, retype, or reflag existing ones, and rejects `enable_dense_embedding` / `enable_sparse_embedding` (declare those at database creation). Changing an existing field definition requires a new database and re-ingestion.
- The `attributes` filter reads declared schema fields only. It does not reach `custom_attributes`; to filter on one of those, `metadata_filters.additional_metadata` still works, with bare values or arrays.
- To change attributes on an indexed item, call `PATCH /context/{id}/metadata` (merges keys), or re-ingest with the same `context_id` and `upsert: true`.
- Do not rename attribute keys without re-ingesting the affected items.

## 12. Error handling

### HTTP status codes

| Code | Meaning | Retry? |
|---|---|---|
| `400` | invalid parameters / malformed request | No |
| `401` | missing/invalid API key | No |
| `403` | authenticated but not permitted | No |
| `404` | database or source not found | No |
| `409` | conflict, e.g. existing database or source ID | Usually no |
| `413` | upload too large | No |
| `422` | semantic validation failure, including `TENANT_INFRA_NOT_READY` | Only for `TENANT_INFRA_NOT_READY`, after polling readiness |
| `429` | rate limited | Yes with backoff |
| `500` | internal error | Yes with backoff |
| `502` | upstream dependency error (`BACKEND_ERROR`) | Yes with backoff |
| `503` | temporary unavailability | Yes with backoff |

Retry only `429`, `500`, `502`, and `503`, with bounded exponential backoff and jitter.

The SDKs already retry `408`, `429`, and `5xx` responses twice with exponential backoff before raising, and the Python SDK also retries `409`. Do not wrap SDK calls in a second retry loop: raise the count with `request_options={"max_retries": 5}` on a Python call, or `maxRetries` on the TypeScript client or call.

### Common error codes

| Code | Meaning |
|---|---|
| `INVALID_INPUT` | required, malformed, or conflicting parameter. This is the code for essentially every `400`. Branch on it, not on a generic name |
| `VALIDATION_ERROR` | request shape valid but failed validation |
| `UNAUTHORIZED` | missing/invalid API key |
| `FORBIDDEN` | key lacks access |
| `DATABASE_ALREADY_EXISTS` | duplicate database ID |
| `DATABASE_NOT_FOUND` | database missing/not visible |
| `TENANT_INFRA_NOT_READY` | `422`: the database exists but its infrastructure is still provisioning. This is what querying before polling readiness returns |
| `FILE_NOT_FOUND` | ID not found **in the selected scope**, usually a `collection` mismatch, not a missing source |
| `SOURCE_PROCESSING` | the source is still indexing and cannot serve this request yet |
| `NOT_FOUND` | requested resource does not exist |
| `PARSE_ERROR` | a document could not be parsed |
| `PROCESSING_FAILED` | indexing failed for a source |
| `RATE_LIMITED` | rate limit exceeded |
| `INTERNAL_ERROR` | unexpected server error |
| `BACKEND_ERROR` | `502`: an upstream dependency returned an error |
| `SERVICE_UNAVAILABLE` | dependency unavailable / under load |

There is no `INVALID_PARAMETERS` and no `SOURCE_NOT_FOUND`: no HydraDB response carries either. Match on `INVALID_INPUT` and `FILE_NOT_FOUND`.

SDK errors:

```python
from hydra_db.core.api_error import ApiError

RETRYABLE = (429, 500, 502, 503)

try:
    result = client.query(
        database="acme_corp",
        query="pricing tiers",
    )
except ApiError as exc:
    # 500 and 503 have typed subclasses (InternalServerError,
    # ServiceUnavailableError); 429 does not, so branch on status_code to cover
    # all three uniformly. Back off and retry.
    if exc.status_code not in RETRYABLE:
        raise
```

```ts
import { HydraDBError } from "@hydradb/sdk";

try {
  const result = await client.query({
    database: "acme_corp",
    query: "pricing tiers",
  });
} catch (error) {
  if (error instanceof HydraDBError) {
    const body = error.body as {
      error?: { code?: string };
      meta?: { request_id?: string };
    } | undefined;
    const code = body?.error?.code;
    const requestId = body?.meta?.request_id;
    console.error({ code, requestId });
  }
  throw error;
}
```

## 13. Common integration patterns

Most integrations follow the same architecture:

1. Create a database with a metadata schema for hot filters.
2. Upload shared documents with stable IDs, and connect apps with connectors.
3. Ingest what each user tells your agent as `context` items, in that user's `collection`.
4. Poll status or use webhooks.
5. Query the collections the answer needs. Send no `type`.
6. Pass `llm_prompt` to the model, or build a prompt from `chunks`, `graph`, and `forceful_relations`.
7. Cite items by `context_id` and handle missing context explicitly.

---

## 14. Common mistakes checklist

Each item is a rule stated in full in the section named. Check all of them before you finish.

Section 1, critical rules:

- [ ] Forgetting `API-Version: 2` in raw HTTP calls.
- [ ] Reading a payload from the top level instead of `data`, in raw HTTP or in the SDKs.
- [ ] Writing with one `collection` and reading with another, or omitting `collection` for per-user context.
- [ ] Splitting a company brain into many collections instead of one collection with the `attributes` filter and `acl`.
- [ ] Sending `type`, `memories`, or a split-database example to a unified database.
- [ ] Querying on behalf of a user without `acl`, which returns everything in scope.
- [ ] Turning on a connector's `enforce_acl` behind one shared API key, which runs every query as the key's creator.

Sections 2 to 7, ingestion and lifecycle:

- [ ] Uploading a file with an unsupported extension, such as source code, and polling an ID that was rejected with `E1002`.
- [ ] Writing your own ingestion for an app instead of using a connector.
- [ ] Editing an existing connector resource with `POST /connectors/{id}/resources`, which returns `409` and changes nothing.
- [ ] Querying right after database creation without polling readiness.
- [ ] Querying right after ingestion without polling `context.status` or using webhooks.
- [ ] Treating `processing` or `queued` context as searchable.
- [ ] Not handling `errored` as the failure status.
- [ ] Omitting `collection` on `context.status` and reading the resulting `FILE_NOT_FOUND` as a genuine indexing failure.
- [ ] Using `??` on `errorMessage`, which is `""`, not null, on some failures, so the fallback never fires.
- [ ] Forgetting to verify webhook signatures when a signing secret is configured.

Sections 8 to 10, query and metadata:

- [ ] Filtering on undeclared keys in the `attributes` filter, or expecting it to reach `custom_attributes`.
- [ ] Using `operator` without `query_by: "text"`.
- [ ] Expecting `query_explicit_relations` to work in `mode: "fast"`.
- [ ] Setting `graph_context: false` and expecting `graph` paths.
- [ ] Reading split-database keys (`chunk_content`, `source_title`, `graph_context`) from a unified result; cite from each chunk's `context_id`, and look titles up with `POST /context/list`.
- [ ] Re-sorting chunks before prompting without a deliberate reranker.
- [ ] Passing raw result JSON or too many chunks to the LLM.
- [ ] Putting hot filters in free-form metadata instead of the metadata schema.

### 15.1 Minimal cURL example

The flow from [4. Minimal end-to-end flow](#4-minimal-end-to-end-flow) over raw HTTP:

```bash
export HYDRADB_API_KEY="your_api_key"
DATABASE="agent_docs_demo"
COLLECTION="user_alex"

# 1. Create a database.
curl -s -X POST 'https://api.hydradb.com/databases' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d "{\"database\":\"${DATABASE}\"}"

# 2. Check readiness. Poll this until .data.infra.ready_for_ingestion is true.
curl -s "https://api.hydradb.com/databases/status?database=${DATABASE}" \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" | jq '.data.infra'

# 3. Ingest what Alex said.
INGEST_ID=$(curl -s -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d "{\"database\":\"${DATABASE}\",\"collection\":\"${COLLECTION}\",\"context\":[{\"context_id\":\"alex_pref_001\",\"text\":\"I prefer concise technical answers.\",\"user_name\":\"Alex\"}]}" \
  | jq -r '.data.results[0].id')

# 4. Poll indexing.
curl -s -G 'https://api.hydradb.com/context/status' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "database=${DATABASE}" \
  --data-urlencode "collection=${COLLECTION}" \
  --data-urlencode "ids=${INGEST_ID}" \
  | jq '.data.statuses[0]'

# 5. Search the collection.
curl -s -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d "{\"database\":\"${DATABASE}\",\"collection\":\"${COLLECTION}\",\"query\":\"How should I answer Alex?\",\"query_by\":\"hybrid\",\"mode\":\"thinking\"}" \
  | jq '.data.chunks'
```
