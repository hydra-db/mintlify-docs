Semantic search matches by meaning, so a paraphrase still finds the right text. On its own it misses exact matches, freshness, scope (database isolation and metadata filters), and graph relationships. `POST /query` combines all of these in one call. There is no separate vector-only endpoint.

---

## Semantic, keyword BM25, and graph

- **Semantic:** finds text with similar meaning. Best for natural-language questions, paraphrases, and conceptual lookup.
- **Keyword BM25:** finds text with matching tokens. Best for error codes, identifiers, names, SKUs, and exact phrases.
- **Graph:** finds related entities and relationships. Best for multi-hop questions, dependencies, ownership, and project context.

Metadata filters sit on top of all three. They decide what is allowed to come back.

`POST /query` is the one retrieval endpoint. Two parameters decide what runs:

- **`type`:** what to search. `"knowledge"` (Knowledge), `"memory"` (user-scoped Memories), or `"all"` (both from the same scope, merged and re-ranked together).
- **`query_by`:** how to match. `"hybrid"` (semantic plus BM25, the default) or `"text"` (BM25 only, with `operator: "or" | "and" | "phrase"`, default `"or"`).

`graph_context` adds the graph, and `metadata_filters` sets the scope.

---

## Why pure semantic search breaks

Pure vector search can miss important production constraints:

- Exact identifiers such as `E_AUTH_429` or `payments-worker-v4` may be generalized away.
- A project name can collide with a normal word, like `strawberry` the project vs strawberry the fruit.
- Old and new documents can look equally relevant without recency or metadata signals.
- Different users can need different context for the same query.
- Relationship questions need graph context, not only similar text chunks.

---

## The `alpha` parameter

`alpha` sets the semantic versus BM25 blend when `query_by: "hybrid"`. Higher values lean semantic. Lower values lean BM25. `alpha` is ignored for `query_by: "text"`.

- `1.0`: semantic-heavy. For conceptual questions and paraphrases.
- `0.8`: the default, a semantic-leaning hybrid. For most agent queries.
- `0.5`: balanced. For mixed natural language and exact terms.
- `0.2`: BM25-leaning. For queries with product names, error strings, or IDs.
- `0.0`: BM25-heavy. For debugging exact-match behavior.

Start with the default (`0.8`, which is also what `"auto"` resolves to) and tune from results. If users query for exact IDs and get loosely related content, lower `alpha`. If they ask broad questions and get sparse results, raise it.

## Query request example

<CodeGroup>

```bash cURL
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "acme",
    "collection": "team-mobile",
    "query": "How do we rotate API keys?",
    "type": "knowledge",
    "query_by": "hybrid",
    "max_results": 8,
    "alpha": 0.8,
    "recency_bias": 0.2,
    "graph_context": true,
    "metadata_filters": {
      "project": "phoenix"
    }
  }'
```

```typescript TypeScript SDK
const result = await client.query({
  database: "acme",
  collection: "team-mobile",
  query: "How do we rotate API keys?",
  type: "knowledge",
  queryBy: "hybrid",
  maxResults: 8,
  alpha: 0.8,
  recencyBias: 0.2,
  graphContext: true,
  metadataFilters: { project: "phoenix" },
});
```

```python Python SDK
result = client.query(
    database="acme",
    collection="team-mobile",
    query="How do we rotate API keys?",
    type="knowledge",
    query_by="hybrid",
    max_results=8,
    alpha=0.8,
    recency_bias=0.2,
    graph_context=True,
    metadata_filters={"project": "phoenix"},
)
```

</CodeGroup>

`metadata_filters` are exact constraints. They run before ranking and are checked again on the loaded results. Use them whenever the query has a scope that should not be violated. Top-level keys match `metadata` and take `equals`, `contains`, or `contains_any`. There is no range or fuzzy match. Nest keys under `additional_metadata` to filter free-form per-document fields. See [Metadata](/essentials/v2/metadata).

## Reading the response

`POST /query` returns ranked chunks and source metadata, not an answer. A typical application flow is:

1. Call `POST /query` with the right `type` and `query_by` for the query.
2. Keep the chunks that are relevant enough for your use case.
3. Format `chunk_content`, source titles, and graph context into a prompt.
4. Ask your LLM to answer using only that context.

See [How to Use API Results](/essentials/v2/api-results) for complete context-building examples.
