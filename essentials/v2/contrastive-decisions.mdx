This page is a **controlled experiment lab**, not another Memory-versus-Knowledge flowchart or end-to-end cookbook. HydraDB requests can look nearly identical while producing meaningfully different behavior. Each card below changes **one controlled variable**, asks you to predict the result, reveals the control and variant side by side, shows **live-verified responses**, and ends with an **agent-readable decision record**.

Use this when you already know *which* decision you face and need proof of *what changes*. Use the canonical reference pages and any journey/cookbook guides when you need the full production recipe.

Together the cards cover the core context workflow: Memory vs Knowledge, `infer`, matching ingest/status/retrieve endpoints, how sources are structured, and combining shared knowledge with user-scoped memories.

## The endpoint chain every card uses

The complete context loop is the same for every experiment. Cards change one variable **inside** this chain; they do not invent alternate APIs.

| Step | Endpoint | Role |
| --- | --- | --- |
| 1. Accept work | [`POST /context/ingest`](/api-reference/v2/endpoint/ingest-context) | Returns `202` and source `id`s. Acceptance is not queryability. |
| 2. Wait for readiness | [`GET /context/status`](/api-reference/v2/endpoint/source-status) | Poll until `indexing_status` reaches at least `graph_creation` (queryable) or `completed` when you need full indexing/graph. |
| 3. Inspect (optional) | [`GET /context/inspect`](/api-reference/v2/endpoint/fetch-content) | Read stored `content` / `inferred_content` without running retrieval. |
| 4. Retrieve | [`POST /query`](/api-reference/v2/endpoint/query) | Search with `type: "memory"`, `"knowledge"`, or `"all"`. |

**Demo scope used below:** `database=contrastive_docs_demo`, user collection `reader_001`. Shared company knowledge is written without a user collection (database default) unless a card says otherwise.

## Choose the store you query

Use `type` to choose whether the same query searches per-user Memories or shared Knowledge.

<Accordion title="Predict before you reveal: what changes when type changes?">
  `type: "memory"` searches context scoped to a user or collection. `type: "knowledge"` searches shared documents and app content. The query text and retrieval method can remain identical, but the result comes from a different store.

### Endpoint chain

Seed both stores first (`POST /context/ingest` → `GET /context/status`). This card only changes the query step: `POST /query`.

## Choose whether HydraDB infers a memory

Use `infer` to decide whether HydraDB should extract a useful memory from raw signal or store the input literally.

<Accordion title="Predict before you reveal: what changes when infer changes?">
  `infer: true` asks HydraDB to extract the underlying preference, trait, or fact. `infer: false` stores and indexes the text as written. Keep the raw input identical so the extraction step is the only behavioral variable.

### Endpoint chain

`POST /context/ingest` → `GET /context/status` (wait until queryable) → `GET /context/inspect`. Upsert is enabled by default, so submit the control, inspect it, then submit the variant with the same `id` so only `infer` changes.

### Requests

For a clean probe, use a fresh throwaway database for the pair when possible.

### Inspect each stored result

After the control becomes queryable, inspect it before submitting the variant. Then run the same request again after the variant becomes queryable. [`GET /context/inspect`](/api-reference/v2/endpoint/fetch-content) returns the `content` and `inferred_content` fields compared below.

```bash
curl -G 'https://api.hydradb.com/context/inspect' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "id=preference_probe" \
  --data-urlencode "database=contrastive_docs_demo" \
  --data-urlencode "collection=reader_001" \
  --data-urlencode "mode=content"
```

### Responses

<Info>

</Info>

## Wait for readiness before you query

Successful ingest means HydraDB **accepted** work. It does not mean chunks are searchable yet. This card keeps the query body identical and changes only whether you wait for a queryable status.

<Accordion title="Predict before you reveal: what changes when you skip the status wait?">
  The control fires `POST /query` immediately after `POST /context/ingest` returns. The variant polls [`GET /context/status`](/api-reference/v2/endpoint/source-status) until `indexing_status` reaches at least `graph_creation`, then runs the **same** query. Use a fresh source `id` each run so prior indexing does not poison the control.

### Endpoint chain

`POST /context/ingest` → (control skips wait) / (variant: `GET /context/status`) → `POST /query`

### Ingest once (shared setup)

```bash
PROBE_ID="readiness_probe_$(date +%s)"

curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=memory" \
  -F "database=contrastive_docs_demo" \
  -F "collection=reader_001" \
  -F "memories=[{\"id\":\"${PROBE_ID}\",\"text\":\"Readiness probe: page on-call in #release-ops for SEV-1.\",\"infer\":false}]"
```

### Status poll (variant only)

```bash
curl -G 'https://api.hydradb.com/context/status' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  --data-urlencode "database=contrastive_docs_demo" \
  --data-urlencode "collection=reader_001" \
  --data-urlencode "ids=${PROBE_ID}"
```

Repeat until `indexing_status` is `graph_creation` or `completed` (or terminal `errored`).

### Requests

The query JSON is identical for both arms. Only the readiness gate changes.

**First meaningful difference:** presence of the **new** source `id` (the `PROBE_ID` you just ingested) in `data.chunks` after a queryable status — not a different query body, and not “empty vs non-empty” when older similar memories exist.

**Selection rule:** never treat ingest `202` as searchable. Poll status (or use a webhook) before correctness checks, evals, or user-facing answers that depend on the new content. `graph_creation` is already queryable for normal retrieval; wait for `completed` when you need full graph behavior.

```yaml Agent decision record

control_value: query_immediately_after_ingest
variant_value: query_after_graph_creation_or_completed
effect: newly ingested content is invisible until processing reaches a queryable status
use_control_when: never for correctness checks; only to demonstrate the async race
use_variant_when: any production or evaluation retrieval after ingest
evidence_status: verified-v2-2026-07-21
```

### Also consider: app-extracted sources

When Slack, Notion, tickets, or email are **already extracted** by your app, use `type=knowledge` with `app_knowledge` instead of a raw file upload. Shape follows the [App sources](/essentials/v2/app-sources) contract; a minimal probe:

```bash
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=knowledge" \
  -F "database=contrastive_docs_demo" \
  -F "collection=reader_001" \
  -F "upsert=true" \
  -F 'app_knowledge=[{
    "id": "structure_slack_probe",
    "database": "contrastive_docs_demo",
    "collection": "reader_001",
    "title": "Escalation channel note",
    "type": "slack",
    "kind": "message",
    "provider": "slack",
    "external_id": "1716213600.000100",
    "fields": {
      "kind": "message",
      "body": "Post escalation updates in #release-ops.",
      "author": "reader_bot",
      "thread_id": "1716213600.000100",
      "created_at": "2026-07-21T00:00:00Z"
    },
    "metadata": { "channel": "release-ops" }
  }]'
```

Conversations and user signals still belong in Memory. Shared channels, pages, and runbooks belong in Knowledge (`documents` or `app_knowledge`).

**Selection rule:**

- Pre-extracted Slack / Notion / tickets / email → Knowledge `app_knowledge`

## Combine shared knowledge with user-scoped memories

Personalized answers need company facts and user-specific context together. This card keeps the query text and `collection` fixed and changes only `type` between `memory` and `all`. **Both stores must be written under a scope the query can see.**

<Accordion title="Predict before you reveal: what changes when type is all instead of memory?">
  Seed a company document **and** a user memory under the **same** `collection` (`reader_001`), wait until both are queryable, then compare `type: "memory"` vs `type: "all"`.

### Endpoint chain

Two ingests → status for both ids → `POST /query` with only `type` changed.

### Seed (run once before the pair)

```bash
# Company knowledge co-scoped with the user collection (required for type:all merge)
printf '%s\n' 'Company rule: Post escalation updates in #release-ops.' > /tmp/shared-in-user-scope.txt

curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=knowledge" \
  -F "database=contrastive_docs_demo" \
  -F "collection=reader_001" \
  -F "upsert=true" \
  -F "documents=@/tmp/shared-in-user-scope.txt;type=text/plain;filename=shared-in-user-scope.txt" \
  -F 'document_metadata=[{"id":"combine_knowledge_user_scope","metadata":{"doc_type":"runbook"}}]'

# User-specific memory (same collection)
curl -X POST 'https://api.hydradb.com/context/ingest' \
  -H "Authorization: Bearer $HYDRA_DB_API_KEY" \
  -H "API-Version: 2" \
  -F "type=memory" \
  -F "database=contrastive_docs_demo" \
  -F "collection=reader_001" \
  -F 'memories=[{
    "id": "combine_memory_probe",
    "text": "Reader prefers escalation updates as a single Slack message, not a thread.",
    "infer": false
  }]'
```

Poll status for both ids until each is queryable.

<Info>

**First meaningful difference:** which stores appear in `data.chunks` (`source_type` / source ids). Control is memory-only; variant includes `document` knowledge when co-scoped.

**Selection rule:**

- User-only personalization → `type: "memory"` with the user's `collection`
- Company-only RAG → `type: "knowledge"` with the shared write scope (often the database default collection)
- Personalized grounded answers → `type: "all"` **and** ensure every store you need is written under a scope the query can see
- **Scoping footgun (live-verified):** knowledge written only on the database default collection did **not** appear under `type: "all"` + a different user `collection`. Co-scope knowledge with that collection for the merge to work, **or** plan an explicit multi-scope `collections` query — do not assume `type: "all"` alone reaches every collection
- Always write memories with the same collection you query for that user
- Do not permanently park company-wide runbooks only under one user's collection if every user needs them; choose write scope based on who must read them later ([Multi-tenant](/essentials/v2/multi-tenant))

## Read the evidence safely

- Treat result ordering and absolute relevance scores as run-specific noise.
- Treat inferred wording as nondeterministic; compare whether meaning was extracted, not the exact sentence.
- Compare only the field or content difference named by the card.
- `type` selects which store is searched; isolation still depends on database, collection, and authorization.
- Wait until ingestion reaches a queryable status before comparing results — except on the readiness card, where that wait is the variable.
- On the structure card, compare `source_type` and scope, not prose formatting.
- On the combine card, compare which stores and source ids appear. If `type: "all"` is missing knowledge, check whether knowledge was written under a different collection than the query.
