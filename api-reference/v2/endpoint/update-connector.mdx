Updates a connector's instructions, sync interval, credentials, or ACL enforcement. Omitted fields keep their existing values.

<RequestExample>

```python Python SDK
client.connectors.update(
    "{connector_id}",
    custom_instructions=(
        "Aurora was renamed to Nimbus in January 2025; they are the same product. "
        "Index all Aurora content under Nimbus."
    ),
    sync_interval_seconds=3600,
)
```

```typescript TypeScript SDK
await client.connectors.update({
  id: "{connector_id}",
  customInstructions:
    "Aurora was renamed to Nimbus in January 2025; they are the same product. " +
    "Index all Aurora content under Nimbus.",
  syncIntervalSeconds: 3600,
});
```

```bash cURL
curl -X PATCH 'https://api.hydradb.com/connectors/{id}' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "custom_instructions": "Aurora was renamed to Nimbus in January 2025; they are the same product. Index all Aurora content under Nimbus.",
    "sync_interval_seconds": 3600
  }'
```

</RequestExample>

<ResponseExample>

```json 200
{
  "connector_id": "{connector_id}",
  "sync_interval_seconds": 3600,
  "enforce_acl": false,
  "next_sync_at": "2026-06-01T13:00:00Z",
  "min_sync_interval_seconds": 300,
  "max_sync_interval_seconds": 604800,
  "custom_instructions_updated": true
}
```

</ResponseExample>

`custom_instructions_updated` and `credentials_updated` are present when the request changed those fields. Sending `{}` changes nothing and returns the current interval and the allowed range.

HydraDB validates every field before saving, so invalid input changes nothing. Credentials are saved before other settings: if a server error occurs afterward, only the credentials may have changed, and retrying the same request is safe.

- `custom_instructions` applies to resources without their own instructions. Send `""` to clear it. Changes affect future syncs. See [Custom ingestion instructions](/essentials/v2/connectors#custom-ingestion-instructions).
- `sync_interval_seconds` reschedules the next sync. Stay within the returned `min_sync_interval_seconds` and `max_sync_interval_seconds`, or send `0` for the provider default.
- `credentials` reconnects the existing connector. Send the provider's complete credential set. Resources and saved sync positions are preserved.
- `enforce_acl` enables or disables ACL enforcement for this connector. Send `true` to enforce the captured ACL for the authenticated caller on every content read, or `false` to return to opt-in request `acl` filtering. Existing connectors remain `false` until an owner or writer enables it. The change takes effect on the next content request for already-synced sources and does not require re-ingestion. Only workspace owners and writers in a signed-in dashboard session can set it, and `true` requires the provider to report `acl_supported: true`. API-key-authenticated requests cannot set it. See [ACL on synced content](/essentials/v2/connectors#enforce-acl) and [Query](/essentials/v2/query#6-query-on-behalf-of-a-user).

To enable enforcement later, send this field in a `PATCH` request, or use **Enforce ACL** in the dashboard's connector settings:

```json
{
  "enforce_acl": true
}
```

A connector's `name`, `database`, `collection`, and `provider_account_scope` cannot be changed after creation. Omit them from the request; unsupported fields can cause a `400` response.

## Errors

- `400`: the request includes an unsupported field, the provider does not report `acl_supported` for `enforce_acl: true`, `custom_instructions` is over 4,000 characters, or `sync_interval_seconds` is outside the provider's range. Nothing is changed.
- `403`: the request tries to set `enforce_acl` without a signed-in dashboard session for a workspace owner or writer. The ACL authorization error message is `only workspace owners and writers can change ACL enforcement`.
- `404`: no connector with this id in your organization.
- `422`: `credentials` does not match the provider's `credential_schema`.
- `503`: HydraDB could not read its provider catalog to check `acl_supported` for `enforce_acl: true`. Nothing is changed. Retry the request.
