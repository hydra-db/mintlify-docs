Every query makes three choices. All fields are on [Query](/api-reference/v2/endpoint/query).

- **`type`:** what to read. `knowledge` for shared docs and app sources, `memory` for user context, or `all` for both.
- **`query_by`:** how to match. `hybrid` (default) for the best overall relevance, or `text` for an exact term or phrase.
- **`mode`:** how much work to spend. `fast` for low latency, `thinking` to expand the query, rerank, and include forceful-relation context, or `auto` (the default), which picks `fast` or `thinking` and chooses `thinking` when it cannot tell. `thinking` always includes graph context.

## Parameters that matter

| Parameter | Values | Use it for |
|---|---|---|
| <Field name="max_results" /> | integer | Prompt size. Default `10`, maximum `250`. Lower it for tight context windows; raise it only when you rerank or summarize downstream. |
| <Field name="alpha" /> | `0.0` to `1.0`, or `"auto"` | Hybrid balance. Lower favors BM25 keywords; higher favors semantic similarity. Default `0.8`, which `"auto"` also resolves to. |
| <Field name="metadata_filters" /> | object | Narrow candidates before ranking. Top-level keys match `metadata`; nested `additional_metadata` matches free-form per-source fields. |
| <Field name="collections" /> | `string[]` or weighted object | Query several user, workspace, or team scopes. A list uses equal weights; an object like `{ "workspace_42": 2, "user_alex": 1 }` sets relative weights with at most one decimal place. Max 100 collections, and each must exist. |
| <Field name="graph_context" /> | boolean | Entity and relation context with the chunks. On by default. Set `false` with `mode: "fast"` for chunk-only responses; `thinking` always includes it. |
| <Field name="query_apps" /> | boolean | App-aware retrieval on top of the full selected knowledge scope, not a restriction to app sources. On by default for knowledge queries; send `false` to turn it off. |

Planning filters? Read [Metadata](/essentials/v2/metadata) before you create the database schema.
</Tip>

## Recommended configurations

- **Fast document RAG:** `type="knowledge"`, `query_by="hybrid"`, `mode="fast"`, `max_results=5-10`, `graph_context=false`.
- **Highest-quality document RAG:** `type="knowledge"`, `query_by="hybrid"`, `mode="thinking"`, `graph_context=true`, `alpha="auto"`.
- **Personalized answer:** `type="all"`, include `collection`, `query_by="hybrid"`, `mode="thinking"`.
- **User preferences only:** `type="memory"`, include `collection`, `query_by="hybrid"`.
- **Exact keyword or phrase:** `type="knowledge"`, `query_by="text"`, `operator="phrase"`.
- **Recent operational updates:** `query_by="hybrid"`, `recency_bias=0.2-0.4`, and a filter for the right document type.
- **Mixed or unpredictable query complexity:** `query_by="hybrid"`, `mode="auto"`.

## Typical patterns

<AccordionGroup>
  <Accordion title="Document Q&A from shared knowledge" defaultOpen>

Standard RAG over docs, PDFs, tickets, pages, or app sources.

```json
{
  "database": "acme",
  "query": "What is our refund policy?",
  "type": "knowledge",
  "query_by": "hybrid",
  "mode": "thinking",
  "max_results": 10,
  "graph_context": true
}
```

  </Accordion>

  <Accordion title="Personalized answer with memories">

Combine shared knowledge with user-specific context. Pass the same `collection` you used at memory ingestion.

```json
{
  "database": "acme",
  "collection": "user_alex",
  "query": "What is our refund policy, and how should I explain it to this user?",
  "type": "all",
  "query_by": "hybrid",
  "mode": "thinking"
}
```

  </Accordion>

  <Accordion title="Fan out across teams, workspaces, or users">

Search several collection scopes and get one globally ranked result set. Use a list for equal weighting, or an object to weight one scope more.

```json
{
  "database": "acme",
  "collections": {
    "workspace_42": 2,
    "user_alex": 1
  },
  "query": "What renewal risks should we discuss?",
  "type": "all",
  "query_by": "hybrid",
  "mode": "thinking"
}
```

  </Accordion>

  <Accordion title="Filtered query for a specific slice">

Use `metadata_filters` when you know the slice you want. Top-level keys match schema-backed `metadata` fields declared in `database_metadata_schema`. Free-form fields go under `additional_metadata` (legacy alias `document_metadata`). Separate keys are ANDed. For the `equals`, `contains`, and `contains_any` operators, see [Filters](/api-reference/v2/endpoint/query#decision-matrix).

```json
{
  "database": "acme",
  "query": "What launch constraints apply to enterprise customers?",
  "type": "knowledge",
  "query_by": "hybrid",
  "metadata_filters": {
    "department": "product",
    "additional_metadata": {
      "source": "launch_plan"
    }
  }
}
```

  </Accordion>

  <Accordion title="Exact phrase lookup">

Use `text` when literal wording matters: legal clauses, SKUs, error codes, IDs, or compliance references.

```json
{
  "database": "acme",
  "query": "GDPR Article 17",
  "type": "knowledge",
  "query_by": "text",
  "operator": "phrase"
}
```

  </Accordion>
</AccordionGroup>

## Response summary

`POST /query` returns ranked `data.chunks[]`, deduplicated `data.sources[]`, optional `data.graph_context`, and optional `data.additional_context` from forceful relations. Keep the `data.chunks[]` order when building prompts; it is already ranked. For prompt formatting and citations, see [How to Use API Results](/essentials/v2/api-results).
