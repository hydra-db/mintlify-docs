The GitHub connector reads the repositories you select. Each issue and each pull request becomes one document that carries its body and its whole discussion: conversation comments and, for a pull request, review comments and review summaries.

Issues and pull requests are linked to the issues they reference or close, to their parent issue, and to the Linear issues, Slack messages and Notion pages they link to.

## Before you connect

GitHub uses a personal access token. A classic token needs `repo`, or `public_repo` for public repositories only. A fine-grained token works with the access GitHub grants it.

**Credentials**

<ResponseField name="access_token" type="secret string" required>
A GitHub personal access token with read access to repositories and issues.
</ResponseField>

**Scopes for a classic token**

- `public_repo`: public repositories only. Use this or `repo`.
- `repo`: private and public repositories. Reading a private repository's collaborators for permissions also needs it.
- `read:org`: reads which organization teams can access a repository, for permissions. If GitHub refuses it, the connector raises a permission warning.

HydraDB checks for `repo` or `public_repo` only when GitHub reports the token's scopes. Fine-grained tokens may not report them.

**Set it up**

<Steps>
  <Step title="Create a token">
    In GitHub, create a personal access token with `repo`, or `public_repo` for public repositories only. Add `read:org` if you want organization team access captured.
  </Step>
  <Step title="Create the connector">
    Paste the token as `access_token`.
  </Step>
  <Step title="Select repositories">
    Discover lists every repository the token's user owns, collaborates on, or can see as an organization member. Select the repositories to sync.
  </Step>
</Steps>

Use provider `github` with [Create Connector](/api-reference/v2/endpoint/create-connector). Then call [Discover Connector Resources](/api-reference/v2/endpoint/discover-connector-resources) to list what the credentials can reach, and [Configure Connector](/api-reference/v2/endpoint/configure-connector) to choose what to sync.

Create one connector per account, each with that account's own credentials. GitHub rate limits apply per token, so a large first sync can use up the hourly quota. That is why the first sync is bounded.

To connect several GitHub accounts, give each connector its own `provider_account_scope`, for example `github-account-a` and `github-account-b`. Both are caller-provided example identifiers. HydraDB stores the value as given and does not check it against GitHub's own account ids. Two connectors that share a scope and write to the same collection can overwrite each other's items. See [several accounts from one provider](/essentials/v2/connectors#6-connect-several-accounts-from-one-provider).

## What gets synced

**What the labels mean**

- **Title:** names the item in results.
- **Searchable:** part of the text a query matches.
- **Date:** the time HydraDB uses for recency.
- **Filter:** a key a query can filter on, typed exactly as shown.
- **Link:** connects this item to another item.
- **Person or group in the graph:** a person or group the knowledge graph attaches the item to.
- **Access:** decides who can read the item.
- **Stored with results:** kept on the document, and shown when you open or inspect it. A search does not match it.
- **Not kept:** the provider has it, and HydraDB does not keep it.

### Issues and pull requests

- **One document:** One issue or one pull request, with its whole discussion inside it.
- **Title:** The issue or pull request title.
- **Text:** The body. Each comment, review comment and review summary is added as its own searchable part of the item, with its author and time, and for a review comment the file, line and the comment it replies to. Empty comments are skipped. Labels are written as a `Labels` line, the creation time as a `Created` line, and a sub-issue's parent as a `Parent` line.
- **Date:** When the issue or pull request was last updated.
- **Link back:** The issue or pull request page on GitHub.
- **Files:** Images and files in bodies and comments are not downloaded.

## How it fits into the graph

**What each item becomes**

- Issues and pull requests: a ticket, an issue, task or support ticket, with its workflow and ownership details.

**Connections GitHub creates**

- A sub-issue to its parent issue.
- An issue or pull request to each issue or pull request it references in its body or discussion.
- A pull request to each issue its body closes with a closing keyword.
- An issue or pull request to a Linear issue it links to, or names after a closing word.
- An issue or pull request to a Slack message or Notion page it links to.
- In the other direction, Linear issues link to the GitHub pull requests attached to them.
- References inside code blocks, inline code and HTML comments are ignored.

**People and groups it names**

- The author of each comment, as a commenter.
- Each `@username` mentioned in the body.
- The person who opened the item and its assignees are not declared as people.

**What HydraDB reads from the text**

The body and discussion text: topics, decisions, and people and projects named in prose.

There is no per-connector setup for this. Every connector maps its items onto the same shared model, and HydraDB finds people, organizations, projects, products and other entities in the text the same way for every source. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Permissions

This connector can carry GitHub permissions into search.

- **Who can read an item:** Access follows the repository, not the single issue. A public or internal repository can be read by everyone in your HydraDB tenant unless you set an access rule. A private repository can be read by its collaborators and by the organization teams that have access to it.
- **How a person is identified:** The email address on a collaborator's public GitHub profile. Teams are added as groups.
- **When permissions cannot be read:** If a collaborator hides their profile email, the collaborator list is incomplete, there are too many people to express, or GitHub refuses a request, the connector raises a permission warning. An access rule you set on the repository stays in force. Without a rule, depending on your deployment's setting, the repository's items are either readable by everyone or hidden until permissions can be read.

- One collaborator with a hidden public email stops HydraDB from capturing a private repository's audience. Set an access rule on such a repository.
- Internal repositories are open to everyone in your HydraDB tenant. Check that this matches who should see them.

Captured permissions filter search only when **Enforce ACL** is on for the connector. Only a signed-in human workspace owner or writer can turn it on, in the dashboard connector settings. API-key requests must omit `enforce_acl`, including `false`. See [Enforce ACL](/essentials/v2/connectors#enforce-acl). You can also [set your own rule on a resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).

Database and collection names decide where content lands; collection names do not authorize access.

## Keeping in sync

- **First sync:** Reaches back 30 days by default, set by `lookback_days`. The window is measured from the repository's most recent activity, not from today, so a quiet repository still brings in its last stretch of work.
- **New and changed items:** Each sync asks GitHub for items updated since the last sync. A changed item is sent again with its whole discussion.
- **Edits:** Editing an issue or pull request, or adding a comment, moves its updated time, so the whole item is sent again.
- **Deletions:** Deleted issues and pull requests are not removed. An item that disappears from GitHub can stay searchable in HydraDB.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` to change it.

## Not synced

- Code, commits and diffs.
- Releases, wikis, projects and GitHub Discussions.
- Images and files attached in bodies and comments.
- Repositories the token's user cannot see.

## Questions this lets you answer

- What was decided in the discussion on the pull request that added rate limiting?
- Which pull request fixed issue `acme/api#412`?
- Which issues in `acme/api` are labelled bug and mention the login timeout?
- Which Linear issue does this pull request close?
- What did reviewers say about the caching change in `acme/web`?

## Good to know

- **Who opened or owns an item is not searchable.** The opener, the assignees and whether the item is open are stored on it, but a query does not match them.
- **Comments arrive inside their issue or pull request.** Each comment is part of its issue or pull request, so a result is the whole item, not a single comment.
