Use the Datadog connector to bring the following content into HydraDB.

## What syncs

The provider description lists these indexed object types:

- `aggregate_logs`
- `metric_response_time`
- `slo_history_us_prod`
- `slo_history_eu_prod`
- `slo_history_ca_prod`
- `monitors`
- `dashboards`
- `slos`
- `notebooks`
- `incidents`

## Connect

1. Datadog needs TWO keys and they do different jobs. Create an API key under Organization Settings → API Keys, and an application key under Organization Settings → Application Keys. The API key identifies the org; the application key carries the scopes, so it is the one that decides what syncs.
2. An application key is created UNSCOPED and the create dialog has no scope picker; the key list will show it as "Not Scoped", meaning it inherits everything its owner can do. You have to open the key afterwards and Edit it to apply scopes, so a key made the obvious way is a full-permission key.
3. Grant exactly these and nothing more: timeseries_query, slos_read, logs_read_data, monitors_read, dashboards_read, notebooks_read and incident_read. Datadog's own description of logs_read_data claims reading logs also needs "Logs Read Index Data"; tested against a live org it does not, so do not grant the extra one.
4. A missing scope does not fail loudly. Datadog answers an unauthorized request with a bare 403 that names no permission, an unknown metric with a 200 and an empty series, and a log query against an org with no indexes with "No valid indexes specified"; so an under-scoped key looks exactly like an empty account.
5. Both keys are site-specific. If your org is not on US1, set the site field (for example us5.datadoghq.com or datadoghq.eu) or every call fails against the wrong region.
6. Datadog has nothing to browse, so the resource step offers a single "All data" row; select it to continue. It syncs the whole org: monitors are indexed with their message text, which is where runbooks live, along with dashboards, SLO definitions, notebooks and declared incidents.
7. Incidents Datadog marks PRIVATE are indexed too, and their restriction is carried over: Datadog scopes a private incident to its participants, and we record it as visible to nobody, so an access-scoped search never returns it. Each indexed incident also records its own visibility in its text, so you can tell which is which.
8. That mirroring only takes effect once access-scoped search is enabled for this connector on our side, which is a per-provider setting rather than something the scopes control. Until it is on, a private incident behaves the way it did before and is searchable by everyone in your HydraDB tenant. Ask us to turn it on, or skip just the incident_read scope if that trade is not acceptable: every other stream syncs without it.
9. The metric query, log query and SLO id fields are optional additions, each selecting one extra time series to index. Leaving them blank costs you those series and nothing else; everything above syncs without them.

Use provider `datadog` with [Create Connector](/api-reference/v2/endpoint/create-connector), then [discover resources](/api-reference/v2/endpoint/discover-connector-resources) and [configure the resources](/api-reference/v2/endpoint/configure-connector) you want to sync. The [provider description](/api-reference/v2/endpoint/list-connector-providers) supplies the credential fields for your deployment.

## Common mistakes

- A provider page describes indexed content, not the access granted to your credentials. Select resources the connected account can read.
- Synced content is not automatically private to each person. Review [ACL enforcement](/essentials/v2/connectors#enforce-acl) and set resource access rules where needed.
