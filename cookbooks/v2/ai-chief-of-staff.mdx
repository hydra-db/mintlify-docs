Build an AI Chief of Staff: an AI version of n8n that takes actions across your apps instead of only answering questions. Any agent asks HydraDB _"What should I do next?"_ and gets back the function to run, which your execution layer calls with the right parameters.

> This 20-minute page covers the core concepts and TypeScript patterns. For the full version (Python SDK, multi-step planning, policy engine, approval workflows, observability, and benchmarks), see the [complete AI Chief of Staff cookbook](/cookbooks/v2/hydradb-cookbook-06).

## Prerequisites

- Base URL: `https://api.hydradb.com`
- A HydraDB API key from [app.hydradb.com](https://app.hydradb.com), exported as `HYDRA_DB_API_KEY`
- Node.js 18 or later (`node --version`)
- `npm install @hydradb/sdk`
- TypeScript basics and environment variables

## How the split works

Your agent talks to the user; HydraDB finds the function. Instead of hardcoding an if-then tree, you ingest each function (Slack, Calendar, Jira) as knowledge, and a query returns the best matches for the task, ranked.

The agent asks:

> _"The user wants to 'prepare for tomorrow's client meeting'. What should I do?"_

Your agent turns the matching functions into steps: check the calendar, pull recent threads with the client, draft briefing notes from the CRM, book the room, and send the agenda. A different user can get a different order, based on their role and memories from earlier runs.

The three parts:

- **Action Orchestrator:** your runtime. It runs HydraDB's suggestions and holds the policy engine, retries and logging, the auth vault, and a function cache.
- **HydraDB:** stores the **function definitions** and ranks them against the task, so your agent knows _which_ function (if any) solves it.
- **Workspace Apps:** anything with an API, such as CRM, calendar, ticketing, or HRIS.

## How HydraDB features enable this

### AI Memories for function learning

Memories record which functions a user picks for which tasks, and personalize later suggestions with no manual training. A query reads them only with `type: "memory"` or `type: "all"`; the default, `type: "knowledge"`, reads the function definitions alone.

**Example:** Sarah prefers Slack over email for urgent updates. After a few runs, HydraDB suggests `send_slack_message` instead of `send_email` for her.

Run outcomes fed back as memories (Step 2) capture how your organization works: marketing requests that need design review, deployment approval chains, escalation paths per account tier, functions that run well together (such as `gather_data`, then `generate_report`, then `schedule_review_meeting`), and functions that fail in certain contexts.

### Multi-step reasoning for complex workflows

A business process needs a sequence. _"Onboard the new hire"_ means creating accounts, sending welcome materials, scheduling orientation, requesting equipment, and notifying the team. Your agent makes one query for the candidate functions, then has its LLM put them in dependency order (see Step 4).

### Multi-tenant function isolation

Put each team's functions in its own collection, so the sales agent sees only sales functions and the engineering agent sees deployment and monitoring functions. With fewer options in scope, the top suggestion is also more likely to be right.

## Step 1: Define and register functions

### 1.1 Function schema

HydraDB treats each callable as a **knowledge object**. The minimal schema:


```jsonc
{
  "id": "send_slack_message",
  "name": "Send a Slack message",
  "description": "Posts a message to a Slack channel on behalf of the user.",
  "parameters": {
    "type": "object",
    "properties": {
      "channel": {"type": "string", "description": "#channel or userId"},
      "text":    {"type": "string", "description": "Message body"},
      "thread_ts": {"type": "string", "description": "Optional thread"}
    },
    "required": ["channel", "text"]
  },
  "auth": {
    "oauth_provider": "slack",
    "scopes": ["chat:write"]
  }
}
```


### 1.2 Upload to HydraDB

Call `/context/ingest` with `app_knowledge` to register each function as a knowledge object.


```ts
import { HydraDBClient } from "@hydradb/sdk";

const client = new HydraDBClient({ token: process.env.HYDRA_DB_API_KEY });

await client.context.ingest({
  database: "your_database",
  collection: "your_collection",
  appKnowledge: JSON.stringify([
    {
      id: "send_slack_message",
      title: "Send a Slack message",
      type: "slack",
      timestamp: new Date().toISOString(),
      content: { text: JSON.stringify(schema) },
      additional_metadata: { permissions: ["workspace_admins"], tags: ["automation", "slack"] }
    }
  ])
});
```


> **Tip:** Write function **descriptions** in plain language, focused on the goal. HydraDB matches tasks against them.

### 1.3 Versioning and deprecation

Store new versions with `id: functionName_v2`. Give every function a `deprecated` field in its `metadata`, set it to `true` on old versions, and query with `metadata_filters: { "deprecated": false }` so old versions stop coming back. Declare `deprecated` in the database metadata schema first, because only declared fields filter.

## Step 2: Build the Action Orchestrator

The orchestrator queries with `mode: "thinking"`, runs the top-ranked function, and stores the result as a memory with `infer: true` so HydraDB extracts what worked.


```ts
import { HydraDBClient } from "@hydradb/sdk";

class Orchestrator {
  private client: HydraDBClient;
  private registry: Map<string, Function>;

  constructor(client: HydraDBClient, registry: Map<string, Function>) {
    this.client = client;
    this.registry = registry;
  }

  async handleTask(task: string, userContext: { database: string; collection: string }) {
    // 1️⃣ Ask HydraDB which function best matches the task
    const result = await this.client.query({
      database: userContext.database,
      collection: userContext.collection,
      query: task,
      mode: "thinking",
      maxResults: 5
    });

    if (!result.data?.chunks || result.data.chunks.length === 0) return { status: "noop" };

    // 2️⃣ Use the top-ranked chunk to identify and execute the function
    const topChunk = result.data.chunks[0];
    const functionId = topChunk.id;
    const exec = this.registry.get(functionId);
    if (!exec) return { status: "noop" };
    const execResult = await exec(topChunk);

    // 3️⃣ Optional: feed result back to HydraDB as a user memory
    await this.client.context.ingest({
      type: 'memory',
      database: userContext.database,
      collection: userContext.collection,
      upsert: true,
      memories: JSON.stringify([
        {
          id: `exec_${functionId}_${Date.now()}`,
          text: `Executed function "${functionId}" for task: "${task}". Result: ${summarize(execResult)}`,
          infer: true
        }
      ])
    });

    return { status: "done", result: execResult };
  }
}
```

## Step 3: Event and trigger model

Write a thin wrapper per event source that forwards a _natural-language_ description of the event to the orchestrator:

1. **Direct commands:** "Book me a 30-min call with Alice next week."
2. **Scheduled jobs:** a daily stand-up summary at 9 AM.
3. **System events:** a new Jira ticket triggers triage.


```bash
# Slack slash-command → cloud-function

```

## Step 4: Planning and multi-step execution

"Ship newsletter" needs **several** calls: get the subscribers, email each one, then return a summary.

1. **Plan generation:** ask HydraDB to "return a JSON array of functions to execute sequentially."
2. **Dependency resolution:** pass the outputs of earlier steps into later ones.
3. **Rollback or compensation:** if step n fails, undo steps 1 to n-1.

## How function matching works

Your function library lives in HydraDB's **knowledge base**, so selection matches on meaning, not only keywords. _"I need to tell the team about the delay"_ can map to:

- `send_slack_announcement` for immediate updates
- `update_project_timeline` for formal documentation
- `schedule_team_meeting` for complex discussions
- `send_client_notification` if external communication is needed

To also match similar past requests and the functions that worked for them, query with `type: "all"`. It reads the function definitions and the Step 2 run memories in the same collection and ranks them together.

### Function metadata

Store each function's constraints in its `metadata` at ingest:


```jsonc
{
  "id": "approve_expense",
  "metadata": {
    "department": "finance",
    "permission_level": "manager",
    "cost_threshold": 1000,
    "business_hours_only": true
  }
}
```


Declare `department` and `permission_level` in the database metadata schema and filter on them with `metadata_filters`, so a finance manager gets only the functions they may run. Filters are exact matches with no ranges, so check `cost_threshold` and `business_hours_only` in your orchestrator. See [Metadata](/essentials/v2/metadata).

## Step 5: Security, auth, and governance

- **OAuth vault:** store per-user tokens. The orchestrator injects the right token at runtime.
- **Policy engine:** block _"delete all records"_ unless the requester is in `admins`.
- **Approval workflow:** route risky actions through a Slack message with "Approve" and "Reject".
- **Audit log:** keep each task, the function chosen, and its result, for compliance.

---

## Step 6: Observability and self-improvement

Track these metrics:

- **Suggested-to-executed ratio:** a high ratio means HydraDB returns the right function.
- **Average time to completion:** spots slow external APIs.
- **Rollback frequency:** detects unstable functions.

Feed them back as memories to tune later suggestions:


```ts
await client.context.ingest({
  type: 'memory',
  database: "your_database",
  collection: "your_collection",
  upsert: true,
  memories: JSON.stringify([
    {
      id: "metrics_calendar_event",
      text: 'Function "create_calendar_event" had slow_response signal with p95 of 2500ms.',
      infer: true
    }
  ])
});
```

## Real-world applications

### Customer success automation

A support ticket asks for a feature demo, which a support agent would otherwise coordinate by hand. Your agent tells HydraDB _"Customer Jane from Acme Corp wants a demo of our new reporting feature."_ HydraDB suggests:

1. `check_customer_tier`: picks the right demo level
2. `find_available_demo_slots`: checks the AE's calendar
3. `create_demo_meeting`: books the event with a Zoom link
4. `update_crm_opportunity`: logs the request and the date
5. `send_confirmation_email`: sends the customer the details

One request triggers all five, and each step uses Jane's account context.

### DevOps incident response

A monitoring alert fires: _"Database response time degraded"_. Based on severity, time of day, and past incidents, HydraDB might suggest:

**During business hours:**

1. `create_incident_ticket`: log it in the tracker
2. `notify_oncall_engineer`: alert through PagerDuty
3. `scale_database_resources`: try auto-remediation
4. `post_status_update`: inform stakeholders

**Off-hours, for minor issues:**

1. `log_incident_details`: document it for the morning review
2. `monitor_for_escalation`: set up closer alerting
3. `schedule_followup_review`: add it to the next standup

## Best practices

- Write **precise descriptions**, and mention side effects.
- Group functions into **collections** (`billing`, `hr`, `sales`).
- Start **read-only** (analytics) before you enable writes.
- Use **idempotent** APIs, or retry with backoff.
- Keep a **simulated staging** workspace for testing.
- Feed execution results back to HydraDB so selection **improves**.
