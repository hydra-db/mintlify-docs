Imagine your AI at the center of a web of information and it can keep crawling the web gathers all relevant information.

This is where the real magic happens. Agents perform better searches with graphs i.e. you notice agents asking less up front, while consistently delivering accurate work that is verifiable with citations across sources.

## Running a query

The following sample request searches the `acme_corp` database.

<Accordion title="Run a query: Python, TypeScript, or cURL">
  Set up your [SDK client](/api-reference/v2/sdks#client-setup) before running the Python or TypeScript example.

  <CodeGroup>

  ```python Python SDK
  result = client.query(
      database="acme_corp",
      collection="company_docs",
      query="How do I rotate API keys?",
      mode="thinking",
      max_results=10,
  )
  
  for chunk in result.data.chunks:
      print(chunk.source_title, chunk.chunk_content)
  ```

  ```typescript TypeScript SDK
  const result = await client.query({
    database: "acme_corp",
    collection: "company_docs",
    query: "How do I rotate API keys?",
    maxResults: 5,
  });
  
  if (!result.data || typeof result.data === "string") throw new Error("Expected structured query results");
  for (const chunk of result.data.chunks ?? []) {
    console.log(chunk.sourceTitle, chunk.chunkContent);
  }
  ```

  ```bash cURL
  curl -X POST 'https://api.hydradb.com/query' \
    -H "Authorization: Bearer $HYDRADB_API_KEY" \
    -H "API-Version: 2" \
    -H "Content-Type: application/json" \
    -d '{
      "database": "acme_corp",
      "collection": "company_docs",
      "query": "How do I rotate API keys?",
      "max_results": 5
    }'
  ```

  </CodeGroup>

### What comes back

- `data.llm_prompt`**:** the query and the entire response to the query in one markdown file, complete with citations, that your agents can easily read.
- `data.chunks`**:** the matching chunks from the graph, ranked by relevance, each with its source `id`, `chunk_content`, `source_title`, `relevancy_score`, and `metadata`.
- **`data.graph_context`** and **`data.additional_graph_context`:** extracted relationships and deterministically linked sources, covered in [section 5](#5-understanding-relationships-in-your-context).
- `data.tabular_data`**:** `null` for a document question. Present in thinking mode when the collection holds spreadsheets and the question is about them: a computed answer (`status: "ok"`) with `columns`, `records`, `sources` and `citations`, or a decline (`status: "not_applicable"`) when the question is not about the tables. See [Ask questions over spreadsheets](#ask-questions-over-spreadsheets).

### Ask questions over spreadsheets

When a collection holds CSV, TSV or Excel files (see [Spreadsheets become queryable tables](/essentials/v2/context#spreadsheets-become-queryable-tables)), a question in `"mode": "thinking"` that needs filtering, grouping or arithmetic over the rows is answered by SQL that HydraDB writes and runs over the complete table. Ask in plain language: "total revenue per region, highest first", "how many units of Gizmo were sold in Mumbai and Pune", "which regions beat their target". Set `include_table_sql: true` to get the statement back.

```bash cURL
curl -X POST 'https://api.hydradb.com/query' \
  -H "Authorization: Bearer $HYDRADB_API_KEY" \
  -H "API-Version: 2" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "your-database",
    "collection": "sales",
    "query": "What is the total revenue per region, highest first?",
    "mode": "thinking",
    "include_table_sql": true,
    "response_format": "structured"
  }'
```

What comes back in `data.tabular_data`:

```json
{
  "status": "ok",
  "answer_type": "computed",
  "sql": "SELECT \"region\", SUM(\"revenue\") AS \"total_revenue\" FROM \"table_1fda2c6d06a92aa70abaf1df\" GROUP BY \"region\" ORDER BY \"total_revenue\" DESC",
  "columns": [
    { "name": "region", "type": "VARCHAR", "kind": "string" },
    { "name": "total_revenue", "type": "HUGEINT", "kind": "integer" }
  ],
  "records": [
    { "region": "East", "total_revenue": 97500 },
    { "region": "West", "total_revenue": 85860 },
    { "region": "North", "total_revenue": 56470 },
    { "region": "South", "total_revenue": 37815 }
  ],
  "truncated": false,
  "sources": [
    { "id": "sales_2026", "title": "sales_2026.csv", "collection": "sales", "version": "9181604be39c" }
  ],
  "citations": {
    "rows": [{ "chunk_id": "sales_2026_chunk_0001", "collection": "sales", "source_id": "sales_2026" }],
    "constants": []
  }
}
```

- **`status`:** `"ok"` is an answer. `"not_applicable"` with `reason` (`not_tabular`: the question is not about the tables; `needs_context`: it needs a value or definition the context does not state; `listing_pending`: tables are still being catalogued, ask again; `scope_too_large`: the request covers more sources than one table query reads, name source IDs or fewer collections) means no SQL ran and the text chunks stand on their own. `"error"` carries a `code` and `message`; the rest of the response is unaffected.
- **`answer_type`:** `"exact"` when every record is a stored row of a table (the rows are named in `citations.rows`); `"computed"` when the records are aggregated or derived.
- **`records`** are the result rows keyed by column name, up to 100 per answer (`truncated` says whether more existed). Values follow each column's `kind`: integers and doubles are JSON numbers, booleans are booleans, decimals are strings (to keep precision), dates and timestamps are strings, a SQL NULL is `null`. `columns` lists each column's name, SQL `type` and `kind`.
- **`sources`** lists every table the SQL read, as you know it: the document `id` and `title`, its `collection`, the `sheet` for a workbook, and the `version` it was ingested as. A re-upload gets a new version.
- **`citations`** is what to cite. `rows` are the stored rows behind the answer, each as `{chunk_id, collection, source_id, row}`: for an `exact` answer one per record, with its one-based stored `row` and the chunk in `data.chunks` that holds it when one does; for a `computed` answer one per chunk that holds rows the SQL read. `constants` are literals the SQL took from the question or from a chunk, such as a target or a threshold stated in a document, each with the chunk it came from.
- The text chunks in `data.chunks` are returned as usual, so the answer and its evidence travel together; in this response, `data.chunks` carries the chunk `sales_2026_chunk_0001` that the citation names. `llm_prompt` and the Markdown rendering include the table under a "Table query" heading.

Table answers run in thinking mode only; `"fast"` returns the ranked chunks without `tabular_data`. Questions that are better answered from text keep working as before: the table path engages only when the question calls for it.

## 3. Tune the ranking

- `alpha`**:** the balance between semantic/meaning (`1.0`) and keywords (`0.0`) in a hybrid query. Default `0.8`; `"auto"` also resolves to `0.8`.
- **`recency_bias`:** how much newer context is favored, from `0.0` to `1.0`. Default `0.6`
- **`max_results`:** drop to `5` for tight context windows; raise to `20` when you rerank downstream.
- **`additional_graph_context`:** a request-time string hint, such as `"user is on the billing page"`, that sharpens retrieval. It is not a filter. This is separate from the response map `data.additional_graph_context` containing linked sources.

## 4. Choose what to search

- **Several collections:** send `collections` instead, as a list, or as an object of weights to rank one collection over another. You can search up to 100 collections in one call.
- **Metadata filtering:** `metadata_filters` narrows results before ranking, such as only specific emails or only one team's documents. [Metadata](/essentials/v2/metadata) covers all operators.

## 5. Understanding relationships in your context

- `graph_context`**:** the relationships HydraDB extracted from your context during ingestion, such as "Payments team owns billing service", in `data.graph_context`.
- **`query_explicit_relations`:** defaults to `true`. Links you declared deterministically during ingestion are returned in `data.additional_graph_context` in thinking mode only. Send `false` to skip linked sources. The legacy response alias `data.additional_context` contains the same map.
- **`query_apps`:** for content synced by [connectors](/essentials/v2/connectors), an extra lane that rebuilds Slack threads, follows ticket and parent links, and matches exact ids and people. It still searches everything else, and has no effect on memories.


## 6. As an admin you can query the app on behalf of a user

- **From ingested context, and connectors without ACL enforcement:** send the caller's email in `acl`, such as `"acl": ["grace@acme.com"]`, to filter results to documents that person may have retrieved themselves. Without `acl`, this content is not filtered by caller identity.
- **From connectors with** `enforce_acl `**enabled:** HydraDB uses the authenticated caller and ignores a request `acl` for that connector's content. API keys use the key creator's email; MCP OAuth and dashboard requests use the signed-in user. If you send `acl` anyway, a successful response includes one `meta.warnings` entry with code `acl_ignored_by_connector_enforcement`.

An `acl` entry on a source or a query is a **principal**:

| Principal | Meaning |
| --- | --- |
| `grace@acme.com` | One person, by email. |
| `domain:acme.com` | Everyone whose email is under that domain. A query as `grace@acme.com` matches it automatically. |
| `group:<provider>:<id>` | A group in the source app, such as `group:slack:C0123`. Group membership is never derived from an email; send it on the query. |
| `__public__` | Every identified caller. |

## 7. Use the results

HydraDB recreates complete context that is helpful to your agents: your application. `build_string(result)` in Python and `buildString(result)` in TypeScript return `data.llm_prompt`, which numbers the ranked results `[1]`, `[2]`, and so on, so you can ask the agent use that for citations.

<CodeGroup>

```python Python SDK
import os
from hydra_db import HydraDB
from hydra_db.helpers import build_string
from openai import OpenAI

hydra = HydraDB(token=os.environ["HYDRADB_API_KEY"])
openai_client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

question = "How does authentication work?"

result = hydra.query(
    database="your-database",
    collection="your-collection",
    query=question,
    type="knowledge",
    query_by="hybrid",
    mode="fast",
    graph_context=True,
)

context = build_string(result)

completion = openai_client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {
            "role": "system",
            "content": "You are a helpful assistant. Answer the user's question using only the context provided. If the answer is not in the context, say you don't know.",
        },
        {
            "role": "user",
            "content": f"Context:\n{context}\n\nQuestion: {question}",
        },
    ],
)

print(completion.choices[0].message.content)
```

```typescript TypeScript SDK
import { HydraDBClient } from "@hydradb/sdk";
import { buildString } from "@hydradb/sdk/helpers";
import OpenAI from "openai";

const hydra = new HydraDBClient({ token: process.env.HYDRADB_API_KEY });
const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

const question = "How does authentication work?";

const result = await hydra.query({
  database: "your-database",
  collection: "your-collection",
  query: question,
  type: "knowledge",
  queryBy: "hybrid",
  mode: "fast",
  graphContext: true,
});

const context = buildString(result);

const completion = await openai.chat.completions.create({
  model: "gpt-4o",
  messages: [
    {
      role: "system",
      content: "You are a helpful assistant. Answer the user's question using only the context provided. If the answer is not in the context, say you don't know.",
    },
    {
      role: "user",
      content: `Context:\n${context}\n\nQuestion: ${question}`,
    },
  ],
});

console.log(completion.choices[0].message.content);
```

# Advanced query patterns (mostly for agents)

| **Common mistakes** | **Cause** | **Fix** |
| --- | --- | --- |
| Empty `query_paths` or `chunk_relations` | `graph_context` set to `false`, or no relationships exist for the result set | Leave `graph_context` on (the default). Empty arrays are normal when there is nothing to return. |
| Recent uploads do not appear in results | Indexing not finished | Poll [`GET /context/status`](/api-reference/v2/endpoint/source-status) with the source ids. Chunks are invisible until indexing reaches at least `graph_creation`. |
| `metadata_filters` does not narrow results | Filter key is in the wrong namespace, the value does not match exactly, or the top-level field was not declared in the metadata schema | Top-level keys match `metadata`; free-form per-source fields must be nested under `additional_metadata`. Declare hot filter keys in `database_metadata_schema` before production ingest. |
| Memories missing from a `type: "knowledge"` query | Wrong store selected | Use `type: "memory"` or `type: "all"`. |
| Knowledge missing from a `type: "all"` query | The documents live in a different collection from the one you sent | List both collections in `collections`. |
| Recency does not seem to matter | `recency_bias` was sent as `0`, or the default `0.6` tilt is too mild | Raise it toward `1.0`. |
| `operator: "phrase"` returns `400` | `query_by` not set to `"text"` | `"and"` and `"phrase"` only apply to BM25 text queries: switch `query_by` to `"text"`. |
| `query_explicit_relations` ignored | Request runs in `mode: "fast"` (or `auto` routed to fast) | Deterministically linked sources are fetched only in thinking mode. Set `mode: "thinking"`. |
| `graph_context: false` ignored | Request runs in thinking mode (`mode: "thinking"`, or `auto` routed to thinking) | Thinking always includes the graph slice; `false` takes effect only in fast mode. Set `mode: "fast"` to drop it. |
| Expected a deterministic `fast` or `thinking` pipeline, got auto-routed instead | `mode` was omitted | Omitting `mode` means `"auto"`. Set `mode` explicitly to `"fast"` or `"thinking"`. |
| No `tabular_data` for a question about a spreadsheet | Request ran in `mode: "fast"` (or `auto` routed to fast) | Table answers run in thinking mode only. Set `mode: "thinking"`. |
| `tabular_data.status` is `not_applicable` with reason `needs_context` | The question relies on a value or definition the context does not state (a target, a threshold, a category) | Add the document that defines it, or state the value in the question. |
