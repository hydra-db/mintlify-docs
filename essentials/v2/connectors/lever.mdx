Sync opportunities, candidates, job postings, contacts, submitted applications and referral forms from one Lever account. Each record is one document. An opportunity links to its contact, and an application links to its candidate when Lever supplies the candidate id. Referral forms are not linked to a candidate.

Lever permissions are not imported, so every synced record is visible to everyone who can query the collection unless you set an access rule. Selecting postings limits only postings: everything else syncs for the whole account. Edits to an application or referral form after it is first synced are not guaranteed to be picked up. Archived and deleted records stay in HydraDB.

<Note>
Lever is in beta.
</Note>

## Permissions

<Warning>
Lever permissions are not imported, so **Enforce ACL** is unavailable for this connector. Every synced item is visible to everyone who can query the collection, unless you [set an access rule on the resource](/essentials/v2/connectors#set-your-own-rule-on-a-resource).
</Warning>

- An access rule on a posting does not cover opportunities, candidates, contacts, applications or referral forms, which sync for the whole account.

API-key requests must omit `enforce_acl`, including `false`. See [ACL on synced content](/essentials/v2/connectors#5-acl-native-rbac-awareness).

## Keeping in sync

- **First sync:** Reaches back the window set by `lookback_days`, 30 days by default.
- **New and changed items:** Opportunities, candidates and selected postings are picked up when they are updated. Contacts, applications and referral forms are reached only through the candidates read in the same sync. A contact is read when such a candidate refers to it. An application or referral form is read when it was created within the sync window.
- **Edits:** An updated opportunity, candidate or posting replaces its document. A contact is read again only when a candidate that refers to it is read. Edits to an application or referral form after it is first synced are not guaranteed to be picked up.
- **Deletions:** Records deleted in Lever stay searchable in HydraDB. Archiving a candidate or application in Lever does not remove or hide its document.
- An opportunity and a candidate that share an id share one document, so the one read last is the one you see.

After the first sync, HydraDB syncs every hour by default. Set `sync_interval_seconds` on the connector to change it.

### Opportunities

- **One document:** One opportunity. A candidate with the same id shares this document.
- **Title:** The person's name. Otherwise `Lever opportunity` and its id.
- **Text:** The name, then `Headline`, `Stage`, `Origin`, `Tags` and `Emails` lines. The creation time is part of the text. The title is searchable too.
- **Date:** When the opportunity was last updated, or created when there is no update time.
- **Link back:** None.
- **Files:** Resumes and other files are not synced.

<ResponseField name="name, headline" type="Searchable text">
The person's name and profile headline. The name forms the title.
</ResponseField>

<ResponseField name="Stage" type="Searchable text">
The stage's display name. When the name cannot be found, the stage id is written instead.
</ResponseField>

<ResponseField name="origin, tags, emails" type="Searchable text">
Whether the person applied, was sourced or was referred, their tags and their email addresses.
</ResponseField>

<ResponseField name="contact" type="Graph connection">
Links the opportunity to its Lever contact. Not searchable.
</ResponseField>

<ResponseField name="created_at" type="Searchable text, Result date">
When the opportunity was created. It is the result date only when there is no update time.
</ResponseField>

<ResponseField name="updated_at" type="Result date">
When the opportunity was last updated. Not searchable.
</ResponseField>

<ResponseField name="additional_metadata.lever_opportunity_id" type="Query filter">
The Lever opportunity id. Finds one opportunity. Not searchable.
</ResponseField>

<Accordion title="Stored only, not searchable (1)">

<ResponseField name="owner" type="Stored only">
The owner's Lever user id. It is not turned into a name.
</ResponseField>

</Accordion>

- **Date:** When the candidate was last interacted with, or created when there is no interaction time.
- **Link back:** None.
- **Files:** Resumes and other files are not synced.

## How it fits into the graph

- Opportunities use the Ticket class.
- Candidates use the Ticket class.
- Postings use the Ticket class.
- Contacts use the Record class.
- Applications use the Ticket class.
- Referral forms use the Ticket class.

[Graph classes](/essentials/v2/connector-providers#graph-classes) explains each class.

**Connections Lever creates**

- An opportunity to its contact.
- An application to its candidate, when Lever supplies the candidate id.
- Applications are not linked to their posting, and referral forms are not linked to a candidate.
- No links to other tools.

**People and groups**

No one is attached to a record as a person. Owners, creators and referrers are kept as Lever user ids only. Candidate and contact names are in the text.

**Found in the text**

Profiles, posting descriptions, application comments and answers, and referral form answers. HydraDB identifies people, organizations, projects and other named things in this text. To steer what it looks for, use [custom instructions](/essentials/v2/connectors#4-custom-ingestion-instructions).

## Not synced

- Postings you did not select.
- Interview feedback, notes and scorecards.
- Resumes and other files.
- Lever users, requisitions, sources and tags as documents.
- Whether a posting is open or closed, and posting sections other than its categories and description.
- Separate fields for contact phone numbers, applicant profile details and question answers. Their values are in the text only.
- Deletions: records deleted in Lever stay in HydraDB.
