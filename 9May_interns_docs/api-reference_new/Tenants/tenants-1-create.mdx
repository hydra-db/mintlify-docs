  **Important**: When a tenant is created, HydraDB automatically creates a **DEFAULT sub-tenant** that acts as a global space for that tenant. Any documents ingested or API calls made with the `tenant_id` but without specifying a `sub_tenant_id` will automatically reference this default sub-tenant.

## Creating Additional Sub-Tenants

**No Separate API Required**: HydraDB doesn't require a separate API call to create additional sub-tenants. Sub-tenants are created automatically when you first use a new `sub_tenant_id` that doesn't exist yet.

### How Sub-Tenant Creation Works

1. **Automatic Creation**: When you upload content with a `sub_tenant_id` that doesn't exist, HydraDB automatically creates that sub-tenant
2. **First Upload Triggers Creation**: The first API call with a new `sub_tenant_id` will create the sub-tenant and then process your content
3. **Immediate Availability**: Once created, the sub-tenant is immediately available for all subsequent operations

### Sub-Tenant ID Best Practices

**For B2C Applications (Individual Users):**

```javascript
// Use user IDs as sub-tenant IDs for personal workspaces
sub_tenant_id: "user_12345"
sub_tenant_id: "user_67890"
```

**For B2B Applications (Departments/Teams):**

```javascript
// Use descriptive department or team names
sub_tenant_id: "engineering"
sub_tenant_id: "sales"
sub_tenant_id: "hr"
sub_tenant_id: "marketing"
```

**For Project-Based Organizations:**

```javascript
// Use project identifiers
sub_tenant_id: "project_alpha"
sub_tenant_id: "client_acme_corp"
```

<Info>
  **Naming Convention**: Use consistent prefixes like `user_`, `dept_`, or `project_` to make the purpose of each sub-tenant clear. Avoid special characters and keep names descriptive but concise.
</Info>

<Warning>
  **Important**: Tenant metadata keys are **immutable** once set during tenant creation. Choose your keys carefully as they cannot be modified later. `additional_metadata` remains fully flexible and can be set per document during upload.
</Warning>

## Reserved Keywords

The following keywords are **reserved** and cannot be used as keys in `tenant_metadata_schema`:

- `id`
- `source_title`
- `source_url`
- `source_type`
- `source_collection`
- `source_owner`
- `source_collaborator`
- `source_upload_time`
- `source_last_updated_time`
- `chunk_id`
- `chunk_uuid`
- `chunk_content`
- `additional_metadata`
- `base_metadata`
- `layout`
- `description`

These keywords are used internally by HydraDB for document processing and search functionality. Using any of these reserved keywords in `tenant_metadata_schema` will result in an error during tenant creation.

## Metadata Schema Structure

Each schema object in the `tenant_metadata_schema` array should specify:

| Field | Type | Description |
|---|---|---|
| `name` | string | The metadata field name (immutable once set). |
| `data_type` | string | The field's data type. See [Supported Metadata Types](#supported-metadata-types). |
| `enable_match` | boolean | Enables this field for exact-match filtering at recall time via `metadata_filters`. |
| `enable_dense_embedding` | boolean | Indexes the field for dense (semantic) vector search. |
| `enable_sparse_embedding` | boolean | Indexes the field for sparse (keyword) search. |
| `enable_analyzer` | boolean | Enables full-text analysis on the field. |
| `max_length` | integer | Maximum string length. Required for `VARCHAR` fields. |
| `nullable` | boolean | Whether the field accepts `null` values. |

## Supported Metadata Types

| `data_type` | Description | Example values |
|---|---|---|
| `VARCHAR` | Text (variable-length string). Requires `max_length`. | `"Engineering"`, `"SOC2"` |
| `INT64` | 64-bit signed integer. | `5`, `100`, `2024` |
| `FLOAT` | Single-precision floating point. | `0.95`, `3.14` |
| `DOUBLE` | Double-precision floating point. | `99.999999` |
| `BOOL` | Boolean. | `true`, `false` |
| `JSON` | Structured/nested data. | `{"city": "SF", "country": "USA"}` |
| `ARRAY` | Multi-valued field. | `["security", "api", "compliance"]` |

## `enable_match` vs `enable_dense_embedding` vs `enable_sparse_embedding`

**`enable_match: true`** — exact-match filtering via `metadata_filters` (e.g. `department = "Engineering"`). Use for fields you want to filter on with hard equality before semantic ranking runs.

```json
{
  "name": "data_classification",
  "data_type": "VARCHAR",
  "enable_match": true,
  "max_length": 64
}
```

**`enable_dense_embedding: true`** — indexes the field for dense (semantic) vector search. Use when you want users to find documents by asking conceptual questions that involve this field.

```json
{
  "name": "department",
  "data_type": "VARCHAR",
  "enable_dense_embedding": true,
  "max_length": 256
}
```

**`enable_sparse_embedding: true`** — indexes the field for sparse (keyword / BM25-style) search. Use when exact term matches matter (product SKUs, codes, names).

```json
{
  "name": "product_sku",
  "data_type": "VARCHAR",
  "enable_sparse_embedding": true,
  "max_length": 64
}
```

**Combined.** A field can have multiple flags enabled at once if you need both deterministic filtering and semantic / keyword retrieval on it:

```json
{
  "name": "compliance_framework",
  "data_type": "VARCHAR",
  "enable_match": true,
  "enable_dense_embedding": true,
  "enable_sparse_embedding": true,
  "max_length": 256
}
```

## Metadata Best Practices

**1. Naming Conventions**

- **Use snake_case**: `business_unit` instead of `businessUnit`
- **Be descriptive**: `data_classification_level` instead of `classification`
- **Use consistent prefixes**: `compliance_*`, `security_*`, `business_*`

**2. Type Selection Guidelines**

- **`VARCHAR`**: Text, labels, and any field that needs semantic or keyword search. Always set `max_length`.
- **`INT64`**: Counts, versions, priorities
- **`FLOAT` / `DOUBLE`**: Scores, percentages, measurements
- **`BOOL`**: Binary flags and status indicators
- **`JSON`**: Structured, hierarchical data
- **`ARRAY`**: Multi-value fields like tags and categories

**3. Index Flag Strategy**

- **`enable_match`**: Fields used for precise exact-match filtering
- **`enable_dense_embedding`**: Fields users will ask natural-language questions about
- **`enable_sparse_embedding`**: Fields where exact term matching matters (SKUs, codes, names)
- Combine flags on the same field when both filtering and retrieval are needed

**4. Performance Considerations**

- **Limit total fields**: Keep metadata schema focused and purposeful
- **Use appropriate types**: Choose the most specific type for your data
- **Consider query patterns**: Design for your most common use cases
- **Plan for growth**: Design schema to accommodate future needs

### Query Examples

With the metadata schema defined above, users can perform sophisticated queries:

#### Semantic Search (Dense Embedding Fields)

```
"Find all engineering documents about security compliance"
```

- Searches through `department` (`enable_dense_embedding: true`)
- Searches through `compliance_framework` (`enable_dense_embedding: true`)
- Searches through document content and titles

#### Precise Filtering (Match Fields)

```
department = "Engineering" AND data_classification = "internal" AND is_confidential = false
```

- Exact match on `department` (`enable_match: true`)
- Exact match on `data_classification` (`enable_match: true`)
- Scalar filter on `is_confidential` (`data_type: "BOOL"`, `enable_match: true`)

#### Combined Queries

```
"Show me all SOC2 compliance documents from the Product business unit"
```

- Semantic search for "SOC2 compliance" (`enable_dense_embedding: true` fields)
- Precise filter: `business_unit = "Product"` (`enable_match: true`)

### Real-World Use Cases

#### 1. Legal Document Management

**Schema**: Practice area, client ID, confidentiality level, jurisdiction
**Query**: "Find all corporate law documents for client ACME that are not confidential"
**Filter**: `practice_area = "corporate_law" AND client_id = "ACME" AND confidentiality_level != "confidential"`

#### 2. Engineering Documentation

**Schema**: Product line, team, component, priority, tags
**Query**: "Show me all high-priority API documentation from the backend team"
**Filter**: `product_line = "API" AND team = "backend" AND priority >= 4`

#### 3. HR Document Management

**Schema**: Department, employee type, salary band, status
**Query**: "Find all active full-time employees in the Engineering department"
**Filter**: `department = "Engineering" AND employee_type = "full_time" AND status = "active"`

### Metadata Schema Usage

All documents in your tenant can use the metadata schema you define. This means:

1. **Consistency**: Documents share the same tenant-level metadata structure
2. **Compliance**: Organizational policies are enforced across all documents
3. **Queryability**: You can filter and search by configured metadata attributes
4. **Scalability**: New documents can follow your established metadata model

### Migration and Updates

<Warning>
  **Schema Immutability**: Once you create a tenant with a metadata schema, the keys cannot be changed. However, you can:

  - Add new fields to `additional_metadata` (fully flexible)
  - Update values for existing `metadata` fields
  - Create new sub-tenants with different schemas if needed
</Warning>

> **Note:**
>
> - The `tenant_metadata_schema` field in the request body is optional but recommended for enterprise setups. It defines immutable tenant-level `metadata` keys that apply to documents in this tenant.
> - For more detailed information about metadata usage, filtering, and querying, see our [Metadata documentation](/essentials/metadata).

## Sample Response

```json
{
  "status": "success",
  "message": "Tenant 'tenant_1234' created successfully.",
  "tenant_id": "tenant_1234"
}
```

### Functionality

- Accepts an optional `tenant_id` in the request body
- Generates a new `tenant_id` if none is provided
- Creates and persists the tenant
- Returns the final `tenant_id` and a confirmation message

> **Note:** If your use case is to directly upload and search embeddings (without document/text ingestion), pass `"is_embeddings_tenant": true` (and optionally `"embeddings_dimension"`) in the request body to `POST /tenants/create`. This sets `sub_tenant_id = tenant_id` and prepares the tenant for embeddings-first workloads.
