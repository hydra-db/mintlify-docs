<Warning>
**Irreversible:** deleting a collection permanently removes all its knowledge, memories, embeddings, graph nodes, and storage objects. The parent database and its other collections are unaffected. There is no soft delete and no recovery window.
</Warning>

## Query parameters
| Name | Description |
| --- | --- |
| <Field name="database" type="string" required /> | Database that owns the collection. Deprecated alias: `tenant_id`, which the API accepts though the SDKs and OpenAPI spec model only the canonical name. |
| <Field name="collection" type="string" required /> | Collection to delete. Deprecated alias: `sub_tenant_id`. Unlike the read endpoints, there is no default: a delete has no safe default collection. |

## While cleanup is running

Deletion is asynchronous. A `200` means the request was accepted; cleanup of vector stores, graphs, and storage objects runs in the background. From that moment the collection is fenced:

- Every ingest, query, and read addressed to it returns `404`, so nothing can write into it during the purge. Sibling collections and the database keep serving normally.
- Ingestion already in flight for it is cancelled before any store is purged, so an earlier job cannot repopulate it.
- It disappears from [List Collections](/api-reference/v2/endpoint/list-sub-tenants) once its records are dropped, before the slower vector, graph, and object-store cleanup completes.

There is no collection-level completion endpoint, and a repeated `DELETE` that returns `200` is not a completion signal either.

**Reusing the name:** you do not need a completion signal. Ingestion creates a missing collection implicitly, and the fence keeps reuse safe: writes return `404` until every store is purged. So write when you are ready. A `404` means cleanup is still running, so try again later; a success means it had finished. Do not send a write as a *probe*, because a successful write also creates the collection.

## Behavior notes

- **Repeat calls are the retry path:** deleting the same collection again is idempotent. A duplicate call during cleanup joins the delete in progress. If cleanup fails part-way, the collection stays fenced and re-issuing the `DELETE` re-runs it.
- **Drain your writers first:** the API cancels in-flight ingestion for you, but a job cancelled mid-run is reported as failed to whatever started it.
- **Dashboard:** owners can also expand a database on the Databases page and delete a collection from the inline list.

## Errors

Common codes:

- `400 INVALID_INPUT`: `database` or `collection` is missing.
- `401 UNAUTHORIZED`: missing or invalid API key.
- `404 DATABASE_NOT_FOUND`: the database does not exist. A database that is itself being deleted returns `404 NOT_FOUND`.
- `503 SERVICE_UNAVAILABLE`: an earlier failed deletion of this collection is still releasing its lock. The collection stays fenced; retry in a few seconds.
- `500 INTERNAL_ERROR`: transient. Retry the same `DELETE`.

See [Error Responses](/api-reference/v2/error-responses) for the full list.
